# 一、导论

## 1、设计模式的由来

在 1994 年，由 Erich Gamma、Richard Helm、Ralph Johnson 和 John Vlissides 四人合著出版了一本名为 Design Patterns - Elements of Reusable Object-Oriented Software（中文译名：设计模式 - 可复用的面向对象软件元素） 的书，该书首次提到了软件开发中设计模式的概念。

==对接口编程而不是对实现编程。==

==优先使用对象组合而不是继承。==

**设计模式的基石**

-   面向对象三大特性（封装、继承、多态）构建类的结构
-   顺序、判断、循环来构成方法

## 3、设计的七大原则

### 3.1 开闭原则

开闭原则（Open Closed Principle，OCP）：软件实体应当对扩展开放，对修改关闭（Software entities should be open for extension，but closed for modification）合成复用原则、里氏替换原则相辅相成，都是开闭原则的具体实现规范

==扩展新类而不是修改旧类==



### 3.2 里氏替换原则

里氏替换原则（Liskov Substitution Principle，LSP）继承必须确保超类所拥有的性质在子类中仍然成立（Inheritance should ensure that any property proved about supertype objects also holds for subtype objects）

==继承父类而不去改变父类，对新功能的扩展通过继承父类来添加扩展的功能==



### 3.3 依赖倒置原则

依赖倒置原则（Dependence Inversion Principle，DIP）高层模块不应该依赖低层模块，两者都应该依赖其抽象；抽象不应该依赖细节，细节应该依赖抽象（High level modules shouldnot depend upon low level modules.Both should depend upon abstractions.Abstractions should not depend upon details. Details should depend upon abstractions）

==面向接口编程，而不是面向实现类，使用接口进行抽象，不同的实现交由不同的实现类来实现，细节应该依赖抽象说的是在实现类中引用另外一个实现类的抽象，在需要修改的时候只需要替换实现类即可==



### 3.4 单一职责原则

单一职责原则（Single Responsibility Principle，SRP）一个类应该有且仅有一个引起它变化的原因，否则类应该被拆分（There should never be more than one reason for a class to change）

==每个类只负责自己的事情，而不是变成万能==



### 3.5 接口隔离原则

接口隔离原则（Interface Segregation Principle，ISP）一个类对另一个类的依赖应该建立在最小的接口上（The dependency of one class to another one should depend on the smallest possible interface）。

==各个类建立自己的专用接口，而不是建立万能接口==



### 3.6 迪米特法则

迪米特法则（Law of Demeter，LoD）最少知识原则（Least Knowledge Principle，LKP)只与你的直接朋友交谈，不跟“陌生人”说话（Talk only to your immediate friends and not to strangers）

==无需直接交互的两个类，如果需要交互，使用中间者==

<span style="color: red;">过度使用迪米特法则会使系统产生大量的中介类，从而增加系统的复杂性，使模块之间的通信效率降低</span>



### 3.7 合成复用原则

合成复用原则（Composite Reuse Principle，CRP）又叫组合/聚合复用原则（Composition/Aggregate Reuse Principle，CARP）软件复用时，要尽量先使用组合或者聚合等关联关系来实现，其次才考虑使用继承关系来实现

==优先组合，其次继承==





# 二、创建型模式

- 单例（Singleton）模式
- 原型（Prototype）模式
- 工厂方法（FactoryMethod）模式
- 抽象工厂（AbstractFactory）模式
- 建造者（Builder）模式

**为什么使用创建者模式**

- 创建型模式关注点是 “怎样创建出对象”
- 将对象的创建和使用分离
- 降低系统的耦合度
- 使用者无需关注对象的创建细节
    - 对象始终在系统中只有一个单例；（单例模式）
    - 对象的创建由原来对象克隆完成；（原型模式）
    - 对象的创建由一个创造者来完成；（建造者模式）
    - 对象的创建由相关的工厂来完成；（各种工厂模式）





## 单例(Singleton)模式

### 概述

单例模式就是在系统只有一份实例，要实现需要满足以下条件：

-   构造器私有
-   对象唯一，自己编写实例化逻辑
-   提供方法创建实例，方法中要保证对象的唯一性

### 饿汉式

获取之前就已经进行创建了，获取直接返回创建好的实例

```java
public class PersonHungryMan {

    private String name;
    private Integer age;
    public final static PersonHungryMan instance = new PersonHungryMan();

    private PersonHungryMan() {}

    public static PersonHungryMan getInstance() {
        return instance;
    }
}
```





### 懒汉式

在获取的时候才进行创建，需要进行判断是否已经创建了，创建了就直接返回



#### 简单版

```java
public class IdlerPerson {

    private String name;
    private Integer age;
    public static IdlerPerson instance;
    private IdlerPerson() {}
    public static IdlerPerson getInstance() {
        // 如果为空就创建
        if (instance == null) {
            instance = new IdlerPerson();
        }
        return instance;
    }
}
```



#### 多线程版

多线程环境下要保证安全性就需要加锁，但是锁的位置可以决定它的执行效率

```java
public synchronized static IdlerPerson getInstance() {
    // 如果为空就创建
    if (instance == null) {
        instance = new IdlerPerson();
    }
    return instance;
}
```

在方法上直接加锁锁太大，会导致效率低

```java
public static IdlerPerson getInstance() {
    // 如果为空就创建
    synchronized (IdlerPerson.class) {
        if (instance == null) {
            instance = new IdlerPerson();
        }
    }
    return instance;
}
```

这种方式比第一种的要好，但是还不是最好的，它每次都要在锁内进行一次判断是否创建了对象，效率还不是最高的

```java
public volatile static IdlerPerson instance;

public static IdlerPerson getInstance() {
    // 如果为空就创建
    if (instance == null) {
        synchronized (IdlerPerson.class) {
            if (instance == null) {
                instance = new IdlerPerson();
            }
        }
    }
    return instance;
}
```

双重检查锁 + 内存可见性的方式效率最大化，双重检查可以不用进行锁内判断节省了资源的浪费，内存可见性是为了解决指令重排等问题。





## 原型(prototype)模式

### 概述

原型（Prototype Patten）模式用于创建重复对象，同时又能保持性能。本体给外部提供一个克隆体进行使用

**什么场景用到？*

- 资源优化
- 性能和安全要求
- 一个对象多个修改者的场景。
- 一个对象需要提供给其他对象访问，而且各个调用者可能都需要修改其值时可以考虑使用原型模式拷贝多个对象供调用者使用。
- 深拷贝（两个完全对象不一样的【递归克隆】，内容却完全一样）、浅拷贝（只是属性赋值）
- ..........

原型模式已经与 Java 融为浑然一体。 对象可以通过实现 Cloneable 接口来实现克隆的逻辑

```java
public interface Cloneable {}
```

它只是一个标识接口，我们还需要实现一下 Object#clone() 方法，在方法中定义我们的克隆逻辑



### 案例

**问题**：我们现在需要从数据库中查数据，我们一般使用 Mybatis 框架，然后由它来将返回的数据封装成对象来使用，如果我们并发多次查询同一条记录，Mybatis就会封装多个对象返回，也就是在内存中存在 多个个内容同样的对象，造成性能的损耗。

**解决**：我们可以使用缓存来解决这个问题

这里我们使用自定义 Mybaits 来模拟问题



#### 实现

```java
public class ConsumerMybatis {
    private final Map<String, User> CACHE = new HashMap<>();
    public User getUser(String username) {
        User user = null;
        if (CACHE.containsKey(username)) {
            user = CACHE.get(username);
            System.out.println("从缓存中获取值：" + user.getName());
        } else {
            user = getUserByName(username);
            System.out.println("从数据库中获取值：" + user.getName());
        }
        return user;
    }
    // 从数据库中获取数据然后将数据放入到缓存中
    public User getUserByName(String username) {
        User user = new User();
        user.setName("xiaozhi");
        user.setAge(18);
        CACHE.put(username, user);
        return user;
    }
}
@Data
public class User{
    private String name;
    private Integer age;
}
```

测试

```java
public class TestGetUser {
    public static void main(String[] args) {
        ConsumerMybatis cm = new ConsumerMybatis();
        for (int i = 0; i < 5; i++) {
            User user = cm.getUser("xiaozhi");
            if (i == 1) {
                user.setName("zhangsan");
            }
            System.out.println(i  + "==>" + user.getName());
        }
    }
}
```

说明：模拟连续访问 5 次， 在 i = 1时修改一下 username

结果发现我们修改了从缓存中获取的对象，因此导致了整个缓存发生了变化，这样影响是非常大的



#### 使用原型模式修改

我们不应该将原本的对象返回，而是将我们的克隆体返回，这样它修改也不会对缓存中的对象产生影响，也就不会影响后面的输出

我们之前说过，Java 全面支持原型模式，只需要实现 Cloneable 接口并实现 Object#clone()

```java
public class User implements Cloneable
@Override
protected Object clone() throws CloneNotSupportedException {
    User user = new User();
    user.setName(this.name);
    user.setAge(this.age);
    return user;
}
```

ConsumerMybatis#getUser(username)

```java
public User getUser(String username) throws CloneNotSupportedException {
    User user = null;
    if (CACHE.containsKey(username)) {
        user = CACHE.get(username);
        // 返回克隆体
        user = (User) user.clone();
        System.out.println("从缓存中获取值：" + user.getName());
    } else {
        user = getUserByName(username);
        // 返回克隆体
        user = (User) user.clone();
        System.out.println("从数据库中获取值：" + user.getName());
    }
    return user;
}
```

我们再次测试一下

```java

从缓存中获取值：xiaozhi
修改username：zhangsan

2==>xiaozhi
从缓存中获取值：xiaozhi

```

可以发现我们这次的修改并没有影响我们后面的输出





## 工厂(Factory)模式

工厂帮我们创建对象，我们只需要提供所需要的材料，不需要关心对象创建的细节，它会根据我们所提供的材料返还给我们不同的产品

有一下三种类型的工厂：

- 简单(simple)工厂
- 方法(method)工厂
- 抽象(abstract)工厂

上面这三种工厂从以到难，规模也是从小到大，需要创建的对象较少可以选择简单工厂，对于同一系列的多个对象可以选择方法工厂来创建，对于不同系列的多个对象可以选择抽象工厂来创建

==个人认为，抽象工厂破坏了单一职责原则（学习阶段）==

缺点：这种方式违背了我们的开闭原则，每次添加新的产品就需要添加一个 if，所以它只适用于仅有少数对象的场景

## 建造者(builder)模式

### 概述

#### 什么时候使用呢？

我们创建类的方式无非就是两种，一种有参构造和无参构造，复杂的对象一般都会有多个参数，这就会导致我们需要多个构造器，**当一个类的构造函数参数个数超过4个，而且这些参数有些是可选的参数，考虑使用构造者模式**



#### 什么是建造者模式

通过选择不同的材料（参数）来构造对象，屏蔽过程而不是屏蔽细节，细节由使用者来控制

举个例子：我们要组装一台电脑，需要主板、CPU、内存条、磁盘、电源、摄像头

建造者模式的作用就是可以让我们随意组合搭配出不同性能或不同用处的电脑，比如：

- 学习编程：CPU要好一点的，内存条也要16G以上，磁盘大一点，电源功率高一点
- 办公：CPU差不多就可以了，内存条也不需要很大，磁盘大一点可以，电源功率也不需要太高，再搭配一个摄像头，方便开会的时候使用

可以看到我们选择不同的材料建造出来的是不同的电脑，使用的场景也不一样，我们需要知道创建的过程，只需要将这些关键的材料准备好即可



#### 为什么要使用建造者模式呢？

- 构造器阅读起来不方便
- get和set方法在构建的过程中对象的状态易变，因为类中的属性设置是分布设置的，容易出错

为了解决这两个痛点，所以就建造者模式横空出世

创建的东西细节复杂，还必须暴露给使用者，让他们来选择不同的材料（参数）



### 使用

#### 创建电脑类对象


## 桥接(Bridge)模式

### 概述

> 将抽象与解耦分离，使两者都可以独立变化

**理解**：我们可以通过属性来定义类的特征，但是有些时候属性多变，它可能有多种形态，每次我们都要修改一下它的形态，所以我们可以将它抽象出来，在类中依赖它的抽象，需要那种状态我们就给它

**举个例子**：我们现在的商品有多种渠道购买，比如线下或者通过电商购买，电商又可以去京东、淘宝、拼夕夕等等购买，那么对于同种类型的产品就存在着多种渠道，所以我们可以把渠道抽象出来，不同的渠道有不同的实现

**桥接（Bridge）模式包含以下主要角色**：

- 抽象化（Abstraction）角色：定义抽象类，并包含一个对实现化对象的引用。
- 扩展抽象化（Refined Abstraction）角色：是抽象化角色的子类，实现父类中的业务方法，并通过组合关系调用实现化角色中的业务方法。
- 实现化（Implementor）角色：定义实现化角色的接口，供扩展抽象化角色调用。
- 具体实现化（Concrete Implementor）角色：给出实现化角色接口的具体实现。

**应用场景**

- 当一个类存在两个独立变化的维度，且这两个维度都需要进行扩展时。
- 当一个系统不希望使用继承或因为多层次继承导致系统类的个数急剧增加时。
- 当一个系统需要在构件的抽象化角色和具体化角色之间增加更多的灵活性时。

## 装饰器(Decorator/Warpper)模式

#### 概述

给现有的对象添加新的功能，同时不改变它原有的结构。通过创建一个装饰类来包装原来的类，并在保持方法签名完整性的前提下，提供额外的功能

装饰器模式满足了开闭原则，扩展新类而不是修改旧类

**举例子**：

- 目前系统存在直播功能，我们想要在直播功能上面添加开启美颜功能，那么此时我们就可以用装饰器来装饰我们的直播功能，给它添加开启美颜功能，而这个给直播添加开启美颜功能的就是我们的装饰器
- 购买了一栋叙利亚风格房子，要给它装修，那么这个负责装修的师傅它就是装饰器，由它来给我们的房子 “舔砖java”

**装饰器模式角色**：

- 抽象构件（Component）角色：定义一个抽象接口以规范准备接收附加责任的对象。
- 具体构件（ConcreteComponent）角色：实现抽象构件，通过装饰角色为其添加一些职责。
- 抽象装饰（Decorator）角色：继承抽象构件，并包含具体构件的实例，可以通过其子类扩展具体构件的功能。
- 具体装饰（ConcreteDecorator）角色：实现抽象装饰的相关方法，并给具体构件对象添加附加的责任。

## 代理(Proxy)模式

### 概述

代理模式(Proxy Pattern) ,给某一个对象提供一个代理，并由代理对象控制对原对象的引用,对象结构型模式。

举个例子：我是房东，要将房子出租，为了方便，我将我的房子交到中介的手中，让他代理我去出租房子，他帮我做交付需要做的其他事情，比如带人看房子、签订合同、续约....，而我需要做的事情就只是将房子出租，不需要管理其他事情，这就是代理模式的体现

==*装饰器模式也是代理模式的一种*==

**代理模式包含如下角色**：

- *Subject*: 抽象主体角色(抽象类或接口)
- *Proxy*: 代理主体角色(代理对象类)
- *RealSubject*: 真实主体角色(被代理对象类)

举例：*Subject* = 房东，*RealSubject* = 小智房东，*Proxy* = 中介，销售来帮小智出租房子

**代理模式分类**：

- 静态代理
- 动态代理（Java）
    - JDK代理
    - Cglib代理

##### JDK动态代理



- 优点：JDK原生支持，不需要导入任何依赖
- 缺点：只能使用接口类型接收返回结果，使用类接收回报错

**实现**

```java
public class IntermediaryJDKProxy<T> implements InvocationHandler {

    private T target;
    public IntermediaryJDKProxy(T target) {
        this.target = target;
    }

    /**
     * 获取被代理对象的 代理对象
     * @param target
     * @return
     * @param <T>
     */
    public static <T> T getProxy(T target) {
        /**
         * ClassLoader loader,      // 当前被代理对象的类加载器
         * Class<?>[] interfaces,   // 当前被代理对象所实现的所有接口
         * InvocationHandler h      // 当前被代理对象执行目标方法的时候我们使用 h 可以定义拦截增强方法
         */
        Object o = Proxy.newProxyInstance(target.getClass().getClassLoader(),
                target.getClass().getInterfaces(),  // 必须接口，接收的时候需要用到
                new IntermediaryJDKProxy(target));
        return (T) o;
    }

    /**
     * 定义目标方法的拦截逻辑；每个方法都会进来
     */
    @Override
    public Object invoke(Object proxy, 
                         Method method, 
                         Object[] args) throws Throwable {
        System.out.println("带客户看房子...");
        System.out.println("签订合同...");
        Object invoke = method.invoke(target, args);
        System.out.println("通知房东：" + args[0] + "已被出租...");
        return invoke;
    }
}
```

**实现**

```java
public class IntermediaryCglibProxy {
    public static <T> T getProxy(T target){
        return (T) getProxy(target.getClass());
    }
    // 根据类来创建代理类
    public static <T> T getProxy(Class<T> target){
        // 1 创建一个增强器
        Enhancer enhancer = new Enhancer();
        
        // 2 设置要增强哪个类的的功能。增强器会为这个类动态创建一个子类
        enhancer.setSuperclass(target);
        
        // 3 设置回调
        enhancer.setCallback(new MethodInterceptor() {
            @Override
            public Object intercept(Object o,      // 被代理对象 
                                    Method method, // 为了获取原方法中的元信息
                                    Object[] args, // 参数
                                    MethodProxy methodProxy) throws Throwable {
                System.out.println("带客户看房子...");
                System.out.println("签订合同...");
                /*
                    注意：是调用父类的方法，而不是自己的
                        invoke ==> 调用自己的
                        invokeSuper ==> 调用父类的
                 */
                Object invoke = methodProxy.invokeSuper(o, args);
                System.out.println("通知房东：" + args[0] + "已被出租...");
                return invoke;
            }
        });
        return (T) enhancer.create();
    }
}
```

## 享元(Flyweight)模式

### 概述

> - 享元模式(Flyweight Pattern)，运用共享技术有效地支持大量细粒度对象的复用。系统只使用少量的对象，而这些对象都很相似，状态变化很小，可以实现对象的多次复用。对象结构型
> - 在享元模式中可以共享的相同内容称为内部状态(IntrinsicState)，而那些需要外部环境来设置的不能共享的内容称为外部状态(Extrinsic State)，由于区分了内部状态和外部状态，因此可以通过设置不同的外部状态使得相同的对象可以具有一些不同的特征，而相同的内部状态是可以共享的。
> - 在享元模式中通常会出现工厂模式，需要创建一个享元工厂来负责维护一个享元池(Flyweight Pool)用于存储具有相同内部状态的享元对象。

意思就是对于重复功能的对象不要重复创建，通过池技术来复用这些对象，以此来优化系统性能，快速返回我们需要的对象。

比如：线程池、连接池、缓存....

**享元模式包含如下角色**：

- Flyweight: 抽象享元类

    要被共享对象的抽象，比如 数据库的 Connection
- ConcreteFlyweight: 具体享元类

    具体要共享的对象，ConnectionImpl，共享的变量可以是账号密码..
- UnsharedConcreteFlyweight: 非共享具体享元类

    非共享的变量，比如说 Connection 的状态，可以根据这个状态来判断当前连接是否已经被使用
- FlyweightFactory: 享元工厂类

    创建享元类的工厂，可以是简单工厂，因为它要创建的对象类型不多

![image-20231226005835383](D:\学习笔记\img\img01\image-20231226005835383.png)

享元模式的核心就在于可共享状态和不可共享状态，通过不共享状态来判断对象是否已经被使用，被使用的对象就不能再向外提供服务

比如：办宴席，服务员一个不能服务多台宴席，他要一个接着一个服务，他的共享状态呢就是这个服务员提供的服务，而他是否繁忙通过谁知道呢，是通过主管来知道的，主管负责管理他们行动，他会指挥空闲的服务员去进行服务

在上述的例子中呢，服务员就是我们的抽象享元类，宴席服务员就是我们的具体享元类，而主管就是我们的非共享享元类，是由他来控制享元类的行动的

# 四、行为模式

> 行为型模式关注点“怎样运行对象/类？”所以我们关注下类/对象的运行时流程控制
>
> 行为型模式用于描述程序在运行时复杂的流程控制，描述多个类或对象之间怎样相互协作共同完成单个对象都无法单独完成的任务，它涉及算法与对象间职责的分配。
>
> 行为型模式分为**类行为模式**和**对象行为模式**，前者采用继承机制来在类间分派行为，后者采用组合或聚合在对象间分配行为。由于组合关系或聚合关系比继承关系耦合度低，满足“合成复用原则”，所以对象行为模式比类行为模式具有更大的灵活性。

说人话就是，制定类的控制和运行，少用继承，多用组合

**有以下 11 种模式**：

- 模板方法（Template Method）模式：父类定义算法骨架，某些实现放在子类
- 策略（Strategy）模式：每种算法独立封装，根据不同情况使用不同算法策略
- 状态（State）模式：每种状态独立封装，不同状态内部封装了不同行为
- 命令（Command）模式：将一个请求封装为一个对象，使发出请求的责任和执行请求的责任分割开
- 职责链（Chain of Responsibility）模式：所有处理者封装为链式结构，依次调用
- 备忘录（Memento）模式：把核心信息抽取出来，可以进行保存
- 解释器（Interpreter）模式：定义语法解析规则
- 观察者（Observer）模式：维护多个观察者依赖，状态变化通知所有观察者
- 中介者（Mediator）模式：取消类/对象的直接调用关系，使用中介者维护
- 迭代器（Iterator）模式：定义集合数据的遍历规则
- 访问者（Visitor）模式：分离对象结构，与元素的执行算法

注：除了**模板方法模式**和**解释器模式**是**类行为型模式**，**其他的全部属于对象行为型模式**

## 策略（Strategy）模式

### 概述

> 策略（Strategy）模式定义了一系列算法，并将每个算法封装起来，使它们可以相互替换，且算法的变化不会影响使用算法的客户。属于对象行为模式。

将多个算法封装成多个类，类引用它的抽象，当使用到需要的算法的时候就传递封装了对应算法的类，这样的好处就是不用很多算法都放在一个类上，而且方便扩展和调用

为什么方便呢？如果我们将很多算法放在同一个类上，那么在调用的时候我们就需要使用对应的方法名来进行调用，每次我需要替换的时候我就需要重新更换一个方法名，这样的方式不优雅也不安全，所以策略模式就是替我们解决这个问题的，调用的是我的抽象，至于是什么实现那就是又调用者来进行传递。是不是非常优雅呢哈哈

**策略模式的主要角色如下**：

- 抽象策略（Strategy）类：公共接口，各种不同的算法以不同的方式实现这个接口，环境角色使用这个接口调用不同的算法，一般使用接口或抽象类实现。
- 具体策略（Concrete Strategy）类：实现了抽象策略定义的接口，提供具体的算法实现。
- 环境（Context）类：持有一个策略类的引用，最终给客户端调用。 



### 使用场景

- 使用策略模式可以避免使用多重条件语句，如 if...else 语句、switch...case 语句

## 命令（Command）模式

> 命令（Command）模式：将一个请求封装为一个对象，使发出请求的责任和执行请求的责任分割开。这样两者之间通过命令对象进行沟通，这样方便将命令对象进行储存、传递、调用、增加与管理。

我们使用的 web mvc 分层策略就是命令模式，controller -> service -> dao

**命令模式包含以下主要角色**：

- 抽象命令类（Command）角色：声明执行命令的接口，拥有执行命令的抽象方法 execute()。
- 具体命令类（Concrete Command）角色：是抽象命令类的具体实现类，它拥有接收者对象，并通过调用接收者的功能来完成命令要执行的操作。
- 实现者/接收者（Receiver）角色：执行命令功能的相关操作，是具体命令对象业务的真正实现者。
- 调用者/请求者（Invoker）角色：是请求的发送者，它通常拥有很多的命令对象，并通过访问命令对象来执行相关请求，它不直接访问接收者。



### 使用场景

- mvc就是典型的命令模式
- 当系统需要执行一组操作时，命令模式可以定义宏命令（一个命令组合了多个命令）来实现该功能。
- 结合备忘录模式还可以实现命令的撤销和恢复

## 职责链（Chain of Responsibility）模式

> 责任链（Chain of Responsibility）模式：为了避免请求发送者与多个请求处理者耦合在一起，于是将所有请求的处理者通过前一对象记住其下一个对象的引用而连成一条链；当有请求发生时，可将请求沿着这条链传递，直到有对象处理它为止。属于对象行为型模式

当前对象处理完了接着调用下一个对象进行处理，这样的方式就是链式调用

**包含的角色**：

- 抽象处理者（Handler）角色：定义一个处理请求的接口，包含抽象处理方法和一个后继连接。
- 具体处理者（Concrete Handler）角色：实现抽象处理者的处理方法，判断能否处理本次请求，如果可以处理请求则处理，否则将该请求转给它的后继者。
- 客户类（Client）角色：创建处理链，并向链头的具体处理者对象提交请求，它不关心处理细节和请求的传递过程。

4.定义过滤链，在过滤链中我们需要一个列表维护整个链，还需要定义一个游标来卡住执行的顺序

```java
@Data
public class FilterChain implements Filter{
    private final List<Filter> filters = new ArrayList<>();
    private int cursor;
    private My target;

    public void addFilter(Filter filter) {
        filters.add(filter);
    }
    @Override
    public void doFilter(Request req, Response resp, FilterChain chain) {
        if (cursor < filters.size()) {
            Filter filter = filters.get(cursor++);
            filter.doFilter(req, resp, chain);
        } else {
            // 执行对应方法处理请求
            target.sayHello();
        }
    }
}
```

## 备忘录（Memento）模式

### 概述

> 备忘录（Memento）模式：在不破坏封装性的前提下，捕获一个对象的内部状态，并在该对象之外保存这个状态，以便以后当需要时能将该对象恢复到原先保存的状态。该模式又叫快照模式。对象行为型模式

说明：将需要的属性保存，需要的时候在拿出来，很像缓存有没有....

## 解释器（Interpreter）模式

### 概述

> 解释器（Interpreter）模式：给分析对象定义一个语言，并定义该语言的文法表示，再设计一个解析器来解释语言中的句子。也就是说，用编译语言的方式来分析应用中的实例。这种模式实现了文法表达式处理的接口，该接口解释一个特定的上下文。类行为型模式

定义规则，解析规则，这个就是解析器的作用，解析器模式中有多个子解析器和总解析器，子解析器负责主要的解析逻辑，也就是下面所说的终结符表达式，总解析器负责最终的解析逻辑，总解析中包括多个子解析器。

**包含角色**：

- 抽象表达式（Abstract Expression）角色：定义解释器的接口，约定解释器的解释操作，主要包含解释方法 interpret()。
- 终结符表达式（Terminal Expression）角色：是抽象表达式的子类，用来实现文法中与终结符相关的操作，文法中的每一个终结符都有一个具体终结表达式与之相对应。
- 非终结符表达式（Nonterminal Expression）角色：也是抽象表达式的子类，用来实现文法中与非终结符相关的操作，文法中的每条规则都对应于一个非终结符表达式。
- 环境（Context）角色：通常包含各个解释器需要的数据或是公共的功能，一般用来传递被所有解释器共享的数据，后面的解释器可以从这里获取这些值。
- 客户端（Client）：主要任务是将需要分析的句子或表达式转换成使用解释器对象描述的抽象语法树，然后调用解释器的解释方法，当然也可以通过环境角色间接访问解释器的解释方法。



### 应用场景

- Spring的表达式解析：#{}
- Thymeleaf等模板引擎的语法解析
- 编译原理
- ......

    ```java
                if (data.contains(s)) {
    ```

## 迭代器（Iterator）模式

> 迭代器（Iterator）模式：提供一个对象(迭代器)来顺序访问聚合对象(迭代数据)中的一系列数据，而不暴露聚合对象的内部表示。对象行为型模式

**包含角色如下**：

- 抽象聚合（Aggregate）角色：定义存储、添加、删除聚合对象以及创建迭代器对象的接口。
- 具体聚合（ConcreteAggregate）角色：实现抽象聚合类，返回一个具体迭代器的实例。
- 抽象迭代器（Iterator）角色：定义访问和遍历聚合元素的接口，通常包含 hasNext()、first()、next() 等方法。
- 具体迭代器（Concretelterator）角色：实现抽象迭代器接口中所定义的方法，完成对聚合对象的遍历，记录遍历的当前位置。



### 使用场景

- jdk容器接口的Iterator定义
- 现实开发中，我们几乎无需编写迭代器，基本数据结构链表、树、图的迭代器已经都有了。除非要重写迭代逻辑
- ......

- 具体聚合（ConcreteAggregate）角色和体迭代器（Concretelterator）角色

    为了方便的使用聚合类提供的聚合，我们这里将迭代器设置成内部类

    ```java
    public class GuiguBM implements BeautifulMan {
        public List<String> girlFriends = new ArrayList<>();
        @Override
        public void likeYou(String name) {
            girlFriends.add(name);
        }
    
        @Override
        public void sayBy(String name) {
            girlFriends.remove(name);
        }
    
        @Override
        public LoveIterator getIterator() {
            return new LoveIteratorImpl();
        }
    
        private class LoveIteratorImpl implements LoveIterator {
            int cursor;
            public List<String> getFriendList() {
                return girlFriends;
            }
            @Override
            public String firstLove() {
                return girlFriends.get(0);
            }
    
            @Override
            public String nextLove() {
                return girlFriends.get(cursor++);
            }
    
            @Override
            public boolean hasNext() {
                return cursor != girlFriends.size();
            }
        }
    }
    ```
