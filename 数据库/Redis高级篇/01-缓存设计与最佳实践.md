# 缓存设计与最佳实践

## 1、缓存常见策略

缓存策略是决定如何将数据写入缓存和从缓存中读取数据的核心规则。不同的策略适用于不同的业务场景，理解它们是设计高性能系统的基础。

### 1.1 Cache-Aside（旁路缓存）

旁路缓存是最常用的缓存模式，应用程序直接管理缓存和数据库的交互。

#### 读流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           Cache-Aside 读流程                             │
└─────────────────────────────────────────────────────────────────────────┘

    ┌───────┐                              ┌─────────┐                      │
    │ 请求  │                              │  缓存   │                      │
    └───┬───┘                              └────┬────┘                      │
        │                                       │                            │
        │  1. 读取数据                          │                            │
        │ ─────────────────────────────────────>│                            │
        │                                       │                            │
        │  2. 命中缓存?                         │                            │
        │                                       │                            │
        ├──────────────────────────────────────┤                            │
        │                                       │                            │
        │         【命中】直接返回              │                            │
        │         【未命中】查数据库            │                            │
        │                                       │                            │
        │  3. 未命中，从数据库查询              │                            │
        │ ─────────────────────────────────────>│                            │
        │                                       │                            │
        │  4. 返回数据                          │                            │
        │ <─────────────────────────────────────│                            │
        │                                       │                            │
        │  5. 写入缓存                          │                            │
        │ ─────────────────────────────────────>│                            │
        │                                       │                            │
```

#### 写流程

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           Cache-Aside 写流程                             │
└─────────────────────────────────────────────────────────────────────────┘

    ┌───────┐     ┌─────────┐     ┌─────────────┐                          │
    │ 请求  │     │  缓存   │     │    数据库    │                          │
    └───┬───┘     └────┬────┘     └──────┬──────┘                          │
        │              │                 │                                 │
        │  1. 写数据    │                 │                                 │
        │ ─────────────>│                 │                                 │
        │              │                  │                                 │
        │  2. 写入数据库 │                 │                                 │
        │ ─────────────────────────────────>│                                │
        │              │                  │                                 │
        │  3. 删除缓存  │                 │                                 │
        │ ─────────────>│                 │                                 │
        │              │                  │                                 │
```

#### 代码示例

```java
/**
 * Cache-Aside 模式实现
 */
public class CacheAsideService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    /**
     * 读操作：先查缓存，未命中则查数据库，并写入缓存
     */
    public Product getProduct(Long id) {
        String cacheKey = "product:" + id;

        // 1. 查询缓存
        Product product = (Product) redisTemplate.opsForValue().get(cacheKey);
        if (product != null) {
            // 缓存命中，直接返回
            return product;
        }

        // 2. 缓存未命中，查询数据库
        product = productMapper.selectById(id);
        if (product == null) {
            return null;
        }

        // 3. 写入缓存，设置过期时间
        redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);

        return product;
    }

    /**
     * 写操作：先更新数据库，再删除缓存
     */
    public void updateProduct(Product product) {
        // 1. 更新数据库
        productMapper.updateById(product);

        // 2. 删除缓存（而不是更新缓存）
        String cacheKey = "product:" + product.getId();
        redisTemplate.delete(cacheKey);
    }

    /**
     * 删除操作：删除数据库记录后，删除缓存
     */
    public void deleteProduct(Long id) {
        // 1. 删除数据库记录
        productMapper.deleteById(id);

        // 2. 删除缓存
        String cacheKey = "product:" + id;
        redisTemplate.delete(cacheKey);
    }
}
```

#### 适用场景

- 读多写少的数据：如商品详情、用户信息、配置数据
- 一致性要求较高的场景：数据库是数据的来源，缓存只是加速读取
- 缓存层和数据库层都可以独立扩展

### 1.2 Read-Through（读穿透）

读穿透模式下，缓存负责自动从数据库加载数据，应用程序只与缓存交互。

#### 原理

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           Read-Through 流程                             │
└─────────────────────────────────────────────────────────────────────────┘

    ┌───────────┐                      ┌─────────┐                      ┌─────────────┐
    │  应用代码  │                      │   缓存   │                      │    数据库    │
    └─────┬─────┘                      └────┬────┘                      └──────┬──────┘
          │                                 │                                │
          │  1. 请求数据                    │                                │
          │────────────────────────────────>│                                │
          │                                 │                                │
          │         2. 缓存未命中           │                                │
          │                                 │                                │
          │              3. 自动查询数据库  │                                │
          │                                 │───────────────────────────────>│
          │                                 │                                │
          │                                 │  4. 返回数据                    │
          │                                 │<───────────────────────────────│
          │                                 │                                │
          │  5. 返回数据                    │                                │
          │<────────────────────────────────│                                │
          │                                 │                                │
```

#### 特点

- 应用程序代码更简洁，不需要手动处理缓存未命中的情况
- 缓存层自动完成数据加载逻辑
- 需要缓存层支持 "load-through" 能力（Redis 本身不直接支持，需要封装）

#### 代码示例

```java
/**
 * Read-Through 模式实现
 */
public class ReadThroughService {

    private final CacheLoader<String, Product> cacheLoader;

    public ReadThroughService(ProductMapper productMapper) {
        // 创建缓存加载器
        this.cacheLoader = new CacheLoader<String, Product>() {
            @Override
            public Product load(String key) throws Exception {
                // 从数据库加载数据
                Long id = Long.parseLong(key.split(":")[1]);
                return productMapper.selectById(id);
            }
        };
    }

    /**
     * 获取产品 - 缓存未命中时自动从数据库加载
     */
    public Product getProduct(Long id) {
        String cacheKey = "product:" + id;

        try {
            // 使用缓存加载器获取数据
            return cacheLoader.load(cacheKey);
        } catch (Exception e) {
            // 降级处理
            return productMapper.selectById(id);
        }
    }
}
```

### 1.3 Write-Through（写穿透）

写穿透模式下，写操作同时更新缓存和数据库，保证数据一致性。

#### 原理

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          Write-Through 流程                             │
└─────────────────────────────────────────────────────────────────────────┘

    ┌───────────┐                      ┌─────────┐                      ┌─────────────┐
    │  应用代码  │                      │   缓存   │                      │    数据库    │
    └─────┬─────┘                      └────┬────┘                      └──────┬──────┘
          │                                 │                                │
          │  1. 写数据                       │                                │
          │────────────────────────────────>│                                │
          │                                 │                                │
          │              2. 同步写入数据库   │                                │
          │                                 │───────────────────────────────>│
          │                                 │                                │
          │                                 │  3. 写入成功                    │
          │                                 │<───────────────────────────────│
          │                                 │                                │
          │  4. 写入成功                    │                                │
          │<────────────────────────────────│                                │
          │                                 │                                │
```

#### 特点

- 数据一致性最高，缓存和数据库始终保持同步
- 写操作延迟较高，需要等待两次写入完成
- 适用于对一致性要求极高的场景（如金融交易）

#### 代码示例

```java
/**
 * Write-Through 模式实现
 */
public class WriteThroughService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    /**
     * 写操作：同时写入缓存和数据库
     */
    @Transactional
    public void updateProduct(Product product) {
        String cacheKey = "product:" + product.getId();

        // 1. 先写入数据库
        productMapper.updateById(product);

        // 2. 再写入缓存（同步写穿）
        redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);
    }
}
```

### 1.4 Write-Behind（异步写）

写操作先更新缓存，后台异步批量同步到数据库。

#### 原理

```
┌─────────────────────────────────────────────────────────────────────────┐
│                           Write-Behind 流程                             │
└─────────────────────────────────────────────────────────────────────────┘

    ┌───────────┐                      ┌─────────┐                      ┌─────────────┐
    │  应用代码  │                      │   缓存   │                      │    数据库    │
    └─────┬─────┘                      └────┬────┘                      └──────┬──────┘
          │                                 │                                │
          │  1. 写数据（快速返回）           │                                │
          │────────────────────────────────>│                                │
          │                                 │                                │
          │  2. 写入成功（低延迟）           │                                │
          │<────────────────────────────────│                                │
          │                                 │                                │
          │              【后台线程】       │                                │
          │              3. 批量写入数据库   │                                │
          │                                 │───────────────────────────────>│
          │                                 │                                │
```

#### 特点

- 写入性能最高，适合高并发写场景
- 数据一致性较低，存在数据丢失风险
- 需要考虑数据持久化和失败重试机制

#### 代码示例

```java
/**
 * Write-Behind 模式实现
 */
public class WriteBehindService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final BlockingQueue<WriteBehindTask> writeQueue;

    /**
     * 写操作：先更新缓存，异步批量写入数据库
     */
    public void updateProduct(Product product) {
        String cacheKey = "product:" + product.getId();

        // 1. 立即更新缓存
        redisTemplate.opsForValue().set(cacheKey, product);

        // 2. 写入队列，异步处理
        writeQueue.offer(new WriteBehindTask(
            WriteOperation.UPDATE,
            product.getId(),
            product
        ));
    }

    /**
     * 后台写线程
     */
    @Scheduled(fixedDelay = 1000)
    public void flushToDatabase() {
        List<WriteBehindTask> batch = new ArrayList<>();
        writeQueue.drainTo(batch, 100);

        if (batch.isEmpty()) {
            return;
        }

        // 批量写入数据库
        try {
            productMapper.batchUpdate(batch);
        } catch (Exception e) {
            // 失败重试或记录日志
            batch.forEach(task -> writeQueue.offer(task));
        }
    }
}
```

### 1.5 四种策略对比

| 策略 | 一致性 | 性能 | 复杂度 | 适用场景 |
|------|--------|------|--------|----------|
| Cache-Aside | 高 | 高 | 中 | 读多写少，一致性要求高 |
| Read-Through | 高 | 高 | 中 | 读多写少，简化代码 |
| Write-Through | 最高 | 低 | 中 | 写少，一致性要求极高 |
| Write-Behind | 低 | 最高 | 高 | 高并发写，允许短暂不一致 |

## 2、缓存过期与淘汰策略

### 2.1 TTL 设置原则

#### TTL 设置考虑因素

```
┌─────────────────────────────────────────────────────────────────────────┐
│                            TTL 设置决策                                  │
└─────────────────────────────────────────────────────────────────────────┘

                        ┌─────────────────┐
                        │   数据类型分析    │
                        └────────┬────────┘
                                 │
            ┌────────────────────┼────────────────────┐
            ▼                    ▼                    ▼
    ┌───────────────┐    ┌───────────────┐    ┌───────────────┐
    │   热点数据     │    │   冷数据      │    │   准实时数据   │
    │  TTL: 较短    │    │  TTL: 较长    │    │  TTL: 极短    │
    │  如首页推荐    │    │  如历史订单   │    │  如库存数量   │
    └───────────────┘    └───────────────┘    └───────────────┘
            │                    │                    │
            ▼                    ▼                    ▼
    ┌───────────────┐    ┌───────────────┐    ┌───────────────┐
    │  5-30 分钟    │    │  1-24 小时    │    │  几秒-1 分钟   │
    └───────────────┘    └───────────────┘    └───────────────┘
```

#### 业务场景 TTL 设计案例

| 场景 | 数据类型 | 建议 TTL | 原因 |
|------|----------|----------|------|
| 商品详情 | 热点数据 | 30 分钟 | 变化不频繁，访问频繁 |
| 用户 Session | 临时数据 | 24 小时 | 用户会话周期 |
| 验证码/Token | 临时数据 | 5-15 分钟 | 安全性考虑 |
| 促销价格 | 准实时 | 1-5 分钟 | 价格变动频繁 |
| 用户画像 | 相对稳定 | 1-24 小时 | 变化缓慢 |
| 排行榜 | 定时刷新 | 5-15 分钟 | 按时间窗口计算 |

### 2.2 淘汰策略详解

Redis 基础篇已介绍 `maxmemory-policy` 配置项，下面详细对比各种淘汰策略的使用场景。

#### 八种淘汰策略对比

```
┌─────────────────────────────────────────────────────────────────────────┐
│                          Redis 淘汰策略分类                              │
└─────────────────────────────────────────────────────────────────────────┘

                          ┌──────────────────┐
                          │  maxmemory-policy │
                          └────────┬─────────┘
                                   │
        ┌──────────────────────────┼──────────────────────────┐
        │                          │                          │
        ▼                          ▼                          ▼
┌───────────────┐         ┌───────────────┐         ┌───────────────┐
│   不淘汰       │         │   易失淘汰     │         │   全局淘汰     │
│  (noeviction)  │         │ (volatile-*)  │         │ (allkeys-*)   │
└───────────────┘         └───────────────┘         └───────────────┘
                                   │                          │
           ┌───────────┬───────────┼───────────┬───────────┐  │
           ▼           ▼           ▼           ▼           ▼  │
     ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
     │volatile-│ │volatile-│ │volatile-│ │volatile-│ │volatile-│
     │  lru    │ │  lfu    │ │  ttl    │ │ random  │ │  all    │
     └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘
           │           │           │           │           │
           ▼           ▼           ▼           ▼           ▼
     ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐
     │ 删除最   │ │ 删除最   │ │ 删除    │ │ 随机    │ │ 删除    │
     │ 近最少   │ │ 常使用   │ │ 最近    │ │ 删除    │ │ 所有    │
     │ 使用    │ │ 最少    │ │ 将过期   │ │         │ │         │
     └─────────┘ └─────────┘ └─────────┘ └─────────┘ └─────────┘
```

#### 策略选择指南

| 策略 | 原理 | 适用场景 | 注意事项 |
|------|------|----------|----------|
| **volatile-lru** | 在设置了过期时间的 key 中删除最近最少使用 | 有明确冷热区分的数据 | 非过期 key 不会被淘汰 |
| **allkeys-lru** | 在所有 key 中删除最近最少使用 | 无明确过期时间，要求内存控制 | 可能删除热点数据 |
| **volatile-lfu** | 在设置了过期时间的 key 中删除使用次数最少 | 访问频率有明显差异的数据 | 较新的 key 可能被优先删除 |
| **allkeys-lfu** | 在所有 key 中删除使用次数最少 | 极度热点化场景 | 冷数据占用大量内存 |
| **volatile-ttl** | 删除最近即将过期的 key | 强调过期时间的数据 | 无过期时间的 key 安全 |
| **volatile-random** | 随机删除有过期时间的 key | 数据重要性相近 | 不可控性强 |
| **allkeys-random** | 随机删除所有 key | 无明显热点区分 | 不推荐生产使用 |
| **noeviction** | 不淘汰，返回错误 | 内存充足场景 | 可能导致写失败 |

#### LRU vs LFU 实战选择

```
场景分析：

1. 新闻推荐系统
   - 特点：新闻访问频率随时间递减，但可能被反复访问
   - 推荐：volatile-lru
   - 原因：过期数据自动清理，热点新闻保留

2. 用户行为分析
   - 特点：高频用户行为数据，低频用户少访问
   - 推荐：allkeys-lfu
   - 原因：保留高频热点，减轻数据库压力

3. 缓存防穿透
   - 特点：大量不存在的数据被访问
   - 推荐：allkeys-lru + 短 TTL
   - 原因：快速淘汰不存在的数据
```

### 2.3 实际业务中的 TTL 设计案例

#### 案例一：电商商品缓存

```java
/**
 * 商品缓存 TTL 设计
 */
public class ProductCacheService {

    // 商品基本信息 - 变化少，访问多
    private static final long BASIC_INFO_TTL = 30 * 60;      // 30分钟

    // 商品价格 - 变化频繁
    private static final long PRICE_TTL = 5 * 60;           // 5分钟

    // 商品库存 - 实时性要求高
    private static final long STOCK_TTL = 30;               // 30秒

    // 商品评论 - 变化较少
    private static final long COMMENT_TTL = 60 * 60;        // 1小时

    public void cacheProductBasicInfo(Product product) {
        String key = "product:basic:" + product.getId();
        redisTemplate.opsForValue().set(key, product, BASIC_INFO_TTL, TimeUnit.SECONDS);
    }

    public void cacheProductPrice(Long productId, BigDecimal price) {
        String key = "product:price:" + productId;
        redisTemplate.opsForValue().set(key, price, PRICE_TTL, TimeUnit.SECONDS);
    }

    public void cacheProductStock(Long productId, Integer stock) {
        String key = "product:stock:" + productId;
        redisTemplate.opsForValue().set(key, stock, STOCK_TTL, TimeUnit.SECONDS);
    }
}
```

#### 案例二：用户会话缓存

```java
/**
 * 用户会话缓存 TTL 设计
 */
public class SessionCacheService {

    // 普通用户会话
    private static final long USER_SESSION_TTL = 24 * 60 * 60;    // 24小时

    // 记住登录状态
    private static final long REMEMBER_ME_TTL = 7 * 24 * 60 * 60; // 7天

    // 验证码会话
    private static final long VERIFY_CODE_TTL = 5 * 60;            // 5分钟

    // 短信限流
    private static final long SMS_RATE_LIMIT_TTL = 60;             // 1分钟

    public void cacheUserSession(String token, UserSession session, boolean rememberMe) {
        String key = "session:user:" + token;
        long ttl = rememberMe ? REMEMBER_ME_TTL : USER_SESSION_TTL;
        redisTemplate.opsForValue().set(key, session, ttl, TimeUnit.SECONDS);
    }

    public void cacheVerifyCode(String phone, String code) {
        String key = "verify:code:" + phone;
        redisTemplate.opsForValue().set(key, code, VERIFY_CODE_TTL, TimeUnit.SECONDS);
    }

    public boolean checkSmsRateLimit(String phone) {
        String key = "sms:rate:" + phone;
        Long count = redisTemplate.opsForValue().increment(key);
        if (count == 1) {
            redisTemplate.expire(key, SMS_RATE_LIMIT_TTL, TimeUnit.SECONDS);
        }
        return count != null && count <= 10; // 每分钟最多10条
    }
}
```

## 3、缓存一致性解决方案

### 3.1 Cache Aside + TTL（最常用方案）

这是业界最广泛使用的方案，通过设置合理的 TTL 来保证最终一致性。

```
┌─────────────────────────────────────────────────────────────────────────┐
│                    Cache Aside + TTL 工作流程                           │
└─────────────────────────────────────────────────────────────────────────┘

    读操作：
    ┌────────┐      ┌────────┐      ┌────────┐
    │ 请求   │ ───> │ 缓存   │ ───> │ 数据库 │
    └────────┘      └────────┘      └────────┘
         │            │命中            │
         │            ▼               │
         │      ┌────────┐            │
         │      │ 返回   │            │
         │      └────────┘            │
         │ 未命中     │               │
         │            ▼               │
         │ ─────────────────────────>│
         │            │               │
         │            │    查询数据    │
         │            │<──────────────│
         │            ▼               │
         │      ┌────────┐            │
         │      │ 写入   │            │
         │      │ 缓存   │            │
         │      └────────┘            │
         ▼

    写操作：
    ┌────────┐      ┌────────┐      ┌────────┐
    │ 请求   │ ───> │ 数据库 │      │ 缓存   │
    └────────┘      └────────┘      └────────┘
         │                              ▲
         │ ────────────────────────────│
         │         删除缓存             │
         ▼
```

#### 优势与局限

**优势：**
- 实现简单，易于维护
- 读性能高，适合读多写少场景
- 数据库压力小

**局限：**
- 存在短暂不一致窗口（删除缓存到下次查询之间）
- 并发场景下可能出现缓存不一致

### 3.2 双写一致性（延迟双删）

在 Cache Aside 基础上，对写操作进行优化，解决并发场景下的不一致问题。

#### 方案原理

```
┌─────────────────────────────────────────────────────────────────────────┐
│                         延迟双删流程                                     │
└─────────────────────────────────────────────────────────────────────────┘

    Time ─────────────────────────────────────────────────────────────>
    
    ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐   ┌────────┐
    │ 请求A  │   │ 缓存    │   │ 数据库  │   │ 请求B   │   │ 缓存    │
    │ 写操作 │   │        │   │        │   │ 读操作  │   │        │
    └────┬───┘   └────┬───┘   └────┬───┘   └────┬───┘   └────┬───┘
         │            │            │            │            │
         │ 1.删除缓存  │            │            │            │
         │───────────>│            │            │            │
         │            │            │            │            │
         │ 2.更新数据库│            │            │            │
         │────────────────────────>│            │            │
         │            │            │            │            │
         │            │            │    3.查询   │            │
         │            │            │<───────────│            │
         │            │            │            │            │
         │            │ 4.缓存未命中│            │            │
         │            │<───────────│            │            │
         │            │            │            │            │
         │            │ 5.查询旧数据 │            │            │
         │            │<────────────────────────│            │
         │            │            │            │            │
         │            │ 6.写入缓存(旧数据)        │            │
         │            │<───────────│            │            │
         │            │            │            │            │
         │ 7.延迟N毫秒 │            │            │            │
         │ (sleep)    │            │            │            │
         │            │            │            │            │
         │ 8.再次删除缓存│           │            │            │
         │───────────>│            │            │            │
         │            │            │            │            │
```

#### 延迟时间计算

```
延迟双删的延迟时间确定：

考虑因素：
1. 主从数据库同步延迟（通常 1-100ms）
2. 业务代码执行时间
3. 网络延迟

计算公式：
延迟时间 = max(主从延迟) + 代码执行时间 + 网络延迟 + 安全余量

典型场景：
- 单机部署：20-50ms
- 主从架构：100-500ms
- 跨机房部署：500-2000ms

建议：
- 初学者：使用 500ms 作为保守值
- 生产环境：根据监控的主从延迟 P99 值调整
```

#### 代码实现

```java
/**
 * 延迟双删实现
 */
public class DelayDoubleDeleteService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    // 延迟时间（毫秒），根据主从延迟调整
    private static final long DELAY_DELETE_TIME = 500L;

    /**
     * 更新商品 - 延迟双删保证一致性
     */
    public void updateProduct(Product product) {
        String cacheKey = "product:" + product.getId();

        // 1. 先删除缓存
        redisTemplate.delete(cacheKey);

        // 2. 更新数据库
        productMapper.updateById(product);

        // 3. 延迟后再次删除缓存
        CompletableFuture.runAsync(() -> {
            try {
                Thread.sleep(DELAY_DELETE_TIME);
                redisTemplate.delete(cacheKey);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }

    /**
     * 更新商品 - 使用线程池管理延迟删除
     */
    public void updateProductWithThreadPool(Product product) {
        String cacheKey = "product:" + product.getId();

        // 1. 先删除缓存
        redisTemplate.delete(cacheKey);

        // 2. 更新数据库
        productMapper.updateById(product);

        // 3. 延迟后再次删除缓存
        delayDeleteCache(cacheKey);
    }

    private void delayDeleteCache(String cacheKey) {
        Schedul edExecutorService executor =
            new ScheduledThreadPoolExecutor(1,
                new ThreadFactoryBuilder()
                    .setNameFormat("cache-delete-%d")
                    .build());

        executor.schedule(() -> {
            try {
                redisTemplate.delete(cacheKey);
            } finally {
                executor.shutdown();
            }
        }, DELAY_DELETE_TIME, TimeUnit.MILLISECONDS);
    }
}
```

### 3.3 直接删除 vs 更新：哪种更安全

#### 两种方案对比

| 操作 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **删除缓存** | 简单，不会有脏数据 | 并发时可能短暂不一致 | 大多数场景 |
| **更新缓存** | 实时性更好 | 并发时可能产生脏数据 | 写入不频繁场景 |

#### 为什么推荐删除而不是更新

```
并发场景分析：

时间线：
T1: 请求A 更新 product:1 = 100
T2: 请求B 更新 product:1 = 200
T3: 请求C 读取 product:1

【更新缓存的问题】

    T1: 写数据库 product:1 = 100
    T2: 写缓存 product:1 = 100  (旧值)
    T3: 写数据库 product:1 = 200
    T4: 写缓存 product:1 = 200  (新值)

    但如果顺序错乱：
    T1: 写数据库 product:1 = 100
    T2: 写数据库 product:1 = 200
    T3: 写缓存 product:1 = 200  (后写的先缓存)
    T4: 写缓存 product:1 = 100  (先写的后缓存) -> 脏数据！

【删除缓存的优势】

    T1: 删缓存
    T2: 写数据库 product:1 = 100
    T3: 删缓存  (第二次删除)
    T4: 读请求 -> 未命中 -> 查数据库 -> 缓存最新值

    即使有并发，删除操作的结果是确定的：
    删除 + 查数据库 + 写缓存 = 最终一致
```

### 3.4 实战案例：商品库存更新场景

#### 场景描述

```
电商系统中商品库存的特点：
1. 库存数量实时性要求极高
2. 并发扣减场景多（秒杀、抢购）
3. 库存超卖后果严重

解决方案：
- 缓存库存用于快速读取
- 数据库库存作为最终权威
- 使用乐观锁/分布式锁保证一致性
```

#### 完整实现

```java
/**
 * 商品库存缓存一致性实战
 */
@Service
public class StockCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final StockMapper stockMapper;

    // 库存缓存 Key
    private static final String STOCK_CACHE_KEY = "stock:item:{}";
    // 库存锁 Key
    private static final String STOCK_LOCK_KEY = "stock:lock:{}";
    // 缓存过期时间
    private static final long STOCK_CACHE_TTL = 30;

    /**
     * 查询库存 - Cache Aside
     */
    public Integer getStock(Long itemId) {
        String cacheKey = String.format(STOCK_CACHE_KEY, itemId);

        // 1. 查询缓存
        Integer stock = (Integer) redisTemplate.opsForValue().get(cacheKey);
        if (stock != null) {
            return stock;
        }

        // 2. 缓存未命中，查数据库
        Stock stockDB = stockMapper.selectByItemId(itemId);
        stock = stockDB != null ? stockDB.getStock() : 0;

        // 3. 写入缓存
        redisTemplate.opsForValue().set(cacheKey, stock,
            STOCK_CACHE_TTL, TimeUnit.SECONDS);

        return stock;
    }

    /**
     * 扣减库存 - 延迟双删 + 分布式锁
     */
    @Transactional
    public boolean deductStock(Long itemId, Integer quantity) {
        String cacheKey = String.format(STOCK_CACHE_KEY, itemId);
        String lockKey = String.format(STOCK_LOCK_KEY, itemId);

        // 1. 获取分布式锁
        String lockValue = UUID.randomUUID().toString();
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, 10, TimeUnit.SECONDS);

        if (!Boolean.TRUE.equals(acquired)) {
            // 获取锁失败，视为扣减失败
            return false;
        }

        try {
            // 2. 扣减数据库库存（乐观锁）
            int affectedRows = stockMapper.deductStockWithVersion(itemId, quantity);
            if (affectedRows == 0) {
                return false;
            }

            // 3. 删除缓存（第一次删除）
            redisTemplate.delete(cacheKey);

            // 4. 延迟双删 - 延迟后再次删除
            CompletableFuture.runAsync(() -> {
                try {
                    Thread.sleep(500); // 等待主从同步
                    redisTemplate.delete(cacheKey);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            });

            return true;

        } finally {
            // 5. 释放锁
            redisTemplate.delete(lockKey);
        }
    }

    /**
     * 补偿库存（退款场景）
     */
    @Transactional
    public void revertStock(Long itemId, Integer quantity) {
        String cacheKey = String.format(STOCK_CACHE_KEY, itemId);

        // 1. 补偿数据库库存
        stockMapper.revertStock(itemId, quantity);

        // 2. 删除缓存（延迟双删）
        redisTemplate.delete(cacheKey);

        CompletableFuture.runAsync(() -> {
            try {
                Thread.sleep(500);
                redisTemplate.delete(cacheKey);
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
        });
    }
}
```

### 4.1 缓存击穿（Cache Breaker）

#### 问题描述

```
热点 key 失效瞬间，大量并发请求同时访问该 key
由于缓存未命中，所有请求都打到数据库

┌─────────────────────────────────────────────────────────────────┐
│                        缓存击穿示意                                │
└─────────────────────────────────────────────────────────────────┘

         ┌────────┐
         │ 热点key │ ──────────────────┐
         │(失效中) │                   │
         └────────┘                   │
              │                      │
    ┌─────────┼─────────┬────────────┤
    │         │         │            │
    ▼         ▼         ▼            ▼
  请求A    请求B     请求C         请求D
    │         │         │            │
    │         │         │            │
    ▼         ▼         ▼            ▼
  ┌─────────────────────────────────────────┐
  │              数据库                      │
  │         (被大量并发请求打爆)              │
  └─────────────────────────────────────────┘
```

#### 解决方案一：互斥锁

```java
/**
 * 互斥锁方案解决缓存击穿
 */
public class MutexCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    // 锁的过期时间
    private static final long LOCK_EXPIRE_TIME = 10;
    private static final TimeUnit LOCK_TIME_UNIT = TimeUnit.SECONDS;

    public Product getProductWithMutex(Long id) {
        String cacheKey = "product:" + id;
        String lockKey = "lock:product:" + id;

        // 1. 先查缓存
        Product product = (Product) redisTemplate.opsForValue().get(cacheKey);
        if (product != null) {
            return product;
        }

        // 2. 获取互斥锁
        String lockValue = UUID.randomUUID().toString();
        Boolean acquired = redisTemplate.opsForValue()
            .setIfAbsent(lockKey, lockValue, LOCK_EXPIRE_TIME, LOCK_TIME_UNIT);

        try {
            if (Boolean.TRUE.equals(acquired)) {
                // 获得锁后，再次检查缓存（可能其他线程已经写入）
                product = (Product) redisTemplate.opsForValue().get(cacheKey);
                if (product != null) {
                    return product;
                }

                // 3. 查询数据库
                product = productMapper.selectById(id);

                // 4. 写入缓存
                if (product != null) {
                    redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);
                }

                return product;
            } else {
                // 未获得锁，短暂等待后重试
                Thread.sleep(50);
                return getProductWithMutex(id);
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            // 降级：直接查数据库
            return productMapper.selectById(id);
        } finally {
            // 5. 释放锁
            if (lockValue.equals(redisTemplate.opsForValue().get(lockKey))) {
                redisTemplate.delete(lockKey);
            }
        }
    }
}
```

```java
            return loadProductWithMutex(id);

            // 未过期，直接返回
            return cacheProduct.getProduct();
```

### 4.2 缓存穿透（Cache Pierce）

#### 问题描述

```
请求访问不存在的数据，缓存中找不到，数据库中也找不到
如果大量此类请求，会绕过缓存直接打到数据库

┌─────────────────────────────────────────────────────────────────┐
│                        缓存穿透示意                               │
└─────────────────────────────────────────────────────────────────┘

    请求查询 ID = -1 的商品
         │
         ▼
    ┌────────┐
    │  缓存   │ ── 未命中 ──> 数据库 ──> 也不存在
    └────────┘                  │
         ▲                      │
         └──────────────────────┘
              每次都查数据库
```

#### 解决方案一：布隆过滤器

```
┌─────────────────────────────────────────────────────────────────┐
│                       布隆过滤器原理                               │
└─────────────────────────────────────────────────────────────────┘

    数据写入：
    ┌─────────┐     ┌──────────────┐     ┌─────────────────────┐
    │  数据ID  │ ──> │  Hash函数1   │ ──> │  Bit Array 位置1   │
    │         │ ──> │  Hash函数2   │ ──> │  Bit Array 位置2   │
    │         │ ──> │  Hash函数3   │ ──> │  Bit Array 位置3   │
    └─────────┘     └──────────────┘     └─────────────────────┘

    查询验证：
    ┌─────────┐     ┌──────────────┐     ┌─────────────────────┐
    │ 查询ID  │ ──> │  Hash函数1,2,3│     │ 所有对应位都是1？   │
    │         │     │              │     │  → 可能在           │
    │         │     │              │     │  → 有0位 → 一定不在  │
    └─────────┘     └──────────────┘     └─────────────────────┘

布隆过滤器特点：
✓ 空间效率高
✓ 查询效率高 O(k)，k 为 hash 函数个数
✓ 不存在漏报（说不在就一定不在）
✗ 存在误报（说在不一定在）
✗ 删除困难（可能有误伤其他数据）
```

#### 代码实现

```java
/**
 * 布隆过滤器解决缓存穿透
 */
@Service
public class BloomFilterService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final RedissonClient redissonClient;

    // 布隆过滤器大小（建议设置成预期数据量的 10 倍）
    private static final long BLOOM_FILTER_SIZE = 1000000;
    // 误报率
    private static final double FALSE_POSITIVE_RATE = 0.01;
    // Hash 函数数量
    private static final int HASH_FUNCTIONS = 7;

    /**
     * 初始化布隆过滤器
     */
    @PostConstruct
    public void initBloomFilter() {
        RBloomFilter<String> bloomFilter = redissonClient.getBloomFilter("product:bloom");
        bloomFilter.tryInit(BLOOM_FILTER_SIZE, FALSE_POSITIVE_RATE);
    }

    /**
     * 添加商品 ID 到布隆过滤器
     */
    public void addProductToBloom(Long productId) {
        RBloomFilter<String> bloomFilter = redissonClient.getBloomFilter("product:bloom");
        bloomFilter.add(String.valueOf(productId));
    }

    /**
     * 批量添加商品 ID 到布隆过滤器
     */
    public void addProductsToBloom(List<Long> productIds) {
        RBloomFilter<String> bloomFilter = redissonClient.getBloomFilter("product:bloom");
        productIds.forEach(id -> bloomFilter.add(String.valueOf(id)));
    }

    /**
     * 查询商品（带布隆过滤器）
     */
    public Product getProduct(Long id) {
        RBloomFilter<String> bloomFilter = redissonClient.getBloomFilter("product:bloom");

        // 1. 先检查布隆过滤器
        if (!bloomFilter.contains(String.valueOf(id))) {
            // 布隆过滤器说不在，一定不在
            return null;
        }

        // 2. 布隆过滤器说可能在，查询缓存
        String cacheKey = "product:" + id;
        Product product = (Product) redisTemplate.opsForValue().get(cacheKey);

        if (product != null) {
            return product;
        }

        // 3. 缓存未命中，查询数据库
        product = productMapper.selectById(id);

        if (product != null) {
            redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);
        }

        return product;
    }
}
```

#### 解决方案二：空值缓存

```java
/**
 * 空值缓存解决缓存穿透
 */
public class NullValueCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    // 空值缓存的 TTL（不能太长，否则会影响数据一致性）
    private static final long NULL_VALUE_TTL = 5 * 60; // 5分钟

    public Product getProduct(Long id) {
        String cacheKey = "product:" + id;

        // 1. 查询缓存
        Object cached = redisTemplate.opsForValue().get(cacheKey);

        if (cached != null) {
            // 2. 判断是否是空值
            if (cached instanceof NullValue) {
                return null; // 恶意攻击或无效请求
            }
            return (Product) cached;
        }

        // 3. 缓存未命中，查询数据库
        Product product = productMapper.selectById(id);

        if (product == null) {
            // 4. 数据库也没有，缓存空值
            redisTemplate.opsForValue().set(cacheKey, new NullValue(), NULL_VALUE_TTL, TimeUnit.SECONDS);
            return null;
        }

        // 5. 写入缓存
        redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);

        return product;
    }

    /**
     * 空值标记类
     */
    public static class NullValue implements Serializable {
        private static final long serialVersionUID = 1L;
    }
}
```

### 4.3 缓存雪崩（Cache Avalanche）

#### 问题描述

#### 解决方案一：随机 TTL

```java
/**
 * 随机过期时间解决缓存雪崩
 */
@Service
public class RandomExpireCacheService {

    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    // 基础过期时间
    private static final long BASE_TTL = 30 * 60;  // 30分钟
    // 随机范围
    private static final long RANDOM_TTL = 10 * 60; // 最多再加10分钟随机

    /**
     * 写入缓存 - 随机过期时间
     */
    public void cacheProduct(Product product) {
        String cacheKey = "product:" + product.getId();

        // 计算随机过期时间：基础时间 + 随机偏移
        long randomExpire = BASE_TTL + new Random().nextInt((int) RANDOM_TTL);

        redisTemplate.opsForValue().set(cacheKey, product, randomExpire, TimeUnit.SECONDS);
    }

    /**
     * 批量写入缓存 - 随机过期时间
     */
    public void batchCacheProducts(List<Product> products) {
        Random random = new Random();

        for (Product product : products) {
            String cacheKey = "product:" + product.getId();
            long randomExpire = BASE_TTL + random.nextInt((int) RANDOM_TTL);
            redisTemplate.opsForValue().set(cacheKey, product, randomExpire, TimeUnit.SECONDS);
        }
    }
}
```

#### 代码实现

```java
/**
 * 多级缓存实现
 */
@Service
public class MultiLevelCacheService {

    private final Cache<String, Product> localCache;
    private final RedisTemplate<String, Object> redisTemplate;
    private final ProductMapper productMapper;

    // 本地缓存配置
    private static final long LOCAL_CACHE_SIZE = 1000;
    private static final long LOCAL_CACHE_TTL = 60; // 1分钟

    public MultiLevelCacheService() {
        // 初始化本地缓存（Caffeine）
        this.localCache = Caffeine.newBuilder()
            .maximumSize(LOCAL_CACHE_SIZE)
            .expireAfterWrite(LOCAL_CACHE_TTL, TimeUnit.SECONDS)
            .build();
    }

    /**
     * 获取产品 - 多级缓存查询
     */
    public Product getProduct(Long id) {
        String cacheKey = "product:" + id;

        // 1. 查询 L1 本地缓存
        Product product = localCache.getIfPresent(cacheKey);
        if (product != null) {
            return product;
        }

        // 2. 查询 L2 Redis 缓存
        product = (Product) redisTemplate.opsForValue().get(cacheKey);
        if (product != null) {
            // 写入 L1 缓存
            localCache.put(cacheKey, product);
            return product;
        }

        // 3. L2 也未命中，查询数据库
        product = productMapper.selectById(id);
        if (product != null) {
            // 写入 L2 缓存
            redisTemplate.opsForValue().set(cacheKey, product, 30, TimeUnit.MINUTES);
            // 写入 L1 缓存
            localCache.put(cacheKey, product);
        }

        return product;
    }

    /**
     * 更新产品 - 多级缓存更新
     */
    public void updateProduct(Product product) {
        String cacheKey = "product:" + product.getId();

        // 1. 更新数据库
        productMapper.updateById(product);

        // 2. 删除 L2 缓存
        redisTemplate.delete(cacheKey);

        // 3. 删除 L1 缓存（或者更新）
        localCache.invalidate(cacheKey);
    }
}
```

| 大量同时过期 | 多级缓存 + 随机 TTL | 防雪崩 |

### 5.2 常见错误

#### 错误一：缓存容量规划不当

```
问题：
- 内存设置过大，导致 Redis 性能下降
- 内存设置过小，频繁淘汰，缓存命中率低

正确做法：
- 监控缓存命中率，保持在 95% 以上
- 根据数据量和 key 大小规划内存
- 预留 20-30% 内存作为 buffer
```

#### 错误二：Key 设计不规范

```
问题：
- Key 过长，消耗内存
- Key 无命名空间，冲突风险高
- 未设置过期时间，导致内存无限增长

正确做法：
- 使用简短有意义的 Key
- 使用冒号分隔命名空间：user:session:12345
- 始终设置 TTL，包含过期策略注释
```

#### 错误三：忽视缓存穿透风险

```
问题：
- 只处理正常请求，忽视恶意攻击
- 数据库不存在的数据反复查询

正确做法：
- 参数校验拦截无效请求
- 使用布隆过滤器
- 缓存空值（设置短 TTL）
```

#### 错误四：缓存雪崩

```
问题：
- 所有缓存使用相同的过期时间
- 大量 key 同时过期

正确做法：
- 使用随机过期时间
- 实现多级缓存
- 热点数据预热
```

#### 错误五：分布式锁使用不当

```
问题：
- 锁未设置过期时间
- 释放锁时未验证拥有者
- 锁粒度过大

正确做法：
- 始终设置过期时间
- 使用唯一值标识锁的拥有者
- 缩小锁的粒度
```
