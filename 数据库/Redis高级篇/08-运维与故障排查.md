# Redis运维与故障排查

## 1、持久化调优

### 1.1 RDB调优参数

#### 1.1.1 save规则优化

RDB的save规则配置直接影响快照生成的频率和性能。在生产环境中，需要根据数据量和业务场景进行合理配置。

```sh
# Redis 6.2及以上版本支持多规则配置
save 3600 1    # 1小时内有1次修改就触发bgsave
save 300 100   # 5分钟内有100次修改就触发bgsave
save 60 10000  # 1分钟内有10000次修改就触发bgsave

# 关闭自动RDB（仅使用手动bgsave）
save ""
```

**调优建议：**

- 高写入场景：减小时间窗口，增加修改次数阈值，避免频繁bgsave
- 低写入场景：可适当放宽规则，保证数据安全性
- 关键业务：建议配置多个规则，确保不同时段都有保护

#### 1.1.2 bgsave错误处理

bgsave过程中可能因为磁盘空间不足、权限问题等导致失败，需要配置错误处理策略：

```sh
# bgsave失败时是否停止写入
stop-writes-on-bgsave-error yes

# 是否对rdb文件进行压缩
rdbcompression yes

# 是否使用CRC64校验RDB文件
rdbchecksum yes
```

**常见bgsave错误及处理：**

| 错误类型 | 原因 | 解决方案 |
|---------|------|---------|
| bgsave失败 | 磁盘空间不足 | 清理磁盘或调整`dir`路径 |
| bgsave失败 | 父进程fork失败 | 减少内存使用或增大`vm.overcommit_memory` |
| RDB文件损坏 | 非正常关闭 | 使用`redis-check-rdb`修复 |

```sh
# 检查RDB文件完整性
redis-cli --rdb /path/to/dump.rdb

# 或使用redis-check-rdb
redis-check-rdb /path/to/dump.rdb
```

### 1.2 AOF调优

#### 1.2.1 appendfsync策略选择

AOF的`appendfsync`策略直接影响的性能和数据安全性：

```sh
# 三种策略选择
appendfsync always    # 每次写入都同步，最安全但性能最差
appendfsync everysec  # 每秒同步，推荐选择，默认策略
appendfsync no        # 由操作系统决定何时同步，性能最好但最不安全
```

**性能对比：**

```
appendfsync always:  ~1,000 QPS
appendfsync everysec: ~50,000 QPS
appendfsync no:       ~100,000+ QPS
```

**场景选择建议：**

- 金融、支付等关键业务：`always`
- 一般业务系统：`everysec`
- 高性能缓存场景：`no`（但需要接受数据丢失风险）

#### 1.2.2 auto-aof-rewrite优化

AOF文件过大会触发重写，可以通过以下参数优化：

```sh
# 触发重写的AOF文件大小比例（当前文件比上次重写后的文件大100%时触发）
auto-aof-rewrite-percentage 100

# 触发重写的最小AOF文件大小
auto-aof-rewrite-min-size 64mb

# 重写过程中是否停止写入（Redis 7.0+）
aof-rewrite-incremental-fsync yes

# 是否加载不完整的AOF文件
aof-load-truncated yes
```

**优化建议：**

```sh
# 高写入场景配置示例
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 512mb
aof-rewrite-incremental-fsync yes
```

### 1.3 混合持久化配置优化

Redis 4.0引入了混合持久化，结合了RDB和AOF的优点：

```sh
# 开启混合持久化
aof-use-rdb-preamble yes

# 完整的混合持久化配置示例
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
aof-use-rdb-preamble yes
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
```

**混合持久化工作原理：**

- AOF重写时，先以RDB格式写入当前数据，然后增量追加AOF操作
- 恢复时，先加载RDB部分，再执行增量AOF操作
- 兼顾快速恢复和数据完整性

### 1.4 持久化与性能权衡

持久化配置需要在性能和数据安全之间找到平衡：

```sh
# 最佳实践配置
# RDB配置
save 3600 1 300 100 60 10000
dbfilename dump.rdb
dir /path/to/fast-disk
rdbcompression yes
rdbchecksum yes
stop-writes-on-bgsave-error yes

# AOF配置
appendonly yes
appendfilename "appendonly.aof"
appendfsync everysec
aof-use-rdb-preamble yes
auto-aof-rewrite-percentage 100
auto-aof-rewrite-min-size 64mb
aof-rewrite-incremental-fsync yes

# 限制AOF和RDB文件大小
aof-max-size 10gb
```

## 2、主从延迟问题排查

### 2.1 主从延迟原因分析

主从延迟是指从节点同步主节点数据时产生的时间差，可能由以下原因导致：

| 原因类型 | 具体原因 | 影响程度 |
|---------|---------|---------|
| 网络因素 | 主从网络延迟、网络抖动 | 中 |
| 写入压力 | 主节点写入QPS过高 | 高 |
| 从节点性能 | 从节点处理能力不足 | 高 |
| 同步机制 | repl_backlog配置过小 | 高 |
| 大命令 | 单个命令数据过大 | 中 |
| 长事务/阻塞 | 主节点执行阻塞操作 | 高 |

### 2.2 repl_backlog配置

`repl_backlog`是从节点断开连接后保存增量数据的缓冲区，配置不当会导致全量同步：

```sh
# 环形缓冲区大小，建议设置大一些
repl-backlog-size 10mb

# 当所有从节点断开后，保留backlog的时间
repl-backlog-ttl 3600
```

**计算公式：**

```
repl-backlog-size = 主节点写入速度 × 最大延迟时间 × 1.5
```

**示例：**

```sh
# 假设主节点写入速度为10MB/s，最大网络延迟为5秒
# repl-backlog-size = 10MB × 5s × 1.5 = 75MB
repl-backlog-size 75mb
```

### 2.3 延迟监控命令

#### 2.3.1 INFO replication

```sh
# 查看主从复制状态
redis-cli INFO replication
```

关键指标解读：

```sh
# 从节点输出
role:slave
master_link_status:up              # 连接状态，up表示正常
master_link_last_io_seconds_ago:0   # 最近一次IO距今秒数
seconds_since_last_repl_backlog_transfer:0  # 最近一次backlog传输距今秒数
repl_backlog_active:1               # backlog是否活跃
repl_backlog_size:10485760         # backlog总大小
repl_backlog_first_byte_offset:0   # backlog起始偏移量
repl_backlog_histlen:0             # backlog已使用大小
```

#### 2.3.2 延迟监控脚本

```java
import redis.clients.jedis.Jedis;
import redis.clients.jedis.ReplicationTest;

public class ReplicationLatencyMonitor {
    public static void main(String[] args) {
        Jedis master = new Jedis("master-host", 6379);
        Jedis slave = new Jedis("slave-host", 6379);

        // 获取主从延迟
        Long masterOffset = master.getReplOffset();
        Long slaveOffset = slave.getReplOffset();

        long lag = masterOffset - slaveOffset;
        System.out.println("主从复制延迟: " + lag + " bytes");

        // 持续监控
        while (true) {
            try {
                Thread.sleep(1000);
                masterOffset = master.getReplOffset();
                Long currentSlaveOffset = slave.getReplOffset();
                long currentLag = masterOffset - currentSlaveOffset;

                System.out.println("当前延迟: " + currentLag + " bytes");

                // 延迟超过阈值告警
                if (currentLag > 10485760) { // 10MB
                    System.out.println("警告: 主从延迟超过10MB!");
                }
            } catch (Exception e) {
                e.printStackTrace();
            }
        }
    }
}
```

## 3、内存增长问题诊断

### 3.1 内存突然增长排查思路

当Redis内存突然增长时，按以下思路排查：

```sh
# 1. 查看内存使用情况
redis-cli INFO memory

# 输出示例
used_memory:10485760
used_memory_human:10.00M
used_memory_rss:12582912
used_memory_rss_human:12.00M
mem_fragmentation_ratio:1.20
```

**排查流程：**

```
内存增长 → 分析内存组成 → 定位问题类型 → 针对性处理
     │
     ├── 键值对数量增长 → 检查业务逻辑
     ├── 单个值变大 → 查找bigkey
     ├── 内存碎片 → 调整内存分配器
     └── 缓冲区膨胀 → 调整配置
```

### 3.2 键值对分析

#### 3.2.1 使用SCAN扫描键

```sh
# 使用SCAN渐进式扫描，避免阻塞
redis-cli --scan | head -100 | xargs -L 1 redis-cli DEBUG OBJECT

# 按模式扫描
redis-cli --scan --pattern "user:*" | wc -l
```

#### 3.2.2 使用DEBUG OBJECT分析

```sh
# 查看单个键的详细信息
redis-cli DEBUG OBJECT "key_name"

# 输出示例
Key "user:1001"
type:string
encoding:embstr
serializedlength:1024
lru:12345678
lru_seconds_idle:3600
```

**各字段含义：**

| 字段 | 含义 |
|-----|------|
| type | 键类型（string/list/hash/set/zset） |
| encoding | 编码方式（raw/embstr/int/ht/ziplist等） |
| serializedlength | 序列化后的长度 |
| lru_seconds_idle | 键的空闲时间 |

### 3.3 bigkey导致内存增长

#### 3.3.1 识别bigkey

```sh
# 使用redis-cli --bigkeys分析（采样方式）
redis-cli --bigkeys

# 统计各类键的数量和大小
# Scanning 100000 keys ...
# -------- summary -------
# big   : 5 (avg size 2097152 bytes)
# string keys: 10000
# list keys: 5000 (avg len 1000)
```

#### 3.3.2 渐进式删除bigkey

```java
// 使用SCAN + UNLINK渐进式删除
public void deleteBigKey(Jedis jedis, String key) {
    String type = jedis.type(key);

    switch (type) {
        case "string":
            jedis.del(key);
            break;
        case "list":
            long len = jedis.llen(key);
            while (len > 0) {
                jedis.ltrim(key, 0, -1000); // 每次删除1000个
                len = jedis.llen(key);
            }
            jedis.del(key);
            break;
        case "hash":
            // 使用hscan + hdel渐进删除
            ScanParams params = new ScanParams().count(1000);
            String cursor = "0";
            do {
                ScanResult<Map.Entry<String, String>> result =
                    jedis.hscan(key, cursor, params);
                for (Map.Entry<String, String> entry : result.getResult()) {
                    jedis.hdel(key, entry.getKey());
                }
                cursor = result.getCursor();
            } while (!cursor.equals("0"));
            jedis.del(key);
            break;
        // 其他类型类似处理
    }
}
```

#### 3.3.3 防止bigkey产生

```sh
# 配置最大单项限制（需Redis 7.0+）
proto-max-bulk-len 10mb
```

### 3.4 内存碎片导致内存虚高

#### 3.4.1 判断内存碎片

```sh
# 调整内存分配策略

```

## 4、集群故障处理

### 4.1 节点故障处理流程

#### 4.1.1 节点故障发现

```sh
# 查看集群节点状态
redis-cli --cluster check <host>:6379

# 查看集群信息
redis-cli CLUSTER INFO
```

#### 4.1.2 故障节点隔离

```
故障节点处理流程：
1. 发现节点不可达
2. 标记节点为疑似失败（PFAIL）
3. 超过半数主节点确认后标记为失败（FAIL）
4. 从节点发起选举
5. 新主节点接管槽位
```

#### 4.1.3 节点恢复

```sh
# 修复后重新加入集群
redis-cli --cluster add-node <new_host>:6379 <existing_host>:6379

# 如果是主节点，需要重新分配槽位
redis-cli --cluster reshard <host>:6379
```

### 4.2 脑裂问题处理

#### 4.2.1 脑裂原因

脑裂是指集群中多个节点认为对方不可用，导致产生多个主节点同时存在的情况。

```
脑裂发生场景：
1. 网络分区导致多个节点组无法通信
2. 主节点假死（主节点正常但响应超时）
3. 从节点假死
```

#### 4.2.2 预防配置

```sh
# 主节点最小从节点数量
min-replicas-to-write 2

# 从节点最大延迟
min-replicas-max-lag 10

# 节点超时时间
cluster-node-timeout 15000
```

#### 4.2.3 脑裂处理步骤

```sh
# 1. 确认脑裂范围
redis-cli --cluster check <host>:6379

# 2. 识别所有主节点及其槽位分布
redis-cli CLUSTER NODES

# 3. 关闭多余的从节点
redis-cli CLUSTER FORGET <node-id>

# 4. 手动重新分片
redis-cli --cluster reshard <host>:6379

# 5. 验证集群状态
redis-cli --cluster check <host>:6379
```

### 4.3 槽位迁移中断处理

#### 4.3.1 迁移状态查看

```sh
# 查看槽位迁移状态
redis-cli CLUSTER NODES | grep " <slot>"

# 查看迁移中的key数量
redis-cli --cluster check <host>:6379
```

#### 4.3.2 迁移中断恢复

```sh
# 如果迁移中断，执行以下步骤恢复：

# 1. 确定源节点和目标节点
# 2. 使用SET slot <node_id>命令设置槽位归属
redis-cli CLUSTER SETSLOT 1000 <node_id>

# 3. 重新触发迁移
redis-cli --cluster reshard <host>:6379

# 4. 或者使用migrate命令手动迁移key
redis-cli MIGRATE <target_host> 6379 "" 0 5000 KEYS key1 key2 key3
```

#### 4.3.3 迁移脚本

```java
public class ClusterMigrationRecovery {
    public JedisCluster jedis;

    // 恢复迁移中断的槽位
    public void recoverMigration(int slot, String targetNodeId) {
        // 1. 设置槽位归属
        String result = jedis.clusterSetSlot(slot, targetNodeId);
        System.out.println("设置槽位结果: " + result);

        // 2. 手动迁移剩余的key
        List<String> keys = getKeysInSlot(slot);
        for (String key : keys) {
            try {
                jedis.clusterSetSlotMigrating(slot, targetNodeId);
                String value = jedis.get(key);
                jedis.set(key, value);
                jedis.clusterSetSlotStable(slot);
            } catch (Exception e) {
                System.out.println("迁移key失败: " + key + ", " + e.getMessage());
            }
        }
    }
}
```

### 4.4 集群不可用情况分析

#### 4.4.1 不可用原因

| 场景 | 原因 | 影响 |
|-----|------|------|
| 半数主节点宕机 | 节点故障 | 集群不可写 |
| 某槽位无主节点 | 主从全部宕机 | 部分数据不可用 |
| 所有从节点宕机 | 主节点故障 | 主节点故障后无备份 |
| 网络分区 | 节点间通信中断 | 可能导致脑裂 |

#### 4.4.2 恢复流程

```sh

redis-cli CLUSTER INFO

# 2. 检查节点状态
redis-cli CLUSTER NODES

# 3. 尝试自动恢复
redis-cli --cluster fix <host>:6379

# 4. 如果自动恢复失败，手动指定槽位
redis-cli --cluster reshard <host>:6379

# 5. 添加新节点补充
redis-cli --cluster add-node <new_host>:6379 <existing_host>:6379
```

## 5、常见故障场景与解决方案

### 5.1 OOM（内存溢出）

#### 5.1.1 原因分析

```sh
# 查看内存使用
redis-cli INFO memory | grep -E "used_memory|maxmemory"
```

**常见原因：**

- `maxmemory`未设置或设置过大
- 突发流量导致数据暴增
- 内存碎片占用大量空间
- 客户端输出缓冲区溢出

#### 5.1.2 解决方案

**方案一：配置内存限制**

```sh
# 设置最大内存（根据服务器可用内存设置）
maxmemory 8gb

# 设置内存淘汰策略
maxmemory-policy allkeys-lru
```

**方案二：处理突发流量**

```java
// 使用限流保护
public class RedisRateLimiter {
    private Jedis jedis;
    private int maxRequests;
    private int windowSeconds;

    public boolean isAllowed(String key) {
        String current = jedis.get("rate:" + key);
        if (current == null) {
            jedis.setex("rate:" + key, windowSeconds, "1");
            return true;
        }
        if (Integer.parseInt(current) >= maxRequests) {
            return false;
        }
        jedis.incr("rate:" + key);
        return true;
    }
}
```

**方案三：使用内存分析**

```sh
# 使用MEMORY STATS查看内存详情
redis-cli MEMORY STATS

# 使用MEMORY USAGE查看单个键内存
redis-cli MEMORY USAGE key_name
```

### 5.2 连接数打满

#### 5.2.1 原因分析

```sh
# 查看连接数
redis-cli INFO clients

# 输出
connected_clients:5000
client_longest_output_list:0
blocked_clients:0
```

**常见原因：**

- 客户端连接未正确关闭
- 使用了连接池但配置过小
- Redis端口暴露被扫描利用
- 慢查询阻塞连接

#### 5.2.2 解决方案

**方案一：配置连接限制**

```sh
# 最大客户端数
maxclients 10000

# 客户端输出缓冲区限制
client-output-buffer-limit normal 32mb 8mb 60
client-output-buffer-limit replica 256mb 64mb 360
client-output-buffer-limit pubsub 32mb 8mb 60
```

**方案二：优化连接管理**

```java
// 使用连接池
public class RedisConnectionPool {
    private static JedisPool jedisPool;

    static {
        JedisPoolConfig config = new JedisPoolConfig();
        config.setMaxTotal(100);
        config.setMaxIdle(50);
        config.setMinIdle(10);
        config.setMaxWaitMillis(3000);
        config.setTestOnBorrow(true);
        config.setTestOnReturn(true);

        jedisPool = new JedisPool(config, "redis-host", 6379);
    }

    public static Jedis getConnection() {
        return jedisPool.getResource();
    }
}
```

### 5.3 CPU使用率过高

#### 5.3.1 原因分析

```sh
# 查看CPU使用
redis-cli INFO cpu

# 查看正在执行的命令
redis-cli CLIENT LIST | grep cmd=
```

**常见原因：**

- 频繁执行复杂命令（SORT、SINTER等）
- 大key遍历（KEYS、SMEMBERS）
- 大量并发请求
- 持久化操作（bgsave、aofrewrite）

#### 5.3.2 解决方案

**方案一：避免使用阻塞命令**

```java
// 避免使用KEYS，使用SCAN替代
public void scanKeys(Jedis jedis, String pattern) {
    ScanParams params = new ScanParams();
    params.match(pattern);
    params.count(1000);

    String cursor = "0";
    do {
        ScanResult<String> result = jedis.scan(cursor, params);
        List<String> keys = result.getResult();
        // 处理keys
        cursor = result.getCursor();
    } while (!cursor.equals("0"));
}

// 避免使用SORT，使用Sorted Set替代
```

**方案二：使用Pipeline**

```java
// 使用Pipeline批量操作
public void batchOperation(Jedis jedis, List<String> keys) {
    Pipeline pipeline = jedis.pipelined();
    for (String key : keys) {
        pipeline.get(key);
    }
    List<Object> results = pipeline.syncAndReturnAll();
}
```

### 5.4 持久化失败

#### 5.4.1 原因分析

```sh
# 查看持久化状态
redis-cli INFO persistence

# 查看最新持久化错误
redis-cli LASTSAVE
redis-cli DEBUG SLEEP 1 && redis-cli LASTSAVE
```

**常见原因：**

- 磁盘空间不足
- 权限问题
- Fork失败（内存不足）
- AOF文件损坏

#### 5.4.2 解决方案

**方案一：检查磁盘空间**

```sh
# 查看磁盘空间
df -h /path/to/redis

# 清理磁盘
docker system prune -a
```

**方案二：修复AOF文件**

```sh
# 使用redis-check-aof修复
redis-check-aof --fix /path/to/appendonly.aof
```

**方案三：调整内存配置**

```sh
# 调整overcommit_memory
sysctl -w vm.overcommit_memory=1

# 添加到/etc/sysctl.conf永久生效
echo "vm.overcommit_memory = 1" >> /etc/sysctl.conf
```

### 7.3 备份策略

#### 7.3.1 自动备份脚本

```sh
#!/bin/bash
# Redis自动备份脚本
# 配置
REDIS_HOST="localhost"
REDIS_PORT="6379"
BACKUP_DIR="/data/backup/redis"
DATE=$(date +%Y%m%d_%H%M%S)
BACKUP_FILE="${BACKUP_DIR}/redis_backup_${DATE}.rdb"

# 创建备份目录
mkdir -p ${BACKUP_DIR}

# 执行BGSAVE
redis-cli -h ${REDIS_HOST} -p ${REDIS_PORT} BGSAVE

# 等待BGSAVE完成
while [ $(redis-cli -h ${REDIS_HOST} -p ${REDIS_PORT} LASTSAVE) == $(redis-cli -h ${REDIS_HOST} -p ${REDIS_PORT} LASTSAVE) ]; do
    sleep 1
done

# 复制RDB文件
cp /path/to/redis/dump.rdb ${BACKUP_FILE}

# 压缩备份文件
gzip ${BACKUP_FILE}

# 备份AOF文件（如果启用）
if [ -f /path/to/redis/appendonly.aof ]; then
    cp /path/to/redis/appendonly.aof ${BACKUP_DIR}/redis_backup_${DATE}.aof
    gzip ${BACKUP_DIR}/redis_backup_${DATE}.aof
fi

# 清理7天前的备份
find ${BACKUP_DIR} -name "redis_backup_*" -mtime +7 -delete

echo "备份完成: ${BACKUP_FILE}.gz"
```
