# 内存优化与监控

## 1、Redis内存结构深入分析

Redis是一个基于内存的数据库，内存管理是Redis核心知识点。理解Redis的内存结构对于性能调优和问题排查至关重要。

### 1.1 内存相关核心指标

Redis提供了`INFO memory`命令来查看详细的内存使用情况：

```sh
127.0.0.1:6379> INFO memory
# Memory
used_memory:1048576
used_memory_human:1.00M
used_memory_rss:1572864
used_memory_rss_human:1.50M
used_memory_peak:2097152
used_memory_peak_human:2.00M
used_memory_peak_perc:50.12%
used_memory_overhead:520080
used_memory_startup:520080
used_memory_dataset:528496
used_memory_dataset_perc:50.62%
total_system_memory:33554432000
total_system_memory_human:31.25G
used_memory_lua:37888
used_memory_lua_human:37.00K
mem_fragmentation_ratio:1.50
mem_fragmentation_bytes:524288
mem_not_counted_for_evict:0
mem_replication_backlog:1048576
mem_clients_slaves:16448
mem_clients_normal:49694
mem_aof_buffer:3145728
mem_allocator:jemalloc-5.3.0
mem_not_counted_for_evict:0
```

### 1.2 关键指标详解

| 指标名称 | 说明 |
|---------|------|
| **used_memory** | Redis数据实际使用的内存总量（字节），包括所有数据、键值对、内部编码等 |
| **used_memory_human** | used_memory的人类可读格式 |
| **used_memory_rss** | 操作系统视角看到的Redis进程占用的物理内存（包含内存碎片） |
| **used_memory_rss_human** | used_memory_rss的人类可读格式 |
| **used_memory_peak** | Redis历史峰值内存使用量 |
| **mem_fragmentation_ratio** | 内存碎片率 = used_memory_rss / used_memory |
| **mem_allocator** | Redis使用的内存分配器（通常为jemalloc） |

### 1.3 内存碎片率计算

内存碎片率是评估Redis内存健康状态的重要指标：

```
内存碎片率 = used_memory_rss / used_memory
```

**碎片率含义**：
- **碎片率 = 1.0**：内存使用完美，无碎片
- **碎片率 < 1.0**：Redis已使用swap分区（性能严重下降）
- **碎片率 > 1.0**：存在内存碎片

**正常范围**：1.0 ~ 1.5被认为是合理范围

```sh
# 计算内存碎片率
redis-cli INFO memory | grep mem_fragmentation_ratio
# mem_fragmentation_ratio:1.50

# 手动计算
python3 -c "print(1572864/1048576)"  # 输出: 1.5
```

### 1.4 内存分配器

Redis使用内存分配器来管理内存，现代Redis版本默认使用jemalloc：

```sh
# 查看使用的内存分配器
redis-cli INFO memory | grep mem_allocator
# mem_allocator:jemalloc-5.3.0
```

**常见的内存分配器对比**：

| 分配器 | 特点 |
|-------|------|
| jemalloc | Redis默认，性能优秀，减少碎片 |
| glibc malloc | 简单但容易产生碎片 |
| tcmalloc | Google开发，适用于多线程 |

## 2、内存碎片处理

### 2.1 内存碎片产生原因

内存碎片的产生是内存分配器工作的自然结果，主要原因包括：

**1. 键值对过期删除**
```java
// 当删除过期键值对时，Redis不会立即归还内存给操作系统
// 内存分配器会将这部分空间标记为可用，但可能无法被完全利用

SET session:user:1001 "user_data"
EXPIRE session:user:1001 3600  // 1小时后过期
// 过期后释放的空间可能成为碎片
```

**2. 数据类型编码转换**
```java
// Redis会根据数据大小自动选择编码
// 从ziplist转换为hashtable时，会分配新空间

// 字符串长度 < 44字节时使用embstr编码
// 字符串长度 >= 44字节时转换为raw编码
SET small_key "short_value"    // embstr编码
SET large_key "a_very_long_value_that_exceeds_44_bytes..." // raw编码
```

**3. 大小不一的键值对**
```java
// 频繁的SET/DELETE操作会导致内存分配器产生碎片
for (int i = 0; i < 10000; i++) {
    SET "key:" + i, "value_" + i;
    if (i % 2 == 0) {
        DEL "key:" + i;  // 删除操作产生碎片
    }
}
```

**4. 内存分配算法**
```c
// jemalloc将内存按大小划分池（chunk、run、bin）
// 当请求的大小与池不匹配时，会产生内部碎片和外部碎片
```

### 2.2 主动碎片整理（active-defrag）

Redis 4.0引入了`active-defrag`机制，可以自动进行内存碎片整理。

#### 2.2.1 开启主动碎片整理

```sh
# 在redis.conf中配置

# 开启主动碎片整理
activedefrag yes

# 内存碎片率达到多少时开始整理（默认5%）
active-defrag-ignore-start 5%

# 碎片整理的最小工作力度（CPU百分比）
active-defrag-threshold-lower 5

# 碎片整理的最大工作力度
active-defrag-threshold-upper 75

# 碎片整理期间，词典字段扫描的最少数量
active-defrag-field-threshold-min 100

# 碎片整理的CPU工作时长占比
active-defrag-cycle-min 25

active-defrag-cycle-max 75
```

#### 2.2.2 active-defrag工作原理

```
┌─────────────────────────────────────────────────────────────┐
│                    active-defrag 工作流程                    │
├─────────────────────────────────────────────────────────────┤
│                                                             │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐  │
│  │  监控碎片率   │───▶│  碎片率 > 5%  │───▶│  开始碎片整理  │  │
│  │  mem_        │    │  activedefrag│    │  扫描并移动   │  │
```

### 2.3 内存碎片率监控阈值

| 碎片率范围 | 状态 | 处理建议 |
|-----------|------|---------|
| < 1.0 | 异常 | 检查swap使用，可能存在OOM |
| 1.0 ~ 1.1 | 正常 | 良好状态，无需处理 |
| 1.1 ~ 1.5 | 警告 | 观察趋势，准备处理 |
| > 1.5 | 危险 | 需要立即处理 |

```sh
# 监控脚本示例
#!/bin/bash
THRESHOLD=1.5
FRAG=$(redis-cli INFO memory | grep mem_fragmentation_ratio | cut -d: -f2)

# 使用awk进行浮点数比较
IS_HIGH=$(echo "$FRAG $THRESHOLD" | awk '{if($1 > $2) print 1; else print 0}')

if [ "$IS_HIGH" = "1" ]; then
    echo "警告: 内存碎片率 ${FRAG} 超过阈值 ${THRESHOLD}"
    # 发送告警通知
fi
```

### 2.4 手动触发内存整理

#### 2.4.1 MEMORY PURGE命令

```sh
# 强制将内存归还给操作系统（慎用，可能阻塞Redis）
127.0.0.1:6379> MEMORY PURGE
OK
```

**注意**：`MEMORY PURGE`只清理分配器的缓存，不会减少RSS。

#### 2.4.2 重启Redis

```sh
# 最彻底的碎片清理方式是重启Redis
# 1. 执行SAVE命令保存数据
127.0.0.1:6379> BGSAVE

# 2. 等待SAVE完成，然后重启Redis
redis-cli shutdown
redis-server /etc/redis.conf
```

## 3、内存警戒线与监控

### 3.1 maxmemory设置原则

`maxmemory`配置限制Redis使用的最大内存，是生产环境的必配项。

#### 3.1.1 设置原则

```sh
# 设置为可用内存的70-80%
maxmemory 28gb  # 假设服务器有32GB内存
```

**设置考虑因素**：

| 因素 | 说明 |
|-----|------|
| 数据量 | 预估数据占用的内存 |
| 客户端缓冲区 | client output buffer |
| AOF/RDB缓冲区 | persistence相关缓冲区 |
| 复制积压区 | replication backlog |
| Lua脚本 | script相关内存 |
| 碎片空间 | 通常1.1-1.5倍 |
| 系统预留 | 约10-15%给操作系统 |

#### 3.1.2 maxmemory配置示例

```sh
# 在redis.conf中配置
maxmemory 28gb
maxmemory-policy allkeys-lru

# 查看当前maxmemory设置
redis-cli CONFIG GET maxmemory
# 1) "maxmemory"
# 2) "30000000000"

# 动态修改maxmemory
redis-cli CONFIG SET maxmemory 32gb
```

### 3.2 内存使用率监控

#### 3.2.1 计算内存使用率

```sh
# 获取used_memory和maxmemory
redis-cli INFO memory | grep -E "used_memory|maxmemory"

# 计算使用率（使用bc进行浮点计算）
USED=$(redis-cli INFO memory | grep used_memory | cut -d: -f2)
MAX=$(redis-cli CONFIG GET maxmemory | tail -1)
python3 -c "print(f'使用率: {int(\"$USED\")/int(\"$MAX\")*100:.2f}%')"
```

#### 3.2.2 分级报警阈值

```sh
#!/bin/bash
# 内存监控报警脚本

MAX=$(redis-cli CONFIG GET maxmemory | tail -1)
USED=$(redis-cli INFO memory | grep used_memory | cut -d: -f2)
RATIO=$(python3 -c "print(int($USED)/int($MAX)*100)")

if (( $(echo "$RATIO > 90" | bc -l) )); then
    echo "【紧急】内存使用率: ${RATIO}% - 已超过90%"
elif (( $(echo "$RATIO > 80" | bc -l) )); then
    echo "【警告】内存使用率: ${RATIO}% - 已超过80%"
elif (( $(echo "$RATIO > 70" | bc -l) )); then
    echo "【注意】内存使用率: ${RATIO}% - 已超过70%"
fi
```

## 4、内存优化建议

### 4.1 选择合适的数据结构

Redis支持多种数据结构，选择合适的数据结构可以显著节省内存。

#### 4.1.1 压缩列表（ziplist）vs 哈希表（hashtable）

| 编码 | 适用场景 | 内存优势 | 限制 |
|-----|---------|---------|------|
| ziplist | 少量元素、短值 | 高压缩率 | 元素过多时性能下降 |
| hashtable | 大量元素 | 无压缩 | 内存占用较高 |

**ziplist适用条件**：

```sh
# Hash类型 - 所有field和value都小于指定字节时使用ziplist
hash-max-ziplist-value 64        # value最大64字节
hash-max-ziplist-entries 512     # 最多512个field

# List类型 - 所有元素都小于指定字节时使用ziplist
list-max-ziplist-value 64
list-max-ziplist-entries 512

# Set类型 - 元素数量小于指定值时使用intset
set-max-intset-entries 512
```

#### 4.1.2 数据结构选择示例

```java
// 示例：存储用户信息

// 方案1：使用Hash（推荐）
HSET user:1001 name "zhangsan" age "25" city "beijing"
// 当field数量少、值短时，使用ziplist编码，内存高效

// 方案2：使用String（不推荐，内存效率低）
SET user:1001:name "zhangsan"
SET user:1001:age "25"
SET user:1001:city "beijing"
// 每个key都占用一个dictEntry，内存浪费

// 示例：存储有序数据

// 方案1：使用List（推荐少量数据）
RPUSH user:1001:orders "order1" "order2" "order3"

// 方案2：使用Sorted Set（需要排序时）
ZADD user:1001:orders:score 100 "order1" 200 "order2"
```

### 4.2 短字符串优化（embstr vs raw）

Redis对短字符串有特殊的内存优化。

#### 4.2.1 字符串编码选择

| 编码 | 存储方式 | 大小限制 | 特点 |
|-----|---------|---------|------|
| embstr | 嵌入在redisObject中 | ≤44字节 | 一次内存分配，效率高 |
| raw | 独立分配sds | >44字节 | 两次内存分配 |

```sh
# Redis 3.0-64位系统
# embstr最大长度 = 44字节

# 验证编码
127.0.0.1:6379> DEBUG OBJECT ENCODING small_key
"embstr"

127.0.0.1:6379> DEBUG OBJECT ENCODING large_key
"raw"
```

#### 4.2.2 字符串优化建议

```java
// 优化1：合理设计字符串长度
// 避免频繁的embstr -> raw 转换

// 不好：value长度在44字节附近波动
SET session:token "abcdefghijklmnopqrstuvwxyz1234567890abcd"  // 42字节
SET session:token "abcdefghijklmnopqrstuvwxyz1234567890abcde"  // 43字节，触发转换

// 好：value长度固定在较小范围
SET session:token "token_1234567890"  // 始终16字节

// 优化2：批量操作减少key数量
// 不好：每个用户信息一个key
SET user:1001:name "zhangsan"
SET user:1001:age "25"
SET user:1001:city "beijing"

// 好：使用复合key的Hash
HSET user:1001 name "zhangsan" age "25" city "beijing"
```

### 4.3 Key设计原则

#### 4.3.1 避免BigKey

BigKey会导致内存不均、单线程阻塞等问题。

**BigKey定义**：

| 类型 | BigKey阈值 |
|-----|-----------|
| String | value > 10KB |
| Hash/List/Set/ZSet | 元素 > 10000个 或 总大小 > 10MB |

**发现BigKey**：

```sh
# 使用--bigkeys选项扫描
redis-cli --bigkeys

# Sample output:
# Scanning 50 keys in the keyspace
# Big key (string):    'big:string' (11 bytes)
# Big key (hash):      'big:hash' (3 keys, 1523 bytes)
# Big key (list):      'big:list' (100 items, 4829 bytes)

# 使用MEMORY USAGE检查单个key
redis-cli MEMORY USAGE big:string
# (integer) 112

# 使用SCAN + TYPE遍历
redis-cli --scan | head -100 | xargs -I {} redis-cli TYPE {}
```

**处理BigKey**：

```java
// 方案1：分割大键值对
// 原始: SET big:data "large_value_string..."
// 优化: 分割存储
MSET data:part1 "part1_data" data:part2 "part2_data" data:part3 "part3_data"
HSET big:data:meta parts 3

// 方案2：异步删除，避免阻塞
UNLINK big:list  // 异步删除，非阻塞
// DEL会阻塞，UNLINK会立即返回，后台删除

// 方案3：使用合适的数据结构
// 原始: 存储10000个用户的ID在List中
RPUSH user:ids 1 2 3 ... 10000
// 优化: 使用Set去重，或者分片存储
SADD user:ids 1 2 3 ... 10000
```

#### 4.3.2 Key过期策略优化

```java
// 1. 避免大量key同时过期
// 不好：批量设置过期时间
for (int i = 0; i < 10000; i++) {
    SET "session:" + i, "data"
    EXPIREAT "session:" + i, endOfDayTimestamp;  // 同时过期
}

// 好：添加随机偏移
EXPIREAT "session:" + i, endOfDayTimestamp + random(0, 3600);

// 2. 使用合适的过期策略
// 对于需要精确过期的场景，使用Sorted Set
ZADD refresh:task timestamp "task_data"
ZREMRANGEBYSCORE refresh:task 0 current_timestamp  // 移除过期任务

// 3. 定期清理策略
// 使用SCAN + TTL检查
redis-cli --scan --pattern "temp:*" | while read key; do
    TTL=$(redis-cli TTL "$key")
    if [ "$TTL" -gt 0 ]; then
        echo "Key $key will expire in $TTL seconds"
    fi
done
```

### 5.2 MEMORY USAGE

查看单个key的内存使用量：

```sh
# 查看单个key的内存使用
127.0.0.1:6379> SET mykey "test_value"
OK
127.0.0.1:6379> MEMORY USAGE mykey
(integer) 56

# 查看key及其值的内存使用（samples参数）
127.0.0.1:6379> MEMORY USAGE mykey SAMPLES 5
(integer) 56
```

**返回值说明**：
- 返回值是key的dictEntry + 值的总字节数
- 不包括指针和引用计数等开销

```java
// Java客户端示例
import redis.clients.jedis.Jedis;

try (Jedis jedis = new Jedis("localhost", 6379)) {
    jedis.set("mykey", "myvalue");
    
    // 获取单个key内存使用
    Long memoryUsage = jedis.memoryUsage("mykey");
    System.out.println("Memory usage: " + memoryUsage + " bytes");
    
    // 批量检查key
    String[] keys = {"key1", "key2", "key3"};
    for (String key : keys) {
        Long usage = jedis.memoryUsage(key);
        if (usage != null && usage > 10000) {
            System.out.println("Large key found: " + key + " = " + usage);
        }
    }
}
```

## 6、实战监控脚本

### 6.1 完整监控脚本

```sh
#!/bin/bash
# Redis内存监控脚本
# 用于生产环境监控

REDIS_HOST="${REDIS_HOST:-localhost}"
REDIS_PORT="${REDIS_PORT:-6379}"
REDIS_PASS="${REDIS_PASS:-}"

ALERT_RATIO_70=0.70
ALERT_RATIO_80=0.80
ALERT_RATIO_90=0.90

# 颜色定义
RED='\033[0;31m'
YELLOW='\033[0;33m'
GREEN='\033[0;32m'
NC='\033[0m'

# 获取内存信息
get_memory_info() {
    if [ -n "$REDIS_PASS" ]; then
        INFO=$(redis-cli -h $REDIS_HOST -p $REDIS_PORT -a $REDIS_PASS INFO memory)
    else
        INFO=$(redis-cli -h $REDIS_HOST -p $REDIS_PORT INFO memory)
    fi
    echo "$INFO"
}

# 解析内存使用率
get_usage_ratio() {
    INFO=$(get_memory_info)
    USED=$(echo "$INFO" | grep "used_memory:" | cut -d: -f2 | tr -d '\r')
    MAX=$(redis-cli -h $REDIS_HOST -p $REDIS_PORT CONFIG GET maxmemory | tail -1)
    
    if [ "$MAX" = "0" ]; then
        echo "0"
        return
    fi
    
    python3 -c "print(${USED}/${MAX})"
}

# 解析碎片率
get_fragmentation() {
    INFO=$(get_memory_info)
    echo "$INFO" | grep "mem_fragmentation_ratio:" | cut -d: -f2 | tr -d '\r'
}

# 主监控逻辑
echo "========== Redis 内存监控 =========="
echo "监控时间: $(date '+%Y-%m-%d %H:%M:%S')"
echo ""

# 内存使用率
USAGE_RATIO=$(get_usage_ratio)
echo "内存使用率: $(python3 -c "print(f'{$USAGE_RATIO*100:.2f}%')")"

if (( $(echo "$USAGE_RATIO > $ALERT_RATIO_90" | bc -l) )); then
    echo -e "${RED}状态: 紧急 - 内存使用率超过90%${NC}"
elif (( $(echo "$USAGE_RATIO > $ALERT_RATIO_80" | bc -l) )); then
    echo -e "${YELLOW}状态: 警告 - 内存使用率超过80%${NC}"
elif (( $(echo "$USAGE_RATIO > $ALERT_RATIO_70" | bc -l) )); then
    echo -e "${YELLOW}状态: 注意 - 内存使用率超过70%${NC}"
else
    echo -e "${GREEN}状态: 正常${NC}"
fi

# 内存碎片率
FRAG=$(get_fragmentation)
echo ""
echo "内存碎片率: $FRAG"
if (( $(echo "$FRAG > 1.5" | bc -l) )); then
    echo -e "${RED}状态: 碎片率过高，建议执行MEMORY PURGE或启用activedefrag${NC}"
elif (( $(echo "$FRAG < 1.0" | bc -l) )); then
    echo -e "${RED}状态: 异常 - 可能使用了swap${NC}"
fi

echo ""
echo "========== 详细内存信息 =========="
get_memory_info | grep -E "used_memory|used_memory_rss|mem_fragmentation|maxmemory"
```
