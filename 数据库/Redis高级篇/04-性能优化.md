# 第四章：性能优化

## 4.1 慢查询分析

Redis 慢查询是指执行时间超过预设阈值的命令，通过慢查询日志可以有效识别性能瓶颈并进行针对性优化。

### 4.1.1 慢查询配置

Redis 提供两个关键配置参数来控制慢查询行为：

```properties
# 命令执行时间超过此值（微秒）会被记录到慢查询日志
# 1000000 微秒 = 1 秒，设置为 0 表示记录所有命令
slowlog-log-slower-than 10000

# 慢查询日志最大条数，采用 FIFO 策略淘汰
slowlog-max-len 128
```

可以通过命令行动态修改配置：

```sh
# 设置阈值为 10 毫秒
CONFIG SET slowlog-log-slower-than 10000

# 设置日志最大条数为 256
CONFIG SET slowlog-max-len 256
```

### 4.1.2 慢查询命令

```sh
# 查看最近 N 条慢查询日志
SLOWLOG GET 10

# 查看指定 ID 的慢查询
SLOWLOG GET 12345

# 获取慢查询日志当前长度
SLOWLOG LEN

# 清空慢查询日志
SLOWLOG RESET
```

慢查询日志包含以下信息：

```sh
SLOWLOG GET 5
# 1) 1) (integer) 12345           # 日志 ID
#    2) (integer) 1703123456789    # 时间戳（毫秒）
#    3) (integer) 1523             # 执行时间（微秒）
#    4) 1) "GET"                    # 命令及参数
#       2) "user:profile:12345"
#    5) "127.0.0.1:54321"          # 客户端地址
#    6) ""                          # 客户端名称
```

### 4.1.3 慢查询日志分析

分析慢查询日志时重点关注以下指标：

| 指标 | 说明 | 优化方向 |
|------|------|----------|
| 执行时间 | 命令耗时越长，问题越严重 | 优化命令或数据结构 |
| 命令类型 | O(N) 以上命令需重点关注 | 避免使用 KEYS、SMEMBERS |
| 访问频率 | 频繁执行的慢命令影响更大 | 优化为更高效的命令 |

常见需要优化的慢命令：

```sh
# 慢命令示例：高时间复杂度操作
KEYS pattern           # O(N)，数据量大时极慢
SMEMBERS key           # O(N)，返回集合所有成员
HGETALL key            # O(N)，返回哈希所有字段
LRANGE key 0 -1        # O(N)，返回列表所有元素
FLUSHALL               # O(N)，删除所有数据库

# 优化方案
KEYS user:*            # 使用 SCAN 0 MATCH user:* 替代
SMEMBERS set           # 评估是否真的需要所有成员
HGETALL hash           # 使用 HSCAN 替代
LRANGE list 0 99       # 使用分批获取
```

### 4.1.4 优化慢查询的方法

1. **使用低时间复杂度命令**
   ```sh
   # 避免
   HGETALL hash

   # 改用
   HGET hash field      # O(1)
   HMGET hash f1 f2     # O(N) 但 N 较小
   HSCAN hash cursor    # 增量迭代
   ```

2. **减少数据量**
   ```sh
   # 大哈希分拆为小哈希
   HSET user:1000:info name "tom"    # 按用户 ID 分桶
   HSET user:1001:info name "jerry"

   # 大集合按时间或类型分拆
   SADD user:2024:01:likes 1 2 3     # 按月分表
   SADD user:2024:02:likes 4 5 6
   ```

3. **使用合适的数据结构**
   ```java
   // 场景：需要存储大量布尔值
   // 避免：使用 String 类型
   jedis.set("user:1000:permissions", "1111100111");

   // 推荐：使用 Set 类型，O(1) 操作
   jedis.sadd("user:1000:permissions", "read", "write", "delete");
   jedis.sismember("user:1000:permissions", "read");  // true
   ```

4. **开启 Slowlog 持久化分析**
   ```java
   // 定期采集慢查询日志进行分析
   public void analyzeSlowQuery(Jedis jedis) {
       List<Map<String, Object>> slowLogs = jedisslowlogGet(10);
       for (Map<String, Object> log : slowLogs) {
           long executionTime = (Long) log.get("duration");
           String[] command = (String[]) log.get("command");
           if (executionTime > 50000) {  // 超过 50ms
               System.out.println("慢查询警告: " + Arrays.toString(command));
           }
       }
   }
   ```

## 4.2 BigKey 治理

BigKey 是指 value 占用空间过大的 key，不合理的数据结构设计是产生 BigKey 的主要原因。

### 4.2.1 BigKey 定义标准

| 类型 | BigKey 判定标准 | 示例 |
|------|----------------|------|
| String | value > 10KB | `SET key "a...a"` (10KB+) |
| List | 元素数量 > 10000 | `LPUSH list 1 2 3...` (10000+) |
| Set | 元素数量 > 10000 | `SADD set 1 2 3...` (10000+) |
| Hash | 字段数量 > 10000 | `HSET hash f1 v1 f2 v2...` (10000+) |
| ZSet | 元素数量 > 10000 | `ZADD zset 0 1 0 2...` (10000+) |

### 4.2.2 BigKey 的危害

1. **内存不均**：单节点数据倾斜，导致内存使用率超过集群平均值
2. **操作阻塞**：
   - `DEL key` 删除操作阻塞主线程（O(N) 时间复杂度）
   - `SMEMBERS`、`HGETALL` 等遍历操作耗时巨大
3. **集群问题**：
   - 迁移困难，阻塞主节点
   - 内存倾斜导致节点容量瓶颈
4. **网络带宽**：大 value 占用大量网络带宽

### 4.2.3 发现 BigKey

**使用 redis-cli --bigkeys 扫描**

```sh
# 扫描并输出每种类型的最大 key
redis-cli --bigkeys

# 输出示例

# Big string     : "user:sessions: 123456789" (500.00 KB, 1 keys)
# Big list      : "product:views:2024" (15000 items, 1 keys)
# Big set       : "hot:keywords" (25000 members, 1 keys)
# Big hash      : "user:profiles" (12000 fields, 1 keys)
# Big zset      : "leaderboard:global" (18000 members, 1 keys)
```

**使用 SCAN 配合 SIZE 命令定位**

```sh
# 使用 SCAN 遍历，避免阻塞
SCAN 0 COUNT 1000
# 返回游标和新发现的 key

# 检查各类型 key 的大小
# String 类型
STRLEN key

# List 类型
LLEN key

# Set 类型
SCARD key

# Hash 类型
HLEN key

# ZSet 类型
ZCARD key
```

**使用 MEMORY USAGE 精确分析**

```sh
# 查看 key 及其 value 使用的内存字节数

# (integer) 524288

# 查看 key 的内部编码
DEBUG OBJECT ENCODING user:profile:12345
# Hash, ziplist
```

**Java 代码实现 BigKey 扫描**

```java
public class BigKeyScanner {
    private JedisPool jedisPool;

    public List<String> scanBigKeys(int dbIndex, long maxSize) {
        List<String> bigKeys = new ArrayList<>();

        try (Jedis jedis = jedisPool.getResource()) {
            jedis.select(dbIndex);

            String cursor = "0";
            do {
                // 使用 SCAN 遍历，COUNT 建议 1000
                ScanResult<Tuple> result = jedis.zscan(cursor, new ScanParams().count(1000));
                cursor = result.getCursor();

                for (Tuple tuple : result.getResult()) {
                    String key = tuple.getElement();
                    long memUsage = Optional.ofNullable(jedis.memoryUsage(key)).orElse(0L);

                    if (memUsage > maxSize) {
                        bigKeys.add(String.format("%s (size=%d bytes)", key, memUsage));
                    }
                }
            } while (!"0".equals(cursor));
        }
        return bigKeys;
    }
}
```

### 4.2.4 删除 BigKey

**避免使用 DEL 删除大 key**

`DEL` 命令删除 key 时会阻塞主线程，当 BigKey 占用空间较大时，可能导致 Redis 服务短暂不可用。

**使用 UNLINK 非阻塞删除**

```sh
# UNLINK 是 DEL 的异步版本，立即返回，后台线程负责删除
UNLINK user:sessions:2024

# 对比
DEL user:sessions:2024     # 阻塞，直到删除完成
UNLINK user:sessions:2024  # 立即返回，后台异步删除
```

**分批删除大集合**

```sh
# List 分批删除
LTRIM key 0 9999    # 保留前 10000 个，删除其余

# Set 分批删除
SSCAN set 0 COUNT 1000
# 遍历并逐步删除不需要的元素

# Hash 分批删除
HSCAN hash 0 COUNT 100
# 对每个 field 单独处理
```

**Java 实现安全删除**

```java
public void deleteBigKeySafely(Jedis jedis, String key) {
    String type = jedis.type(key);

    switch (type) {
        case "string":
            jedis.del(key);
            break;
        case "list":
            // 分批 LTRIM 删除
            while (jedis.llen(key) > 0) {
                jedis.ltrim(key, 0, -1001);  // 保留前 1000 个
            }
            jedis.del(key);
            break;
        case "set":
            // SSCAN + SREM 分批删除
            String cursor = "0";
            ScanParams params = new ScanParams().count(1000);
            do {
                ScanResult<String> result = jedis.sscan(key, cursor, params);
                cursor = result.getCursor();
                if (!result.getResult().isEmpty()) {
                    jedis.srem(key, result.getResult().toArray(new String[0]));
                }
            } while (!"0".equals(cursor));
            jedis.del(key);
            break;
        case "hash":
            // HSCAN + HDEL 分批删除
            cursor = "0";
            do {
                ScanResult<Map.Entry<String, String>> result = jedis.hscan(key, cursor, params);
                cursor = result.getCursor();
                if (!result.getResult().isEmpty()) {
                    String[] fields = result.getResult().stream()
                        .map(Map.Entry::getKey)
                        .toArray(String[]::new);
                    jedis.hdel(key, fields);
                }
            } while (!"0".equals(cursor));
            jedis.del(key);
            break;
        default:
            jedis.del(key);
    }
}
```

### 4.2.5 BigKey 优化方案

1. **string 类型大 value 拆分**
   ```sh
   # 避免：存储大文件或序列化对象
   SET user:profile:12345 {"name":"tom","avatar":"base64...复杂结构"}

   # 方案：压缩后存储或拆分
   SET user:profile:12345:info {"name":"tom"}
   SET user:profile:12345:avatar "avatar_url_or_base64"
   ```

2. **大哈希拆分为小哈希**
   ```sh
   # 避免：大哈希存储所有用户信息
   HSET users hash_id "10001" name "user1" email "user1@example.com" ...

   # 方案：按用户 ID 分桶
   HSET user:10001:profile name "user1"
   HSET user:10001:stats followers 1000 following 500
   HSET user:10001:settings theme "dark"
   ```

3. **集合类型优化**
   ```sh
   # 避免：大集合存储（如收藏列表）
   SADD user:12345:favorites 1 2 3 4 5... (100000个)

   # 方案：按时间或类型分桶
   SADD user:12345:favorites:2024:01 1 2 3
   SADD user:12345:favorites:2024:02 4 5 6

   # 或使用 ZSET 替代，按分数（时间戳）排序
   ZADD user:12345:favorites:2024 1703123456 "product:001"
   ZADD user:12345:favorites:2024 1703123457 "product:002"
   ```

4. **合理设置 ziplist 编码阈值**
   ```properties
   # 当 hash 字段数小于此值时使用 ziplist 编码（更节省内存）
   hash-max-ziplist-entries 512

   # 当 string 长度小于此值时使用 ziplist 编码
   hash-max-ziplist-value 64

   # list 节点数小于此值时使用 ziplist 编码
   list-max-ziplist-entries 512
   ```

## 4.3 热 Key 问题

热 Key 是指频繁访问的 key，即使数据量不大，但访问频率极高，也会导致性能问题。

### 4.3.1 热 Key 定义

热 Key 具有以下特征：
- 短时间内访问次数远超其他 key
- 集中在特定业务场景（如秒杀商品、热门文章）
- 访问频率与数据量不成正比

### 4.3.2 热 Key 的危害

1. **请求倾斜**：大量请求集中到某个 Redis 节点
2. **内存倾斜**：热 key 所在节点内存使用率偏高
3. **连接耗尽**：单节点连接数过多
4. **响应延迟**：单节点处理能力达到瓶颈

### 4.3.4 热 Key 解决方案

**方案一：本地缓存**

将热 key 缓存到应用服务器内存中，减少 Redis 请求。

```java
@Component
public class LocalCacheHotKey {
    private final Map<String, Object> localCache = new ConcurrentHashMap<>();
    private final JedisPool jedisPool;
    private final ScheduledExecutorService cleaner = Executors.newSingleThreadScheduledExecutor();

    @PostConstruct
    public void init() {
        // 每 5 分钟清理过期缓存
        cleaner.scheduleAtFixedRate(() -> {
            localCache.clear();
        }, 5, 5, TimeUnit.MINUTES);
    }

    public String getHotKey(String key) {
        // 1. 先查本地缓存
        if (localCache.containsKey(key)) {
            return (String) localCache.get(key);
        }

        // 2. 本地缓存未命中，查 Redis
        try (Jedis jedis = jedisPool.getResource()) {
            String value = jedis.get(key);
            if (value != null) {
                // 写入本地缓存，过期时间 30 秒
                localCache.put(key, value);
            }
            return value;
        }
    }
}
```

**方案二：多级缓存架构**

```
┌─────────────┐     ┌─────────────┐     ┌─────────────┐
│   Client    │────▶│  Local Cache │────▶│    Redis    │
│  (JVM Heap) │     │  (Caffeine)  │     │   Cluster   │
└─────────────┘     └─────────────┘     └─────────────┘
      │                    │                    │
      │  热点数据           │  热点数据           │  全量数据
      │  毫秒级访问         │  亚毫秒级访问        │  微秒级访问
      │  无网络开销         │  少量网络开销        │
```

```java
@Configuration
public class MultiLevelCacheConfig {
    @Bean
    public Cache<String, String> localCache() {
        return Caffeine.newBuilder()
            .maximumSize(10000)           // 最多缓存 10000 个 key
            .expireAfterWrite(30, TimeUnit.SECONDS)  // 30 秒过期
            .recordStats()               // 开启统计
            .build();
    }

    @Bean
    public MultiLevelCache<String, String> multiLevelCache(
            Cache<String, String> localCache, JedisPool jedisPool) {
        return new MultiLevelCache<>(localCache, jedisPool);
    }
}

public class MultiLevelCache<K, V> {
    private final Cache<K, V> l1Cache;  // 本地缓存
    private final JedisPool jedisPool;  // Redis

    public MultiLevelCache(Cache<K, V> l1Cache, JedisPool jedisPool) {
        this.l1Cache = l1Cache;
        this.jedisPool = jedisPool;
    }

    public V get(K key) {
        // L1 缓存命中
        V value = l1Cache.getIfPresent(key);
        if (value != null) {
            return value;
        }

        // L2 Redis 查询
        try (Jedis jedis = jedisPool.getResource()) {
            value = (V) jedis.get(key);
            if (value != null) {
                // 回填 L1 缓存
                l1Cache.put(key, value);
            }
        }
        return value;
    }

    public void put(K key, V value, long expireSeconds) {
        // 同时写入 L1 和 L2
        l1Cache.put(key, value);
        try (Jedis jedis = jedisPool.getResource()) {
            jedis.setex(key, expireSeconds, (String) value);
        }
    }
}
```

**方案三：Redis Cluster 热点 key 分散**

```java
public class HotKeySharding {
    /**
     * 对热 key 添加后缀实现分散存储
     * 读取时随机选择某个后缀 key 访问
     */
    private static final int SHARD_COUNT = 4;

    public void setHotKey(String key, String value) {
        try (Jedis jedis = jedisPool.getResource()) {
            // 写入多个副本
            for (int i = 0; i < SHARD_COUNT; i++) {
                jedis.set(key + ":shard:" + i, value);
            }
        }
    }

    public String getHotKey(String key) {
        try (Jedis jedis = jedisPool.getResource()) {
            // 随机读取一个副本
            int shardIndex = ThreadLocalRandom.current().nextInt(SHARD_COUNT);
            return jedis.get(key + ":shard:" + shardIndex);
        }
    }
}
```

## 4.4 连接池优化

Redis 连接池是客户端与 Redis 服务器之间的连接管理机制，合理的连接池配置对应用性能至关重要。

### 4.4.1 连接池核心参数

| 参数 | 说明 | 推荐值 | 调整依据 |
|------|------|--------|----------|
| maxTotal | 最大连接数 | CPU 核心数 * 2~3 | 并发量、系统资源 |
| maxIdle | 最大空闲连接数 | 与 maxTotal 接近 | 避免频繁创建销毁 |
| minIdle | 最小空闲连接数 | 正常业务量 | 预热连接、应对突发 |
| maxWaitMillis | 获取连接最大等待时间 | 3000ms | 业务容忍度 |
| testOnBorrow | 获取连接时测试 | true | 避免获取无效连接 |
| testOnReturn | 归还连接时测试 | false | 增加开销，可选 |
| testWhileIdle | 空闲时测试 | true | 及时清理无效连接 |
| minEvictableIdleTimeMillis | 空闲连接最小存活时间 | 60000ms | 资源释放策略 |

### 4.4.2 Jedis 连接池配置

```java
JedisPoolConfig poolConfig = new JedisPoolConfig();

// 最大连接数
poolConfig.setMaxTotal(50);

// 最大空闲连接数
poolConfig.setMaxIdle(20);

// 最小空闲连接数
poolConfig.setMinIdle(5);

// 获取连接最大等待时间（毫秒）
poolConfig.setMaxWaitMillis(3000);

// 获取连接时测试连接可用性
poolConfig.setTestOnBorrow(true);

// 空闲时定期测试连接可用性
poolConfig.setTestWhileIdle(true);

// 空闲连接最小存活时间
poolConfig.setMinEvictableIdleTimeMillis(60000);

// 空闲连接扫描间隔
poolConfig.setTimeBetweenEvictionRunsMillis(30000);

// 连接池预热
poolConfig.setBlockWhenExhausted(true);

// 创建连接池
JedisPool jedisPool = new JedisPool(poolConfig, "redis-host", 6379, 2000, "password", 0);

// 使用连接
try (Jedis jedis = jedisPool.getResource()) {
    jedis.set("key", "value");
    String result = jedis.get("key");
}
```

### 4.4.3 Lettuce 连接池配置（Spring Boot 默认）

```yaml

    lettuce:
      pool:
        # 最大连接数
```

### 4.4.4 连接池调优原则

1. **根据并发量设置 maxTotal**
   ```java
   // 估算公式：maxTotal = 并发数 * 单次操作平均耗时 / Redis 单线程处理时间

   // 例如：并发 1000 QPS，每次操作 1ms，Redis 处理时间 0.1ms
   // maxTotal = 1000 * 1 / 0.1 = 10000（理论值）

   // 实际应用中，通常设置为 200-500 即可满足大部分场景
   ```

2. **避免连接池过大**
   - 连接数过多会增加 Redis 负载
   - 每个连接占用客户端和服务器端内存
   - 合理值：正常业务 50-200 连接

3. **设置合理的 minIdle**
   ```java
   // 预热场景：系统启动后立即有大量请求
   ```

### 4.4.6 连接泄漏预防

```java
public class JedisConnectionGuard {
    private final JedisPool jedisPool;

    public String safeGet(String key) {
        Jedis jedis = null;
        try {
            jedis = jedisPool.getResource();
            return jedis.get(key);
        } catch (JedisException e) {
            // 异常时归还损坏的连接
            if (jedis != null) {
                jedis.close();  // 或 jedis.reset()
            }
            throw e;
        } finally {
            // 正常情况下归还连接
            if (jedis != null && jedis.isConnected()) {
                jedis.close();
            }
        }
    }

    // 推荐：使用 try-with-resources 自动管理
    public String safeGetWithTryWith(String key) {
        try (Jedis jedis = jedisPool.getResource()) {
            return jedis.get(key);
        }
        // 自动归还连接，无需 finally
    }
}
```

## 4.5 管道与批量操作

Redis 管道（Pipeline）和批量操作可以显著减少网络往返次数，提升批量数据处理效率。

### 4.5.1 Pipeline 优化

普通模式下，每次命令执行都需要一次网络往返：

```
客户端                      Redis
  │  GET key1                 │
  │─────────────────────────▶│
  │  ←────────────────────────│
  │  GET key2                 │
  │─────────────────────────▶│
  │  ←────────────────────────│
  │  GET key3                 │
  │─────────────────────────▶│
  │  ←────────────────────────│
```

Pipeline 模式下，多条命令打包一次发送：

```
客户端                      Redis
  │  GET key1                 │
  │  GET key2                 │
  │  GET key3                 │
  │─────────────────────────▶│
  │  ←────────────────────────│
  │  value1                   │
  │  value2                   │
  │  value3                   │
```

**Jedis Pipeline 使用**

```java
// Jedis Pipeline 基本用法
try (Jedis jedis = jedisPool.getResource()) {
    Pipeline pipeline = jedis.pipelined();

    // 添加命令到管道
    pipeline.set("key1", "value1");
    pipeline.get("key2");
    pipeline.incr("counter");
    pipeline.hset("hash", "field", "value");

    // 执行管道中的所有命令
    List<Object> results = pipeline.syncAndReturnAll();

    // 解析结果
    String value1 = (String) results.get(0);  // SET 返回 OK
    String value2 = (String) results.get(1);  // GET 返回值
    Long counter = (Long) results.get(2);     // INCR 返回值
    Long hsetResult = (Long) results.get(3);  // HSET 返回 1
}
```

**Pipeline 异步执行**

```java
// 使用 Pipeline 异步执行
try (Jedis jedis = jedisPool.getResource()) {
    Pipeline pipeline = jedis.pipelined();
    Response<String> future1 = pipeline.get("key1");
    Response<String> future2 = pipeline.get("key2");
    Response<Long> future3 = pipeline.incr("counter");

    // 执行管道
    pipeline.sync();

    // 获取异步结果
    String value1 = future1.get();
    String value2 = future2.get();
    Long counter = future3.get();
}
```

### 4.5.3 评估最优批量大小

批量操作虽然高效，但过大的批量会带来以下问题：

| 问题 | 说明 | 解决方案 |
|------|------|----------|
| 内存压力 | 客户端和服务端都需要缓存命令/响应 | 控制单次批量大小 |
| 响应超时 | 批量操作耗时可能较长 | 分批执行 |
| 失败成本 | 一旦失败需要重做整个批量 | 合理的事务或 Lua 脚本 |

**批量大小推荐值**

```java
public class BatchSizeOptimizer {
    private final JedisPool jedisPool;

    // String 类型：建议单次批量 100-500 个 key
    public void batchSetStrings(List<String> keys, List<String> values) {
        int batchSize = 200;
        int total = keys.size();

        for (int i = 0; i < total; i += batchSize) {
            int end = Math.min(i + batchSize, total);
            List<String> batchKeys = keys.subList(i, end);
            List<String> batchValues = values.subList(i, end);

            // 构建 MSET 参数
            String[] kv = new String[batchKeys.size() * 2];
            for (int j = 0; j < batchKeys.size(); j++) {
                kv[j * 2] = batchKeys.get(j);
                kv[j * 2 + 1] = batchValues.get(j);
            }
            jedisPool.getResource().mset(kv);
        }
    }

    // Hash 类型：建议单次批量 100-500 个 field
    public void batchSetHash(String key, Map<String, String> fields) {
        int batchSize = 200;
        List<String> fieldNames = new ArrayList<>(fields.keySet());
        List<String> fieldValues = new ArrayList<>(fields.values());

        for (int i = 0; i < fieldNames.size(); i += batchSize) {
            int end = Math.min(i + batchSize, fieldNames.size());

            Map<String, String> batch = new HashMap<>();
            for (int j = i; j < end; j++) {
                batch.put(fieldNames.get(j), fieldValues.get(j));
            }
            jedisPool.getResource().hmset(key, batch);
        }
    }
}
```

**Pipeline 批量大小建议**

```java
// Pipeline 批量大小的经验值
public class PipelineBatchSize {
    // 网络 RTT 越低，可以设置的批量越大
    // 同机房：RTT < 1ms，批量可设 500-1000
    // 跨机房：RTT > 10ms，批量建议 100-200

    public <T> void pipelineWithChunkedSize(
            List<T> items,
            int batchSize,
            Consumer<List<T>> processor) {

        for (int i = 0; i < items.size(); i += batchSize) {
            int end = Math.min(i + batchSize, items.size());
            List<T> batch = items.subList(i, end);

            try (Jedis jedis = jedisPool.getResource()) {
                Pipeline pipeline = jedis.pipelined();
                processor.accept(batch);
                pipeline.sync();
            }

            // 批次间适当休息，避免 Redis 繁忙
            if (end < items.size()) {
                try {
                    Thread.sleep(10);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                }
            }
        }
    }
}
```
