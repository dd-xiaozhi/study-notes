# 第2章 核心概念与架构

## 概述

本章将深入剖析 ShardingSphere-JDBC 的核心概念与架构设计。理解这些概念是掌握 ShardingSphere-JDBC 的基础，也是进行有效分库分表配置的前提。ShardingSphere-JDBC 作为一个轻量级 Java 框架，通过在 JDBC 层面对 SQL 进行拦截和处理，实现了数据分片、读写分离、分布式事务等高级功能。其设计理念是将分布式能力下沉到数据库访问层，让开发者在使用传统 JDBC API 的同时，享受分布式数据库带来的可扩展性和高可用性。

本章将首先介绍 ShardingSphere-JDBC 的整体架构，然后详细讲解各个核心概念，最后分析其工作流程和各模块的职责分工。通过本章的学习，读者将能够理解 ShardingSphere-JDBC 是如何协调各个组件来完成分布式数据处理的，以及如何在实际项目中应用这些概念进行架构设计。

---

## 2.1 ShardingSphere-JDBC 整体架构解析

### 1.1.1 架构设计理念

ShardingSphere-JDBC 采用了模块化、分层化的架构设计，其核心理念是将数据库访问过程中的各个阶段进行解耦，每个阶段由独立的引擎负责处理。这种设计模式使得系统具有高度的灵活性和可扩展性，同时也便于针对每个阶段进行针对性优化。

ShardingSphere-JDBC 的架构设计遵循了「适配器模式」和「责任链模式」的组合应用。在适配器模式层面，ShardingSphere-JDBC 通过实现标准 JDBC 接口（DataSource、Connection、Statement、PreparedStatement、ResultSet 等），将自己适配到 JDBC 生态中，应用层代码无需感知底层实现细节。在责任链模式层面，SQL 处理流程被拆分为解析引擎、路由引擎、改写引擎、执行引擎和归并引擎五个环节，每个环节作为一个独立的处理器，形成一条完整的责任链。

从部署形态来看，ShardingSphere-JDBC 是一个无中心的中间件产品，不依赖任何外部服务（如 Zookeeper、Etcd 等），这使得它在轻量级应用场景中具有显著优势。同时，由于它运行在应用进程内部，数据传输的延迟极低，能够提供接近原生 JDBC 的性能表现。这种设计选择使得 ShardingSphere-JDBC 特别适合以下场景：单 JVM 内的数据分片、轻量级的读写分离需求、对延迟敏感的事务处理、以及需要快速集成分布式能力的微服务架构。

### 1.1.2 核心架构分层

ShardingSphere-JDBC 的架构可以分为四个主要层次，每个层次承担不同的职责，共同构成了完整的数据处理体系。

**第一层：接口适配层（Interface Adaptation Layer）**

这一层负责与标准 JDBC API 进行对接，是 ShardingSphere-JDBC 对外暴露的入口。它包含了 DataSource、Connection、Statement、PreparedStatement、ResultSet 等核心接口的实现类。当应用代码通过 DataSource 获取连接、执行 SQL 时，实际上获得的是 ShardingSphere-JDBC 提供的代理对象，而非真正的数据库连接。这一层的关键类包括 ShardingDataSource、ShardingConnection、ShardingStatement 和 ShardingPreparedStatement。这些类在接收到标准 JDBC 请求后，会将请求转发到下层的处理引擎，同时保持对 JDBC 规范的完全兼容，使得现有代码无需任何修改即可迁移到分片架构。

**第二层：SQL 处理引擎层（SQL Processing Engine Layer）**

这是 ShardingSphere-JDBC 的核心处理层，包含五个子引擎，分别是解析引擎（Parse Engine）、路由引擎（Routing Engine）、改写引擎（Rewrite Engine）、执行引擎（Execute Engine）和归并引擎（Merge Engine）。每个子引擎专注于处理特定的 SQL 处理任务。解析引擎负责将 SQL 文本解析为抽象语法树（AST），目前支持 MySQL、PostgreSQL、SQL92、SQL2003 等多种 SQL 方言。路由引擎根据解析结果和配置的分片策略，确定 SQL 需要发送到哪些实际数据源和物理表。改写引擎负责修改 SQL 语句，使其能够在实际物理表上正确执行。执行引擎管理物理 SQL 的并发执行策略，包括连接管理、线程调度、结果缓存等。归并引擎将多个执行结果合并为单一结果集，返回给上层调用者。

**第三层：功能特性层（Feature Layer）**

这一层构建在 SQL 处理引擎之上，提供了 ShardingSphere-JDBC 的核心功能特性，包括数据分片（Data Sharding）、读写分离（Read/Write Splitting）、分布式事务（Distributed Transaction）、数据加密（Data Masking）、分布式主键（Distributed ID）等。每个功能特性都可以独立配置和启用，开发者可以根据实际需求进行灵活组合。例如，一个典型的配置可能是同时启用数据分片和读写分离，让分片后的数据也能够实现读写分离，提高查询性能。

**第四层：配置管理层（Configuration Layer）**

这一层负责管理所有的配置信息，包括数据源配置、分片规则配置、属性配置等。ShardingSphere-JDBC 支持多种配置方式，包括 YAML 文件配置、Spring Boot 配置、编程式配置等。配置层会将用户的配置转换为内部的数据结构，并注册到各个引擎中，使得运行时能够根据配置信息进行相应的处理。这一层还负责配置的加载、校验和热更新，确保配置的准确性和实时性。

## 2.2 核心概念详解

### 2.2.1 LogicTable（逻辑表）

**概念定义**

逻辑表是 ShardingSphere-JDBC 中一个非常重要的概念，它代表了开发者在业务逻辑中操作的表，而非数据库中实际存在的物理表。在进行分片配置时，开发者定义的是逻辑表的结构以及分片规则，而 ShardingSphere-JDBC 会在运行时根据这些配置，将针对逻辑表的操作转换为针对实际物理表的操作。

例如，在一个订单系统中，开发者定义了一张订单表 `t_order`，配置将其分为 4 个分片。在物理数据库中，可能存在 `t_order_0`、`t_order_1`、`t_order_2`、`t_order_3` 四张实际表，但开发者在编写业务代码时，始终只需要操作 `t_order`（逻辑表），ShardingSphere-JDBC 会自动处理逻辑表到物理表的映射关系。这种设计极大地简化了开发工作，使得业务代码能够保持对分片透明，不需要关心数据被拆分到了哪个物理表中。

**逻辑表的作用域**

逻辑表在整个 ShardingSphere-JDBC 配置中具有全局作用域。一旦配置了某个逻辑表及其分片规则，所有对该表的 SQL 操作都会自动受到分片规则的影响。这包括 SELECT、INSERT、UPDATE、DELETE 等各种 DML 操作，也包括 ALTER TABLE、DROP TABLE 等 DDL 操作（ShardingSphere-JDBC 对 DDL 操作的处理需要特别配置）。需要注意的是，如果在 SQL 中直接使用了物理表名，ShardingSphere-JDBC 无法识别这种操作，可能会导致数据不一致或查询失败，因此强烈建议业务代码中始终使用逻辑表名。

**逻辑表与别名**

在某些复杂查询场景中，SQL 可能涉及自关联或子查询，此时需要注意表别名的使用。ShardingSphere-JDBC 的 SQL 解析器会正确处理表别名的映射关系，但开发者需要确保别名的使用符合 ShardingSphere-JDBC 的解析规则。特别是在编写跨分片的复杂查询时，建议先在测试环境中验证 SQL 的路由结果，确保查询能够正确执行。

### 2.2.2 ActualTable（实际表/物理表）

**概念定义**

实际表（Physical Table）是指数据库中真实存在的表，是数据分片后存储在各个数据节点上的具体表。每个实际表都对应着物理存储中的一个数据集合。实际表的命名通常遵循一定的规则，常见的是在逻辑表名的基础上添加分片编号后缀，如 `t_order_0`、`t_order_1` 等。

**实际表与数据源的关系**

实际表不仅有物理表名的概念，还与特定的数据源（DataSource）相关联。在多数据源场景下，一个逻辑表的实际表可能分布在不同的数据源上。例如，`t_order_0` 位于 `ds_0` 数据源，而 `t_order_1` 可能位于 `ds_1` 数据源。这种跨数据源的分布是 ShardingSphere-JDBC 能够实现水平扩展的关键——通过将数据分散到多个数据库实例中，单个数据库的负载被有效降低，从而能够处理更大的数据量和更高的并发请求。

**实际表的自动创建**

ShardingSphere-JDBC 提供了 `autoCreateActualTable` 配置选项，用于控制是否自动创建实际表。当启用该选项时，ShardingSphere-JDBC 会在应用启动或首次访问时，根据逻辑表的结构自动创建所需的物理表。这一功能在开发环境和测试环境中非常有用，可以简化表结构的初始化工作。但在生产环境中，通常建议手动创建表结构并进行充分的测试，以确保表结构和索引配置符合性能要求。

### 2.2.3 DataSource（数据源）

**概念定义**

在 ShardingSphere-JDBC 中，数据源（DataSource）是实际数据库连接的配置单元，代表了到物理数据库的连接池。每个数据源包含数据库连接所需的所有信息，如 JDBC URL、用户名、密码、连接池大小等。ShardingSphere-JDBC 支持配置多个数据源，这些数据源可以是相同数据库的不同实例，也可以是不同类型的数据库。

**数据源配置要素**

一个完整的数据源配置通常包含以下要素：数据源唯一标识（用于在规则配置中引用）、JDBC 驱动类名、数据库连接 URL、数据库用户名、数据库密码、连接池相关参数（最小连接数、最大连接数、连接超时时间等）。此外，还可以配置连接属性，如字符编码、时区设置等。这些配置共同决定了 ShardingSphere-JDBC 如何与物理数据库建立和管理连接。

**数据源分组**

ShardingSphere-JDBC 引入了数据源分组（DataSource Group）的概念，用于支持更灵活的数据源管理。常见的数据源分组包括：默认数据源组（用于未分片的表或通用操作）、读写分离数据源组（包含主库和从库）、以及自定义数据源组（根据业务需求自定义的数据源集合）。数据源分组使得 ShardingSphere-JDBC 能够在不同场景下选择合适的数据源执行操作，例如在读写分离场景下，写操作发送到主库，而读操作可以根据配置发送到从库或主库。

### 2.2.4 TableRule（表规则）

**概念定义**

表规则是 ShardingSphere-JDBC 中用于定义逻辑表与实际表映射关系的配置单元。它是实现数据分片的核心配置，包含了逻辑表名、分片策略、数据源分布等信息。每个逻辑表都可以配置独立的表规则，也可以配置为继承默认规则。表规则的设计使得 ShardingSphere-JDBC 能够准确地将业务层发起的逻辑表操作，转换为对底层物理表的操作。

**表规则的核心配置项**

表规则包含多个核心配置项，理解这些配置项的含义对于正确配置分片规则至关重要。

首先是 `logicTableName`（逻辑表名），这是业务代码中使用的表名，也是 SQL 解析时识别的表标识。其次是 `actualDataNodes`（实际数据节点），它定义了逻辑表对应的所有物理表节点，格式为 `数据源.物理表名`，支持多数据源多表的配置。例如 `ds_${0..1}.t_order_${0..3}` 表示数据源 ds_0 和 ds_1 上的 t_order_0 到 t_order_3 共 8 个物理表。第三是 `databaseShardingStrategy`（库分片策略），定义了根据分片键进行数据库级别分片的算法。第四是 `tableShardingStrategy`（表分片策略），定义了根据分片键进行表级别分片的算法。

**表规则的动态更新**

ShardingSphere-JDBC 支持在运行时动态更新表规则配置，这一功能通过配置中心或管理接口实现。动态更新使得系统能够在不重启应用的情况下，调整分片规则，如扩容缩容、调整分片策略等。需要注意的是，动态更新可能带来数据迁移的问题，ShardingSphere-JDBC 本身不提供数据迁移工具，通常需要配合其他工具完成数据迁移。

### 2.2.5 ShardingStrategy（分片策略）

**概念定义**

分片策略是 ShardingSphere-JDBC 中决定数据如何分布到各个物理表的核心算法。它包含了分片键（Sharding Key）的选择和分片算法的实现。分片策略的选择直接影响数据的分布均匀性、查询效率和系统扩展性。一个设计良好的分片策略能够使数据均匀分布在各个节点上，同时保证常见查询能够高效执行。

**分片策略的层级**

ShardingSphere-JDBC 的分片策略分为两个层级：数据库分片策略（Database Sharding Strategy）和表分片策略（Table Sharding Strategy）。

数据库分片策略决定了数据应该落在哪个数据库实例上。当配置了多数据源时，数据库分片策略决定了 SQL 需要发送到哪些数据源。如果只配置了表分片而未配置库分片，那么所有数据都会落在同一个数据库中，只是被分散到了不同的物理表上。

表分片策略决定了数据应该落在哪个物理表上。在单库多表的场景下，只需要配置表分片策略。表分片策略通常与分片键配合使用，通过分片算法计算数据应该落入的物理表编号。

**分片策略配置方式**

ShardingSphere-JDBC 支持多种分片策略配置方式。一种是 inline 表达式配置，使用简化的表达式语法，适合简单的分片场景，如 `ds_${user_id % 2}` 表示按 user_id 取模决定数据源。另一种是 API 配置，通过 Java 代码定义复杂的分片策略，适合需要自定义算法或多个分片键的场景。还有一种是自定义分片策略类，通过实现 ShardingSphere 提供的接口，编写自定义的分片算法。

### 2.2.6 Sharding Key（分片键）选择原则

**分片键的重要性**

分片键是实现数据分片的核心要素，它决定了数据在各个物理节点间的分布方式。一个合适的分片键能够使数据均匀分布，同时保证查询的高效性。分片键选择不当可能导致数据倾斜（部分节点数据量过大）、查询全表扫描（无法定位分片）、以及事务范围扩大（跨节点事务）等性能问题。

**分片键选择原则**

**第一个原则是均匀分布原则**。分片键的值应该能够覆盖尽可能多的取值范围，且各取值的分布应该相对均匀。常见的适合作为分片键的字段包括：用户 ID、订单 ID、时间戳等具有高度散列性的字段。不适合作为分片键的字段包括：性别（只有两个值）、状态码（取值有限且分布不均）等。

**第二个原则是查询关联原则**。分片键应该是业务查询中最常用于条件筛选的字段。如果大多数查询都需要根据 user_id 进行筛选，那么 user_id 是分片键的优选。如果选择了一个不常用于查询的字段作为分片键，可能导致每次查询都需要扫描所有分片，严重影响查询性能。

**第三个原则是事务一致性原则**。如果业务涉及跨表关联查询，关联条件应该与分片键一致。例如，如果订单表和订单详情表都按 order_id 进行分片，那么它们之间的关联查询就能够高效执行。如果关联字段与分片键不一致，ShardingSphere-JDBC 需要进行跨分片的关联查询，这会带来显著的性能开销。

**第四个原则是最少分片键原则**。在大多数场景下，使用单一分片键即可满足需求。增加分片键数量会增加复杂性，且可能导致数据分布不均。只有在单一分片键无法满足查询需求时，才考虑使用复合分片键。

**常见分片键选择场景**

| 业务场景 | 推荐分片键 | 说明 |
|---------|-----------|------|
| 用户中心 | user_id | 用户相关数据按用户 ID 分片，便于用户维度的查询 |
| 订单系统 | order_id | 订单按订单 ID 分片，支持订单维度的快速查询 |
| 日志系统 | timestamp/create_time | 按时间分片，支持时间范围的快速检索 |
| 多租户系统 | tenant_id | 按租户 ID 分片，实现数据隔离 |
| 商品系统 | category_id 或 merchant_id | 按类目或商户分片，支持相关维度的查询 |

### 2.2.7 分片算法详解

ShardingSphere-JDBC 内置了多种分片算法，能够满足不同业务场景的需求。同时，它也支持自定义分片算法，开发者可以根据实际需求实现特定的分片逻辑。

**取模分片算法（Modulo Sharding Algorithm）**

取模分片算法是最简单也最常用的分片算法之一。它根据分片键的值与分片总数取模的结果，来确定数据落入哪个分片。算法公式为：`分片编号 = 分片键值 % 分片数量`。

例如，如果我们将一张表分为 4 个分片，那么分片键值为 1 的记录会落入分片 1（1 % 4 = 1），分片键值为 5 的记录会落入分片 1（5 % 4 = 1），分片键值为 8 的记录会落入分片 0（8 % 4 = 0）。

取模算法的优点是数据分布均匀，实现简单，查询定位精确。缺点是扩容困难——如果需要从 4 个分片扩容到 8 个分片，由于取模的分母发生变化，大部分数据都需要迁移到新的分片中。为了解决扩容问题，可以使用一致性哈希分片算法或逻辑分片算法。

**哈希分片算法（Hash Sharding Algorithm）**

哈希分片算法与取模分片算法类似，都是通过哈希函数计算分片键来确定数据落入哪个分片。两者的区别在于，哈希分片算法会对分片键值进行哈希运算后再取模，这可以一定程度上缓解数据倾斜的问题。

ShardingSphere-JDBC 中的哈希分片算法支持自定义哈希函数，默认使用 MD5、SHA-1 等标准哈希算法。哈希算法的选择需要考虑计算开销和分布均匀性的平衡。

**时间范围分片算法（Range Sharding Algorithm）**

时间范围分片算法按照分片键的时间范围进行分片，每个分片存储特定时间范围内的数据。例如，可以按月分片，每月一张表；也可以按天分片，每天一张表。

时间范围分片的优点是符合时间序列数据的访问模式，便于清理历史数据和归档。缺点是容易造成数据热点不均——如果近期数据访问频繁，而历史数据访问较少，就会导致近期分片负载过高。

时间范围分片特别适合日志系统、交易记录、传感器数据等与时间强相关的场景。在配置时，通常需要指定时间格式和分片时间间隔。

**标准分片算法（Standard Sharding Algorithm）**

标准分片算法是 ShardingSphere-JDBC 提供的一种通用分片算法，它支持对 =、IN、BETWEEN 等运算符进行分片路由。标准分片算法要求分片键值是数值类型，并且需要提供分片数量信息。

当 SQL 条件中包含分片键的等值条件（如 WHERE user_id = 1）时，标准分片算法能够精确定位到单个分片进行查询。当使用 IN 条件（如 WHERE user_id IN (1, 2, 3)）时，算法会将查询路由到对应的多个分片。当使用 BETWEEN 条件（如 WHERE user_id BETWEEN 1 AND 100）时，算法会进行全量路由或范围路由，取决于分片键的分布和查询范围。

**复合分片算法（Complex Sharding Algorithm）**

复合分片算法允许使用多个分片键进行分片，适用于需要同时考虑多个业务维度的场景。例如，一个订单表可能需要同时按用户 ID 和时间进行分片，以便支持用户维度和时间维度的查询。

复合分片算法需要开发者提供多个分片键和对应的分片算法。在路由计算时，算法会综合考虑各个分片键的值，计算出最终的分片位置。复合分片的配置和实现较为复杂，且可能影响查询性能，因此在实际应用中应该谨慎使用。

**强制分片算法（Hint Sharding Algorithm）**

强制分片算法是一种特殊算法，它允许通过 Hint 机制强制指定 SQL 执行的分片，而不是根据分片键计算得到。这个功能主要用于一些特殊场景，如管理员操作、跨分片查询、数据迁移等。

ShardingSphere-JDBC 提供了 HintManager API，开发者可以通过编程方式指定 SQL 应该发送到哪些分片执行。强制分片算法通常与其他分片算法配合使用，作为一个补充手段处理边缘场景。

### 2.2.8 KeyGenerator（主键生成器）

在分布式数据库系统中，唯一主键的生成是一个关键技术问题。ShardingSphere-JDBC 提供了多种主键生成器，用于在分片环境下生成全局唯一的主键值。

**雪花算法（Snowflake Algorithm）**

雪花算法是 Twitter 开源的分布式 ID 生成算法，也是 ShardingSphere-JDBC 默认的主键生成算法。它生成的 ID 是一个 64 位的长整型数值，结构如下：

```
┌──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┬──┐
│                        41位时间戳                              │  10位工作机器ID  │   12位序列号      │
└────────────────────────────────────────────────────────────────┴─────────────────┴──────────────────┘
```

41 位时间戳可以支持约 69 年的时间跨度，10 位工作机器 ID 支持 1024 个节点，12 位序列号支持每个节点每毫秒生成 4096 个 ID。雪花算法的优点是生成的 ID 趋势递增、毫秒数内在高并发情况下不会产生重复 ID、且不依赖外部存储。缺点是依赖于服务器时间，如果服务器时间回拨，可能导致 ID 重复。

ShardingSphere-JDBC 对雪花算法进行了优化，支持配置更多参数，如工作机器 ID 生成方式、序列号初始值、时间戳类型等。

**UUID（Universally Unique Identifier）**

UUID 是通用唯一标识符的标准格式，ShardingSphere-JDBC 支持生成标准 UUID（128 位）和简化 UUID。UUID 的优点是无需配置，天然具有唯一性，可以本地生成。缺点是 UUID 是无序的，这会影响数据库索引的性能——因为无序的主键会导致 B-Tree 索引频繁分裂和重组。此外，UUID 的字符串形式占用空间大（36 个字符），是 bigint 的 4.5 倍。

在 ShardingSphere-JDBC 中使用 UUID，可以通过 `UUIDKeyGenerator` 实现。需要注意的是，如果使用 UUID 作为主键，建议在数据库层面将主键类型设置为 varchar 而不是 bigint，以节省存储空间。

**LEAF（Leaf Segment ID Generator）**

LEAF 是美团点评开源的分布式 ID 生成服务，提供了两种 ID 生成模式：号段模式和雪花算法模式。ShardingSphere-JDBC 提供了对 LEAF 的支持，可以通过配置连接到 LEAF 服务获取 ID。

号段模式是 LEAF 的一大特色，它预先从数据库获取一段 ID 号码，缓存在内存中，本地分配用完后再获取下一段。这种方式可以大大减少对数据库或服务端的请求，提高性能。号段模式的优点是高可用、性能好，缺点是 ID 不是趋势递增的，且存在数据浪费（服务重启时未用完的号段会被丢弃）。

**自定义主键生成器**

除了内置的主键生成器，ShardingSphere-JDBC 还支持自定义主键生成器。开发者可以实现 `KeyGenerator` 接口，编写自己的 ID 生成逻辑。常见的自定义场景包括：接入外部 ID 生成服务（如 UidGenerator、TinyID 等）、对接业务系统的现有 ID 规则、使用特定的算法生成特殊格式的 ID 等。

## 2.3 ShardingSphere-JDBC 工作流程详解

ShardingSphere-JDBC 对 SQL 的处理流程可以分为五个核心阶段：SQL 解析、路由计算、SQL 改写、SQL 执行和结果归并。理解这个流程对于排查问题、优化性能和设计系统架构都非常重要。

### 2.3.1 SQL 解析阶段（Parsing）

**解析引擎的作用**

SQL 解析是整个处理流程的起点，负责将用户输入的 SQL 文本解析为内部的数据结构——抽象语法树（Abstract Syntax Tree，AST）。解析引擎的质量直接影响后续各个阶段的准确性和效率。一个好的解析引擎需要能够正确处理各种 SQL 语法，包括复杂的多表连接、子查询、聚合函数、窗口函数等。

**解析过程**

ShardingSphere-JDBC 的解析过程分为两个阶段：词法分析（Lexical Analysis）和语法分析（Syntax Analysis）。

词法分析阶段，解析器读取 SQL 文本，将其拆解为一系列的词法单元（Token），如关键字（SELECT、FROM、WHERE 等）、标识符（表名、列名）、运算符（=、>、< 等）、字面量（数字、字符串）等。词法分析器会忽略 SQL 中的注释和空白字符，只保留有意义的词法单元。

语法分析阶段，解析器根据 SQL 语法规则，将词法单元组合成语法树。ShardingSphere-JDBC 使用 Apache Calcite 作为 SQL 解析器，Calcite 是一个功能强大的 SQL 解析框架，支持多种 SQL 方言和复杂的 SQL 语法。语法分析的结果是一个树形结构，每个节点代表 SQL 中的一个语法成分，如 SELECT 语句、FROM 子句、WHERE 条件等。

**解析结果**

解析阶段的输出是一个包含 SQL 完整语义信息的语法树。这个语法树会被后续的路由引擎使用，用于确定 SQL 涉及哪些逻辑表、分片键的条件是什么、是否涉及跨分片操作等关键信息。解析结果的质量直接决定了路由引擎能否正确理解 SQL 的意图。

**支持的 SQL 类型**

ShardingSphere-JDBC 的解析引擎支持多种 SQL 类型，包括：

- DML（Data Manipulation Language）：SELECT、INSERT、UPDATE、DELETE
- DDL（Data Definition Language）：CREATE、ALTER、DROP、TRUNCATE
- TCL（Transaction Control Language）：BEGIN、COMMIT、ROLLBACK、SET TRANSACTION
- DCL（Data Control Language）：GRANT、REVOKE（部分支持）

### 2.3.2 路由阶段（Routing）

**路由引擎的作用**

路由阶段是 ShardingSphere-JDBC 进行数据分片处理的核心环节。它的任务是根据解析阶段得到的 SQL 语义信息，以及配置的分片规则，确定 SQL 需要发送到哪些实际的数据源和物理表。路由结果将直接影响后续的 SQL 改写和执行。

**路由类型**

ShardingSphere-JDBC 支持多种路由类型，根据路由条件的选择范围，可以分为以下几类：

**精确路由（Precise Routing）**。当 SQL 条件中包含分片键的等值条件时，路由引擎能够精确计算出 SQL 应该发送到哪个分片。例如，如果分片键是 user_id，且 SQL 条件为 `WHERE user_id = 10086`，路由引擎会直接定位到对应的分片进行查询，无需访问其他分片。精确路由是性能最好的路由方式，因为它只涉及单个分片的访问。

**范围路由（Range Routing）**。当 SQL 条件中包含分片键的范围条件时，路由引擎会计算这个范围覆盖了哪些分片，然后向所有涉及的分片发送 SQL。例如，如果分片键是 user_id，且 SQL 条件为 `WHERE user_id BETWEEN 1000 AND 2000`，路由引擎会计算出所有可能包含这些 user_id 的分片，并向它们发送查询请求。范围路由可能涉及多个分片，查询性能取决于分片的数量和分布。

**全路由（Full Routing）**。当 SQL 条件中不包含分片键，或者分片键的条件无法确定具体分片时，路由引擎需要向所有分片发送 SQL。例如，`SELECT * FROM t_order` 这样的全表查询，或者 `WHERE user_name = '张三'`（user_name 不是分片键）这样的查询。全路由需要访问所有分片，然后对结果进行聚合和过滤，性能开销较大，应该尽量避免。

**路由优化**

路由引擎在执行路由计算时，会进行多种优化以提高性能。例如，对于 OR 条件，如果 OR 的各个分支可以分别精确路由到不同的分片，引擎会分别计算各分支的路由结果，而不是简单地全路由。对于 LIKE 条件，引擎会分析是否能够利用索引进行范围扫描。对于聚合查询，引擎会尽可能将聚合操作下推到各个分片执行，以减少结果归并的数据量。

### 2.3.3 SQL 改写阶段（Rewrite）

**改写引擎的作用**

改写阶段是 ShardingSphere-JDBC 处理分片语法的关键环节。由于用户编写的是针对逻辑表的 SQL，但实际执行时需要访问物理表，因此需要对 SQL 进行相应的改写。改写引擎会根据路由结果，将 SQL 中的逻辑表名替换为实际的物理表名，将逻辑字段替换为实际的物理字段（如需要），并添加必要的分片条件。

**表名改写**

表名改写是最基本的改写操作。当 SQL 中引用了逻辑表名时，改写引擎会将其替换为对应的物理表名。对于单分片的精确查询，直接替换为对应的物理表名即可。对于多分片的查询，需要将 SQL 拆分为多个针对不同物理表的 SQL。

例如，原始 SQL 为 `SELECT * FROM t_order WHERE order_id = 100`，如果 order_id = 100 对应的物理表是 ds_1.t_order_3，改写后的 SQL 为 `SELECT * FROM ds_1.t_order_3 WHERE order_id = 100`。

**分片条件补全**

在某些查询场景中，SQL 原本的条件可能不包含分片键，但为了确保查询结果的正确性，需要补充分片条件。例如，对于分片表的全表查询，ShardingSphere-JDBC 会自动添加分片条件以确保只查询满足分片规则的物理表。

**子查询改写**

ShardingSphere-JDBC 对子查询的改写支持有限。对于简单的相关子查询，引擎会尝试进行改写，但对于复杂的子查询（如包含聚合、窗口函数的相关子查询），可能无法正确改写，需要开发者在编写 SQL 时注意规避。

**DDL 改写**

对于 DDL 语句（如 CREATE TABLE、ALTER TABLE 等），改写引擎会将逻辑表名替换为物理表名。如果配置了自动创建物理表，DDL 语句会在所有相关的物理表上执行。如果物理表已存在，需要根据配置决定是否跳过或报错。

### 2.3.4 SQL 执行阶段（Execute）

**执行引擎的作用**

执行阶段负责将改写后的 SQL 发送到实际的物理数据库执行，并管理整个执行过程。执行引擎需要处理连接管理、并发控制、结果缓存、异常处理等任务。

**连接管理**

执行引擎维护着到各个物理数据库的连接池。当需要向某个数据源发送 SQL 时，引擎从连接池中获取连接，执行 SQL，然后归还连接。连接管理需要考虑连接的复用、生命周期管理和资源限制。

对于跨数据源的分布式事务，ShardingSphere-JDBC 支持 XA 事务和柔性事务两种模式。XA 事务使用两阶段提交协议保证分布式事务的 ACID 特性，但性能开销较大。柔性事务（如 Seata 的 AT 模式）采用最终一致性模型，性能较好但无法保证立即的强一致性。

**并发执行策略**

对于需要访问多个分片的 SQL，执行引擎支持多种并发执行策略：

**串行执行**。按照分片顺序依次执行各分片的 SQL。这种方式实现简单，但无法利用并行优势，延迟较高。

**并行执行**。同时向多个分片发送 SQL 请求。这种方式能够显著降低总延迟，但会增加系统资源消耗。ShardingSphere-JDBC 默认使用并行执行策略。

**流式执行**。对于大数据量的查询，执行引擎支持流式执行模式，避免一次性将所有结果加载到内存。流式执行通过 JDBC 的流式 ResultSet 实现，能够有效降低内存占用。

**结果缓存**

执行引擎支持对查询结果进行缓存，以减少对物理数据库的访问次数。缓存策略可以配置为按分片键、按 SQL 条件等进行缓存。需要注意的是，缓存会带来数据一致性的挑战，ShardingSphere-JDBC 提供了缓存失效机制来处理数据更新场景。

### 2.3.5 结果归并阶段（Merge）

**归并引擎的作用**

归并阶段是整个 SQL 处理流程的最后环节，负责将各个分片返回的结果合并为单一的结果集，返回给上层应用。归并引擎需要处理多种类型的归并操作，包括分页归并、聚合归并、排序归并和分组归并等。

**分页归并**

分页归并是最常见的归并类型。当查询需要分页时，各个分片返回的是符合分页条件的结果，但在内存中归并时，需要按照分页要求重新计算。例如，查询第 100 页（每页 10 条）的数据，各个分片可能需要返回前 1000 条数据，然后在归并引擎中筛选出第 100-110 条。

分页归并的一个重要问题是深度分页的性能。当页码很大时（如查询第 10000 页），各个分片都需要扫描大量的数据，效率很低。常见的优化方案是采用游标分页（基于上一页最后一条记录的 ID 进行筛选），或者限制最大页码。

**聚合归并**

聚合归并处理包含聚合函数（COUNT、SUM、AVG、MAX、MIN）的查询。各分片首先在本地执行聚合计算，然后将局部聚合结果返回给归并引擎。归并引擎对各分片的局部结果进行最终的聚合计算，得到全局聚合值。

例如，对于 `SELECT COUNT(*) FROM t_order WHERE user_id = 1`，如果按 user_id 分片且查询条件包含分片键，各分片会返回本地的 COUNT 值，归并引擎将它们相加得到最终的 COUNT 结果。

**排序归并**

排序归并处理需要排序的查询。各分片返回的的结果是分别排序的，但整体可能并非全局有序。归并引擎需要将各分片的结果按照排序条件进行全局排序。

ShardingSphere-JDBC 使用归并排序算法实现排序归并。它首先从各分片获取一批结果，然后进行排序，当这批结果处理完毕后，再获取下一批结果，直到所有分片的数据都处理完毕。归并排序的特点是只需要有限的内存即可处理大量数据，适合大数据量的排序场景。

**分组归并**

分组归并处理包含 GROUP BY 子句的查询。与聚合归并类似，各分片首先在本地执行分组聚合，然后将分组结果返回给归并引擎。归并引擎按照分组键对各分片的分组结果进行合并。

分组归并的一个挑战是分片数量较多时，部分分组的记录可能分布在多个分片中，需要在归并引擎层面进行二次聚合。另一个挑战是 HAVING 子句的处理，需要在归并后对分组结果进行过滤。

## 2.4 各模块职责说明

### 2.4.1 解析引擎（Parse Engine）

**模块定位**

解析引擎是 ShardingSphere-JDBC 的入口模块，负责将 SQL 文本转换为内部可处理的中间表示。作为整个 SQL 处理流程的第一环，解析引擎的准确性和性能直接影响整个系统的表现。

**核心组件**

解析引擎主要由以下组件构成：

**SQLParser** 是解析引擎的核心类，负责执行词法分析和语法分析。它接收 SQL 文本作为输入，输出 SQL 语句对象（SQLStatement）。ShardingSphere-JDBC 使用 Apache Calcite 作为底层的 SQL 解析器，同时针对分片场景进行了优化和扩展。

**SQLVisitor** 是访问者模式的实现，用于遍历抽象语法树并提取需要的语义信息。ShardingSphere-JDBC 定义了多种 Visitor 类，分别用于提取表名、列名、分片条件、排序信息等不同维度的信息。

**SQLStatement** 是 SQL 语句的面向对象表示。每种 SQL 语句类型（如 SelectStatement、InsertStatement、UpdateStatement 等）都有对应的类来表示其语义信息。SQLStatement 对象会被后续的路由引擎、改写引擎等使用。

**支持的 SQL 标准**

ShardingSphere-JDBC 的解析引擎支持多种 SQL 标准和方言：

- MySQL 5.5、5.6、5.7、8.0
- PostgreSQL 9.x、10.x、11.x、12.x
- SQL92 标准
- SQL2003 标准（部分）

对于未支持的 SQL 语法，解析引擎会尽可能容忍错误，继续解析能解析的部分，但可能会影响路由和改写的准确性。

### 2.4.2 路由引擎（Routing Engine）

**模块定位**

路由引擎是 ShardingSphere-JDBC 的核心决策模块，根据解析引擎提供的 SQL 语义信息和配置的分片规则，计算出 SQL 需要访问的实际数据节点。

**路由策略实现**

路由引擎内部维护着路由策略的注册表，根据配置的路由类型（标准路由、强制路由、简化路由等）选择合适的路由策略执行路由计算。

**标准路由**是最常用的路由策略，适用于 SQL 条件中包含分片键且使用 =、IN、BETWEEN 等运算符的场景。标准路由能够精确定位到需要访问的分片，是性能最好的路由方式。

**简化路由**适用于 SQL 条件中分片键使用表达式但不包含实际分片值（如 WHERE user_id = ?，参数化查询）的场景。简化路由会计算表达式涉及的可能的分片组合，但由于参数值未知，无法精确确定具体的分片。

**强制路由**通过 Hint 机制实现，允许开发者显式指定 SQL 应该访问的分片。强制路由主要用于一些特殊的业务场景，如后台管理操作、数据迁移等。

**路由结果**

路由引擎的输出是一个 `RouteResult` 对象，包含需要访问的 `DataNode` 列表。每个 `DataNode` 代表一个实际的数据节点，包含数据源名称和物理表名称。路由结果会被后续的改写引擎使用，用于生成针对每个数据节点的物理 SQL。

### 2.4.3 改写引擎（Rewrite Engine）

**模块定位**

改写引擎负责将针对逻辑表的 SQL 改写为针对物理表的 SQL。它是连接路由引擎和执行引擎的桥梁，确保路由结果能够正确地转化为可执行的物理 SQL。

**改写策略**

改写引擎支持多种改写策略，分别处理不同的改写场景：

**表名改写**是最基本的改写策略，将逻辑表名替换为物理表名。对于精确路由的 SQL，只涉及单个物理表，改写简单直接。对于范围路由或多分片路由，可能需要将 SQL 拆分为多个物理 SQL。

**列名改写**在大多数场景下不需要，因为逻辑列名与物理列名通常相同。但在某些特殊场景（如数据加密、影子表）下，可能需要将列名或列值进行改写。

**自增主键改写**用于处理自增主键的场景。当 INSERT 语句未指定主键值时，改写引擎会根据配置的主键生成器生成主键值，并将其添加到 INSERT 语句中。

**子查询改写**是较复杂的改写场景。ShardingSphere-JDBC 会尝试将能够下推的子查询改写为联接查询或分别执行，对于无法下推的子查询，会标记为需要全局查询。

**改写结果**

改写引擎的输出是一组 `SQLRewriteResult`，每个结果对应一个需要执行的物理 SQL。改写结果会被传递给执行引擎进行实际执行。

### 2.4.4 执行引擎（Execute Engine）

**模块定位**

执行引擎负责实际执行物理 SQL 并管理执行过程。它封装了数据库连接管理、并发执行策略、事务管理等功能，是 ShardingSphere-JDBC 与物理数据库交互的直接接口。

**连接池管理**

执行引擎为每个物理数据源维护一个连接池。连接池的配置参数包括最小连接数、最大连接数、连接超时时间、连接回收策略等。合理的连接池配置对于系统性能至关重要——连接数过少会导致并发能力受限，连接数过多会消耗过多系统资源。

ShardingSphere-JDBC 默认使用 HikariCP 作为连接池实现，HikariCP 是目前性能最优的 JDBC 连接池之一。它采用了多种优化技术，如无锁并发、连接预热、自定义 FastList 等，能够提供出色的性能表现。

**执行策略**

执行引擎支持多种 SQL 执行策略：

**连接模式**决定了分片间的执行方式。ShardingSphere-JDBC 支持内存限制模式（限制同时打开的连接数）和连接限制模式（限制每个分片使用的连接数）。内存限制模式优先保证内存使用可控，连接限制模式优先保证执行并行度。

**事务策略**决定了跨分片事务的处理方式。ShardingSphere-JDBC 支持本地事务（不支持跨分片事务）、柔性事务（最终一致性）和 XA 事务（强一致性）三种模式。不同的事务模式有不同的性能表现和一致性保证，需要根据业务需求选择。

### 2.4.5 归并引擎（Merge Engine）

**模块定位**

归并引擎负责将各分片返回的结果合并为统一的结果集，是整个 SQL 处理流程的最终环节。归并引擎需要处理多种归并类型，并保证归并结果的正确性和完整性。

**归并类型**

归并引擎支持以下几种归并类型：

**装饰器归并**是最基础的归并类型，不改变结果的内容，只是包装成统一的结果集接口。它通常与其他归并类型组合使用。

**分页归并**处理 LIMIT 子句，按照分页参数从各分片结果中筛选出需要的数据。分页归还需要注意深度分页的性能问题。

**聚合归并**处理聚合函数，包括 COUNT、SUM、AVG、MAX、MIN 等。各分片先在本地执行聚合，归并引擎在全局层面进行二次聚合。

**排序归并**处理 ORDER BY 子句。由于各分片的数据是分别排序的，归并引擎需要使用归并排序算法将结果全局排序。

**分组归并**处理 GROUP BY 子句。各分片返回分组后的数据，归并引擎按照分组键进行合并。分组归并支持两种模式：流式分组和内存分组，取决于分组字段是否与分片键一致。

## 2.5 数据源管理

### 2.5.1 数据源架构设计

ShardingSphere-JDBC 的数据源管理采用了统一入口、多实例管理的架构设计。应用通过 ShardingSphere-JDBC 提供的 DataSource 接口获取连接，这个 DataSource 内部管理着多个物理数据源，屏蔽了底层的复杂性。

**数据源配置模型**

ShardingSphere-JDBC 的数据源配置模型包含以下层次：

数据源配置层定义了到物理数据库的连接信息。每个数据源配置包含 JDBC URL、用户名、密码、连接池参数等基本连接信息。数据源配置是独立的，与分片规则无直接关联。

分片规则配置层定义了逻辑表与物理表的映射关系、分片策略、分片算法等。分片规则引用数据源配置，建立起逻辑表与物理数据源的关联。

数据源注册层将数据源配置注册到 ShardingSphere-JDBC 的内部容器中，使其可以被分片规则引用。注册过程还包括连接池的初始化和验证。

### 2.5.2 多数据源场景

**水平分库场景**

在水平分库场景下，数据按照分片规则分散到多个数据库实例中。每个数据库实例可能有多个物理表，也可能只有一个库但有多个物理表（单库多表场景）。

水平分库的关键配置是 `actualDataNodes`，它定义了逻辑表与物理表节点的映射关系。例如：

```yaml
shardingRule:
  tables:
    t_order:
      actualDataNodes: ds_${0..1}.t_order_${0..3}
```

这个配置表示 `t_order` 逻辑表对应数据源 `ds_0` 和 `ds_1` 上的物理表 `t_order_0` 到 `t_order_3`，共 8 个物理表节点。

**读写分离场景**

读写分离是另一种常见的数据源使用场景。在读写分离架构中，写操作发往主库，读操作发往从库（可以配置为读主库或读从库）。ShardingSphere-JDBC 支持将数据分片与读写分离结合使用，即分片后的数据又采用读写分离策略。

读写分离的配置示例：

```yaml
masterSlaveRule:
  name: ds_ms
  masterDataSourceName: ds_master
  slaveDataSourceNames: ds_slave_0, ds_slave_1
```

### 2.5.3 数据源健康检查

ShardingSphere-JDBC 提供了数据源健康检查机制，用于监控物理数据源的可用性。健康检查包括连接测试、查询测试等方式。当检测到某个数据源不可用时，ShardingSphere-JDBC 会自动将其从可用数据源列表中移除，待恢复后再重新加入。

健康检查的配置参数包括检查周期、检查超时时间、连续失败阈值等。对于生产环境，建议开启健康检查并合理配置参数，以保证系统的可用性。

## 2.6 连接池管理

### 2.6.1 连接池原理

连接池是数据库连接管理的核心组件，它预先建立一定数量的数据库连接并缓存起来，当应用需要访问数据库时，直接从连接池获取连接而不是创建新连接，使用完毕后归还连接池而不是关闭连接。

连接池的工作原理可以概括为以下几个步骤：

**初始化阶段**。应用启动时，连接池根据配置的参数（如最小连接数）创建一定数量的数据库连接，并将它们放入连接池中。这些连接处于可用状态，可以被应用直接获取使用。

**获取连接阶段**。当应用需要执行数据库操作时，调用 `getConnection()` 方法从连接池获取连接。如果池中有可用连接，直接返回；如果可用连接为空但池中连接数小于最大连接数，则创建新连接；如果连接数已达上限，则等待其他连接释放。

**使用连接阶段**。应用获得连接后，执行数据库操作。这个阶段与应用使用普通 JDBC 连接没有区别。

**归还连接阶段**。操作完成后，应用调用 `close()` 方法归还连接。对于连接池而言，`close()` 并不是关闭连接，而是将连接放回可用队列中，等待下次使用。

**销毁阶段**。应用关闭或连接池清理时，连接池会关闭所有持有的连接，释放资源。

### 2.6.2 HikariCP 连接池配置

ShardingSphere-JDBC 默认使用 HikariCP 作为连接池实现。HikariCP 以其卓越的性能著称，相比 Druid、C3P0 等其他连接池，HikariCP 在大多数场景下都有明显优势。

**核心配置参数**

HikariCP 的核心配置参数包括：

`maximumPoolSize`（最大连接数）：连接池允许持有的最大连接数。这个值需要根据数据库服务器的处理能力、应用并发量来设置。通常建议设置为数据库服务器最大连接数的 80% 左右，留一部分给监控和其他用途。

`minimumIdle`（最小空闲连接数）：连接池保持的最小空闲连接数。HikariCP 会尽量保持这个数量的空闲连接，以减少获取连接时的等待时间。

`connectionTimeout`（连接超时时间）：等待获取连接的最大毫秒数。如果超过这个时间还没有可用连接，将抛出 SQLException。

`idleTimeout`（空闲超时时间）：空闲连接的最大存活时间。超过这个时间的空闲连接会被关闭。这个参数只在使用连接数超过最小连接数时生效。

`maxLifetime`（连接最大生命周期）：连接的最大存活时间。无论是否空闲，超过这个时间的连接都会被关闭。这个参数用于处理数据库端的连接超时和连接老化问题。

`connectionTestQuery`（连接测试查询）：从连接池获取连接后、执行前执行的测试查询。用于验证连接仍然有效。对于大多数数据库，可以使用 `SELECT 1`。

**性能优化建议**

以下是 HikariCP 性能优化的一些建议：

确保 `maximumPoolSize` 的设置与数据库服务器的处理能力匹配。可以通过压测找到最优值，通常在 CPU 核心数的 2-3 倍左右。

如果业务是短连接（每次请求获取连接、执行、归还），确保 `minimumIdle` 设置为等于 `maximumPoolSize`，以避免连接创建销毁的开销。

如果业务是长连接（获取连接后保持较长时间），确保 `maxLifetime` 设置合理，通常略短于数据库的连接超时时间。

对于高并发场景，可以考虑启用 `cachePrepStmts` 和相关参数，开启 PreparedStatement 缓存。

### 2.6.3 连接池与分片的协同

在 ShardingSphere-JDBC 的分片场景下，连接池管理变得更加复杂，因为需要在多个数据源之间协调连接资源。

**连接数分配策略**

当应用配置了多个数据源时，每个数据源都有自己的连接池。应用的总连接数消耗是各个数据源连接池的总和。因此，在配置每个数据源的连接池大小时，需要考虑总连接数不能超过数据库服务器的处理能力。

一个常见的做法是：假设数据库服务器允许最多 2000 个连接，应用使用了 4 个数据源，那么每个数据源的 `maximumPoolSize` 可以设置为 500。

**连接获取顺序**

在执行跨分片查询时，ShardingSphere-JDBC 需要从多个数据源获取连接。为了避免死锁，建议按照数据源名称的字典顺序依次获取连接。ShardingSphere-JDBC 内部已经实现了这个策略。

**连接泄漏检测**

连接池提供了连接泄漏检测机制，用于发现应用获取连接后忘记归还的情况。当连接被检出超过一定时间（`leakDetectionThreshold`）没有被归还时，HikariCP 会记录警告日志，包含连接的获取位置信息，帮助开发者定位问题。

### 2.6.4 连接池监控

HikariCP 提供了丰富的监控指标，可以通过 JMX 或编程方式访问。关键的监控指标包括：

活跃连接数（Active Connections）：当前正在使用的连接数。
空闲连接数（Idle Connections）：当前空闲可用的连接数。
等待获取连接的线程数（Threads Waiting）：因为没有可用连接而等待的线程数。
总连接数（Total Connections）：当前池中的总连接数。
连接创建速度（Connection Creation Rate）：每秒创建的连接数。
连接回收速度（Connection Release Rate）：每秒归还的连接数。

通过监控这些指标，可以及时发现连接池的性能问题和潜在风险。例如，如果活跃连接数持续接近最大连接数，且有线程在等待获取连接，说明连接池配置不足或存在性能问题。
