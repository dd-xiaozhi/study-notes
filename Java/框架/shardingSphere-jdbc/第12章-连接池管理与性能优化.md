# 第12章 连接池管理与性能优化

## 概述

在 ShardingSphere-JDBC 架构中，连接池是连接数据库和应用系统的核心组件，其性能直接影响整个系统的吞吐量、响应时间和稳定性。本章将深入探讨连接池的管理策略和性能优化技巧，帮助读者构建高效、稳定的数据库连接管理体系。

连接池的核心目标是复用数据库连接，避免频繁创建和销毁连接带来的性能开销。然而，连接池配置不当也可能导致系统性能下降，甚至引发严重的生产故障。因此，理解连接池的工作原理、掌握配置技巧对于使用 ShardingSphere-JDBC 至关重要。

---

## 12.1 常见连接池对比

在 Java 生态中，存在多种成熟的连接池实现，每种连接池都有其独特的优势和适用场景。本节将对 HikariCP、Druid、C3P0 和 DBCP 进行全面对比。

### 12.1.1 连接池特性对比表

| 特性 | HikariCP | Druid | C3P0 | DBCP |
|------|----------|-------|------|------|
| 性能 | 极高 | 高 | 中 | 中 |
| 稳定性 | 非常高 | 高 | 中 | 中 |
| 可靠性 | 高 | 高 | 中 | 中 |
| 易用性 | 高 | 高 | 中 | 中 |
| 监控 | 有限 | 完善 | 有限 | 有限 |
| 防护 | 连接超时、泄露检测 | SQL注入防护、wall | 有限 | 有限 |
| 维护 | 活跃 | 非常活跃 | 低 | 中 |
| Spring Boot 支持 | 默认 | 需配置 | 需配置 | 需配置 |

### 12.1.2 HikariCP

HikariCP 是目前性能最高的连接池实现，被 Spring Boot 选为默认连接池。它的设计理念是极致的性能优化，通过多种技术手段减少连接获取和归还的开销。

**核心优势：**

1. **极致性能**：HikariCP 通过 FastPath 机制、无锁设计、直接字节码操作等技术实现了极高的性能。在基准测试中，HikariCP 的 throughput 远超其他连接池。

2. **极小 footprint**：整个连接池库体积很小（约130KB），对系统资源消耗极低。

3. **可靠性**：提供了完善的连接验证、心跳检测机制，能够及时发现失效连接。

4. **简洁配置**：相比其他连接池，HikariCP 的配置项更少但更精准。

**主要缺点：**

- 监控功能相对薄弱，不提供内置的 SQL 执行监控
- 缺少 SQL 防火墙等企业级功能

**适用场景：**

- 对性能要求极高的系统
- 微服务架构
- Spring Boot 项目

### 12.1.3 Druid

Druid 是阿里巴巴开源的数据库连接池，不仅提供连接管理功能，还集成了强大的监控和防护能力。

**核心优势：**

1. **完善的监控**：内置 SQL 执行监控、连接状态监控、性能监控等功能，通过 Web 界面可以直观地查看数据库操作详情。

2. **SQL 防火墙**：提供 SQL 注入防护、wall 功能，可配置白名单和黑名单。

3. **连接诊断**：提供强力的连接泄露检测和诊断功能。

4. **多数据源支持**：天然支持分库分表场景下的多数据源管理。

**主要缺点：**

- 相比 HikariCP，性能稍逊一筹
- 配置项较多，学习成本相对较高
- 库体积较大

**适用场景：**

- 需要详细监控的生产系统
- 电商、金融等对数据安全性要求高的系统
- 分库分表场景

### 12.1.4 C3P0

C3P0 是一个历史悠久的连接池实现，曾经是 Hibernate 默认的连接池。

**核心优势：**

1. **稳定性**：经过多年沉淀，稳定性较高。

2. **功能全面**：提供了较为完整的功能集。

3. **兼容性好**：对老版本 JDK 兼容性好。

**主要缺点：**

- 性能相对较差，不适合高并发场景
- 配置复杂，容易出现难以诊断的问题
- 已停止维护

**适用场景：**

- 遗留系统
- 需要兼容老版本 JDK 的系统

### 12.1.5 DBCP (Apache Commons DBCP)

DBCP 是 Apache Commons 项目的一部分，提供了基础的连接池功能。

**核心优势：**

1. **轻量级**：库体积小，依赖少。

2. **兼容性好**：与 Apache 生态其他组件兼容性好。

**主要缺点：**

- 性能一般
- 功能相对简单
- 已停止活跃维护

**适用场景：**

- 对功能要求不高的简单应用
- Apache 生态项目

### 12.1.6 连接池选型建议

在 ShardingSphere-JDBC 环境下，推荐的连接池选择策略如下：

**首选 HikariCP：**

- 当系统追求极致性能
- 使用 Spring Boot 框架
- 不需要详细的 SQL 监控

**选择 Druid：**

- 需要完善的 SQL 执行监控
- 需要 SQL 防火墙功能
- 阿里系技术栈
- 分库分表场景下需要多数据源统一管理

**谨慎使用 C3P0/DBCP：**

- 仅建议在遗留系统维护场景下使用
- 新项目不推荐使用这两个连接池

## 12.2 HikariCP 核心配置参数详解

HikariCP 的配置参数直接影响连接池的行为和性能。本节详细解析各配置项的含义和最佳实践。

### 12.2.1 基础配置参数

```yaml
datasource:
  primary:
    driver-class-name: com.mysql.cj.jdbc.Driver
    jdbc-url: jdbc:mysql://localhost:3306/sharding_db?useSSL=false&serverTimezone=UTC
    username: root
    password: root
    pool-name: PrimaryPool
    maximum-pool-size: 20
    minimum-idle: 5
    connection-timeout: 30000
    idle-timeout: 600000
    max-lifetime: 1800000
```

**pool-name**

连接池的名称，用于在日志和监控中标识该连接池。建议为每个数据源设置有意义的名称，便于问题排查。

```yaml
pool-name: ShardingSphere-Primary-Pool
```

**maximum-pool-size**

连接池最大连接数。这个参数决定了连接池能够同时保持的最大连接数量。设置过大可能导致数据库连接数过多而影响数据库性能；设置过小则可能导致连接不够用，请求排队等待。

```yaml
maximum-pool-size: 20
```

合理的 maximum-pool-size 需要根据数据库服务器配置、业务并发量、响应时间要求等因素综合计算。具体计算方法将在12.3节详细介绍。

**minimum-idle**

连接池保持的最小空闲连接数。HikariCP 会始终保持这个数量的连接处于可用状态，避免连接频繁创建销毁带来的开销。

```yaml
minimum-idle: 5
```

建议设置为能让系统在低峰期保持基本负载，避免连接过度收缩导致性能波动。

**connection-timeout**

获取连接的最大等待时间（毫秒）。当连接池中没有可用连接且连接数已达到 maximum-pool-size 时，请求会等待一定时间。如果超时仍未获得连接，将抛出异常。

```yaml
connection-timeout: 30000  # 30秒
```

建议设置：

- 高并发系统：10-15秒
- 普通业务系统：30秒
- 批处理系统：60秒以上

**idle-timeout**

连接的最大空闲时间（毫秒）。当连接空闲时间超过这个值且当前连接数大于 minimum-idle 时，连接会被关闭。

```yaml
idle-timeout: 600000  # 10分钟
```

设置建议：

- 频繁操作系统：5-10分钟
- 低频系统：30分钟以内
- 不要设置过大，否则可能占用过多数据库连接资源

**max-lifetime**

连接的最大存活时间（毫秒）。无论连接是否空闲，超过这个时间后连接会被关闭并重新创建。

```yaml
max-lifetime: 1800000  # 30分钟
```

设置建议：

- MySQL：不超过30分钟（MySQL 默认的 wait_timeout 是8小时，但建议设置更短）
- Oracle：可以设置得更长
- 需要设置略小于数据库端的连接超时配置

### 12.2.2 连接验证配置

```yaml
validation-timeout: 5000
connection-test-query: SELECT 1
```

**validation-timeout**

验证连接可用性的超时时间（毫秒）。

```yaml
validation-timeout: 5000  # 5秒
```

**connection-test-query**

连接验证 SQL。对于 MySQL，推荐使用 `SELECT 1`，不要使用 `SELECT 1 FROM DUAL`（某些数据库不支持）。

```yaml
connection-test-query: SELECT 1
```

MySQL 推荐使用：

```yaml
# 性能更好的验证方式
connection-test-query: SELECT 1
# 使用 TCP KeepAlive 检测（需数据库支持）
```

对于 PostgreSQL：

```yaml
connection-test-query: SELECT 1
```

对于 Oracle：

```yaml
connection-test-query: SELECT 1 FROM DUAL
```

### 12.2.3 性能优化配置

```yaml
auto-commit: true
cache-prep-stmt: true
prep-stmt-cache-size: 250
prep-stmt-cache-sql-limit: 2048
use-server-prep-stmts: false
```

**auto-commit**

控制连接是否自动提交事务。默认 true，建议保持默认。

```yaml
auto-commit: true
```

除非有特殊需求（如需要手动控制事务），不要修改这个值。

**cache-prep-stmt**

是否缓存预编译语句（PreparedStatement）。启用后可以提升 SQL 执行性能。

```yaml
cache-prep-stmt: true
```

**prep-stmt-cache-size**

预编译语句缓存的最大数量。

```yaml
prep-stmt-cache-size: 250
```

**prep-stmt-cache-sql-limit**

预编译语句缓存的 SQL 最大长度。

```yaml
prep-stmt-cache-sql-limit: 2048
```

**use-server-prep-stmts**

是否使用服务端预编译。开启后性能更好，但需要数据库驱动支持。

```yaml
use-server-prep-stmts: false  # MySQL 建议关闭，使用客户端模拟预编译
```

以下是针对 ShardingSphere-JDBC 的 HikariCP 完整配置示例：


## 12.3 连接池大小计算公式

连接池大小的合理配置是系统性能的关键。配置过小会导致连接等待，配置过大会浪费数据库资源甚至导致数据库过载。本节介绍连接池大小的计算方法。

### 12.3.1 理论公式

连接池大小的计算需要考虑以下几个因素：

**核心公式：**

```
连接池大小 = ((核心数 * 2) + 有效磁盘数) + 预期并发连接数 / 预期线程空闲比例
```

对于 Web 应用，更实用的公式是：

```
连接池大小 = 预期平均并发数 * 响应时间比例 + 峰值缓冲
```

### 12.3.2 简化计算公式

在多数 Web 应用场景下，可以使用以下简化公式：

**公式一：基于 CPU 核心数**

```
连接池大小 = CPU 核心数 * 2 + 有效磁盘数
```

例如：4核CPU，1个SSD：

```
连接池大小 = 4 * 2 + 1 = 9
```

**公式二：基于预期并发**

```
连接池大小 = 预期并发用户数 * (平均思考时间 / 平均响应时间)
```

例如：100并发用户，平均响应时间100ms，平均思考时间2000ms：

```
连接池大小 = 100 * (2000 / 100) = 2000  # 这个值偏大，实际需要调整
```

**公式三：通用经验值**

```
连接池大小 = 核心数 * 3 ~ 核心数 * 5
```

例如：8核CPU，推荐连接池大小为 24-40。

### 12.3.3 数据库服务器连接数限制

在配置连接池大小之前，必须了解数据库服务器的连接数限制。

**MySQL 连接数限制：**

```sql
-- 查看最大连接数
SHOW VARIABLES LIKE 'max_connections';

-- 查看当前连接数
SHOW STATUS LIKE 'Threads_connected';
```

MySQL 默认 max_connections 为 151，可以根据需要调整：

```ini
# my.cnf 配置
max_connections = 1000
```

**PostgreSQL 连接数限制：**

```sql
-- 查看最大连接数
SHOW max_connections;

-- 查看当前连接数
SELECT count(*) FROM pg_stat_activity;
```

PostgreSQL 默认 max_connections 为 100，可以通过修改 postgresql.conf 调整。

**Oracle 连接数限制：**

Oracle 的连接数限制主要由 PROCESSES 参数控制：

```sql
-- 查看进程数限制
SELECT name, value FROM v$parameter WHERE name = 'processes';
```

### 12.3.4 连接池大小计算示例

**场景一：Web 电商系统**

- 服务器配置：8核CPU，16GB内存
- 数据库：MySQL，单机
- 业务特征：高并发，响应时间要求高
- 预期并发：500用户

计算过程：

```
1. 基础连接数 = CPU核心数 * 2 = 8 * 2 = 16
2. 峰值缓冲 = 预期并发 * 5% = 500 * 5% = 25
3. 推荐连接池大小 = 16 + 25 = 41，取整为 40-50
```

但要考虑数据库服务器的限制：

```
假设 MySQL max_connections = 1000
应用服务器数量 = 5台
单台应用连接池 = 1000 / 5 / 2 = 100（预留一半给其他用途）
```

最终建议：每台应用服务器配置连接池大小为 40-50。

**场景二：后台批处理系统**

- 服务器配置：16核CPU，32GB内存
- 数据库：Oracle RAC
- 业务特征：低并发，批量处理，SQL复杂
- 预期并发：20用户

计算过程：

```
1. 基础连接数 = CPU核心数 * 1 = 16 * 1 = 16（批处理不追求极致响应）
2. 考虑复杂SQL需要更多数据库资源
3. 推荐连接池大小 = 10-15
```

批处理系统连接池应该偏小，因为批处理 SQL 通常耗时较长，占用连接时间也长。

**场景三：微服务架构**

假设：

- 整个系统预期峰值并发：2000
- 微服务数量：10个
- 每个服务部署：2实例

单服务计算：

```
1. 单服务峰值并发 = 2000 / 10 = 200
2. 单实例峰值并发 = 200 / 2 = 100
3. 连接池大小 = 100 * (2000 / 100) / 10 = 200（考虑IO等待）
```

实际建议每个实例连接池配置为 15-25。

### 12.3.5 连接池大小配置建议汇总

| 应用类型 | 推荐连接池大小 | 说明 |
|---------|--------------|------|
| 小型应用 | 10-20 | 简单应用，并发低 |
| 标准 Web 应用 | 20-50 | 主流电商、社交应用 |
| 高并发系统 | 50-100 | 秒杀、实时交易系统 |
| 批处理系统 | 5-15 | 后台任务系统 |
| 微服务（单实例） | 15-30 | 微服务架构 |

### 12.3.6 动态调整连接池

在 ShardingSphere-JDBC 环境下，可以结合监控数据进行动态调整：

```yaml
# 监控指标触发调整
alert:
  high-connection-wait:
    threshold: 5000  # 等待时间超过5秒
    action: increase-pool-size
  
  low-connection-usage:
    threshold: 30%  # 连接利用率低于30%
    action: decrease-pool-size
```

建议定期（每周）分析连接池监控数据，根据实际负载调整连接池大小。

## 12.4 分片环境下连接池配置

在分片环境下，每个数据节点都对应一个独立的数据库连接池。连接池的配置需要考虑整体资源分配和单节点负载均衡。

### 12.4.1 分片架构概述

ShardingSphere-JDBC 支持多种分片策略：

**垂直分片：** 按照业务模块将数据拆分到不同的数据库。

```
┌─────────────────────────────────────────┐
│            ShardingSphere-JDBC          │
├─────────────┬─────────────┬─────────────┤
│  用户库     │   订单库    │   商品库    │
│ (ds_user)   │ (ds_order)  │ (ds_product)│
└─────────────┴─────────────┴─────────────┘
```

**水平分片：** 按照数据行将数据拆分到多个表/库。

```
┌─────────────────────────────────────────┐
│            ShardingSphere-JDBC          │
├─────────────┬─────────────┬─────────────┤
│  ds_0       │   ds_1      │   ds_2      │
│ t_user_0    │  t_user_1   │  t_user_2   │
└─────────────┴─────────────┴─────────────┘
```

### 12.4.2 分片环境下连接池配置原则

**原则一：总连接数控制**

系统整体连接数必须控制在数据库服务器承受范围内：

```
总连接数 = 数据源数量 × 连接池大小 ≤ 数据库最大连接数 × 0.8
```

例如：4个分片，每个连接池20个连接，数据库最大连接数100

```
总连接数 = 4 × 20 = 80
安全阈值 = 100 × 0.8 = 80
配置合理
```

**原则二：均匀分配**

每个分片的连接池大小应保持一致，避免某个分片负载过高：

```yaml
# 错误的配置
data-sources:
  ds_0:
    maximum-pool-size: 30  # 分片0连接数多
  ds_1:
    maximum-pool-size: 10  # 分片1连接数少
  
# 正确的配置
data-sources:
  ds_0:
    maximum-pool-size: 20
  ds_1:
    maximum-pool-size: 20
```

**原则三：最小空闲连接**

在分片环境下，适当提高 minimumIdle，以确保每个分片都有足够的备用连接：

```yaml
# 单分片配置
data-source:
  minimumIdle: 5  # 比单机配置略高
  maximumPoolSize: 20
```

### 12.4.3 垂直分片连接池配置

垂直分片架构下，每个数据源对应一个业务模块，连接池配置可以更具针对性。

**配置示例：**

```yaml
dataSources:
  ds_user:  # 用户库
    url: jdbc:mysql://localhost:3306/ds_user?useSSL=false&serverTimezone=UTC
    username: root
    password: root
    poolName: UserPool
    maximumPoolSize: 15
    minimumIdle: 3
    connectionTimeout: 30000
    idleTimeout: 600000
    maxLifetime: 1800000
    
  ds_order:  # 订单库
    url: jdbc:mysql://localhost:3306/ds_order?useSSL=false&serverTimezone=UTC
    username: root
    password: root
    poolName: OrderPool
    maximumPoolSize: 30  # 订单库访问频繁，配置较大
    minimumIdle: 5
    connectionTimeout: 30000
    idleTimeout: 600000
    maxLifetime: 1800000
    
  ds_product:  # 商品库
    url: jdbc:mysql://localhost:3306/ds_product?useSSL=false&serverTimezone=UTC
    username: root
    password: root
    poolName: ProductPool
    maximumPoolSize: 20
    minimumIdle: 3
    connectionTimeout: 30000
    idleTimeout: 600000
    maxLifetime: 1800000
```

**配置说明：**

- 订单库配置较大的连接池，因为订单操作频繁且耗时较长
- 用户库和商品库配置相对较小
- 总连接数：15 + 30 + 20 = 65，需要确保数据库 max_connections >= 82

## 12.5 主从架构下连接池配置

在数据库主从架构下，需要配置读写分离，将读操作分发到从库，写操作路由到主库。ShardingSphere-JDBC 支持透明化的读写分离，连接池配置需要同时考虑主库和从库。

### 12.5.1 主从架构概述

```
┌─────────────────────────────────────────┐
│            ShardingSphere-JDBC          │
├──────────────────┬──────────────────────┤
│   写操作路由      │      读操作路由       │
├──────────────────┼──────────────────────┤
│   Master DB      │      Slave DB 1      │
│   (主库)         │      (从库1)         │
│                  │      Slave DB 2      │
│                  │      (从库2)         │
└──────────────────┴──────────────────────┘
```

### 12.5.2 主从连接池配置要点

**主库连接池配置：**

主库承担所有写操作，需要更高的连接可用性：

### 12.5.5 主从延迟处理

主从架构需要考虑复制延迟，以下策略可以处理延迟问题：

**策略一：强制主库读取**

对于需要强一致性的读操作（如订单状态查询），强制走主库：

```java
/**
 * 使用主库读取，确保数据一致性
 */
@Transactional(isolation = Isolation.READ_COMMITTED)
public Order getOrderById(Long orderId) {
    // 事务内强制走主库
    return orderMapper.selectById(orderId);
}
```

**策略二：读后写一致性**

写操作后等待一段时间再读，使用 ShardingSphere 的延迟检测：

```yaml
spring:
  shardingsphere:
    rules:
      read-write-split:
        props:
          # 读延迟阈值（毫秒），超过阈值后强制读主库
          read-write-split-delay-time: 100
```

**策略三：结果归并后二次验证**

对于关键数据，读从库后与主库进行比对：

```java
public Order getOrderWithVerification(Long orderId) {
    // 先读从库获取订单基本信息
    Order order = readFromReplica(orderId);
    
    // 如果订单状态是关键数据，从主库验证
    if (order != null && order.getStatus() == OrderStatus.PENDING) {
        Order masterOrder = readFromMaster(orderId);
        // 比对数据一致性
        if (!order.equals(masterOrder)) {
            // 触发告警，记录不一致日志
            log.warn("Data inconsistency detected for order: {}", orderId);
            return masterOrder;
        }
    }
    return order;
}
```

## 12.6 连接泄漏检测与处理

连接泄漏是连接池使用中最严重的问题之一，表现为连接被获取后未正确归还，长期积累会导致连接池耗尽、应用无响应。

### 12.6.1 连接泄漏的原因

**常见原因：**

1. **未关闭 PreparedStatement**

```java
// 错误示例：未关闭 PreparedStatement
public void query() {
    Connection conn = dataSource.getConnection();
    PreparedStatement ps = conn.prepareStatement("SELECT * FROM t_user");
    ResultSet rs = ps.executeQuery();
    // 忘记关闭 ps 和 conn
}
```

2. **异常处理时未关闭连接**

```java
// 错误示例：异常时未关闭连接
public void query() {
    Connection conn = dataSource.getConnection();
    try {
        // 业务处理
        throw new RuntimeException("业务异常");
    } finally {
        // 忘记关闭连接
    }
}
```

3. **方法提前返回导致连接未关闭**

```java
// 错误示例：提前返回
public User queryUser(Long userId) {
    Connection conn = dataSource.getConnection();
    if (userId == null) {
        return null;  // 连接未关闭
    }
    // 处理业务
    return user;
}
```

4. **线程复用问题**

```java
// 错误示例：在线程池中忘记归还连接
public class MyTask implements Runnable {
    public void run() {
        Connection conn = dataSource.getConnection();
        // 处理任务
        // 任务结束后连接未归还
    }
}
```

### 12.6.2 HikariCP 连接泄漏检测

HikariCP 提供了 leakDetectionThreshold 参数用于检测连接泄漏：

```yaml
dataSource:
  maximumPoolSize: 20
  minimumIdle: 5
  # 连接泄漏检测阈值（毫秒）
  # 如果连接被借出超过这个时间仍未归还，HikariCP 会记录泄漏警告
  leakDetectionThreshold: 60000  # 60秒
```

**工作原理：**

当连接被借出时，HikariCP 会启动一个定时器。如果连接在 leakDetectionThreshold 时间内没有被归还，定时器会输出警告日志：

```
[HikariPool PoolName] Connection leak detection formed for 60000 milliseconds
```

**配置建议：**

```yaml
# 开发环境：设置较短，便于发现泄漏
leakDetectionThreshold: 10000  # 10秒

# 测试环境：设置中等
leakDetectionThreshold: 30000  # 30秒

# 生产环境：设置为0关闭检测，或者较长阈值
leakDetectionThreshold: 0  # 生产环境建议关闭或设置较长
# 或者
leakDetectionThreshold: 120000  # 2分钟，仅记录严重泄漏
```

### 12.6.3 Druid 连接泄漏检测

Druid 提供了更强大的连接泄漏检测机制：

```yaml
dataSource:
  # 开启连接泄漏检测
  removeAbandoned: true
  # 连接泄漏超时时间（秒）
  removeAbandonedTimeout: 60
  # 关闭连接时是否记录堆栈信息
  logAbandoned: true
  # 怀疑泄漏时是否强制关闭连接
  killWhenSocketReadTimeout: true
```

**Druid 连接泄漏检测的增强功能：**

```yaml

  # 是否自动回收泄漏的连接
  removeAbandoned: true
  # 泄漏超时时间

  # 每多长时间检查一次泄漏（秒）

  # 最小空闲连接数，低于这个值时不会强制关闭空闲超过 removeAbandonedTimeout 的连接
  minEvictableIdleTimeMillis: 300000
  # 是否记录关闭连接的日志
  closeConnectionOpen: true
```

### 12.6.4 连接泄漏处理方案

**方案一：使用 try-with-resources**

Java 7+ 推荐使用 try-with-resources 确保连接关闭：

```java
// 正确示例
public User queryUser(Long userId) {
    try (Connection conn = dataSource.getConnection();
         PreparedStatement ps = conn.prepareStatement("SELECT * FROM t_user WHERE id = ?")) {
        ps.setLong(1, userId);
        try (ResultSet rs = ps.executeQuery()) {
            if (rs.next()) {
                return extractUser(rs);
            }
            return null;
        }
    } catch (SQLException e) {
        throw new RuntimeException("Query user failed", e);
    }
}
```

**方案二：使用封装工具类**

```java
public class ConnectionManager {
    
    private static DataSource dataSource;
    
    public static <T> T execute(ConnectionCallback<T> callback) {
        Connection conn = null;
        try {
            conn = dataSource.getConnection();
            return callback.doInConnection(conn);
        } catch (SQLException e) {
            throw new RuntimeException("Database operation failed", e);
        } finally {
            if (conn != null) {
                try {
                    conn.close();
                } catch (SQLException e) {
                    // 记录日志
                }
            }
        }
    }
    
    @FunctionalInterface
    public interface ConnectionCallback<T> {
        T doInConnection(Connection conn) throws SQLException;
    }
}

// 使用示例
public User queryUser(Long userId) {
    return ConnectionManager.execute(conn -> {
        PreparedStatement ps = conn.prepareStatement("SELECT * FROM t_user WHERE id = ?");
        ps.setLong(1, userId);
        ResultSet rs = ps.executeQuery();
        if (rs.next()) {
            return extractUser(rs);
        }
        return null;
    });
}
```

**方案三：使用 Spring 的 JdbcTemplate**

Spring JdbcTemplate 自动管理连接：

```java
@Service
public class UserService {
    
    @Autowired
    private JdbcTemplate jdbcTemplate;
    
    public User queryUser(Long userId) {
        return jdbcTemplate.queryForObject(
            "SELECT * FROM t_user WHERE id = ?",
            new Object[]{userId},
            (rs, rowNum) -> extractUser(rs)
        );
    }
}
```

## 12.7 慢SQL处理

慢SQL是影响系统性能的重要原因之一。本节介绍如何识别、诊断和处理慢SQL问题。

### 12.7.1 慢SQL的定义

**慢SQL阈值配置：**

- 开发/测试环境：100ms
- 生产标准环境：500ms
- 高性能要求环境：1000ms

### 12.7.2 慢SQL识别方法

**方法一：HikariCP 日志**


**方法三：MySQL 慢查询日志**

**方法四：ShardingSphere-SQL 审计**

### 12.7.3 慢SQL分析工具

**EXPLAIN 分析**

```sql
EXPLAIN SELECT * FROM t_order WHERE order_id = 123456;

-- 更详细的分析
```

**SQL 分析关键指标：**

- type：访问类型（ALL < index < range < ref < eq_ref < const）
- key：使用的索引

**Druid SQL 分析**

```java
    stmt.accept(visitor);
}
```

### 12.7.4 常见慢SQL场景与优化

**场景一：全表扫描**

```sql
-- 问题 SQL
SELECT * FROM t_order WHERE order_status = 'PENDING';

-- 优化方案：添加索引
CREATE INDEX idx_order_status ON t_order(order_status);

-- 如果只需要少量字段，使用覆盖索引
CREATE INDEX idx_order_status_id ON t_order(order_status, order_id);
```

**场景二：深分页**

```sql
-- 问题 SQL：OFFSET 大导致性能问题
SELECT * FROM t_order ORDER BY order_id LIMIT 1000000, 10;

-- 优化方案一：使用基于主键的范围查询
SELECT * FROM t_order WHERE order_id > 1000000 ORDER BY order_id LIMIT 10;

-- 优化方案二：使用延迟关联
SELECT t.* FROM t_order t 
INNER JOIN (SELECT order_id FROM t_order ORDER BY order_id LIMIT 1000000, 10) AS tmp
ON t.order_id = tmp.order_id;
```

**场景三：复杂 JOIN**

```sql
-- 问题 SQL：多表 JOIN
SELECT o.*, u.*, p.*
FROM t_order o
JOIN t_user u ON o.user_id = u.id
JOIN t_product p ON o.product_id = p.id
WHERE o.created_at > '2024-01-01';

-- 优化方案：
-- 1. 确保 JOIN 字段有索引
CREATE INDEX idx_order_user ON t_order(user_id);
CREATE INDEX idx_order_product ON t_order(product_id);
CREATE INDEX idx_order_created ON t_order(created_at);

-- 2. 拆分复杂查询
-- 3. 使用应用层JOIN代替数据库JOIN
```

**场景四：不当使用函数**

```sql
-- 问题 SQL：对索引列使用函数
SELECT * FROM t_order WHERE YEAR(created_at) = 2024;

-- 优化方案：使用日期范围
SELECT * FROM t_order WHERE created_at >= '2024-01-01' AND created_at < '2025-01-01';
```

**场景五：分片键缺失**

在 ShardingSphere 环境下，缺少分片键会导致全路由：

```sql
-- 问题 SQL：缺少分片键，全路由到所有分片
SELECT * FROM t_order WHERE order_status = 'PENDING';

-- 优化方案：添加分片键条件
SELECT * FROM t_order WHERE order_id = ? AND order_status = 'PENDING';

-- 或者修改分片策略，使用其他分片键
```

### 12.7.5 慢SQL处理流程

```
┌──────────────┐
│   识别慢SQL   │
└──────┬───────┘
       │
       ▼
```

### 12.8.5 常见配置误区

**误区一：连接池越大越好**

实际上，连接池过大会导致：

- 数据库并发压力增大
- 上下文切换增加
- 资源竞争加剧

正确做法：根据服务器资源，合理设置连接池大小。

**误区二：连接验证越频繁越好**

过于频繁的验证会影响性能：

- 验证间隔：30-60秒为宜
- 使用轻量级验证 SQL

**误区三：空闲连接保留时间越长越好**

长时间保留空闲连接会浪费资源：

- 低峰期及时收缩连接池
- 设置合理的 idleTimeout

**误区四：关闭连接自动提交**

自动提交会产生大量小事务：

- 批量操作使用手动提交
- 根据业务合理控制事务边界

```java
// 方案一：使用 try-with-resources
try (Connection conn = dataSource.getConnection()) {
    // 业务代码

// 方案二：使用封装工具类
public <T> T execute(ConnectionCallback<T> callback) {

        conn = dataSource.getConnection();
        return callback.doInConnection(conn);
    } finally {
        if (conn != null) {
            conn.close();
        }
    }
```

1. **连接池选择**：HikariCP 以其卓越的性能成为首选，Druid 则在监控和防护方面更胜一筹。

2. **配置参数**：连接池大小的计算需要综合考虑 CPU 核心数、数据库限制、业务并发特征等因素。HikariCP 的 leakDetectionThreshold 是发现连接泄漏的重要工具。

3. **分片环境**：每个数据节点对应独立的连接池，需要合理分配连接资源，避免单点成为瓶颈。

4. **主从架构**：读操作可以分散到从库，但需要关注主从延迟带来的数据一致性问题。

5. **慢SQL处理**：通过 EXPLAIN 分析执行计划，添加适当索引，避免全表扫描和深分页。

6. **性能测试**：使用 JMH、JMeter 等工具进行基准测试，建立性能基线，逐步调优。

7. **问题诊断**：连接池耗尽、响应时间增加、连接获取超时等问题需要系统性排查。

**最佳实践总结：**

- 生产环境建议使用 HikariCP，连接池大小控制在 20-50 之间
- 开启连接泄漏检测（leakDetectionThreshold 设置为 60 秒）
- 慢SQL阈值设置为 1 秒，持续监控和优化
- 分片环境下确保查询包含分片键，避免全路由
- 主从架构下对一致性要求高的查询强制走主库
- 定期进行性能测试和连接池状态监控

通过合理的连接池配置和持续的监控优化，可以确保 ShardingSphere-JDBC 系统在各种负载条件下保持稳定和高效。


```
高并发公式：连接池大小 = 预期并发数 × (平均响应时间 / 平均思考时间)

分片环境：总连接数 = 分片数量 × 单分片连接池大小 ≤ 数据库最大连接数 × 0.8

主从环境：主库连接池 ≈ 从库连接池总数 × 0.3
```
