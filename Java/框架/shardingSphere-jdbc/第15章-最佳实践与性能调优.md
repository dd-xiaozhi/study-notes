# 第15章 最佳实践与性能调优

## 15.1 分片键设计最佳实践

分片键（Sharding Key）的设计是 ShardingSphere-JDBC 数据分片中最关键的决策之一。合理的分片键设计能够最大化查询性能，避免跨分片操作带来的性能损耗；而不当的设计则可能导致数据倾斜、查询效率低下甚至业务无法实现。

### 15.1.1 分片键选择原则

**1. 高度区分度原则**

选择的分片键应当具有高度的区分度，能够将数据均匀分布到各个分片中。区分度越高，数据分布越均匀。

```java
// 好的选择：用户ID具有高度区分度
// 假设有100万用户，数据可以均匀分布
sharding-column: user_id

// 较差的选择：性别字段区分度极低
// 只能分成2个分片，严重数据倾斜
sharding-column: sex
```

**2. 业务查询高频访问原则**

分片键应当与业务中最频繁的查询条件一致。根据二八原则，80%的查询应当能够直接定位到单个分片。

```yaml
# 订单表按 user_id 分片
# 支持的查询场景：
# 1. 查询某用户的所有订单 ✓
# 2. 查询某段时间内某用户的订单 ✓
# 3. 查询某订单详情 ✓
# 4. 查询某时间段内所有订单 ✗（全分片扫描）
tables:
  t_order:
    actualDataNodes: ds_$->{0..7}.t_order_$->{0..15}
    databaseStrategy:
      standard:
        sharding-column: user_id
```

**3. 字段类型选择原则**

优先选择整型字段作为分片键，因为整数比较的效率远高于字符串比较。

```java
// 推荐：使用整型字段
sharding-column: order_id  // BIGINT 类型

// 可行：使用字符串字段（性能稍差）
sharding-column: order_code  // VARCHAR 类型

// 不推荐：使用日期时间字段
sharding-column: create_time  // DATETIME 类型
```

**4. 不可变或低变更频率原则**

分片键的值应当保持稳定，避免频繁更新。更新分片键会导致数据在不同分片间迁移。

```sql
-- 避免更新分片键
UPDATE t_order SET user_id = 'new_user' WHERE order_id = 123;  -- 危险！

-- 正确做法：通过逻辑删除标记
UPDATE t_order SET status = 'CANCELLED' WHERE order_id = 123;
```

### 15.1.2 分片键设计模式

**模式一：单一分片键（推荐）**

对于大多数场景，使用单一分片键是最佳选择。

```yaml
# 用户表按 user_id 分片
tables:
  t_user:
    actualDataNodes: ds_$->{0..3}.t_user
    databaseStrategy:
      standard:
        sharding-column: user_id
        precise-algorithm-class-name: com.example.sharding.UserIdShardingAlgorithm
```

```java
public class UserIdShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        long userId = shardingValue.getValue();
        int dbIndex = (int) (userId % 4);
        return "ds_" + dbIndex;
    }
}
```

**模式二：复合分片键**

当单一分片键无法满足业务需求时，可使用复合分片键。

```yaml
# 订单表按 (user_id, order_type) 复合分片
tables:
  t_order:
    actualDataNodes: ds_$->{0..7}.t_order_$->{0..15}
    databaseStrategy:
      complex:
        sharding-columns: user_id, order_type
        algorithm-class-name: com.example.sharding.ComplexOrderShardingAlgorithm
```

```java
public class ComplexOrderShardingAlgorithm implements ComplexKeysShardingAlgorithm {
    
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         ComplexKeysShardingValue shardingValue) {
        // 获取各分片键的值
        Long userId = shardingValue.getColumnNameAndRangeValuesMap()
            .get("user_id").iterator().next();
        String orderType = shardingValue.getColumnNameAndRangeValuesMap()
            .get("order_type").iterator().next();
        
        // 复合分片算法
        int dbIndex = (int) ((userId + orderType.hashCode()) % 8);
        int tableIndex = (int) (userId % 16);
        
        String targetTable = "t_order_" + tableIndex;
        return Collections.singletonList("ds_" + dbIndex + "." + targetTable);
    }
}
```

**模式三：业务拆分策略**

对于大型业务系统，可以考虑按业务线或租户进行分片。

```yaml
# 多租户系统按租户ID分片
tables:
  t_order:
    actualDataNodes: ds_$->{0..7}.t_order_$->{0..15}
    defaultDatabaseStrategy:
      standard:
        sharding-column: tenant_id
        precise-algorithm-class-name: com.example.sharding.TenantShardingAlgorithm
```

## 15.2 分片数量规划

分片数量的规划直接影响系统的容量和性能。合理的分片数量能够保证系统的扩展性，同时避免过多的分片带来的管理开销。

### 15.2.1 分片数量规划原则

**1. 容量预估**

根据数据增长预期，合理规划分片数量。

| 数据类型 | 单表容量建议 | 分片数规划依据 |
|---------|------------|---------------|
| 日志类 | 1000万~5000万 | 按月份分片 |
| 交易类 | 500万~1000万 | 按业务量分片 |
| 用户类 | 100万~500万 | 按ID范围分片 |
| 配置类 | <10万 | 不需要分片 |

**2. 节点数量计算公式**

```
分片数量 = ceil(数据总量预估 / 单分片容量) × 扩展系数
```

其中扩展系数通常取 1.5~2.0，以预留扩容空间。

```java
// 示例：订单表容量规划
public class ShardingCapacityCalculator {
    
    public static void main(String[] args) {
        // 业务参数
        long dailyOrderCount = 1000000;      // 每日订单量
        int daysToKeep = 730;                 // 数据保留天数
        long totalOrders = dailyOrderCount * daysToKeep;  // 7.3亿
        
        // 单表容量（建议不超过1000万）
        long singleTableCapacity = 10000000L;
        
        // 单分片节点数（每个库8张表）
        long tablesPerShard = 8;
        long singleShardCapacity = singleTableCapacity * tablesPerShard;  // 8000万
        
        // 基础分片数
        long baseShards = (long) Math.ceil((double) totalOrders / singleShardCapacity);
        
        // 扩展系数1.5
        double expansionFactor = 1.5;
        long requiredShards = (long) Math.ceil(baseShards * expansionFactor);
        
        System.out.println("预估总数据量: " + totalOrders + " 条");
        System.out.println("单分片容量: " + singleShardCapacity + " 条");
        System.out.println("基础分片数: " + baseShards);
        System.out.println("考虑扩展系数后的分片数: " + requiredShards);
    }
}
```

**3. 分片均匀性**

选择合适的分片算法，确保数据均匀分布。

```java
// 好的分片算法：数据均匀分布
public class GoodShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        long value = shardingValue.getValue();
        // 使用哈希取模，数据分布均匀
        int index = (int) (value % 4);
        return "ds_" + index;
    }
}

// 差的分片算法：数据倾斜
public class BadShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        long value = shardingValue.getValue();
        // 按范围分片，会导致数据倾斜
        if (value < 1000000) {
            return "ds_0";
        } else {
            return "ds_1";
        }
    }
}
```

### 15.2.2 库表分片规划建议

**1. 分库优先原则**

当分片数量较多时，优先使用分库策略，可以获得更好的并行处理能力。

```yaml
# 推荐：分库策略（4库 × 8表 = 32 分片）
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3

tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..7}
    # 分库不分表的情况
    actualDataNodes: ds_$->{0..7}.t_order  # 8库单表
```

**2. 分片数量配比**

```yaml
# 场景1：数据量大但查询简单的场景（分库优先）
# 4库 × 4表 = 16 分片
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3
tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..3}

# 场景2：数据量巨大且需要分表的场景
# 4库 × 16表 = 64 分片
tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..15}

# 场景3：超高并发写入场景
# 8库 × 4表 = 32 分片（更多数据库节点分散压力）
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3
  - ds_4
  - ds_5
  - ds_6
  - ds_7
tables:
  t_order:
    actualDataNodes: ds_$->{0..7}.t_order_$->{0..3}
```

```yaml
  # 每个数据库的表数
```

## 15.3 避免跨分片查询

跨分片查询是分库分表场景下最大的性能杀手。跨分片查询需要将请求广播到所有分片，然后合并结果，当数据量巨大时，这种操作的延迟可能是单分片查询的数十倍甚至数百倍。

### 15.3.1 跨分片查询的类型

**1. 全分片扫描查询**

```sql
-- 按订单ID分片，但查询所有状态为待支付的订单
-- 这会触发全分片扫描
SELECT * FROM t_order WHERE status = 'PENDING';
```

**2. 跨分片关联查询**

```sql
-- 订单表按 user_id 分片，订单明细表按 order_id 分片
-- 跨分片关联导致笛卡尔积
SELECT o.*, d.* 
FROM t_order o 
JOIN t_order_detail d ON o.order_id = d.order_id
WHERE o.user_id = 12345;
```

**3. 跨分片聚合查询**

```sql
-- 需要扫描所有分片才能得到准确的结果
SELECT COUNT(*), SUM(amount), AVG(amount) 
FROM t_order 
WHERE create_time >= '2024-01-01';
```

### 15.3.2 避免跨分片查询的策略

**策略一：设计良好的分片键**

```yaml
# 订单表和订单明细表都按 user_id 分片
tables:
  t_order:
    actualDataNodes: ds_$->{0..7}.t_order_$->{0..15}
    databaseStrategy:
      standard:
        sharding-column: user_id
        
  t_order_detail:
    actualDataNodes: ds_$->{0..7}.t_order_detail_$->{0..15}
    databaseStrategy:
      standard:
        sharding-column: user_id  # 统一分片键
```

```java
// 查询某用户订单及明细，可定位到单一分片
public List<OrderDetailVO> queryOrderDetails(Long userId, Long orderId) {
    // 由于 t_order 和 t_order_detail 都按 user_id 分片
    // ShardingSphere 可以直接定位到 ds_X.t_order_Y 和 ds_X.t_order_detail_Y
    String sql = "SELECT o.*, d.* FROM t_order o " +
                 "JOIN t_order_detail d ON o.order_id = d.order_id " +
                 "WHERE o.user_id = ? AND o.order_id = ?";
    return jdbcTemplate.query(sql, userId, orderId);
}
```

**策略二：使用绑定表（Binding Table）**

绑定表是具有相同分片规则的表，查询时可以确保在同一分片内完成。

```yaml
# 配置绑定表
bindingTables:
  - t_order,t_order_detail,t_order_item  # 这三张表互为绑定表
  
tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..7}
    databaseStrategy:
      standard:
        sharding-column: user_id
        
  t_order_detail:
    actualDataNodes: ds_$->{0..3}.t_order_detail_$->{0..7}
    databaseStrategy:
      standard:
        sharding-column: user_id  # 与 t_order 相同的分片键
        
  t_order_item:
    actualDataNodes: ds_$->{0..3}.t_order_item_$->{0..7}
    databaseStrategy:
      standard:
        sharding-column: user_id  # 与 t_order 相同的分片键
```

```java
// 绑定表查询示例
public List<OrderVO> queryOrderWithItems(Long userId, Long orderId) {
    // ShardingSphere 会自动将查询路由到同一分片
    String sql = "SELECT o.*, d.*, i.* " +
                 "FROM t_order o " +
                 "LEFT JOIN t_order_detail d ON o.order_id = d.order_id " +
                 "LEFT JOIN t_order_item i ON d.detail_id = i.detail_id " +
                 "WHERE o.user_id = ? AND o.order_id = ?";
    return jdbcTemplate.query(sql, userId, orderId);
}
```

**策略三：字段冗余设计**

对于需要跨分片关联查询的场景，可以考虑字段冗余设计。

```yaml
# 订单表按 order_id 分片
tables:
  t_order:
    actualDataNodes: ds_$->{0..7}.t_order
    tableStrategy:
      standard:
        sharding-column: order_id
        
  # 冗余设计：商家表按 merchant_id 分片
  t_merchant:
    actualDataNodes: ds_$->{0..3}.t_merchant
    tableStrategy:
      standard:
        sharding-column: merchant_id
```

```sql
-- 订单表冗余商家名称，避免跨分片关联
CREATE TABLE t_order (
    order_id BIGINT PRIMARY KEY,
    user_id BIGINT,
    merchant_id BIGINT,
    merchant_name VARCHAR(100),  -- 冗余字段
    amount DECIMAL(10,2),
    create_time DATETIME
);
```

**策略四：数据汇总表**

对于统计分析类查询，使用定期刷新的汇总表。

```sql
-- 创建日汇总表（按天分片）
CREATE TABLE t_order_daily_summary (
    summary_date DATE,           -- 分片键
    merchant_id BIGINT,
    order_count INT,
    total_amount DECIMAL(15,2),
    PRIMARY KEY (summary_date, merchant_id)
);

-- 创建月汇总表
CREATE TABLE t_order_monthly_summary (
    summary_month VARCHAR(7),    -- 格式：2024-01
    merchant_id BIGINT,
    order_count INT,
    total_amount DECIMAL(15,2),
    PRIMARY KEY (summary_month, merchant_id)
);
```

```java
// 定时任务刷新汇总数据
@Scheduled(cron = "0 5 0 * * ?")  // 每天凌晨0:05执行
public void refreshDailySummary() {
    String sql = "INSERT INTO t_order_daily_summary " +
                 "SELECT DATE(create_time), merchant_id, " +
                 "       COUNT(*), SUM(amount) " +
                 "FROM t_order " +
                 "WHERE create_time >= CURRENT_DATE " +
                 "GROUP BY merchant_id";
    jdbcTemplate.execute(sql);
}
```

```java
// 场景：用户想查询历史订单（跨多分片）
// 限制返回结果，避免内存溢出
public List<Order> queryHistoricalOrders(Long userId, int offset, int limit) {
    // 强制限制最大返回条数
    int maxLimit = Math.min(limit, 1000);
    
    String sql = "SELECT * FROM t_order WHERE user_id = ? " +
                 "ORDER BY create_time DESC LIMIT ? OFFSET ?";
    return jdbcTemplate.query(sql, userId, maxLimit, offset);
}
```

**技巧三：异步并行查询**

```java
// 使用 CompletableFuture 并行查询多个分片
public List<Order> parallelQueryOrders(Long userId) {
    ExecutorService executor = Executors.newFixedThreadPool(8);
    List<CompletableFuture<List<Order>>> futures = new ArrayList<>();
    
    for (int i = 0; i < 8; i++) {
        final int dbIndex = i;
        CompletableFuture<List<Order>> future = CompletableFuture.supplyAsync(() -> {
            return queryOrdersFromShard(userId, dbIndex);
        }, executor);
        futures.add(future);
    }
    
    // 合并结果
    return futures.stream()
        .flatMap(f -> f.join().stream())
        .collect(Collectors.toList());
}
```

## 15.4 绑定表使用

绑定表（Bingding Table）是 ShardingSphere 中用于优化多表关联查询的重要特性。通过配置绑定表，可以确保关联查询在同一分片内完成，避免跨分片查询带来的性能损耗。

### 15.4.1 绑定表概念

绑定表是指具有相同分片规则的表，它们之间的关联查询可以直接定位到同一分片，无需广播到所有分片。

```yaml
# t_order 和 t_order_item 都按 user_id 分片，它们互为绑定表
bindingTables:
  - t_order,t_order_item
```

### 15.4.2 绑定表配置示例

**基础配置**

```yaml
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3

tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..7}
    databaseStrategy:
      standard:
        sharding-column: user_id
        precise-algorithm-class-name: com.example.sharding.OrderUserIdShardingAlgorithm
    tableStrategy:
      standard:
        sharding-column: user_id
        precise-algorithm-class-name: com.example.sharding.OrderUserIdShardingAlgorithm
        
  t_order_item:
    actualDataNodes: ds_$->{0..3}.t_order_item_$->{0..7}
    databaseStrategy:
      standard:
        sharding-column: user_id  # 必须与 t_order 相同
        precise-algorithm-class-name: com.example.sharding.OrderUserIdShardingAlgorithm
    tableStrategy:
      standard:
        sharding-column: user_id  # 必须与 t_order 相同
        precise-algorithm-class-name: com.example.sharding.OrderUserIdShardingAlgorithm

# 配置绑定表关系
bindingTables:
  - t_order,t_order_item
```

**关联分片算法**

```java
public class OrderUserIdShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    
    private static final int SHARDING_DATABASE_SIZE = 4;
    private static final int SHARDING_TABLE_SIZE = 8;
    
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        Long userId = shardingValue.getValue();
        
        // 计算分库索引
        int dbIndex = (int) (userId % SHARDING_DATABASE_SIZE);
        
        // 计算分表索引
        int tableIndex = (int) (userId % SHARDING_TABLE_SIZE);
        
        String logicTableName = shardingValue.getLogicTableName();
        String targetName = logicTableName + "_" + tableIndex;
        
        return "ds_" + dbIndex + "." + targetName;
    }
}
```

### 15.5.1 常见分布式ID方案对比

| 方案 | 生成方式 | 趋势递增 | 性能 | 依赖 | 适用场景 |
|------|---------|---------|------|------|---------|
| UUID | 本地生成 | 否 | 极高 | 无 | 内部使用、不对外暴露 |

| Leaf | 代理服务 | 是 | 高 | ZooKeeper | 高可用要求 |

### 15.5.2 Snowflake 算法详解

Snowflake 是 Twitter 提出的分布式ID生成算法，具有高性能、低延迟、趋势递增的特点。

**结构分析**

```
64 bit = 1 bit（符号位） + 41 bit（时间戳） + 10 bit（机器ID） + 12 bit（序列号）
```

```java
public class SnowflakeIdGenerator {
    
    // 起始时间戳：2024-01-01 00:00:00
    private final long twepoch = 1704067200000L;
    
    // 机器ID占用的位数
    private final long workerIdBits = 10L;
    // 最大机器ID
    private final long maxWorkerId = ~(-1L << workerIdBits);
    
    // 序列号占用的位数
    private final long sequenceBits = 12L;
    // 序列号最大值
    private final long sequenceMask = ~(-1L << sequenceBits);
    
    // 时间戳左移位数
    private final long timestampLeftShift = sequenceBits + workerIdBits;
    
    private long workerId;
    private long sequence = 0L;
    private long lastTimestamp = -1L;
    
    public SnowflakeIdGenerator(long workerId) {
        if (workerId > maxWorkerId || workerId < 0) {
            throw new IllegalArgumentException("Worker ID can't be greater than " + maxWorkerId);
        }
        this.workerId = workerId;
    }
    
    public synchronized long nextId() {
        long timestamp = timeGen();
        
        if (timestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards");
        }
        
        if (lastTimestamp == timestamp) {
            sequence = (sequence + 1) & sequenceMask;
            if (sequence == 0) {
                timestamp = tilNextMillis(lastTimestamp);
            }
        } else {
            sequence = 0L;
        }
        
        lastTimestamp = timestamp;
        
        return ((timestamp - twepoch) << timestampLeftShift)
                | (workerId << sequenceBits)
                | sequence;
    }
    
    private long tilNextMillis(long lastTimestamp) {
        long timestamp = timeGen();
        while (timestamp <= lastTimestamp) {
            timestamp = timeGen();
        }
        return timestamp;
    }
    
    private long timeGen() {
        return System.currentTimeMillis();
    }
}
```

```java
import org.apache.shardingsphere.sharding.spi.KeyGenerateAlgorithm;

public class CustomIdGenerator implements KeyGenerateAlgorithm {
    
    private Properties props;
    private AtomicLong sequence = new AtomicLong(0);
    private long workerId;
    
    @Override
    public void init(Properties props) {
        this.workerId = Long.parseLong(props.getProperty("worker-id", "0"));
    }
    
    @Override
    public Comparable<?> generateKey() {
        return generateSnowflakeId();
    }
    
    private synchronized long generateSnowflakeId() {
        long timestamp = System.currentTimeMillis() - 1704067200000L;
        long sequence = this.sequence.getAndIncrement() & 0xFFF;
        return (timestamp << 22) | (workerId << 12) | sequence;
    }
    
    @Override
    public Properties getProps() {
        return props;
    }
    
    @Override
    public String getType() {
        return "CUSTOM_SNOWFLAKE";
    }
}
```

## 15.7 SQL编写规范

在 ShardingSphere-JDBC 环境下，SQL编写的规范性直接影响查询性能和系统稳定性。本节详细介绍分片环境下的SQL编写规范。

### 15.7.1 分片键操作规范

**1. 分片键条件必须精确**

```sql
-- 推荐：使用分片键精确查询
SELECT * FROM t_order WHERE order_id = 123456;

-- 推荐：使用分片键 IN 查询
SELECT * FROM t_order WHERE user_id IN (1, 2, 3);

-- 不推荐：使用分片键范围查询（会触发全分片扫描）
SELECT * FROM t_order WHERE user_id BETWEEN 1 AND 1000;

-- 避免：分片键进行函数运算
SELECT * FROM t_order WHERE DATE(create_time) = '2024-01-01';
```

**2. 分片键值类型必须一致**

```java
// 正确：类型一致
Long userId = 12345L;
String sql = "SELECT * FROM t_order WHERE user_id = ?";

// 错误：类型不一致导致索引失效
String userId = "12345";  // 字符串类型
String sql = "SELECT * FROM t_order WHERE user_id = ?";  // 可能导致类型转换
```

### 15.7.2 查询规范

**1. 避免 SELECT *** 

```sql
-- 推荐：指定需要的字段
SELECT order_id, user_id, amount, status FROM t_order WHERE user_id = ?;

-- 不推荐：SELECT *
SELECT * FROM t_order WHERE user_id = ?;
```

**2. 使用合理的分页**

## 15.8 分页查询优化

分页查询是 Web 应用中最常见的查询场景之一。在分库分表环境下，不当的分页查询可能导致严重的性能问题。

### 15.8.1 分页查询原理

**普通分页查询**

```sql
-- Page 1
SELECT * FROM t_order WHERE user_id = ? ORDER BY create_time DESC LIMIT 10 OFFSET 0;

-- Page 2
SELECT * FROM t_order WHERE user_id = ? ORDER BY create_time DESC LIMIT 10 OFFSET 10;
```

在 ShardingSphere 中，分页查询会路由到包含该用户数据的分片。如果用户数据分布在多个分片，ShardingSphere 会从各分片查询数据，然后在 ShardingSphere-JDBC 层进行归并排序。

### 15.8.2 分页查询问题

**1. 深度分页问题**

```java
// 问题：深度分页查询性能极差
public List<Order> queryOrdersBad(Long userId, int page, int pageSize) {
    int offset = page * pageSize;  // Page 1000 时，offset = 10000
    String sql = "SELECT * FROM t_order WHERE user_id = ? " +
                 "ORDER BY create_time DESC LIMIT ? OFFSET ?";
    return jdbcTemplate.query(sql, userId, pageSize, offset);
}

// 深度分页的查询流程：
// 1. 查询 Page 1000 时，需要跳过前 9990 条数据
// 2. 如果数据分散在 8 个分片，每个分片需要跳过约 1250 条
// 3. 数据库需要先排序，然后才能获取 limit/offset 的数据
```

**2. 分页翻页性能骤降**

| 页码 | 预估延迟 | 原因 |
|-----|---------|------|
| Page 1 | 5ms | 直接获取前10条 |
| Page 100 | 50ms | 需要跳过990条 |
| Page 1000 | 500ms | 需要跳过9990条 |
| Page 10000 | 5000ms | 需要跳过99990条 |

### 15.8.3 分页优化方案

**方案一：游标分页（推荐）**

```java
// 使用游标分页，避免深度分页问题
public class CursorPageQuery {
    
    public List<Order> queryByCursor(Long userId, Long lastOrderId, int pageSize) {
        String sql;
        if (lastOrderId == null) {
            // 首次查询
            sql = "SELECT * FROM t_order WHERE user_id = ? " +
                  "ORDER BY order_id DESC LIMIT ?";
            return jdbcTemplate.query(sql, userId, pageSize);
        } else {
            // 游标查询：基于上一页最后一条记录的ID
            sql = "SELECT * FROM t_order WHERE user_id = ? AND order_id < ? " +
                  "ORDER BY order_id DESC LIMIT ?";
            return jdbcTemplate.query(sql, userId, lastOrderId, pageSize);
        }
    }
}
```

```java
            }
```

### 15.10.1 分片环境索引设计原则

```java
     * 分片环境索引创建脚本生成
     */
    public String generateIndexDDL(String tableName, String indexName, 
                                    List<String> columns) {

        // 获取表的分片信息
        ShardingRuleConfiguration config = getShardingRuleConfig(tableName);

            String ds = parts[0];
            String table = parts[1];

                indexName, ds, table, String.join(", ", columns)));

        // 1. 创建新索引
        String createSql = String.format(
            "ALTER TABLE %s ADD INDEX %s (%s)", 
            tableName, newIndexName, "column_list");

            "ALTER TABLE %s RENAME INDEX %s TO %s",
            tableName, indexName, newIndexName + "_old");
        jdbcTemplate.execute(renameSql);
        
        // 3. 删除旧索引
        String dropSql = String.format(
            "ALTER TABLE %s DROP INDEX %s", 
            tableName, newIndexName + "_old");
        jdbcTemplate.execute(dropSql);
```

### 15.11.4 分片扩容迁移

**扩容策略：一致性哈希**

```java
public class ConsistentHashMigration {
    
    private final int virtualNodes;
    private final TreeMap<Long, String> hashRing;
    
    public ConsistentHashMigration(int virtualNodes) {
        this.virtualNodes = virtualNodes;
        this.hashRing = new TreeMap<>();
    }
    
    /**
     * 添加新节点
     */
    public void addNode(String node) {
        for (int i = 0; i < virtualNodes; i++) {
            long hash = hash(node + "_" + i);
            hashRing.put(hash, node);
        }
    }
    
    /**
     * 迁移数据：根据 key 计算新旧节点
     */
    public MigrationPlan createMigrationPlan(Object key) {
        long hash = hash(key.toString());
        
        // 旧环上的节点
        Map.Entry<Long, String> oldEntry = hashRing.floorEntry(hash);
        String oldNode = oldEntry != null ? oldEntry.getValue() : hashRing.lastEntry().getValue();
        
        // 新环上的节点
        String newNode = getNode(hash);
        
        return new MigrationPlan(key, oldNode, newNode);
    }
    
    /**
     * 计算数据应该路由到哪个节点
     */
    private String getNode(long hash) {
        Map.Entry<Long, String> entry = hashRing.ceilingEntry(hash);
        if (entry == null) {
            entry = hashRing.firstEntry();
        }
        return entry.getValue();
    }
}
```

## 15.12 扩容缩容方案

分库分表的一个重要优势是可以通过扩容来提升系统容量。本节介绍常见的扩容缩容方案及其实现。

### 15.12.1 扩容策略

**1. 垂直扩容**

```
增加单个数据库实例的资源（CPU、内存、磁盘）
优点：无需修改分片规则
缺点：有物理上限
适用：分片数量已足够，但单分片负载较高
```

**2. 水平扩容（增加分片数）**

```
从 4 分片扩展到 8 分片
优点：理论上无上限
缺点：需要数据迁移
适用：数据量持续增长
```

### 15.12.2 扩容方案实现

**方案一：倍数扩容**

```yaml
# 扩容前：4 库
```

```java
public class ModShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    
    // 扩容前的分片数
    private static final int OLD_SHARD_COUNT = 4;
    // 扩容后的分片数
    private static final int NEW_SHARD_COUNT = 8;
    
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        Long userId = shardingValue.getValue();
        
        // 扩容后使用新的分片数
        int dbIndex = (int) (userId % NEW_SHARD_COUNT);
        return "ds_" + dbIndex;
    }
}
```

**方案二：一致性哈希扩容**

```java
public class ConsistentHashShardingAlgorithm {
    
    private final TreeMap<Long, String> virtualNodes = new TreeMap<>();
    private final int virtualNodeCount;
    
    public ConsistentHashShardingAlgorithm(int virtualNodeCount) {
        this.virtualNodeCount = virtualNodeCount;
        initVirtualNodes();
    }
    
    private void initVirtualNodes() {
        // 初始节点
        String[] nodes = {"ds_0", "ds_1", "ds_2", "ds_3"};
        for (String node : nodes) {
            addVirtualNode(node);
        }
    }
    
    public void addNode(String node) {
        for (int i = 0; i < virtualNodeCount; i++) {
            long hash = hash(node + "_VN_" + i);
            virtualNodes.put(hash, node);
        }
    }
    
    public String getShardingNode(Long userId) {
        long hash = hash(userId.toString());
        Map.Entry<Long, String> entry = virtualNodes.ceilingEntry(hash);
        if (entry == null) {
            entry = virtualNodes.firstEntry();
        }
        return entry.getValue();
    }
    
    /**
     * 计算迁移计划
     */
    public Map<String, List<Long>> calculateMigration(String newNode) {
        Map<String, List<Long>> migrationPlan = new HashMap<>();
        addNode(newNode);
        
        // 重新计算每个用户ID的路由，找出需要迁移的数据
        // 这需要结合数据迁移服务使用
        return migrationPlan;
    }
}
```

### 15.12.3 缩容方案

**注意事项**

```
1. 缩容风险高于扩容，需要谨慎操作
2. 缩容前必须确保数据量在目标分片容量内
3. 建议使用灰度缩容，逐步迁移
4. 缩容后无法回退，必须确保数据完整
```

**缩容执行流程**

```java
     * 缩容执行

            .mapToObj(i -> "ds_" + i)
            .collect(Collectors.toList());
        
        // 迁移流程：
        // 1. 创建新分片配置
        // 2. 灰度切换流量
        // 3. 等待数据同步完成
        // 4. 清理旧分片数据
    }

     * 验证数据完整性
```

## 总结

本章详细介绍了 ShardingSphere-JDBC 最佳实践与性能调优的各个方面：

1. **分片键设计**：遵循高度区分度、高频访问、类型选择和稳定性原则
2. **分片数量规划**：根据容量预估和扩展系数合理规划
3. **避免跨分片查询**：通过绑定表、字段冗余、汇总表等策略优化
4. **绑定表使用**：配置具有相同分片规则的表进行高效关联
5. **分布式ID使用**：推荐使用 Snowflake 算法生成趋势递增的唯一ID
6. **事务使用**：根据一致性要求和性能需求选择合适的事务类型
7. **SQL编写规范**：遵循分片键操作、查询优化和DML操作规范
8. **分页查询优化**：推荐使用游标分页，避免深度分页问题
9. **批量操作优化**：按分片键分组，合理控制批次大小
10. **索引设计**：创建合理的单字段和复合索引
11. **数据迁移方案**：根据业务特点选择停机迁移或在线迁移
12. **扩容缩容方案**：采用一致性哈希等策略实现平滑扩缩容
13. **性能调优检查清单**：系统化地进行性能优化和问题排查

通过遵循这些最佳实践，可以构建高性能、高可用的 ShardingSphere-JDBC 分库分表系统。
