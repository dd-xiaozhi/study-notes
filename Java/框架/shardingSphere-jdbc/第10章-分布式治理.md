# 第10章 分布式治理

## 10.1 概述

分布式治理是 ShardingSphere-JDBC 在生产环境中不可或缺的核心能力。随着微服务架构的普及，单一数据库实例已经无法满足业务需求，业务系统通常需要连接多个数据源、分片库和集群实例。在这种情况下，如何统一管理配置、协调分布式操作、保证数据一致性和系统高可用，就成为了分布式治理的核心目标。

ShardingSphere-JDBC 的分布式治理能力主要包含以下几个维度：

1. **配置中心/注册中心**：统一管理配置元数据，支持配置持久化和动态更新
2. **数据源治理**：管理多个数据源的连接、健康检查和故障转移
3. **分片策略治理**：动态调整分片规则而无需重启应用
4. **安全治理**：密码加密、敏感数据保护
5. **高可用保障**：熔断器、分布式锁等机制保证系统稳定性

本章将深入剖析这些治理能力，帮助读者掌握在生产环境中部署和运维 ShardingSphere-JDBC 的核心技能。

## 10.2 配置中心与注册中心

### 10.2.1 概念解析

在分布式系统中，配置中心（Configuration Center）和注册中心（Registry Center）是两个既相关又有所区别的概念。

**注册中心**的主要职责是服务发现和健康检查。在 ShardingSphere-JDBC 场景中，注册中心用于：
- 注册数据源节点信息
- 监测各分片节点的存活状态
- 提供服务节点的列表查询
- 实现故障自动发现和转移

**配置中心**的核心职责是配置管理，包括：
- 存储和分发配置元数据
- 支持配置的版本管理和回滚
- 配置变更的实时推送
- 多环境配置隔离

在实际应用中，很多注册中心和配置中心是合并实现的，例如 ZooKeeper、Nacos、Etcd 等都同时提供了两种能力。ShardingSphere-JDBC 将它们统称为"注册中心"，但在内部实现中会区分配置存储和服务发现两个功能模块。

### 10.2.2 ZooKeeper

Apache ZooKeeper 是 Apache Hadoop 生态系统中的一员，最初是为 Hadoop 分布式协调服务设计的，后来广泛应用于各种分布式系统中。ZooKeeper 采用了经典的 Paxos 算法（ZAB 协议）来保证分布式一致性，具有以下特点：

- **顺序一致性**：从同一个客户端发起的请求会严格按照发送顺序执行
- **原子性**：更新操作要么成功要么失败，不存在中间状态
- **单一视图**：每个客户端看到的系统状态是一致的
- **高可用性**：采用集群部署，只要半数以上节点正常就能提供服务

#### ZooKeeper 数据模型

ZooKeeper 采用了层次化的命名空间（Namespace），类似于文件系统的目录结构：

```
/shardingsphere
├── /datasources          # 数据源配置
├── /sharding             # 分片规则配置
├── /encrypt              # 加密规则配置
└── /governance           # 治理元数据
```

每个节点称为 ZNode，可以存储少量数据（默认限制为 1MB）。ZNode 有四种类型：
- **持久节点（PERSISTENT）**：创建后一直存在，直到被主动删除
- **临时节点（EPHEMERAL）**：与客户端会话绑定，会话断开后自动删除
- **顺序节点（SEQUENTIAL）**：节点名后会追加递增序号
- **临时顺序节点（EPHEMERAL_SEQUENTIAL）**：临时节点 + 顺序特性

#### ShardingSphere-JDBC 集成 ZooKeeper

在 ShardingSphere-JDBC 中使用 ZooKeeper 作为注册中心，需要添加以下 Maven 依赖：

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-registry-zookeeper-curator</artifactId>
    <version>${shardingsphere.version}</version>
</dependency>
```

配置示例：

```yaml
registry:
  type: ZooKeeper
  namespace: shardingsphere
  server-lists: localhost:2181,localhost:2182,localhost:2183
  props:
    connect.timeout.ms: 5000
    session.timeout.ms: 60000
    digest: ''
    operation.timeout.ms: 30000
    # 指数退避重试策略参数
    max.retries: 3
    retry.interval.ms: 1000
    exponential.backoff.sleep.ms: 500
```

关键配置说明：

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| type | 注册中心类型 | ZooKeeper |
| namespace | 命名空间，用于隔离不同环境 | shardingsphere |
| server-lists | ZooKeeper 服务器列表，逗号分隔 | - |
| connect.timeout.ms | 连接超时时间 | 5000 |
| session.timeout.ms | 会话超时时间 | 60000 |
| digest | 权限认证信息，格式为 user:password | 空（无认证） |
| operation.timeout.ms | 操作超时时间 | 30000 |
| max.retries | 最大重试次数 | 3 |
| retry.interval.ms | 重试间隔时间 | 1000 |

#### ZooKeeper 集群架构

生产环境中 ZooKeeper 必须以集群方式部署，推荐使用 3 或 5 个节点：

```
                    ┌─────────────────┐
                    │     Client      │
                    └────────┬────────┘
                             │
                    ┌────────▼────────┐
                    │   ZooKeeper     │
                    │     Client      │
                    └────────┬────────┘
                             │
         ┌───────────────────┼───────────────────┐
         │                   │                   │
    ┌────▼────┐        ┌────▼────┐        ┌────▼────┐
    │ Leader  │        │Follower │        │Follower │
    │(Write)  │◄──────►│(Read)   │◄──────►│(Read)   │
    └────┬────┘        └─────────┘        └─────────┘
         │
    ┌────▼────┐
    │  Data   │
    │  Store  │
    └─────────┘
```

ZooKeeper 集群中会有一个 Leader 节点负责处理写请求，所有写操作都要通过 Leader 完成，然后同步到 Follower 节点。读请求可以由任何节点处理，具有更好的性能。

### 10.2.3 Nacos

Nacos 是阿里巴巴开源的动态服务发现、配置管理和服务管理平台。相比 ZooKeeper，Nacos 提供了更现代化的 REST API 和更友好的管理界面，在云原生时代应用广泛。

Nacos 的核心能力：

1. **服务发现**：支持 DNS 和 RPC 两种服务发现方式
2. **配置管理**：支持配置的集中管理和动态刷新
3. **多环境隔离**：通过 Namespace 和 Group 实现配置隔离
4. **高可用**：支持单机、集群和多活部署模式

#### ShardingSphere-JDBC 集成 Nacos

添加 Maven 依赖：

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-registry-nacos</artifactId>
    <version>${shardingsphere.version}</version>
</dependency>
```

配置示例：

```yaml
registry:
  type: Nacos
  namespace: shardingphere
  server-lists: localhost:8848
  props:
    group: SHARDINGSPHERE_DEFAULT_GROUP
    connectTimeout: 3000
    socketTimeout: 5000
    # Nacos 命名空间 ID（非命名空间名称）
    namespaceId: 0de24f2a-4a0e-4b2f-9e3d-8c1f7a3b2d1e
```

关键配置说明：

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| type | 注册中心类型 | Nacos |
| namespace | Nacos 命名空间 ID，用于隔离环境 | shardingphere |
| server-lists | Nacos 服务器地址 | - |
| group | 分组名称 | SHARDINGSPHERE_DEFAULT_GROUP |
| connectTimeout | 连接超时时间（毫秒） | 3000 |
| socketTimeout | Socket 超时时间（毫秒） | 5000 |
| namespaceId | 命名空间 ID | public |

#### Nacos 数据模型

Nacos 的数据模型采用以下层级结构：

```
Registry (实例级别)
├── 服务（Service）
│   ├── 实例（Instance）
│   └── 集群（Cluster）
│
Configuration (配置级别)
├── 命名空间（Namespace）
├── 分组（Group）
└── 数据ID（Data ID）
```

在 ShardingSphere-JDBC 与 Nacos 的集成中：
- **Namespace** 对应不同的环境（如 dev、test、prod）
- **Group** 对应不同的配置分组（默认为 SHARDINGSPHERE_DEFAULT_GROUP）
- **Data ID** 对应具体的配置数据，如数据源配置、分片规则等

### 10.2.4 Etcd

Etcd 是 CoreOS 开发的分布式键值存储系统，基于 Raft 共识算法实现了强一致性。Etcd 是 Kubernetes 的核心组件之一，被广泛应用于服务发现、配置共享和分布式锁等场景。

Etcd 的特点：
- **强一致性**：基于 Raft 协议，保证数据一致性
- **高可用**：支持集群部署，自动故障转移
- **简单易用**：提供 gRPC 和 HTTP API
- **安全认证**：支持 TLS 加密和 RBAC 权限控制

#### ShardingSphere-JDBC 集成 Etcd

添加 Maven 依赖：

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-registry-etcd</artifactId>
    <version>${shardingsphere.version}</version>
</dependency>
```

配置示例：

```yaml
registry:
  type: Etcd
  server-lists: localhost:2379,localhost:2378
  props:
    # 连接 Etcd 的超时时间
    connect.timeout.ms: 3000
    # 等待连接建立的最大时间
    connection.timeout.ms: 5000
    # 租约存活时间（秒）
    lease.ttl: 45
    # 等待锁的最大时间（毫秒）
    lock.timeout.millis: 30000
    # Etcd 最大流控窗口
    max.stream.window.size: 524288
```

关键配置说明：

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| type | 注册中心类型 | Etcd |
| server-lists | Etcd 服务器列表 | - |
| connect.timeout.ms | 连接超时时间 | 3000 |
| connection.timeout.ms | 连接建立超时 | 5000 |
| lease.ttl | 租约存活时间（秒） | 45 |
| lock.timeout.millis | 分布式锁等待超时 | 30000 |
| max.stream.window.size | 最大流控窗口 | 524288 |

### 10.2.5 注册中心对比

| 特性 | ZooKeeper | Nacos | Etcd |
|------|-----------|-------|------|
| 一致性算法 | ZAB (Paxos 变种) | Raft | Raft |
| 客户端协议 | Zookeeper Client | HTTP/DNS | gRPC |
| 配置推送 | Watch 机制 | Long Polling | Watch |
| 权限控制 | ACL | RBAC | RBAC |
| 管理界面 | 无（需第三方） | Web UI | 无（需第三方） |
| 多语言支持 | 原生 Java/C | 多语言 SDK | 多语言 SDK |
| 云原生友好度 | 一般 | 高 | 高 |
| 典型应用 | Hadoop 生态 | 微服务架构 | Kubernetes |
| 学习曲线 | 较陡 | 平缓 | 中等 |

**选型建议**：
- 如果已经使用 ZooKeeper（Hadoop 生态），继续使用 ZooKeeper
- 如果是 Spring Cloud 项目，优先选择 Nacos（生态集成更好）
- 如果是 Kubernetes 环境，优先选择 Etcd
- 如果追求配置管理的现代化体验，选择 Nacos

## 10.3 配置持久化

### 10.3.1 配置持久化的意义

在分布式系统中，配置持久化是配置中心的核心功能之一。ShardingSphere-JDBC 将配置存储在注册中心，具有以下意义：

1. **配置集中管理**：所有分片节点共享同一份配置，保证配置一致性
2. **配置高可用**：注册中心通常是集群部署，配置不会因单点故障丢失
3. **配置版本化**：支持配置变更历史回溯
4. **配置热更新**：无需重启应用即可动态生效

### 10.3.2 配置持久化模型

ShardingSphere-JDBC 的配置在注册中心以树形结构存储，以 ZooKeeper 为例：

```
/shardingsphere
├── /schemas
│   └── /sharding_db
│       ├── /datasources
│       │   └── /ds_0 (数据源配置 JSON)
│       │   └── /ds_1 (数据源配置 JSON)
│       ├── /rules
│       │   ├── /sharding
│       │   │   └── /algorithm
│       │   │       └── /mod (分片算法)
│       │   └── /encrypt
│       │       └── /algorithm
│       └── /props (属性配置)
└── /instance
    └── /registry (实例注册信息)
```

配置以 JSON 格式存储，包含数据源配置、分片规则、加密规则等完整信息。

### 10.3.3 配置持久化实现

ShardingSphere-JDBC 的配置持久化通过 RegistryRepository 接口实现，主要方法包括：

```java
public interface RegistryRepository {

    /**
     * 获取配置值
     */
    String get(String key);

    /**
     * 保存配置值
     */
    void persist(String key, String value);

    /**
     * 保存配置值（如果不存在）
     */
    boolean persistEphemeral(String key, String value);

    /**
     * 删除配置
     */
    void delete(String key);

    /**
     * 获取子节点
     */
    List<String> getChildren(String key);

    /**
     * 监听节点变化
     */
    void watch(String key, StateChangedListener listener);

    /**
     * 监听子节点变化
     */
    void watchDirectly(String key, ChildrenChangedListener listener);
}
```

不同注册中心的实现类：
- ZooKeeper：ZookeeperRegistryRepository
- Nacos：NacosRegistryRepository
- Etcd：EtcdRegistryRepository

### 10.3.4 配置持久化示例

下面以 ZooKeeper 为例，展示配置如何持久化到注册中心：

```yaml
# ShardingSphere-JDBC 配置文件
dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://localhost:3306/ds_0?useSSL=false&serverTimezone=UTC
    username: root
    password: password123
  ds_1:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://localhost:3306/ds_1?useSSL=false&serverTimezone=UTC
    username: root
    password: password123

rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${0..1}.t_order_${0..15}
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: database_mod
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: table_mod
    defaultDatabaseStrategy:
      standard:
        shardingColumn: user_id
        shardingAlgorithmName: database_mod

  - !ENCRYPT
    encryptors:
      aes_encrypt:
        type: AES
        props:
          aes-key-value: 1234567890123456
    tables:
      t_order:
        columns:
          phone:
            plainColumn: phone
            cipherColumn: phone_cipher
            encryptorName: aes_encrypt
```

配置会被序列化为 JSON 并存储到注册中心：

```json
{
  "dataSourceClassName": "com.zaxxer.hikari.HikariDataSource",
  "driverClassName": "com.mysql.cj.jdbc.Driver",
  "jdbcUrl": "jdbc:mysql://localhost:3306/ds_0",
  "username": "root",
  "cipher": "encrypted_password_value"
}
```

## 10.4 配置动态更新

### 10.4.1 动态更新机制

配置动态更新是 ShardingSphere-JDBC 的核心能力之一，它允许在不重启应用的情况下动态修改分片规则、数据源配置等参数。这对于生产环境中的运维工作非常重要，可以大大减少因配置变更导致的系统停机时间。

动态更新的实现依赖于注册中心的 Watch 机制：

1. **配置订阅**：应用启动时向注册中心订阅配置节点
2. **变更通知**：注册中心检测到配置变化，通知所有订阅者
3. **配置reload**：应用收到通知后，重新加载配置并应用到内存
4. **平滑切换**：新旧配置平滑切换，保证业务连续性

### 10.4.2 支持动态更新的配置项

ShardingSphere-JDBC 支持动态更新的配置项包括：

| 配置类别 | 支持动态更新 | 说明 |
|----------|-------------|------|
| 数据源配置 | 部分支持 | 连接池参数可动态调整，地址变更需重启 |
| 分片规则 | 支持 | 可动态添加/修改/删除分片表规则 |
| 加密规则 | 支持 | 可动态修改加密算法和字段映射 |
| 读写分离 | 支持 | 可动态调整读写分离策略 |
| 熔断规则 | 支持 | 可实时修改熔断阈值 |
| 分布式锁 | 支持 | 锁超时时间可动态调整 |

### 10.4.3 动态更新实现原理

动态更新的核心实现是采用了监听器模式：

```java
// 配置监听器接口
public interface SchemaChangedListener {
    void changed(SchemaChangedEvent event);
}

// 数据源变更监听器
public class DataSourceChangedListener implements SchemaChangedListener {
    @Override
    public void changed(SchemaChangedEvent event) {
        if (event.getType() == EventType.DATA_SOURCE_CHANGED) {
            // 重新加载数据源配置
            reloadDataSource(event.getSchemaName());
        }
    }
}

// 分片规则变更监听器
public class RuleChangedListener implements SchemaChangedListener {
    @Override
    public void changed(SchemaChangedEvent event) {
        if (event.getType() == EventType.RULE_CHANGED) {
            // 重新加载分片规则
            reloadRules(event.getSchemaName());
        }
    }
}
```

### 10.4.4 配置动态更新示例

#### 场景一：动态修改分片规则

假设原来 `t_order` 表按 `user_id` 分片，现在需要改为按 `order_id` 分片：

1. 在注册中心（ZooKeeper）更新配置：

```bash
# 更新前
/shardingsphere/schemas/sharding_db/rules/sharding/tables/t_order
{
  "tableStrategy": {
    "standard": {
      "shardingColumn": "user_id",
      "shardingAlgorithmName": "table_mod_by_user"
    }
  }
}

# 更新后
{
  "tableStrategy": {
    "standard": {
      "shardingColumn": "order_id",
      "shardingAlgorithmName": "table_mod_by_order"
    }
  }
}
```

2. ShardingSphere-JDBC 感知到配置变化，自动重新加载分片规则

3. 新的查询请求会使用新的分片规则

#### 场景二：动态添加数据源

在不停机的情况下添加新的数据源：

```yaml

    password: password123

  - !SHARDING

      t_order:
        actualDataNodes: ds_${0}.t_order_${0..15}
```


### 10.4.5 配置更新监听器配置

在 ShardingSphere-JDBC 中启用配置动态更新需要配置监听器：

```yaml
registry:
  type: ZooKeeper
  namespace: shardingsphere
  server-lists: localhost:2181
  props:
    connect.timeout.ms: 5000
    session.timeout.ms: 60000
  # 配置监听器
  listeners:
    - type: DataSourceChangedListener
      enabled: true
    - type: RuleChangedListener
      enabled: true
    - type: SchemaChangedListener
      enabled: true
```

### 10.4.6 动态更新注意事项

1. **配置验证**：更新配置前应先验证配置合法性，避免错误配置导致系统不可用
2. **灰度发布**：生产环境建议先在单个节点验证，再全量发布
3. **回滚机制**：应保留配置历史版本，出现问题时能够快速回滚
4. **并发控制**：多个节点同时更新配置时，应使用分布式锁避免冲突
5. **缓存清理**：配置更新后应及时清理相关缓存，保证数据一致性

## 10.5 数据源治理

### 10.5.1 数据源治理概述

在分布式数据库架构中，应用通常需要管理多个数据源。数据源治理的核心目标是：
- 统一管理多个数据源的连接
- 监测数据源健康状态
- 实现故障自动转移
- 提供连接池管理

ShardingSphere-JDBC 的数据源治理建立在标准 DataSource 接口之上，通过包装原生数据源来实现分片、读写分离等能力。

### 10.5.2 数据源健康检查

ShardingSphere-JDBC 内置了数据源健康检查机制，定期检测各数据源的可用性：

```java
public interface HealthCheckStrategy {
    /**
     * 执行健康检查
     */
    HealthCheckResult check();

    /**
     * 检查是否所有数据源都可用
     */

// 数据源健康状态
public enum DataSourceStatus {
    AVAILABLE,      // 可用
    UNAVAILABLE,    // 不可用

```

健康检查策略配置：

```yaml
dataSources:

```

### 10.5.3 数据源故障转移

当检测到数据源故障时，ShardingSphere-JDBC 会自动进行故障转移：

1. **故障检测**：连续 N 次健康检查失败，判定为故障
2. **节点隔离**：将故障节点标记为不可用，剔除出连接池
3. **请求路由**：将请求自动路由到健康节点
4. **恢复检测**：定期对故障节点进行探测
5. **节点恢复**：故障节点恢复后，重新加入连接池

```yaml
governance:
  healthCheck:
    enabled: true
    # 故障转移配置
    failover:
      enabled: true
      maxRetries: 3                    # 最大重试次数
      retryInterval: 1000              # 重试间隔（毫秒）
      autoRecovery: true               # 是否自动恢复
      recoveryThreshold: 3            # 恢复检测连续成功次数
```

### 10.5.4 连接池管理

| 参数 | 说明 | 推荐值 |

| maximumPoolSize | 最大连接数 | CPU 核心数 * 2 |
| connectionTimeout | 获取连接超时（毫秒） | 30000 |
| idleTimeout | 空闲连接超时（毫秒） | 600000 |

| poolName | 连接池名称 | 自定义 |

## 10.6 分片策略治理

### 10.6.1 分片策略概述

分片策略是 ShardingSphere-JDBC 实现数据水平分片的核心。分片策略包括分片键（Sharding Column）和分片算法（Sharding Algorithm）两个维度。

ShardingSphere-JDBC 将分片策略抽象为两层：
- **分片策略（Sharding Strategy）**：定义分片键和分片算法的关系
- **分片算法（Sharding Algorithm）**：具体的分片计算逻辑

### 10.6.2 分片策略类型

ShardingSphere-JDBC 支持多种分片策略：

#### 1. 标准分片策略（Standard）

最常用的分片策略，适用于单分片键场景：

```yaml
rules:
  - !SHARDING
    tables:
      t_order:
        databaseStrategy:
          standard:
            shardingColumn: user_id
            shardingAlgorithmName: database_mod
        tableStrategy:
          standard:
            shardingColumn: order_id
            shardingAlgorithmName: table_mod
```

#### 2. 复合分片策略（Complex）

支持多分片键的场景：

```yaml
rules:
  - !SHARDING
    tables:
      t_order:
        databaseStrategy:
          complex:
            shardingColumns: user_id, order_type
            shardingAlgorithmName: database_complex
        tableStrategy:
          complex:
            shardingColumns: order_id, order_type
            shardingAlgorithmName: table_complex
```

#### 3. 行表达式分片策略（Inline）

使用 Groovy 表达式定义分片规则：

```yaml
rules:
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_${user_id % 2}.t_order_${order_id % 16}
```

#### 4. Hint 分片策略（Hint）

通过编程方式强制指定分片键值：

```java
HintManager hintManager = HintManager.getInstance();
hintManager.setDatabaseShardingValue(0, "user_id", 12345);
hintManager.setTableShardingValue(0, "order_id", 67890);

List<Order> orders = orderMapper.selectAll();
```

#### 5. 默认分片策略（Default）

当没有为表指定特定策略时使用的默认策略：

```yaml
rules:
  - !SHARDING
    defaultDatabaseStrategy:
      standard:
        shardingColumn: user_id
        shardingAlgorithmName: default_database_mod
    defaultTableStrategy:
      none  # 无分片，按原表名查询
```

### 10.6.3 分片算法实现

ShardingSphere-JDBC 内置了多种分片算法：

#### 取模分片算法（Mod）

最简单也是最常用的分片算法：

```yaml
shardingAlgorithms:
  database_mod:
    type: MOD
    props:
      sharding-count: 4  # 分片数量
  table_mod:
    type: MOD
    props:
      sharding-count: 16
```

#### 哈希分片算法（Hash）

使用哈希值进行分片，分布均匀：

```yaml
shardingAlgorithms:
  database_hash:
    type: HASH_MOD
    props:
      sharding-count: 4
  table_hash:
    type: HASH_MOD
    props:
      sharding-count: 16
```

#### 范围分片算法（Range）

按数值范围进行分片：

```yaml
shardingAlgorithms:
  database_range:
    type: RANGE
    props:
      sharding-ranges: '0-10000=0,10001-20000=1,20001-30000=2,30001-40000=3'
```

#### 基于时间范围的分片算法

按时间范围分片，适用于日志表、流水表：

```yaml
shardingAlgorithms:
  monthly_range:
    type: INTERVAL
    props:
      datetime-pattern: 'yyyy-MM-dd'
      datetime-lower: '2020-01-01'
      datetime-interval: 1
      datetime-unit: MONTHS
      sharding-ranges: '2020-01=0,2020-02=0,2020-03=1'
```

### 10.6.4 分片策略动态调整

在实际生产环境中，数据库数据量会随着时间增长，当某个分片的数据量接近上限时，需要动态调整分片策略。ShardingSphere-JDBC 支持在线调整分片策略而无需重启应用。

#### 场景：分片迁移

假设原有 4 个分片库，需要扩展到 8 个分片库：

1. **第一阶段：双写**

在注册中心修改分片算法配置：

```yaml
shardingAlgorithms:
  database_mod:
    type: MOD
    props:
      # 从 4 改为 8
      sharding-count: 8
```

新旧数据都会写入新旧分片。

2. **第二阶段：数据补偿**

执行数据迁移脚本，将老数据同步到新分片：

```sql
-- 数据迁移存储过程示例
DELIMITER //

CREATE PROCEDURE migrate_data()
BEGIN
  DECLARE i INT DEFAULT 0;
  DECLARE batch_size INT DEFAULT 1000;

  -- 迁移 ds_0 的数据到新分片
  WHILE i < (SELECT COUNT(*) FROM t_order WHERE user_id % 4 = 0) DO
    INSERT INTO t_order_target SELECT * FROM t_order
    WHERE user_id % 8 IN (0, 4) AND user_id % 4 = 0
    LIMIT batch_size;
    SET i = i + batch_size;
  END WHILE;

END //

DELIMITER ;
```

3. **第三阶段：验证与切换**

验证数据一致性后，切换到新分片策略。

### 10.6.5 分片策略治理最佳实践

1. **分片键选择原则**
   - 选择查询最频繁的字段作为分片键
   - 避免选择区分度低的字段（如状态、类型）
   - 分片键值应分布均匀

2. **分片数量规划**
   - 预估数据增长量，预留足够余量
   - 单库分片数建议不超过 10 个
   - 总分片数 = 分库数 × 分表数

3. **跨分片查询优化**
   - 使用 Hint 强制路由到特定分片
   - 开启并行查询提升性能
   - 考虑使用 Elasticsearch 做复杂查询

4. **分片策略版本管理**
   - 在注册中心保留历史配置版本
   - 重大变更前先在测试环境验证
   - 准备好回滚预案

## 10.7 用户名密码加密

### 10.7.1 加密需求背景

在分布式数据库环境中，数据源配置包含了数据库用户名和密码等敏感信息。这些信息明文存储在配置文件或注册中心中存在严重的安全风险：
- 配置文件中明文密码容易被泄露
- 注册中心被攻击导致凭证外泄
- 日志输出可能暴露敏感信息

ShardingSphere-JDBC 提供了完善的安全加密机制，保护敏感数据安全。

### 10.7.2 加密配置方式

#### 使用加密算法配置数据源密码

```yaml
dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    driverClassName: com.mysql.cj.jdbc.Driver
    jdbcUrl: jdbc:mysql://localhost:3306/ds_0?useSSL=false
    username: root
    password: cipher: AES(encrypted_password)

encryptors:
  aes_encrypt:
    type: AES
    props:
      aes-key-value: 1234567890123456
```

配置格式说明：
- `cipher:algorithm_name(encrypted_value)`：表示加密后的值
- `plain:original_value`：表示明文值（仅用于测试）

支持的加密算法：
- AES
- RSA
- RC4
- DES

### 10.7.3 加密算法配置

```yaml
encryptRule:
  encryptors:
    # AES 加密
    aes_encrypt:
      type: AES
      props:
        aes-key-value: 1234567890123456   # AES 密钥（16字节）

    # RSA 加密（非对称加密，更安全）
    rsa_encrypt:
      type: RSA
      props:
        # RSA 私钥（PEM 格式）
        private-key: |
          -----BEGIN RSA PRIVATE KEY-----
          MIICXQIBAAJBAL...
          -----END RSA PRIVATE KEY-----
        # RSA 公钥
        public-key: |
          -----BEGIN RSA PUBLIC KEY-----
          MIIBIjANBgkqhki...
          -----END RSA PUBLIC KEY-----

    # 配置脱敏（用于日志输出）
    mask_encrypt:
      type: MASK
      props:
        mask-char: '*'
        mask-length: 4
```

### 10.7.4 密码加密工具

ShardingSphere-JDBC 提供了加密工具用于生成加密后的密码：

```java

    public static void main(String[] args) {
        String originalPassword = "mySecretPassword123";
        String aesKey = "1234567890123456";

        // 使用 AES 加密

        encryptor.setProps(PropertiesBuilder.builder()
            .setProperty("aes-key-value", aesKey)
            .build());

        String encryptedPassword = encryptor.encrypt(originalPassword);
        System.out.println("Encrypted: " + encryptedPassword);

        // 解密验证
        String decrypted = encryptor.decrypt(encryptedPassword);
        System.out.println("Decrypted: " + decrypted);
    }
}
```

除了密码加密外，ShardingSphere-JDBC 还支持对其他敏感数据进行脱敏处理：

## 10.8 黄狗问题与解决方案

### 10.8.1 什么是黄狗问题

"黄狗问题"（Yellow Dog Problem）是 ShardingSphere-JDBC 在分布式环境下特有的一个问题。当分片集群中某个数据节点出现故障时，该节点上的数据无法被正常访问，但如果查询请求恰好被路由到这个故障节点，就会导致请求失败。

这个问题之所以叫"黄狗"，是因为 ShardingSphere 的 Logo 是一只蓝色的小狗，当某个节点故障时，这个节点就像一只"生病的黄狗"一样，无法正常提供服务。

### 10.8.2 问题现象

1. **部分查询失败**：只有路由到故障节点的查询会失败
2. **连接超时**：无法建立到故障节点的连接
3. **资源泄漏**：未正确关闭的连接消耗资源
4. **服务雪崩**：故障节点影响正常节点

### 10.8.3 根本原因分析

黄狗问题的根本原因在于 ShardingSphere-JDBC 默认使用强一致性路由策略：

```
客户端请求 → 路由计算 → 故障节点 → 失败
                    ↓
              没有降级处理
```

当出现以下情况时会触发黄狗问题：
1. 分片节点宕机
2. 网络分区导致节点不可达
3. 数据库连接池耗尽
4. 数据库死锁或长时间阻塞

### 10.8.4 解决方案

#### 方案一：启用故障转移（Failover）

配置健康检查和故障转移机制：

```yaml
governance:
  healthCheck:
    enabled: true
    interval: 3000
    threshold: 2
  failover:
    enabled: true
    maxRetries: 3
    retryInterval: 1000
    autoRecovery: true
```

当某个节点故障时，自动将请求路由到其他健康节点。

#### 方案二：配置降级策略

```yaml
rules:
  - !SHARDING
    tables:
      t_order:
        # 降级策略配置
        auditing:
          # 查询超时时间
          queryTimeout: 30000
          # 是否允许最小可用分片
          allow-minimum: 1
```

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| queryTimeout | 查询超时时间（毫秒） | 30000 |
| allow-minimum | 允许的最小可用分片数 | 1 |
| failover-threshold | 触发故障转移的连续失败次数 | 3 |

#### 方案三：使用读写分离背书

当主库故障时，使用从库作为备份：

```yaml
rules:
  - !READ_WRITE_SPLITTING
    dataSources:
      ds_master:
        writeDataSourceName: ds_0
        readDataSources:
          - ds_0_readonly
          - ds_1_readonly
      failover:
        enabled: true
        dataSourceNames:
          - ds_0_readonly
```

#### 方案四：Hint 强制路由降级

使用 Hint 机制强制指定路由到健康节点：

```java
HintManager hintManager = HintManager.getInstance();

// 强制路由到 ds_0
hintManager.setDatabaseShardingValue(0, "user_id", specificUserId);

// 如果 ds_0 不可用，自动降级到 ds_1
hintManager.setFallbackDatabases(Arrays.asList("ds_1"));

List<Order> orders = orderMapper.selectAll();
```

### 10.8.5 完整解决方案配置示例

```yaml
# 综合黄狗问题解决方案配置
governance:
  name: shardingSphere governance

  # 注册中心配置
  registry:
    type: ZooKeeper
    server-lists: localhost:2181,localhost:2182,localhost:2183
    namespace: shardingsphere
    props:
      connect.timeout.ms: 5000
      session.timeout.ms: 60000

  # 健康检查配置

    enabled: true
    interval: 5000                    # 健康检查间隔
    threshold: 3                     # 连续失败次数阈值
    timeout: 3000                    # 单次检查超时
    schemaCheck: true                 # 是否检查 Schema
    connectionCheck: true             # 是否检查连接

  # 故障转移配置

    enabled: true

    retryPolicy:                     # 重试策略
      type: EXPOENTIAL_BACKOFF      # 指数退避

      maxInterval: 30000

  circuitBreaker:
    enabled: true

    tables:

            - ds_1

    shardingAlgorithms:
      database_mod:
        type: MOD
        props:
          sharding-count: 4

    # 默认分片策略
    defaultDatabaseStrategy:
      standard:
        shardingColumn: user_id
        shardingAlgorithmName: database_mod
```

## 10.9 熔断器配置

### 10.9.1 熔断器概念

熔断器（Circuit Breaker）模式是微服务架构中常用的保护机制。当某个服务或数据源持续出现故障时，如果继续向故障节点发送请求，不仅会失败，还可能耗尽资源导致系统雪崩。熔断器的作用就是在检测到故障达到一定阈值后，"跳闸"切断请求，快速失败而不是无限等待。

熔断器有三种状态：
1. **Closed（关闭）**：正常状态，请求可以通行
2. **Open（打开）**：检测到故障阈值，请求被拒绝，快速失败
3. **Half-Open（半开）**：尝试恢复，允许少量请求通过探测

```
           失败率 > 阈值
    ┌────────────────────────┐
    │                        ▼
┌───┴───┐   成功恢复    ┌────┐   失败率 > 阈值   ┌──────┐
│Closed │ ───────────► │Open│ ───────────────► │Half  │
│       │   连续失败    │    │    重试失败       │Open  │
└───────┘              └────┘                   └──────┘
     ▲                                              │
     │              恢复成功                         │
     └──────────────────────────────────────────────┘
```

### 10.9.2 ShardingSphere-JDBC 熔断器配置

ShardingSphere-JDBC 基于 Sentinel 实现了熔断器功能，支持对数据源、分片节点进行熔断保护。

```yaml
circuitBreaker:
  enabled: true
  # 熔断器配置
  breaker:
    # 错误率阈值（百分比），超过后触发熔断
    errorRateThreshold: 50
    # 最小请求数，达到这个数量后才开始统计错误率
    minRequestAmount: 10
    # 统计时间窗口（毫秒）
    statInterval: 60000
    # 熔断持续时间（毫秒），超时后进入半开状态
    duration: 30000
    # 半开状态允许的试探请求数
    halfOpenMaxRequestAmount: 5
```

| 配置项 | 说明 | 默认值 |
|--------|------|--------|
| enabled | 是否启用熔断器 | false |
| errorRateThreshold | 错误率阈值（百分比） | 50 |
| minRequestAmount | 最小请求数 | 10 |
| statInterval | 统计时间窗口（毫秒） | 60000 |
| duration | 熔断持续时间（毫秒） | 30000 |
| halfOpenMaxRequestAmount | 半开状态最大试探请求数 | 5 |

### 10.9.3 熔断器策略配置

除了全局熔断器配置，还可以针对不同的数据源和操作配置具体的熔断策略：

```yaml
rules:
  - !SHARDING
    tables:
      t_order:
        # 查询操作熔断策略
        queryCircuitBreaker:
          enabled: true
          errorRateThreshold: 30        # 查询更敏感，降低阈值
          minRequestAmount: 5
          statInterval: 30000

        # 更新操作熔断策略
        updateCircuitBreaker:
          enabled: true
          errorRateThreshold: 60        # 更新操作可以容忍稍高错误率
          minRequestAmount: 3
          duration: 60000

# 数据源级别熔断配置
dataSourcesCircuitBreaker:
  ds_0:
    enabled: true
    errorRateThreshold: 40
    minRequestAmount: 8
```

### 10.9.4 熔断触发场景

以下场景会触发熔断器：

1. **连接超时**：无法在配置时间内建立连接
2. **查询超时**：SQL 执行超过超时时间
3. **连接池耗尽**：无法获取可用连接
4. **SQL 语法错误率高**：连续多条 SQL 执行失败
5. **响应错误率高**：超过阈值的请求返回错误

### 10.9.5 熔断恢复机制

熔断触发后，ShardingSphere-JDBC 会按照以下流程尝试恢复：

1. **熔断持续时间**：熔断器保持打开状态，快速拒绝所有请求
2. **半开试探**：超时后进入半开状态，允许少量请求通过
3. **健康检测**：试探请求成功则认为故障已恢复
4. **关闭熔断器**：连续成功数达到阈值则恢复正常

```yaml
circuitBreaker:
  recovery:
    # 恢复策略类型
    type: GRADUAL          # GRADUAL-渐进式, IMMEDIATE-立即
    # 每次试探间隔
    probeInterval: 5000
    # 成功阈值，连续成功次数达到则恢复
    successThreshold: 3
    # 恢复时逐步增加流量
    gradual:
      initialRate: 0.1     # 初始允许 10% 流量
      increment: 0.2       # 每次增加 20%
```

### 10.9.6 熔断监控

启用熔断器后，应该配置监控以便及时发现和处理熔断事件：

```yaml
metrics:
  enabled: true
  circuitBreaker:
    # 熔断器指标
    metrics:
      - name: circuit_breaker_state
        type: gauge
        description: 熔断器状态 (0-关闭, 1-打开, 2-半开)
        labels:
          - schema
          - datasource
      - name: circuit_breaker_error_rate
        type: gauge
        description: 当前错误率
      - name: circuit_breaker_request_total
        type: counter
        description: 被熔断拒绝的请求总数
      - name: circuit_breaker_recovery_total
        type: counter
        description: 熔断恢复次数
```

### 10.9.7 熔断器配置最佳实践

1. **合理设置阈值**
   - 不要设置过低（如 10%）导致正常波动触发熔断
   - 不要设置过高（如 90%）导致熔断器形同虚设
   - 建议设置为 50-70% 之间

2. **设置足够的最小请求数**
   - 避免小流量场景误触发熔断
   - 建议设置为 10-20

3. **合理设置熔断持续时间**
   - 太短：故障未恢复就又打开
   - 太长：故障恢复后长时间无法服务
   - 建议设置为 30-60 秒

4. **配置监控告警**
   - 熔断器打开时及时告警
   - 频繁熔断说明有问题需要排查
   - 建立熔断事件分析机制

## 10.10 分布式锁

### 10.10.1 分布式锁概念

在分布式系统中，多个应用节点可能同时访问共享资源，需要一种机制来协调各节点的访问顺序，这就是分布式锁。ShardingSphere-JDBC 在以下场景需要使用分布式锁：

1. **配置更新**：多个节点同时更新配置时防止数据不一致
2. **分片迁移**：数据迁移过程中的并发控制
3. **弹性伸缩**：节点扩缩容时的协调
4. **主从切换**：读写分离架构中的主库选举

### 10.10.2 分布式锁实现方式

ShardingSphere-JDBC 支持多种分布式锁实现：

| 实现方式 | 说明 | 适用场景 |
|----------|------|----------|
| ZooKeeper | 基于临时顺序节点 + Watch | 高可靠场景 |
| Etcd | 基于 Lease 和 Range | 高性能场景 |
| Nacos | 基于 CP 模式的分布式锁 | Spring Cloud 生态 |
| JDBC | 基于数据库表 | 简单场景，无需额外组件 |

### 10.10.3 ZooKeeper 分布式锁配置

```yaml
registry:
  type: ZooKeeper
  server-lists: localhost:2181,localhost:2182,localhost:2183
  namespace: shardingsphere
  props:
    connect.timeout.ms: 5000
    session.timeout.ms: 60000

# 分布式锁配置
distributedLock:
  type: ZooKeeper
  props:
    # 锁路径前缀
    lockPath: /shardingsphere/locks
    # 锁超时时间（毫秒）
    timeout: 30000
    # 最大重试次数
    maxRetries: 3
    # 重试间隔（毫秒）
    retryInterval: 300
    # 是否可重入
    reentrant: true
```

### 10.10.4 Etcd 分布式锁配置

```yaml
registry:
  type: Etcd
  server-lists: localhost:2379
  props:
    connect.timeout.ms: 3000
    connection.timeout.ms: 5000

distributedLock:
  type: Etcd
  props:
    # 锁前缀
    lockPrefix: /shardingsphere/locks
    # 锁超时时间
    lockTimeout: 30000
    # TTL 用于自动释放锁
    leaseTtl: 60
```

### 10.10.5 使用分布式锁

在应用程序中使用 ShardingSphere-JDBC 的分布式锁：

```java
import org.apache.shardingsphere.infra.metadata.instance.spi.LockRegistry;

public class DistributedLockExample {

    @Autowired
    private LockRegistry lockRegistry;

    /**
     * 执行分片迁移
     */
    public void migrateSharding() {
        String lockKey = "/sharding/migration/t_order";

        // 尝试获取锁
        Lock lock = lockRegistry.getLock(lockKey);
        boolean acquired = lock.tryLock(30, TimeUnit.SECONDS);

        if (!acquired) {
            throw new RuntimeException("无法获取分布式锁，分片迁移正在进行中");
        }

        try {
            // 执行分片迁移逻辑
            doMigrate();
        } finally {
            // 释放锁
            lock.unlock();
        }
    }

    /**
     * 使用 Lock 包装器自动释放锁
     */
    public void migrateWithAutoRelease() {
        String lockKey = "/sharding/migration/t_order";

        lockRegistry.executeLocked(lockKey, () -> {
            // 在锁保护下执行操作
            doMigrate();
            return null;
        });
    }
}
```

### 10.10.6 锁粒度设计

合理的锁粒度设计对于系统性能和并发能力至关重要：

1. **粗粒度锁**：锁住整个操作，简单但并发度低
   ```java
   // 锁住所有表的所有分片
   lock("/sharding/migration/all");
   ```

2. **细粒度锁**：锁住具体的分片，并发度高但实现复杂
   ```java
   // 按表和分片分别加锁
   for (int i = 0; i < shardCount; i++) {
       String lockKey = "/sharding/migration/t_order/shard_" + i;
       lock(lockKey);
   }
   ```

3. **层级锁**：先锁库，再锁表，最后锁分片
   ```java
   // 层级锁示例
   lock("/sharding/db/ds_0");           // 先锁库
   lock("/sharding/table/t_order");     // 再锁表
   lock("/sharding/shard/t_order_0");    // 最后锁分片
   ```

### 10.10.7 分布式锁最佳实践

1. **锁超时设置**
   - 设置合理的锁超时时间，防止死锁
   - 建议设置为主要操作耗时的 2-3 倍

2. **锁失败处理**
   - 获取锁失败应该有重试机制
   - 设置最大重试次数，避免无限重试

3. **锁释放保证**
   - 使用 try-finally 确保锁释放
   - 考虑使用锁续约机制

4. **监控锁状态**
   - 监控锁等待时间
   - 告警长期未获取到的锁

```yaml
# 分布式锁监控配置
metrics:
  enabled: true
  lockMetrics:
    - name: lock_acquire_total
      type: counter
      description: 锁获取总次数
    - name: lock_acquire_failed_total
      type: counter
      description: 锁获取失败总次数
    - name: lock_wait_duration
      type: histogram
      description: 锁等待时长分布
      buckets: [100, 500, 1000, 5000, 10000]
    - name: lock_hold_duration
      type: histogram
      description: 锁持有时长分布
```

## 10.11 配置中心高可用

### 10.11.1 高可用架构重要性

配置中心是 ShardingSphere-JDBC 的大脑，一旦配置中心故障，所有节点将无法获取配置，导致整个集群不可用。因此，配置中心的高可用设计至关重要。

配置中心的高可用需要解决以下问题：
- 单点故障：任何组件不可用都会导致系统不可用
- 数据一致性：多个节点间的配置数据必须一致
- 故障转移：节点故障时能自动切换到备用节点
- 数据持久化：配置数据不能因故障丢失

### 10.11.2 ZooKeeper 高可用部署

#### ZooKeeper 集群架构

ZooKeeper 集群称为 Ensemble，推荐使用奇数个节点（3、5、7）：

```
                    ┌─────────────────┐

              ┌──────────────┼──────────────┐

        ┌─────▼─────┐ ┌─────▼─────┐ ┌─────▼─────┐
        │  Server 1 │ │  Server 2 │ │  Server 3 │
```

本章详细介绍了 ShardingSphere-JDBC 的分布式治理能力，涵盖配置中心/注册中心、配置持久化、配置动态更新、数据源治理、分片策略治理、用户名密码加密、黄狗问题解决方案、熔断器、分布式锁以及配置中心高可用等核心内容。

**关键要点回顾**：

1. **注册中心选择**：ZooKeeper 适合成熟稳定的 Hadoop 生态；Nacos 适合 Spring Cloud 生态和云原生场景；Etcd 适合 Kubernetes 环境。

2. **配置动态更新**：利用注册中心的 Watch 机制，实现分片规则、数据源配置等的实时生效，无需重启应用。

3. **黄狗问题解决**：通过健康检查、故障转移、降级策略等机制，保证系统在节点故障时仍能正常运行。

4. **熔断器配置**：合理设置错误率阈值和熔断持续时间，防止故障扩散和系统雪崩。

5. **分布式锁**：在配置更新、分片迁移等场景使用分布式锁，保证操作的原子性和一致性。

6. **高可用部署**：注册中心必须以集群方式部署，客户端需要配置多个服务器地址，确保整个系统的高可用性。

掌握这些分布式治理能力，是在生产环境中成功部署和运维 ShardingSphere-JDBC 的关键。随着业务规模的增长，合理规划和实施这些治理措施，将为系统的稳定运行提供坚实保障。
