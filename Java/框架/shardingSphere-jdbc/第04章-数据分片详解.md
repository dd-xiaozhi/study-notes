# 第4章：数据分片详解

## 4.1 数据分片概述

### 4.1.1 为什么需要数据分片

随着业务的快速发展，单一数据库实例在面对海量数据存储时逐渐暴露出诸多瓶颈：

| 问题类型 | 具体表现 | 影响 |
|---------|---------|------|
| **存储容量瓶颈** | 单表数据量超过千万级，数据库索引效率急剧下降 | 查询性能严重劣化 |
| **并发处理瓶颈** | 所有请求都集中在单一数据库节点 | 响应延迟增加，系统吞吐量受限 |
| **连接资源瓶颈** | 数据库连接数达到上限 | 新请求被拒绝，服务中断 |
| **备份恢复耗时** | 超大数据库实例备份和恢复时间极长 | 运维窗口缩短，业务风险增加 |

**数据分片（Sharding）** 是解决上述问题的核心方案。通过将数据分散存储到多个数据库实例中，实现数据的水平扩展，使系统具备处理海量数据的能力。

### 4.1.2 数据分片概念

数据分片是指将数据按照一定的规则拆分到多个数据存储节点（可以是数据库实例或表）的过程。ShardingSphere-JDBC 支持两种基本的分片方式：**水平分片** 和 **垂直分片**。

```
┌─────────────────────────────────────────────────────────────────┐
│                        原始未分片数据                             │
├─────────────────────────────────────────────────────────────────┤
│  id │    name     │   create_time    │   status   │  user_id   │
├─────┼────────────┼──────────────────┼────────────┼────────────┤
│  1  │  Product-A  │  2024-01-01 10:00 │  active    │    1001    │
│  2  │  Product-B  │  2024-01-02 11:00 │  inactive  │    1002    │
│  3  │  Product-C  │  2024-01-03 12:00 │  active    │    1001    │
│  ...│    ...      │       ...        │    ...     │    ...     │
└─────────────────────────────────────────────────────────────────┘
                                 │
            ┌────────────────────┴────────────────────┐
            ▼                                         ▼
┌───────────────────────────┐         ┌───────────────────────────┐
│      水平分片 (HS)         │         │      垂直分片 (VS)         │
│   按行拆分，数据分散到     │         │   按列拆分，字段分到        │
│   多个表/库中             │         │   不同表/库中              │
│                           │         │                           │
│  ┌─────┬─────┬─────┐      │         │  ┌─────────┬───────────┐   │
│  │ds_0│ds_1│ds_2│ds_3│     │         │  │ 主表    │  扩展表   │   │
│  │t_0 │t_1 │t_2 │t_3 │     │         │  │ id      │  detail   │   │
│  └─────┴─────┴─────┘      │         │  │ name    │  status   │   │
│   所有字段都在每个分片     │         │  │ create  │  ext1     │   │
│                           │         │  │         │  ext2     │   │
└───────────────────────────┘         └───────────────────────────┘
```

## 4.2 水平分片详解

### 4.2.1 水平分片概念

**水平分片（Horizontal Sharding）** 是指将一张表的数据按照某种规则拆分成多片，每一片包含部分行数据，所有分片的并集就是原始表的完整数据集。

**核心特征：**
- 每个分片包含原始表的部分数据行
- 所有分片的表结构完全相同
- 数据通过分片键（Sharding Key）分散到不同分片

**典型场景：**

| 场景 | 分片方式 | 说明 |
|-----|---------|------|
| 订单表按用户ID分片 | user_id % 4 | 同一用户的数据在同一分片 |
| 订单表按时间分片 | create_time 按月 | 历史数据归档到冷分片 |
| 商品表按类目分片 | category_id % 8 | 同一类目商品聚合 |

### 4.2.2 水平分片实现原理

ShardingSphere-JDBC 在 JDBC 层面拦截 SQL，通过分片算法计算目标数据节点，然后将 SQL 路由到相应分片执行。

```
┌──────────────────────────────────────────────────────────────────────┐
│                         SQL 拦截与路由流程                            │
├──────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   ┌─────────┐    ┌──────────────┐    ┌────────────┐    ┌──────────┐ │
│   │  User   │───▶│ ShardingSphere │───▶│  Sharding  │───▶│  分片    │ │
│   │   SQL   │    │    JDBC      │    │   Engine   │    │  执行器  │ │
│   └─────────┘    └──────────────┘    └────────────┘    └──────────┘ │
│                                    │                   │            │
│                          ┌──────────┴──────────┐       │            │
│                          ▼                     ▼       ▼            │
│                   ┌────────────┐         ┌────────────┐  ┌─────────┐ │
│                   │  SQL解析   │         │ 条件分析   │  │ 路由   │ │
│                   │  & 改写    │         │  & 优化    │  │ 计算   │ │
│                   └────────────┘         └────────────┘  └─────────┘ │
│                                                                      │
│   执行阶段：                                                         │
│   ┌─────────┐  ┌─────────┐  ┌─────────┐  ┌─────────┐               │
│   │ ds_0    │  │ ds_1    │  │ ds_2    │  │ ds_3    │               │
│   │ t_order │  │ t_order │  │ t_order │  │ t_order │               │
│   │_0       │  │_1       │  │_2       │  │_3       │               │
│   └─────────┘  └─────────┘  └─────────┘  └─────────┘               │
│                                                                      │
└──────────────────────────────────────────────────────────────────────┘
```

**核心处理流程：**

1. **SQL 解析**：将用户 SQL 解析为抽象语法树（AST），识别分片键、条件表达式等
2. **条件提取**：从 WHERE 子句中提取分片键相关条件
3. **路由计算**：根据分片算法计算 SQL 需路由的目标分片
4. **SQL 改写**：将逻辑表名改写为实际物理表名
5. **并行执行**：将 SQL 发送到多个目标分片并行执行
6. **结果合并**：将各分片返回的结果进行合并处理

### 4.2.3 水平分片配置示例

```yaml
# 水平分片配置示例：订单表按 user_id 分片到 4 个分片
dataSourceConfig:
  dataSources:
    ds_0:
      url: jdbc:mysql://localhost:3306/ds_0?serverTimezone=UTC
      username: root
      password: 
    ds_1:
      url: jdbc:mysql://localhost:3306/ds_1?serverTimezone=UTC
      username: root
      password: 
    ds_2:
      url: jdbc:mysql://localhost:3306/ds_2?serverTimezone=UTC
      username: root
      password: 
    ds_3:
      url: jdbc:mysql://localhost:3306/ds_3?serverTimezone=UTC
      username: root
      password: 

rules:
- !SHARDING
  tables:
    # t_order 逻辑表，分片到 4 个物理表
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..3}
      databaseStrategy:
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: mod
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: mod
  
  shardingAlgorithms:
    mod:
      type: MOD
      props:
        # 分片数量
        sharding-count: 4
```

## 4.3 垂直分片详解

### 4.3.1 垂直分片概念

**垂直分片（Vertical Sharding）** 是指将一张表的字段按照业务分类或访问频率拆分到不同的表中，每个分片包含原始表的部分列。

**核心特征：**
- 每个分片包含原始表的部分列
- 通常按照字段的访问频率或业务边界进行拆分
- 分片后各表保持主键关联关系

**典型场景：**

| 场景 | 拆分方式 | 说明 |
|-----|---------|------|
| 用户表拆分 | 基础信息 + 扩展信息 | 核心字段与低频字段分离 |
| 订单表拆分 | 主干信息 + 详情信息 | 常用字段与详情字段分离 |
| 商品表拆分 | 核心属性 + 销售属性 | 基础属性与业务属性分离 |

### 4.3.2 垂直分片实现原理

垂直分片的实现相对简单，主要关注点在于：
1. 确保拆分后的表保持主键一致性
2. 跨分片查询时需要做表关联处理
3. 保持业务逻辑的完整性

```
┌────────────────────────────────────────────────────────────────┐
│                      垂直分片示意                               │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│   原始表: t_user                                               │
│   ┌────┬──────────┬────────┬──────────┬──────────┬──────────┐ │
│   │ id │ username │ mobile │  email   │ address  │  ext_1   │ │
│   └────┴──────────┴────────┴──────────┴──────────┴──────────┘ │
│                           │                                    │
│           ┌───────────────┴───────────────┐                   │
│           ▼                               ▼                   │
│  ┌──────────────────┐           ┌──────────────────┐          │
│  │   t_user_base    │           │   t_user_ext     │          │
│  │  (基础信息表)     │           │  (扩展信息表)     │          │
│  ├────┬─────────────┤           ├────┬─────────────┤          │
│  │ id │ username    │           │ id │  ext_1      │          │
│  │    │ mobile      │           │    │  ext_2      │          │
│  │    │ email       │           │    │  ext_3      │          │
│  └────┴─────────────┘           └────┴─────────────┘          │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 4.3.3 垂直分片配置示例

```yaml
rules:
- !SHARDING
  tables:
    # 用户基础信息表
    t_user_base:
      actualDataNodes: ds_0.t_user_base
      
    # 用户扩展信息表
    t_user_ext:
      actualDataNodes: ds_1.t_user_ext
      
  bindingTables:
    - t_user_base,t_user_ext
```

## 4.4 分片键选择策略

### 4.4.1 分片键的重要性

分片键（Sharding Key）是决定数据如何分散的核心字段，直接影响：
- **查询性能**：是否能够高效定位数据分片
- **数据分布均匀性**：各分片数据量是否均衡
- **跨分片操作代价**：是否产生大量跨分片查询

### 4.4.2 分片键选择原则

| 原则 | 说明 | 重要性 |
|-----|------|-------|
| **高查询频率** | 选择经常用于查询条件的字段 | ★★★★★ |
| **高选择性** | 选择值域广泛、分布均匀的字段 | ★★★★☆ |
| **避免跨分片关联** | 关联查询的表使用相同的分片键 | ★★★★☆ |
| **单值查询优先** | 优先支持点查，其次范围查询 | ★★★☆☆ |
| **避免更新操作** | 分片键值最好不要被更新 | ★★★☆☆ |

### 4.4.3 常见分片键选择

| 业务场景 | 推荐分片键 | 理由 |
|---------|-----------|------|
| 电商订单 | user_id 或 order_id | 用户维度查询、商家维度查询 |
| 社交帖子 | user_id | 用户时间线查询、帖子详情查询 |
| 日志数据 | create_time | 时间范围归档、历史清理 |
| 会员系统 | member_id | 会员详情、会员关联查询 |

### 4.4.4 分片键选择陷阱

**问题一：低选择性字段作为分片键**

```sql
-- status 字段只有 ACTIVE/INACTIVE 两个值，分片后数据严重不均
-- 假设分成 4 片，ACTIVE 可能占 95%，INACTIVE 只占 5%
SELECT * FROM t_order WHERE status = 'ACTIVE'  -- 95% 数据跨 4 片查询
```

**问题二：使用 update 字段作为分片键**

```sql
-- 订单状态会频繁更新，不适合作为分片键
-- 更新分片键值会导致数据迁移
UPDATE t_order SET status = 'COMPLETED' WHERE order_id = 'xxx'
```

**问题三：未考虑跨分片查询频率**

```sql
-- 按 user_id 分片，但经常需要按 merchant_id 查询同一商户的订单
-- 导致严重的跨分片查询
SELECT * FROM t_order WHERE merchant_id = 'M001'
```

## 4.5 分片算法详解

### 4.5.1 取模分片算法（ModShardingAlgorithm）

#### 算法原理

取模分片是最简单也是最常用的分片算法，通过 `hash_value % sharding_count` 计算数据所属分片。

```
数据节点: ds_${key % 4}
数据分片: t_order_${order_id % 4}

示例:
order_id = 1001, 1001 % 4 = 1  -> ds_1.t_order_1
order_id = 1002, 1002 % 4 = 2  -> ds_2.t_order_2
order_id = 1003, 1003 % 4 = 3  -> ds_3.t_order_3
order_id = 1004, 1004 % 4 = 0  -> ds_0.t_order_0
```

#### 适用场景

- 数据分布要求均匀
- 对分片键值域无特殊要求
- 点查询场景（等值条件）

#### 配置示例

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..3}
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: order_mod
  
  shardingAlgorithms:
    order_mod:
      type: MOD
      props:
        sharding-count: 4
```

#### Java 配置

```java
public class ModShardingAlgorithm implements StandardShardingAlgorithm<Long> {
    
    private int shardingCount;
    
    @Override
    public void init(Properties props) {
        this.shardingCount = Integer.parseInt(
            props.getProperty("sharding-count", "4")
        );
    }
    
    @Override
    public String doSharding(Collection<String> availableTargetNames, 
                             PreciseShardingValue<Long> shardingValue) {
        long id = shardingValue.getValue();
        int shardingIndex = (int) (id % shardingCount);
        String target = "t_order_" + shardingIndex;
        if (availableTargetNames.contains(target)) {
            return target;
        }
        // 计算实际节点
        int dbIndex = shardingIndex / 4;
        int tableIndex = shardingIndex % 4;
        return String.format("ds_%d.t_order_%d", dbIndex, tableIndex);
    }
    
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         RangeShardingValue<Long> shardingValue) {
        // 范围查询时返回所有分片
        return availableTargetNames;
    }
}
```

#### 算法特点

| 特性 | 说明 |
|-----|------|
| 优点 | 实现简单，数据分布均匀，O(1) 时间复杂度 |
| 缺点 | 扩容困难，新增分片后需要迁移大量数据 |
| 适用规模 | 预估数据量稳定，扩缩容不频繁 |

### 4.5.2 哈希分片算法（HashShardingAlgorithm）

#### 算法原理

哈希分片通过哈希函数计算分片键的哈希值，然后对分片数取模得到目标分片。

```
分片键: user_id
哈希函数: hash(user_id) % sharding_count

示例:
user_id = "user_001", hash("user_001") = 1234567 -> 1234567 % 4 = 3 -> ds_3
user_id = "user_002", hash("user_002") = 2345678 -> 2345678 % 4 = 2 -> ds_2
```

#### 适用场景

- 分片键为字符串类型
- 需要更均匀的数据分布
- 对分片键值有一定隐私要求

#### 配置示例

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order
      databaseStrategy:
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: order_hash
  
  shardingAlgorithms:
    order_hash:
      type: HASH_MOD
      props:
        sharding-count: 4
```

#### Java 实现

```java
public class HashShardingAlgorithm implements StandardShardingAlgorithm<String> {
    
    private int shardingCount;
    
    @Override
    public void init(Properties props) {
        this.shardingCount = Integer.parseInt(
            props.getProperty("sharding-count", "4")
        );
    }
    
    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<String> shardingValue) {
        String value = shardingValue.getValue();
        int hashCode = Math.abs(value.hashCode());
        int shardingIndex = hashCode % shardingCount;
        
        for (String target : availableTargetNames) {
            if (target.endsWith(String.valueOf(shardingIndex))) {
                return target;
            }
        }
        throw new UnsupportedOperationException(
            "No such data node: " + shardingIndex
        );
    }
    
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                        RangeShardingValue<String> shardingValue) {
        // 字符串不支持范围查询，返回所有分片
        return availableTargetNames;
    }
}
```

#### 算法特点

| 特性 | 说明 |
|-----|------|
| 优点 | 对字符串类型分片键友好，数据分布较均匀 |
| 缺点 | 扩容时数据迁移量大，无法范围查询 |
| 改进 | 一致性哈希算法可减少扩容迁移 |

### 4.5.3 时间范围分片算法（RangeShardingAlgorithm）

#### 算法原理

时间范围分片按照分片键的时间范围进行数据划分，每个分片存储特定时间段的数据。

```
分片键: create_time
时间范围: 按月划分

示例:
create_time = 2024-01-15 -> ds_0.t_order_2024_01
create_time = 2024-02-20 -> ds_1.t_order_2024_02
create_time = 2024-03-10 -> ds_2.t_order_2024_03
```

#### 适用场景

- 数据有明显的时间特征
- 需要定期归档或清理历史数据
- 主要查询条件包含时间范围

#### 配置示例

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..2}.t_order_${202401..202412}
      tableStrategy:
        standard:
          shardingColumn: create_time
          shardingAlgorithmName: order_range
  
  shardingAlgorithms:
    order_range:
      type: RANGE
      props:
        # 时间格式
        date-format: yyyyMM
        # 日期范围下限
        date-lower: 202401
        # 日期范围上限
        date-upper: 202412
        # 单个分片月份数
        sharding-interval: 1
```

#### Java 实现

```java
public class RangeShardingAlgorithm implements StandardShardingAlgorithm<String> {
    
    private String dateFormat;
    private int dateLower;
    private int dateUpper;
    private int shardingInterval;
    
    @Override
    public void init(Properties props) {
        this.dateFormat = props.getProperty("date-format", "yyyyMM");
        this.dateLower = Integer.parseInt(props.getProperty("date-lower", "202401"));
        this.dateUpper = Integer.parseInt(props.getProperty("date-upper", "202412"));
        this.shardingInterval = Integer.parseInt(props.getProperty("sharding-interval", "1"));
    }
    
    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<String> shardingValue) {
        String value = shardingValue.getValue();
        LocalDateTime dateTime = LocalDateTime.parse(value, 
            DateTimeFormatter.ofPattern(dateFormat));
        int yearMonth = dateTime.getYear() * 100 + dateTime.getMonthValue();
        
        // 计算分片索引
        int intervalIndex = (yearMonth - dateLower) / shardingInterval;
        String targetSuffix = String.valueOf(dateLower + intervalIndex * shardingInterval);
        
        for (String target : availableTargetNames) {
            if (target.endsWith(targetSuffix)) {
                return target;
            }
        }
        return null;
    }
    
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                        RangeShardingValue<String> shardingValue) {
        // 范围查询，返回覆盖范围内的所有分片
        Range<String> rangeValue = shardingValue.getValue();
        List<String> result = new ArrayList<>();
        
        int lower = dateLower;
        int upper = dateUpper;
        
        if (rangeValue.hasLowerBound()) {
            LocalDateTime lowerDate = LocalDateTime.parse(
                rangeValue.getLowerEndpoint().getValue(),
                DateTimeFormatter.ofPattern(dateFormat));
            lower = lowerDate.getYear() * 100 + lowerDate.getMonthValue();
        }
        
        if (rangeValue.hasUpperBound()) {
            LocalDateTime upperDate = LocalDateTime.parse(
                rangeValue.getUpperEndpoint().getValue(),
                DateTimeFormatter.ofPattern(dateFormat));
            upper = upperDate.getYear() * 100 + upperDate.getMonthValue();
        }
        
        for (int month = lower; month <= upper; month += shardingInterval) {
            for (String target : availableTargetNames) {
                if (target.endsWith(String.valueOf(month)) && !result.contains(target)) {
                    result.add(target);
                }
            }
        }
        
        return result.isEmpty() ? availableTargetNames : result;
    }
}
```

#### 算法特点

| 特性 | 说明 |
|-----|------|
| 优点 | 支持范围查询，数据按时间有序，适合冷热数据分离 |
| 缺点 | 可能产生数据热点不均，历史分片访问频率低 |
| 适用规模 | 适用于时序数据，如日志、订单、监控数据 |

### 4.5.4 标准分片算法（StandardShardingAlgorithm）

#### 算法原理

标准分片算法是 ShardingSphere 的基础分片接口，提供了精确查询和范围查询两个方法。

```java
public interface StandardShardingAlgorithm<T extends Comparable<T>> 
    extends ShardingAlgorithm {
    
    /**
     * 精确查询，返回单个目标分片
     */
    String doSharding(Collection<String> availableTargetNames, 
                      PreciseShardingValue<T> shardingValue);
    
    /**
     * 范围查询，返回多个目标分片
     */
    Collection<String> doSharding(Collection<String> availableTargetNames, 
                                  RangeShardingValue<T> shardingValue);
}
```

#### PreciseShardingValue 与 RangeShardingValue

```java
// 精确查询值（等值查询）
public final class PreciseShardingValue<T extends Comparable<T>> {
    private final String logicTableName;      // 逻辑表名
    private final String columnName;          // 分片键列名
    private final T value;                    // 分片键值
    
    public T getValue() { return value; }
}

// 范围查询值（范围查询）
public final class RangeShardingValue<T extends Comparable<T>> {
    private final String logicTableName;
    private final String columnName;
    private final Range<T> value;             // 值范围
    
    public Range<T> getValue() { return value; }
}
```

#### 配置示例

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..3}
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: standard_order
  
  shardingAlgorithms:
    standard_order:
      type: STANDARD
      props:
        # 使用自定义算法类
        algorithm-class-name: com.example.MyStandardShardingAlgorithm
```

#### 自定义标准分片算法

```java
public class MyStandardShardingAlgorithm implements StandardShardingAlgorithm<Long> {
    
    @Override
    public String doSharding(Collection<String> availableTargetNames,
                             PreciseShardingValue<Long> shardingValue) {
        Long value = shardingValue.getValue();
        // 自定义分片逻辑
        int shardingIndex = (int) (value % availableTargetNames.size());
        return new ArrayList<>(availableTargetNames).get(shardingIndex);
    }
    
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         RangeShardingValue<Long> shardingValue) {
        // 范围查询可能跨多个分片
        Range<Long> range = shardingValue.getValue();
        
        // 如果范围跨度过大，返回所有分片
        if (isWideRange(range)) {
            return availableTargetNames;
        }
        
        // 计算范围内的分片
        return calculateRangeShardingTargets(availableTargetNames, range);
    }
}
```

### 4.5.5 复合分片算法（ComplexShardingAlgorithm）

#### 算法原理

复合分片算法支持基于多个分片键进行分片，通过表达式计算确定目标分片。

```java
public interface ComplexShardingAlgorithm<T extends Comparable<T>> 
    extends ShardingAlgorithm {
    
    /**
     * 多键分片
     * @param availableTargetNames 可用目标分片列表
     * @param shardingValues 所有分片键的值
     * @return 目标分片集合
     */
    Collection<String> doSharding(Collection<String> availableTargetNames,
                                  Collection<ShardingValue<T>> shardingValues);
}
```

#### 适用场景

- 需要同时使用多个分片键
- 分片策略复杂，简单的单键分片无法满足
- 业务逻辑需要综合考虑多个字段

#### 配置示例

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..15}
      # 使用复合分片策略
      tableStrategy:
        complex:
          shardingColumns: user_id, order_id
          shardingAlgorithmName: order_complex
  
  shardingAlgorithms:
    order_complex:
      type: COMPLEX
      props:
        # 表达式分片算法类
        algorithm-class-name: com.example.MyComplexShardingAlgorithm
```

#### 表达式分片配置

```yaml
# 使用表达式进行复合分片
order_complex:
  type: COMPLEX_INLINE
  props:
    # 复合分片表达式：user_id 后两位 + order_id 后两位
    # 结果 0-15 对应 t_order_0 到 t_order_15
    sharding-columns: user_id,order_id
    algorithm-expression: "ds_${user_id % 4}.t_order_${(user_id % 4) * 4 + (order_id % 4)}"
```

#### 自定义复合分片算法

```java
public class MyComplexShardingAlgorithm implements ComplexShardingAlgorithm<Long> {
    
    @Override
    public Collection<String> doSharding(Collection<String> availableTargetNames,
                                         Collection<ShardingValue<Long>> shardingValues) {
        // 分离用户ID和订单ID
        Long userId = null;
        Long orderId = null;
        
        for (ShardingValue<Long> sv : shardingValues) {
            if ("user_id".equals(sv.getColumnName())) {
                userId = sv.getValue();
            } else if ("order_id".equals(sv.getColumnName())) {
                orderId = sv.getValue();
            }
        }
        
        // 复合分片逻辑
        int dbShardingIndex = (int) (userId % 4);
        int tableShardingIndex = (int) ((userId % 4) * 4 + (orderId % 4));
        
        String target = String.format("ds_%d.t_order_%d", dbShardingIndex, tableShardingIndex);
        
        Set<String> result = new HashSet<>();
        for (String name : availableTargetNames) {
            if (name.equals(target) || name.startsWith("ds_" + dbShardingIndex + ".")) {
                result.add(name);
            }
        }
        return result;
    }
}
```

## 4.7 绑定表概念与配置

### 4.7.1 绑定表概念

**绑定表（Binding Tables）** 是指具有相同分片规则的表，在关联查询时可以避免跨分片笛卡尔积，提升查询性能。

```
┌────────────────────────────────────────────────────────────────┐
│                     非绑定表关联查询                            │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  t_order (user_id % 4 -> 0,1,2,3)                             │
│  t_order_item (order_id % 4 -> 0,1,2,3)                       │
│                                                                │
│  查询: SELECT * FROM t_order o                                 │
│        JOIN t_order_item i ON o.order_id = i.order_id         │
│        WHERE o.user_id = 1001                                  │
│                                                                │
│  笛卡尔积结果:                                                 │
│  - t_order: 命中 ds_1 (user_id=1001 -> 1001%4=1)              │
│  - t_order_item: 需要扫描所有 4 个分片进行关联                 │
│                                                                │
└────────────────────────────────────────────────────────────────┘

┌────────────────────────────────────────────────────────────────┐
│                      绑定表关联查询                             │
├────────────────────────────────────────────────────────────────┤
│                                                                │
│  配置: bindingTables: [t_order,t_order_item]                   │
│                                                                │
│  查询: SELECT * FROM t_order o                                 │
│        JOIN t_order_item i ON o.order_id = i.order_id         │
│        WHERE o.user_id = 1001                                  │
│                                                                │
│  优化后:                                                       │
│  - 先定位 t_order 在 ds_1                                      │
│  - order_id 分片键相同，自动计算 t_order_item 在 ds_1           │
│  - 仅查询 ds_1 的两个表，避免笛卡尔积                          │
│                                                                │
└────────────────────────────────────────────────────────────────┘
```

### 4.7.2 绑定表配置

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..3}
      databaseStrategy:
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: mod
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: mod
    
    t_order_item:
      actualDataNodes: ds_${0..3}.t_order_item_${0..3}
      databaseStrategy:
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: mod
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: mod
  
  # 绑定表配置 - 具有相同分片规则的表
  bindingTables:
    - t_order,t_order_item
```

### 4.7.3 绑定表查询示例

```java
// 查询用户订单及其明细 - 使用绑定表
String sql = """
    SELECT o.order_id, o.user_id, o.total_amount,
           i.product_name, i.quantity, i.price
    FROM t_order o
    JOIN t_order_item i ON o.order_id = i.order_id
    WHERE o.user_id = ?
    """;
    
// 假设 user_id = 1001
// 自动路由到 ds_1，无需跨分片查询
List<OrderDetail> results = jdbcTemplate.query(sql, 1001);
```

## 4.8 分片后 SQL 执行情况分析

### 4.8.1 SQL 执行场景分类

| 场景 | 路由类型 | 说明 |
|-----|---------|------|
| 查询单分片 | 单点路由 | 分片键等值查询，定位到单一分片 |
| 查询多分片 | 广播路由 | 无分片键或范围查询，扫描所有分片 |
| 插入单分片 | 单点路由 | 分片键等值插入，定位到单一分片 |
| 插入多分片 | 多点路由 | 无分片键插入，广播到所有分片 |
| 更新单分片 | 单点路由 | 分片键等值更新，定位到单一分片 |
| 更新多分片 | 多点路由 | 无分片键或条件路由到多个分片 |

### 4.8.2 路由情况分析

#### 场景一：分片键等值查询

```sql
-- 分片键 = 1001
SELECT * FROM t_order WHERE user_id = 1001
```

```
路由结果：
- 定位到 ds_1（user_id % 4 = 1）
- 仅查询 t_order_1
- 执行：1 次查询
```

#### 场景二：分片键 IN 查询

```sql
-- 分片键 IN
SELECT * FROM t_order WHERE user_id IN (1001, 1002, 1003)
```

```
路由结果：
- user_id = 1001 -> ds_1
- user_id = 1002 -> ds_2
- user_id = 1003 -> ds_3
- 并行查询 3 个分片
- 执行：3 次查询，结果合并
```

#### 场景三：范围查询

```sql
-- 分片键范围
SELECT * FROM t_order WHERE user_id BETWEEN 1001 AND 1010
```

```
路由结果：
- user_id % 4 可能落在任意分片
- 广播到所有 4 个分片
- 执行：4 次查询，结果合并
```

#### 场景四：无分片键查询

```sql
-- 无分片键
SELECT * FROM t_order WHERE status = 'COMPLETED'
```

```
路由结果：
- 无法定位分片
- 广播到所有分片
- 执行：4 次查询，结果合并
```

### 4.8.3 分片后 SQL 限制

```sql
-- ❌ 不支持跨分片排序（LIMIT 在分片内执行）
SELECT * FROM t_order ORDER BY create_time LIMIT 10
-- 正确做法：应用层合并后再排序

-- ❌ 不支持跨分片分组聚合（需返回各分片结果后合并）
SELECT status, COUNT(*) FROM t_order GROUP BY status
-- 需要使用 SHARDING_SPHERE 提供的聚合函数

-- ❌ 不支持跨分片联合查询（可能笛卡尔积）
SELECT * FROM t_order_0 UNION SELECT * FROM t_order_1
-- 应避免此类查询
```

## 4.9 跨分片查询处理

### 4.9.1 跨分片查询挑战

| 挑战 | 说明 | 处理方式 |
|-----|------|---------|
| 数据合并 | 多分片结果集需合并排序 | 应用层处理或使用 Streaming |
| 聚合计算 | COUNT/SUM/AVG 等需合并 | 二次聚合或 Pushdown |
| 分页查询 | 分页需获取全局偏移量 | 先聚合后分页 |
| 分布式事务 | 跨分片更新需事务保障 | XA 事务或柔性事务 |

### 4.9.2 跨分片查询配置

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..3}
  
  # 广播表（每分片都有相同数据，用于跨分片关联）
  broadcastTables:
    - t_config
  
  # 默认分片策略
  defaultDatabaseStrategy:
    standard:
      shardingColumn: user_id
      shardingAlgorithmName: mod
  
  defaultTableStrategy:
    none:
```

### 4.9.3 跨分片查询最佳实践

#### 1. 优先使用分片键查询

```java
// ✅ 最佳实践：使用分片键定位单分片
@Query("SELECT * FROM t_order WHERE user_id = ?1 AND order_id = ?2")
Order findByUserIdAndOrderId(Long userId, Long orderId);

// ⚠️ 次优：范围查询，跨多个分片
@Query("SELECT * FROM t_order WHERE user_id BETWEEN ?1 AND ?2")
List<Order> findByUserIdRange(Long startUserId, Long endUserId);

// ❌ 避免：无分片键全分片扫描
@Query("SELECT * FROM t_order WHERE status = ?1")
List<Order> findByStatus(String status);
```

#### 2. 分页查询优化

```java
// ❌ 低效：深度分页
String sql = "SELECT * FROM t_order ORDER BY create_time LIMIT 10000, 10";

// ✅ 高效：基于分片键的分页
String sql = "SELECT * FROM t_order WHERE user_id = ? AND order_id > ? ORDER BY order_id LIMIT 10";
// 基于上次查询的最大 order_id
```

#### 3. 关联查询优化

```java
// ✅ 使用绑定表关联
@Query("""
    SELECT o.*, i.*
    FROM t_order o
    JOIN t_order_item i ON o.order_id = i.order_id
    WHERE o.user_id = ?
    """)
List<OrderWithItem> findOrderWithItems(Long userId);

// ⚠️ 跨分片关联需谨慎
@Query("""
    SELECT o.*, c.*
    FROM t_order o
    JOIN t_customer c ON o.customer_id = c.customer_id
    WHERE o.user_id = ?
    """)
// 确保 customer 表使用相同的分片键或配置为广播表
```

#### Streaming 查询模式

```java
// 使用 Streaming 避免一次性加载所有数据
try (Stream<Order> orderStream = orderRepository.streamAllByUserId(userId)) {
    orderStream.forEach(order -> {
        // 逐条处理，避免 OOM
    });
}
```

### 关键概念总结

| 概念 | 说明 | 重要性 |
|-----|------|-------|
| 分片键 | 确定数据拆分方向的字段 | ★★★★★ |
| 水平分片 | 按行拆分，数据分布到多个分片 | ★★★★★ |
| 垂直分片 | 按列拆分，字段分布到不同分片 | ★★★☆☆ |
| 绑定表 | 具有相同分片规则的关联表 | ★★★★☆ |
| 路由策略 | 决定 SQL 执行的分片 | ★★★★★ |

### 最佳实践建议

1. **分片键选择**：优先选择高选择性、经常作为查询条件的字段
2. **分片算法**：根据数据特征选择合适的算法，取模适合均匀分布，时间范围适合时序数据
3. **绑定表配置**：关联查询的表应配置为绑定表，避免笛卡尔积
4. **避免跨分片**：尽量将关联数据的分片键保持一致
5. **分页优化**：深度分页应基于分片键进行游标分页
