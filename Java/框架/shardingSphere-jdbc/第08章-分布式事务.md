# 第8章：分布式事务

## 8.1 分布式事务背景

### 8.1.1 从本地事务到分布式事务

在传统的单体应用中，所有业务操作都在同一个数据库实例中完成，可以简单地使用本地事务（Local Transaction）来保证数据一致性。当应用需要同时操作多个数据库实例，或者拆分为微服务架构后，每个服务拥有独立的数据存储时，单一数据库的本地事务机制已无法满足需求。

考虑以下业务场景：
- 订单服务与库存服务分别部署在不同进程，订单扣款与库存扣减需要保持一致
- 数据库分库分表后，同一业务操作可能涉及多个数据节点
- 微服务架构中，一次请求需要调用多个服务并保证数据一致性

这些场景下，事务的参与者不再处于同一个进程或同一个数据库实例中，传统的 ACID 事务模型无法直接使用，必须引入分布式事务解决方案。

### 8.1.2 CAP 理论

1999 年，Eric Brewer 提出了 CAP 理论，用于指导分布式系统设计。该理论指出分布式系统无法同时满足以下三个特性：

| 特性 | 含义 |
|------|------|
| **Consistency（一致性）** | 所有节点在同一时刻看到相同的数据副本，写操作完成后，任何读操作都能获取到最新的数据 |
| **Availability（可用性）** | 每个请求都能在有限时间内得到响应，无论成功或失败 |
| **Partition Tolerance（分区容错性）** | 系统在遇到网络分区故障时仍能继续运行 |

CAP 理论的核心结论是：在存在网络分区的情况下，无法同时保证一致性和可用性。设计师必须在 C 和 A 之间做出权衡：

- **CP 系统**：优先保证一致性，在网络分区时可能拒绝服务。Zookeeper、HBase 等采用此策略。
- **AP 系统**：优先保证可用性，允许在网络分区时返回过期数据但仍可访问。Cassandra、DynamoDB 等采用此策略。

对于分布式事务系统而言，通常会在网络分区发生时选择牺牲可用性，以确保事务的一致性。

### 8.1.3 BASE 理论

2008 年，eBay 的架构师基于大规模分布式系统的实践提出了 BASE 理论，作为 CAP 理论的实际应用指南。BASE 是 **Basically Available、Soft State、Eventually Consistent** 的缩写：

| 术语 | 含义 |
|------|------|
| **Basically Available（基本可用）** | 允许系统在故障时降级服务，但保持核心功能可用。例如秒杀场景下降级为排队机制 |
| **Soft State（软状态）** | 允许系统数据存在中间状态，不要求强一致性。例如订单状态为"处理中"而非"已完成" |
| **Eventually Consistent（最终一致性）** | 系统在故障恢复后，经过一定时间窗口达到一致状态。不要求瞬时一致，但保证最终一致 |

BASE 理论是对强一致性（ACID）的妥协，通过牺牲实时一致性换取可用性和性能。这正是 Saga 模式等柔性事务的思想基础。

### 8.1.4 分布式事务的两种模式

根据对一致性的不同承诺，分布式事务分为两大模式：

**刚性事务（Hard Transaction）**：遵循 ACID 原则，通过强一致性协议保证原子性。如 XA 事务（两阶段提交、三阶段提交）。优点是数据一致性有保障，缺点是性能开销大，资源锁定时间长。

**柔性事务（Soft Transaction）**：遵循 BASE 理论，通过补偿机制实现最终一致性。如 Saga 模式、最大努力送达模式。优点是性能高、资源锁定时间短，缺点是只能保证最终一致性，可能存在短暂的数据不一致窗口。

ShardingSphere-JDBC 对上述两种模式均有支持，可根据业务场景灵活选择。

## 8.2 ShardingSphere-JDBC 事务架构

### 8.2.1 事务核心接口

ShardingSphere 通过 `TransactionManager` 接口统一管理分布式事务，该接口定义了所有事务操作的核心方法：

```java
public interface TransactionManager {
    
    /**
     * 开启新事务
     */
    TransactionType getTransactionType();
    
    /**
     * 创建保存点，允许部分回滚
     */
    Savepoint createSavepoint();
    
    /**
     * 回滚到指定保存点
     */
    void rollbackToSavepoint(Savepoint savepoint);
    
    /**
     * 释放保存点
     */
    void releaseSavepoint(Savepoint savepoint);
    
    /**
     * 获取事务所在数据库连接
     */
    Connection getConnection();
    
    /**
     * 事务是否活跃
     */
    boolean isActive();
    
    /**
     * 是否为自动提交模式
     */
    boolean isAutoCommit();
    
    /**
     * 设置为自动提交
     */
    void setAutoCommit(boolean autoCommit) throws SQLException;
    
    /**
     * 物理连接是否已关闭
     */
    boolean isClosePhysicalConnection();
    
    /**
     * 物理连接超时时间
     */
    long getConnectionCreationTimeMillis();
    
    /**
     * 同步事务状态
     */
    void doInTransaction(TransactionCallback callback) throws SQLException;
    
    /**
     * 忽略事务隔离级别的约束
     */
    void addTransactionIsolationLevelIgnoredConnection(Connection connection);
    
    /**
     * 设置事务超时时间
     */
    void setTransactionTimeout(int seconds);
}
```

事务类型通过 `TransactionType` 枚举定义，包括 `LOCAL`、`XA` 和 `BASE` 三种类型：

```java
public enum TransactionType {
    LOCAL,   // 本地事务
    XA,      // XA 事务（两阶段提交）
    BASE     // 柔性事务（Saga）
}
```

### 8.2.2 事务 Hook 机制

ShardingSphere 通过 `Transaction Sachs` 机制在数据库操作关键节点注入自定义逻辑，主要包括：

```java
public interface TransactionSach {
    
    /**
     * 事务开始时调用
     */
    void onTransactionBegin();
    
    /**
     * 事务提交前调用
     */
    void beforeTransactionCommit();
    
    /**
     * 事务提交后调用
     */
    void afterTransactionCommit();
    
    /**
     * 事务回滚前调用
     */
    void beforeTransactionRollback();
    
    /**
     * 事务回滚后调用
     */
    void afterTransactionRollback();
}
```

通过实现此接口，可以在事务生命周期中进行日志记录、性能监控等操作。

## 8.3 LOCAL 事务

### 8.3.1 原理概述

LOCAL 事务是 ShardingSphere-JDBC 默认的事务处理模式，也称为"本地事务"或"无事务"。在这种模式下，ShardingSphere-JDBC 不会真正参与分布式事务的协调，而是将所有操作直接透传到底层数据库执行。

**工作原理**：
- 当配置为 LOCAL 事务时，ShardingSphere-JDBC 不提供跨数据节点的事务保证
- 每个数据库连接独立提交或回滚，不存在全局事务协调
- 跨分片操作各自独立成功或失败，不保证原子性

这种模式适用于：
- 单个数据库实例内的操作（无跨库需求）
- 对一致性要求不高，可以接受最终不一致的场景
- 追求最高性能，不需要事务支持的场景

### 8.3.2 配置方式

在 `ShardingSphere-JDBC` 的配置文件中，可以通过 `transaction` 配置项指定事务类型：

```yaml
data-source-proxy.yaml 配置示例：

dataSources:
  ds_0:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    url: jdbc:mysql://localhost:3306/ds_0?useSSL=false&serverTimezone=UTC
    username: root
    password: 
  ds_1:
    dataSourceClassName: com.zaxxer.hikari.HikariDataSource
    url: jdbc:mysql://localhost:3306/ds_1?useSSL=false&serverTimezone=UTC
    username: root
    password: 

rules:
  - !TRANSACTION
    defaultType: LOCAL
    providerType: Atomikos
```

其中：
- `defaultType`：指定默认事务类型，可选 `LOCAL`、`XA`、`BASE`
- `providerType`：指定事务提供者，`LOCAL` 类型无需特殊提供者

### 8.3.3 代码使用示例

```java
public class LocalTransactionDemo {
    
    public void transfer(ShardingSphereDataSource dataSource) throws SQLException {
        // 获取连接（自动使用 LOCAL 事务）
        try (Connection conn = dataSource.getConnection()) {
            conn.setAutoCommit(false);
            
            // 操作 ds_0
            conn.prepareStatement("UPDATE account SET balance = balance - 100 WHERE user_id = ?")
                .setInt(1, 1).executeUpdate();
            
            // 操作 ds_1
            conn.prepareStatement("UPDATE account SET balance = balance + 100 WHERE user_id = ?")
                .setInt(1, 2).executeUpdate();
            
            conn.commit();
        }
    }
}
```

**注意**：LOCAL 事务模式下，上述两次跨库操作实际是两个独立的事务。如果第二个操作失败，第一个操作已经提交，无法自动回滚。这正是 LOCAL 事务的局限性所在。

### 8.3.4 使用场景分析

| 场景 | 推荐使用 LOCAL | 说明 |
|------|----------------|------|
| 单库操作 | 是 | 同一数据库实例内，无跨库需求 |
| 只读操作 | 是 | 不涉及数据修改，不需要事务保护 |
| 分库分表但单库操作 | 是 | 所有操作落在同一数据节点 |
| 跨库操作 | 否 | 需要 XA 或 BASE 事务保证原子性 |
| 对数据一致性要求极高 | 否 | 必须使用 XA 事务 |

## 8.4 XA 事务

### 8.4.1 两阶段提交协议原理

XA（eXtended Architecture）是 X/Open 组织定义的分布式事务处理标准，其核心是 **两阶段提交（Two-Phase Commit，2PC）** 协议。

**两阶段提交流程**：

```
                    ┌─────────────────────────────────────────┐
                    │              应用层                      │
                    └───────────────────┬─────────────────────┘
                                        │ 1. 开启事务
                                        ▼
                    ┌─────────────────────────────────────────┐
                    │         事务管理器（TM）                  │
                    │   ─────────────────────────────────   │
                    │   协调所有参与者（RM）执行事务             │
                    └───────────────────┬─────────────────────┘
                                        │ 2. 执行阶段（Phase 1）
                                        │    "Prepare"
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
            ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
            │  RM (ds_0)    │   │  RM (ds_1)    │   │  RM (ds_n)    │
            │  执行操作      │   │  执行操作      │   │  执行操作      │
            │  锁定资源      │   │  锁定资源      │   │  锁定资源      │
            │  写预提交日志  │   │  写预提交日志  │   │  写预提交日志  │
            └───────┬───────┘   └───────┬───────┘   └───────┬───────┘
                    │                   │                   │
                    │ 3. 投票：Yes/No   │                   │
                    ▼                   ▼                   ▼
                    └───────────────────┬─────────────────────┘
                                        │
                    ┌───────────────────┴───────────────────┐
                    │         事务管理器（TM）                  │
                    │   如果所有 RM 都投票 Yes：                │
                    │     进入提交阶段                          │
                    │   如果任何 RM 投票 No：                   │
                    │     通知所有 RM 回滚                       │
                    └───────────────────┬─────────────────────┘
                                        │ 4. 提交阶段（Phase 2）
                                        │    "Commit"
                    ┌───────────────────┼───────────────────┐
                    ▼                   ▼                   ▼
            ┌───────────────┐   ┌───────────────┐   ┌───────────────┐
            │  RM (ds_0)    │   │  RM (ds_1)    │   │  RM (ds_n)    │
            │  提交事务      │   │  提交事务      │   │  提交事务      │
            │  释放锁       │   │  释放锁       │   │  释放锁       │
            └───────────────┘   └───────────────┘   └───────────────┘
```

**阶段一（Prepare）**：
1. 事务管理器向所有参与者发送 `prepare` 请求
2. 参与者执行事务操作（但不提交），锁定所需资源
3. 参与者写入 `redo` 日志（用于恢复），然后返回 `vote-commit` 或 `vote-abort`

**阶段二（Commit/Rollback）**：
- 如果所有参与者都返回 `vote-commit`：事务管理器发送 `commit` 请求，所有参与者正式提交事务并释放锁
- 如果任何一个参与者返回 `vote-abort`：事务管理器发送 `rollback` 请求，所有参与者回滚事务并释放锁

**XA 的优点**：
- 提供强一致性保证，所有参与者同时提交或同时回滚
- 事务 ACID 属性得到完整保持

**XA 的缺点**：
- 性能开销大，需要多次网络通信和磁盘同步
- 资源锁定时间长，从 prepare 到 commit 期间，所有资源被锁定
- 单点故障风险：事务管理器崩溃将导致所有参与者阻塞

### 8.4.2 ShardingSphere-JDBC 中的 XA 实现

ShardingSphere-JDBC 的 XA 事务支持基于 JTA（Java Transaction API）实现，内部集成了多种 XA 事务管理器：

| **Atomikos** | 开源、轻量级 XA 事务管理器，默认推荐 |
| **Narayana** | JBoss 开源事务管理器，功能全面 |
| **Bitronix** | 曾经流行的开源 XA 实现（已停止维护） |

### 8.4.5 XA 事务代码示例

```java
public class XATransactionDemo {
    
    private final ShardingSphereDataSource dataSource;
    
    public XATransactionDemo(ShardingSphereDataSource dataSource) {
        this.dataSource = dataSource;
    }
    
    /**
     * 跨库转账，使用 XA 事务保证一致性
     */
    public void transferWithXA(int fromUserId, int toUserId, BigDecimal amount) throws SQLException {
        // 方式一：自动事务模式
        try (Connection conn = dataSource.getConnection()) {
            // 设置事务类型为 XA
            conn.setAutoCommit(false);
            
            // 在 ds_0 扣款
            String sql1 = "UPDATE account SET balance = balance - ? WHERE user_id = ? AND balance >= ?";
            try (PreparedStatement ps = conn.prepareStatement(sql1)) {
                ps.setBigDecimal(1, amount);
                ps.setInt(2, fromUserId);
                ps.setBigDecimal(3, amount);
                int rows = ps.executeUpdate();
                if (rows == 0) {
                    throw new SQLException("余额不足");
                }
            }
            
            // 在 ds_1 收款
            String sql2 = "UPDATE account SET balance = balance + ? WHERE user_id = ?";
            try (PreparedStatement ps = conn.prepareStatement(sql2)) {
                ps.setBigDecimal(1, amount);
                ps.setInt(2, toUserId);
                ps.executeUpdate();
            }
            
            conn.commit();
        } catch (SQLException e) {
            // XA 事务自动回滚
            throw e;
        }
    }
    
    /**
     * 方式二：使用 TransactionType 显式指定
     */
    public void transferWithTransactionType(int fromUserId, int toUserId, BigDecimal amount) throws SQLException {
        // 通过 SPI 加载的事务管理器创建 XA 事务
        TransactionType transactionType = TransactionType.XA;
        
        // 获取 XA 连接
        XAConnection xaConnection = ((XAConnection) dataSource.getConnection());
        XAResource xaResource = xaConnection.getXAResource();
        
        // 开启 XA 事务
        Xid xid = new XidImpl(new byte[]{1}, new byte[]{2}, new byte[]{3});
        xaResource.start(xid, XAResource.TMNOFLAGS);
        
        try {
            // 执行 SQL 操作
            Connection conn = xaConnection.getConnection();
            // ... 执行操作 ...
            conn.commit();
            
            xaResource.end(xid, XAResource.TMSUCCESS);
            xaResource.prepare(xid);
            xaResource.commit(xid, false);
        } catch (SQLException e) {
            xaResource.end(xid, XAResource.TMFAIL);
            xaResource.rollback(xid);
            throw e;
        }
    }
}
```

### 8.4.6 XA 事务的局限性

虽然 XA 事务提供了强一致性保证，但在生产环境中存在以下挑战：

**性能开销**：
- 每个参与者需要多次磁盘同步（prepare log、commit log）
- 网络通信开销显著
- 资源锁定时间从 prepare 持续到 commit

**隔离性限制**：
- XA 事务在 prepare 阶段锁定资源，其他事务无法访问
- 长时间运行的 XA 事务会严重影响系统吞吐量

**建议场景**：
- 跨多个数据库的强一致性操作
- 对数据一致性要求极高的金融场景
- 事务执行时间较短的场景

## 8.5 BASE 柔性事务（Saga 模式）

### 8.5.1 Saga 模式原理

Saga 模式是一种基于补偿的分布式事务解决方案，由 Hector Garcia-Molina 和 Kenneth Salem 于 1987 年提出。其核心思想是将长事务拆分为多个短事务，每个短事务都有对应的补偿操作。

**基本原理**：
```
  T1       T2       T3       T4
 ┌───┐    ┌───┐    ┌───┐    ┌───┐
 │ A │───▶│ B │───▶│ C │───▶│ D │   正向操作
 └───┘    └───┘    └───┘    └───┘

  C4       C3       C2       C1
 ┌───┐    ┌───┐    ┌───┐    ┌───┐
 │ D │◀───│ C │◀───│ B │◀───│ A │   补偿操作
 └───┘    └───┘    └───┘    └───┘
```

**执行流程**：
1. 执行 T1，如果成功则继续执行 T2
2. 执行 T2，如果成功则继续执行 T3
3. 如果 Tn 执行失败，触发补偿 C(n-1)、C(n-2)、...、C1
4. 所有补偿操作执行完成后，事务"最终一致"

### 8.5.2 Saga 与 XA 的区别

| 特性 | Saga | XA |
|------|------|-----|
| 一致性模型 | 最终一致 | 强一致 |
| 资源锁定 | 无锁定（乐观并发） | 两阶段锁定 |
| 性能 | 高 | 中等 |
| 隔离性 | 无隔离保证 | 可序列化隔离 |
| 适用场景 | 长事务 | 短事务 |
| 补偿复杂度 | 高（需要编写补偿逻辑） | 低（自动回滚） |

## 8.6 最大努力送达型事务

### 8.6.1 原理概述

最大努力送达型（Best Effort Delivery）事务是一种介于可靠消息与刚性事务之间的折中方案。其核心思想是：

1. 尽力尝试执行事务操作
2. 如果操作失败，允许多次重试
3. 重试超过阈值后，放弃并记录异常

**与 Saga 的区别**：
- Saga 通过补偿操作回滚，最大努力送达不提供回滚
- Saga 保证最终一致性，最大努力送达只保证"尽力"
- 最大努力送达实现更简单，但一致性保证较弱

### 8.6.2 实现方式

最大努力送达通常通过**消息队列 + 本地消息表**实现：

```
┌─────────────────────────────────────────────────────────────┐
│                        应用层                                │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│   ┌────────────────────────────────────────────────────┐   │
│   │               本地消息表                            │   │
│   │  ┌──────┬──────────┬────────┬─────────────────┐    │   │
│   │  │ msg_1│  PENDING │ ds_0   │ {"userId": 1}  │    │   │
│   │  │ msg_2│  SENT    │ ds_1   │ {"amount": 100}│    │   │
│   │  │ msg_3│  FAILED  │ ds_0   │ {"id": 999}   │    │   │
│   │  └──────┴──────────┴────────┴─────────────────┘    │   │
│   └────────────────────────────────────────────────────┘   │
│                           ▲                                 │
│                           │ 定时扫描                        │
│                           ▼                                 │
│   ┌────────────────────────────────────────────────────┐   │
│   │            消息发送服务（RetryScheduler）           │   │
│   └────────────────────────────────────────────────────┘   │
│                           │                                 │
│                           ▼                                 │
│   ┌────────────────────────────────────────────────────┐   │
│   │                  消息队列                           │   │
│   └────────────────────────────────────────────────────┘   │
│                           │                                 │
│                           ▼                                 │
│   ┌────────────────────────────────────────────────────┐   │
│   │               消息消费服务                           │   │
│   └────────────────────────────────────────────────────┘   │
│                           │                                 │
└───────────────────────────┼─────────────────────────────────┘
                            ▼
                    ┌─────────────┐
                    │  目标数据库   │
                    └─────────────┘
```

**工作流程**：
1. 业务操作与消息记录在同一本地事务中写入本地消息表
2. 后台任务定时扫描 PENDING 状态的消息
3. 将消息发送到消息队列
4. 更新消息状态为 SENT
5. 如果发送失败，更新为 FAILED 并记录重试次数

```yaml
    max-attempts: 5           # 最大重试次数
    initial-interval: 1000     # 初始重试间隔（毫秒）
```

### 8.6.4 代码示例

```java
@Service
public class BestEffortDeliveryService {
    
    @Autowired
    private ShardingSphereDataSource dataSource;
    
    /**
     * 异步消息发送实现
     */
    public void sendAsyncMessage(String bizType, Object payload) {
        try (Connection conn = dataSource.getConnection()) {
            conn.setAutoCommit(false);
            
            // 1. 执行业务操作
            executeBusinessOperation(bizType, payload);
            
            // 2. 写入本地消息表
            String sql = "INSERT INTO async_message (biz_type, payload, status, create_time) VALUES (?, ?, ?, ?)";
            try (PreparedStatement ps = conn.prepareStatement(sql)) {
                ps.setString(1, bizType);
                ps.setString(2, JSON.toJSONString(payload));
                ps.setString(3, "PENDING");
                ps.setTimestamp(4, new Timestamp(System.currentTimeMillis()));
                ps.executeUpdate();
            }
            
            conn.commit();
        }
    }
    
    /**
     * 后台任务：重试发送失败的消息
     */
    @Scheduled(fixedDelay = 5000)
    public void retryPendingMessages() {
        String querySql = "SELECT id, biz_type, payload FROM async_message WHERE status = 'FAILED' AND retry_count < ?";
        String updateSql = "UPDATE async_message SET status = ?, retry_count = retry_count + 1 WHERE id = ?";
        
        try (Connection conn = dataSource.getConnection();
             PreparedStatement queryPs = conn.prepareStatement(querySql);
             PreparedStatement updatePs = conn.prepareStatement(updateSql)) {
            
            queryPs.setInt(1, 5); // max retry
            ResultSet rs = queryPs.executeQuery();
            
            while (rs.next()) {
                Long id = rs.getLong("id");
                String bizType = rs.getString("biz_type");
                String payload = rs.getString("payload");
                
                try {
                    // 重新发送消息
                    sendToMQ(bizType, payload);
                    
                    // 更新状态为已发送
                    updatePs.setString(1, "SENT");
                    updatePs.setLong(2, id);
                    updatePs.executeUpdate();
                } catch (Exception e) {
                    // 更新重试次数
                    updatePs.setString(1, "FAILED");
                    updatePs.setLong(2, id);
                    updatePs.executeUpdate();
                }
            }
        } catch (SQLException e) {
            log.error("重试消息失败", e);
        }
    }
}
```

- 业务操作具有幂等性
- 异步任务、通知类场景（如发送短信、邮件通知）
- 数据同步类场景（如跨系统数据备份）

## 8.7 Seata 集成配置

### 8.7.1 Seata 简介

Seata（Simple Extensible Atomic Transaction Architecture）是阿里巴巴开源的分布式事务解决方案，支持 AT、TCC、Saga、XA 四种事务模式。ShardingSphere-JDBC 可以与 Seata 无缝集成，扩展事务处理能力。

**Seata 核心组件**：

| 组件 | 说明 |
|------|------|
| TC（Transaction Coordinator） | 事务协调器，维护全局事务状态，协调各分支事务的提交/回滚 |
| TM（Transaction Manager） | 事务管理器，定义全局事务的边界，开启/提交/回滚全局事务 |
| RM（Resource Manager） | 资源管理器，管理分支事务处理的资源，与 TC 交互注册分支事务和报告状态 |

### 8.7.3 ShardingSphere + Seata 集成原理

ShardingSphere 与 Seata 的集成通过以下机制实现：

**数据源代理**：ShardingSphere 将普通 DataSource 包装为 Seata 可管理的分支事务资源：

```java
// SeataDataSourceProxy 包装逻辑
public class SeataDataSourceProxy implements DataSource {
    
    private final DataSource originalDataSource;
    private final ConnectionProxy connectionProxy;
    
    // 每个数据源自动注册到 TC
    public SeataDataSourceProxy(DataSource dataSource) {
        this.originalDataSource = dataSource;
        this.connectionProxy = new ConnectionProxy(dataSource.getConnection());
        
        // 向 TC 注册资源
        ResourceManager resourceManager = RmClient.getInstance().getResourceManager();
        resourceManager.registerResource(new Resource(dataSource));
    }
}
```

**全局事务扫描**：通过 AOP 拦截 `@GlobalTransactional` 注解，自动开启全局事务：

```java
@Aspect
public class GlobalTransactionalInterceptor {
    
    @Around("@annotation(io.seata.spring.annotation.GlobalTransactional)")
    public Object intercept(ProceedingJoinPoint point) throws Throwable {
        // 1. 向 TC 注册全局事务，获取 XID
        String xid = TransactionManagerHolder.get().begin();
        
        // 2. 将 XID 绑定到当前线程
        RootContext.bind(xid);
        
        try {
            // 3. 执行业务逻辑
            Object result = point.proceed();
            
            // 4. 提交全局事务
            TransactionManagerHolder.get().commit(xid);
            
            return result;
        } catch (Exception e) {
            // 5. 回滚全局事务
            TransactionManagerHolder.get().rollback(xid);
            throw e;
        } finally {
            // 6. 清除 XID
            RootContext.unbind();
        }
    }
}
```

### 8.7.5 Seata TCC 模式

TCC（Try-Confirm-Cancel）是 Seata 的另一种事务模式，适用于对性能要求较高且业务逻辑可拆分为 Try/Confirm/Cancel 三阶段的场景。

```java
/**
 * TCC 参与者实现
 */
@LocalTCC
public class InventoryTccService implementsInventoryService {
    
    @Override
    @TwoPhaseBusinessAction(name = "deductInventory", 
                           commitMethod = "confirm", 
                           rollbackMethod = "cancel")
    public boolean deductInventory(BusinessActionContext actionContext, 
                                   Long productId, Integer quantity) {
        // Try 阶段：预留资源
        // 检查库存是否充足，冻结对应数量
        boolean success = inventoryRepository.freezeStock(productId, quantity);
        if (!success) {
            throw new BizException("库存不足");
        }
        
        // 将操作上下文存入 BranchSession
        actionContext.setActionContext("productId", productId);
        actionContext.setActionContext("quantity", quantity);
        return true;
    }
    
    /**
     * Confirm 阶段：确认扣减
     */
    public boolean confirm(BusinessActionContext actionContext) {
        Long productId = (Long) actionContext.getActionContext("productId");
        Integer quantity = (Integer) actionContext.getActionContext("quantity");
        
        // 真正扣减冻结的库存
        inventoryRepository.confirmDeduct(productId, quantity);
        return true;
    }
    
    /**
     * Cancel 阶段：取消操作，释放冻结的库存
     */
    public boolean cancel(BusinessActionContext actionContext) {
        Long productId = (Long) actionContext.getActionContext("productId");
        Integer quantity = (Integer) actionContext.getActionContext("quantity");
        
        // 回滚冻结的库存
        inventoryRepository.unfreezeStock(productId, quantity);
        return true;
    }
}
```

## 8.8 事务隔离级别

### 8.8.1 隔离级别概述

数据库隔离级别定义了并发事务之间相互影响的程度。SQL 标准定义了四个隔离级别：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|----------|------|------------|------|
| **Read Uncommitted** | 可能 | 可能 | 可能 |
| **Read Committed** | 不可能 | 可能 | 可能 |
| **Repeatable Read** | 不可能 | 不可能 | 可能 |
| **Serializable** | 不可能 | 不可能 | 不可能 |

### 8.8.2 ShardingSphere 中的隔离级别

在 ShardingSphere 环境中，事务隔离级别的处理需要特别考虑：

**本地事务隔离级别**：

```java
try (Connection conn = dataSource.getConnection()) {
    // 设置隔离级别
    conn.setTransactionIsolation(Connection.TRANSACTION_SERIALIZABLE);
    
    conn.setAutoCommit(false);
    // ... 业务操作 ...
    conn.commit();
}
```

**XA 事务隔离级别**：
- XA 事务通常使用 `TRANSACTION_READ_COMMITTED` 隔离级别
- 由于 XA 的两阶段锁定机制，可重复读通过全局锁实现

**Saga 事务隔离级别**：
- Saga 模式本身不提供隔离保证
- 需要业务层通过乐观锁（如版本号）或悲观锁（如 SELECT FOR UPDATE）实现

```java
// 业务层乐观锁实现
@SagaCompensable(compensationMethod = "cancel")
public void updateAccount(Long userId, BigDecimal delta) {
    // 获取当前版本
    Account account = accountRepository.findById(userId);
    int currentVersion = account.getVersion();
    
    // 执行更新时检查版本
    String sql = "UPDATE account SET balance = balance + ?, version = version + 1 WHERE id = ? AND version = ?";
    int rows = jdbcTemplate.update(sql, delta, userId, currentVersion);
    if (rows == 0) {
        throw new ConcurrentModificationException("并发更新，请重试");
    }
}
```

### 8.8.3 跨分片事务隔离

当事务涉及多个分片时，隔离级别管理更为复杂：

**解决方案一：强制所有分片使用相同隔离级别**

```yaml
shardingsphere:
  rules:
    transaction:
      defaultType: XA
      providerType: Atomikos
    # 全局强制隔离级别
    shadow:
      enabled: true
      # 强制所有连接使用 SERIALIZABLE
      forcedSerialiableIsolationLevel: true
```

**解决方案二：在应用层处理隔离**

```java
@Service
public class BusinessService {
    
    public void crossShardOperation() {
        // 开启全局事务
        @GlobalTransactional
        public void execute() {
            // 在每个分片上执行操作
            // 通过分布式锁或乐观版本控制实现隔离
        }
    }
}
```

### 8.9.3 典型场景选型建议

| 场景 | 推荐事务类型 | 理由 |
|------|-------------|------|
| 单库操作 | LOCAL | 无跨库需求，本地事务性能最优 |

| 数据同步、备份 | 最大努力送达 | 对一致性要求低 |

**业务代码**：

```java
@Service
@RequiredArgsConstructor
public class OrderServiceImpl implements OrderService {
    
    private final ShardingSphereDataSource dataSource;
    private final OrderRepository orderRepository;
    private final InventoryService inventoryService;
    private final AccountService accountService;
    
    /**
     * 创建订单 - XA 事务保证跨库一致性
     */
    @Override
    public Order createOrder(CreateOrderRequest request) {
        // 验证请求
        validateRequest(request);
        
        // 计算订单金额
        BigDecimal orderAmount = calculateOrderAmount(request.getItems());
        
        // 获取 XA 连接
        try (Connection conn = dataSource.getConnection()) {
            conn.setAutoCommit(false);
            
            try {
                // 1. 扣减账户余额（ds_1）
                accountService.deductBalance(conn, request.getUserId(), orderAmount);
                
                // 2. 扣减库存（ds_1）
                for (OrderItem item : request.getItems()) {
                    inventoryService.deductStock(conn, item.getProductId(), item.getQuantity());
                }
                
                // 3. 创建订单记录（ds_0）
                Order order = createOrderRecord(conn, request, orderAmount);
                
                // 4. 保存订单明细（ds_0）
                saveOrderItems(conn, order.getId(), request.getItems());
                
                // 所有操作成功，提交事务
                conn.commit();
                
                // 发送订单创建事件（异步，不在事务内）
                publishOrderCreatedEvent(order);
                
                return order;
                
            } catch (Exception e) {
                // 发生异常，回滚 XA 事务
                conn.rollback();
                log.error("创建订单失败，已回滚", e);
                throw new OrderException("创建订单失败：" + e.getMessage(), e);
            }
        } catch (SQLException e) {
            throw new OrderException("获取数据库连接失败", e);
        }
    }
    
    private void accountService.deductBalance(Connection conn, Long userId, BigDecimal amount) throws SQLException {
        String sql = "UPDATE m_account SET balance = balance - ?, frozen_balance = frozen_balance + ? WHERE user_id = ? AND balance >= ?";
        try (PreparedStatement ps = conn.prepareStatement(sql)) {
            ps.setBigDecimal(1, amount);
            ps.setBigDecimal(2, amount);
            ps.setLong(3, userId);
            ps.setBigDecimal(4, amount);
            int rows = ps.executeUpdate();
            if (rows == 0) {
                throw new InsufficientBalanceException("账户余额不足");
            }
        }
    }
    
    private Order createOrderRecord(Connection conn, CreateOrderRequest request, BigDecimal amount) throws SQLException {
        String sql = "INSERT INTO t_order (order_no, user_id, total_amount, status, create_time) VALUES (?, ?, ?, ?, ?)";
        try (PreparedStatement ps = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, generateOrderNo());
            ps.setLong(2, request.getUserId());
            ps.setBigDecimal(3, amount);
            ps.setString(4, OrderStatus.PENDING.name());
            ps.setTimestamp(5, new Timestamp(System.currentTimeMillis()));
            ps.executeUpdate();
            
            ResultSet rs = ps.getGeneratedKeys();
            if (rs.next()) {
                Order order = new Order();
                order.setId(rs.getLong(1));
                order.setOrderNo(ps.getString(1));
                order.setTotalAmount(amount);
                order.setStatus(OrderStatus.PENDING);
                return order;
            }
            throw new SQLException("获取订单ID失败");
        }
    }
}
```

### 8.10.2 编程式事务使用

ShardingSphere 也支持编程式事务控制：

```java
@Service
public class TransactionalService {
    
    @Autowired
    private ShardingSphereDataSource dataSource;
    
    /**
     * 编程式事务管理
     */
    public void executeWithTransaction(TransactionType type) {
        // 方式一：使用 TransactionManager
        TransactionManager manager = TransactionManagerEngine.getTransactionManager(type);
        
        manager.begin();
        try {
            // 执行业务操作
            doBusinessOperation();
            manager.commit();
        } catch (Exception e) {
            manager.rollback();
            throw e;
        }
        
        // 方式二：使用 TransactionTemplate
        TransactionTemplate template = new TransactionTemplate(manager);
        template.execute(() -> {
            doBusinessOperation();
            return null;
        });
    }
    
    /**
     * 嵌套事务（保存点）
     */
    public void nestedTransaction() throws SQLException {
        try (Connection conn = dataSource.getConnection()) {
            conn.setAutoCommit(false);
            
            // 主事务操作 1
            executeMainOperation1(conn);
            
            // 创建保存点
            Savepoint savepoint = conn.setSavepoint("SP_1");
            
            try {
                // 嵌套事务操作
                executeNestedOperation(conn);
                conn.releaseSavepoint(savepoint);
            } catch (Exception e) {
                // 回滚到保存点
                conn.rollbackToSavepoint(savepoint);
                // 主事务继续
            }
            
            // 主事务操作 2
            executeMainOperation2(conn);
            
            conn.commit();
        }
    }
}
```

## 8.11 事务异常处理与回滚

### 8.11.1 异常分类

分布式事务中的异常可以分为以下几类：

| 异常类型 | 触发场景 | 处理策略 |
|----------|----------|----------|
| **业务异常** | 余额不足、库存不足等 | 正常回滚 |
| **超时异常** | 事务超时未响应 | 自动回滚 |
| **资源不足** | 连接池耗尽 | 重试或回滚 |
| **网络异常** | 分区故障 | 自动回滚 |
| **数据不一致** | 部分提交 | 触发补偿 |

### 8.11.2 异常处理模式

**模式一：自动回滚**

```java
public void autoRollbackDemo() throws SQLException {
    try (Connection conn = dataSource.getConnection()) {
        conn.setAutoCommit(false);
        
        // 执行操作
        executeOperation(conn);
        
        // 提交
        conn.commit();
    } catch (SQLException e) {
        // 异常时自动回滚
        throw e;
    }
}
```

**模式二：手动回滚**

```java
public void manualRollbackDemo() throws SQLException {
    Connection conn = null;
    try {
        conn = dataSource.getConnection();
        conn.setAutoCommit(false);
        
        executeOperation(conn);
        
        conn.commit();
    } catch (Exception e) {
        if (conn != null) {
            try {
                conn.rollback();
            } catch (SQLException rollbackEx) {
                log.error("回滚失败", rollbackEx);
            }
        }
        throw e;
    } finally {
        if (conn != null) {
            conn.close();
        }
    }
}
```

**模式三：部分回滚（保存点）**

```java
public void savepointDemo() throws SQLException {
    try (Connection conn = dataSource.getConnection()) {
        conn.setAutoCommit(false);
        
        // 操作 1
        executeStep1(conn);
        
        // 设置保存点
        Savepoint sp1 = conn.setSavepoint("STEP1_COMPLETE");
        
        try {
            // 操作 2（可能失败）
            executeStep2(conn);
        } catch (Exception e) {
            // 回滚到保存点，操作 1 保留
            conn.rollbackToSavepoint(sp1);
            conn.releaseSavepoint(sp1);
        }
        
        // 操作 3（继续执行）
        executeStep3(conn);
        
        conn.commit();
    }
}
```

```java
public class SagaCompensationService {

    @Scheduled(cron = "0 0 * * * ?") // 每小时执行

                retryCompensation(letter);
                letter.setStatus("PROCESSED");

                letter.setStatus("FAILED");
                letter.setErrorMessage(e.getMessage());
            }
            deadLetterRepository.save(letter);
        }
    }
```

### 8.11.5 事务最佳实践

1. **事务范围最小化**：只将必要的操作放入事务，避免长事务
2. **避免事务嵌套**：嵌套事务增加复杂度，降低性能
3. **幂等性设计**：所有事务参与者都应支持幂等操作
4. **超时合理设置**：根据业务特点设置合理的超时时间
5. **监控与告警**：对事务失败率、事务耗时进行监控
6. **优雅降级**：当事务服务不可用时，提供备选方案

```java
        this.activeTransactions = Gauge.builder("shardingsphere.transaction.active")
            .description("Active transactions")
            .register(registry, AtomicInteger::new);
    }
    
    public void recordTransaction(TransactionType type, long durationMs, boolean success) {
        transactionTotal.increment();
        if (success) {
            transactionSuccess.increment();
        } else {
            transactionFailure.increment();
        }
        transactionDuration.record(Duration.ofMillis(durationMs));
    }
}
```

### 8.12.4 告警配置

```java
@Component
public class TransactionAlertService {
    
    private static final double P99_THRESHOLD_MS = 5000; // P99 超过 5 秒告警
    private static final double FAILURE_RATE_THRESHOLD = 0.05; // 失败率超过 5% 告警
    
    @Autowired
    private AlertManager alertManager;
    
    @Autowired
    private MetricsFacade metricsFacade;
    
    @Scheduled(fixedRate = 60000) // 每分钟检查
    public void checkTransactionHealth() {
        // 检查 P99 延迟
        double p99Duration = metricsFacade.getP99Duration("transaction.duration");
        if (p99Duration > P99_THRESHOLD_MS) {
            alertManager.sendAlert(new Alert(
                "TransactionLatencyHigh",
                "Transaction P99 latency is " + p99Duration + "ms, threshold: " + P99_THRESHOLD_MS,
                AlertSeverity.WARNING
            ));
        }
        
        // 检查失败率
        double totalCount = metricsFacade.getMetric("transaction.total");
        double failureCount = metricsFacade.getMetric("transaction.failure");
        double failureRate = totalCount > 0 ? failureCount / totalCount : 0;
        
        if (failureRate > FAILURE_RATE_THRESHOLD) {
            alertManager.sendAlert(new Alert(
                "TransactionFailureRateHigh",
                "Transaction failure rate is " + (failureRate * 100) + "%, threshold: " + (FAILURE_RATE_THRESHOLD * 100) + "%",
                AlertSeverity.CRITICAL
            ));
        }
    }
}
```

**事务日志切面**：

```java
@Aspect
@Component
public class TransactionLoggingAspect {
    
    private static final Logger log = LoggerFactory.getLogger(TransactionLoggingAspect.class);
    
    @Around("execution(* *..service.*.*(..)) && @annotation(transactional)")
    public Object logTransaction(ProceedingJoinPoint joinPoint, Transactional transactional) throws Throwable {
        String methodName = joinPoint.getSignature().toShortString();
        long startTime = System.currentTimeMillis();
        
        log.info("事务开始 - 方法: {}, 类型: {}", methodName, transactional.type());
        
        try {
            Object result = joinPoint.proceed();
            long duration = System.currentTimeMillis() - startTime;
            log.info("事务提交 - 方法: {}, 耗时: {}ms", methodName, duration);
            return result;
        } catch (Exception e) {
            long duration = System.currentTimeMillis() - startTime;
            log.error("事务回滚 - 方法: {}, 耗时: {}ms, 异常: {}", methodName, duration, e.getMessage());
            throw e;
        }
    }
}
```

## 8.13 本章小结

本章详细介绍了 ShardingSphere-JDBC 的分布式事务解决方案，涵盖以下核心内容：

1. **分布式事务背景**：从 CAP/BASE 理论出发，分析了刚性事务与柔性事务的适用场景和权衡。

2. **事务架构**：ShardingSphere 通过 `TransactionManager` 接口和 `TransactionType` 枚举提供统一的事务管理抽象，支持 LOCAL/XA/BASE 三种事务类型。

3. **LOCAL 事务**：无事务协调，适用于单库或单分片操作，性能最优但不提供跨库一致性保证。

4. **XA 事务**：基于两阶段提交协议，提供强一致性保证。ShardingSphere 支持 Atomikos 和 Narayana 两种实现，适合金融级场景。

5. **BASE 柔性事务**：通过 Saga 模式实现最终一致性，性能高、资源锁定时间短，适合长事务场景，通过补偿处理异常。

6. **最大努力送达型事务**：通过消息队列和本地消息表实现，性能最高但一致性最弱，适用于允许短暂不一致的场景。

7. **Seata 集成**：ShardingSphere 可与 Seata 无缝集成，支持 AT、TCC、Saga、XA 等多种模式。

8. **事务隔离级别**：详细分析了不同事务模式下的隔离级别实现，强调业务层需要通过乐观锁或悲观锁补充 Saga 的隔离性。

9. **性能对比与选型**：通过 TPS、延迟、吞吐量等指标对比不同事务类型，并提供选型决策树指导实际场景选择。

10. **异常处理与回滚**：涵盖自动回滚、手动回滚、保存点、部分回滚等模式，以及 XA 悬挂处理和 Saga 补偿失败处理。

11. **监控与告警**：通过 Prometheus 指标采集、自定义告警规则、事务日志集成构建完整的可观测性体系。

在实际项目中，应根据业务特点（一致性要求、事务时长、性能需求）合理选择事务类型，并建立完善的异常处理和监控体系确保系统稳定运行。
