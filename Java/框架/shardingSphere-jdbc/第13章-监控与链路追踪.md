# 第13章：监控与链路追踪

## 13.1 监控体系概述

### 13.1.1 为什么需要监控

在生产环境中，对 ShardingSphere-JDBC 进行全面监控是保障系统稳定性和性能优化的基础。通过监控体系，运维人员可以实时掌握以下关键信息：

- **性能指标**：SQL 执行时间、吞吐量、响应延迟
- **分片效果**：数据分布均匀度、路由效率、跨库查询比例
- **连接池健康**：活跃连接数、空闲连接、连接泄漏检测
- **系统资源**：CPU、内存、线程池状态
- **异常告警**：慢查询、路由失败、连接超时

### 13.1.2 ShardingSphere-JDBC 监控架构

ShardingSphere-JDBC 的监控体系采用多层次、多维度的设计思路：

```
┌─────────────────────────────────────────────────────────────────────┐
│                         监控数据采集层                               │
├─────────────────────────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │ SQL执行监控 │  │ 分片路由监控 │  │ 连接池监控  │  │ 业务指标监控│ │
│  └─────────────┘  └─────────────┘  └─────────────┘  └─────────────┘ │
├─────────────────────────────────────────────────────────────────────┤
│                         指标聚合处理层                               │
│  ┌─────────────────────────────────────────────────────────────┐    │
│  │              OpenTelemetry / Micrometer                     │    │
│  └─────────────────────────────────────────────────────────────┘    │
├─────────────────────────────────────────────────────────────────────┤
│                         数据导出层                                   │
│  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐  ┌─────────────┐ │
│  │ Prometheus  │  │  Grafana    │  │   Jaeger    │  │   Zipkin    │ │
│  └─────────────┘  └─────────────┘  └─────────────┘  └─────────────┘ │
└─────────────────────────────────────────────────────────────────────┘
```

**核心组件说明：**

| 组件 | 职责 | 说明 |
|------|------|------|
| SQL 执行监控器 | 采集 SQL 执行时间、次数、成功率 | 识别慢查询和异常 SQL |
| 分片路由监控器 | 采集路由次数、数据源分布 | 评估分片策略有效性 |
| 连接池监控器 | 采集连接获取/释放、等待时间 | 预防连接泄漏和等待阻塞 |
| 指标导出器 | 将指标数据转换为标准格式 | 支持 Prometheus 等多种导出方式 |

## 13.2 Metrics 配置详解

### 13.2.1 基于 Micrometer 的指标体系

ShardingSphere-JDBC 内部使用 Micrometer 作为指标抽象层，提供统一的指标采集 API。Micrometer 支持多种监控后端，包括 Prometheus、Grafana、Datadog 等。

**核心指标类型：**

```java
// MeterRegistry 注册表 - 所有指标的容器
MeterRegistry registry = new PrometheusMeterRegistry();

// 计数器 - 记录事件发生次数
Counter sqlExecutionCounter = registry.counter("shardingsphere.sql.execute");

// 计时器 - 记录操作耗时
Timer sqlExecutionTimer = registry.timer("shardingsphere.sql.execute.time");

// gauge - 记录当前值（如连接池活跃连接数）
Gauge.builder("shardingsphere.pool.active", pool, Pool::getActiveCount)
    .register(registry);
```

## 13.3 OpenTelemetry 集成

### 13.3.1 OpenTelemetry 概述

OpenTelemetry（简称 OTel）是 CNCF 的可观测性标准项目，提供了统一的指标、日志、链路追踪规范。ShardingSphere-JDBC 支持通过 OpenTelemetry 进行监控数据导出。

**OpenTelemetry 核心概念：**

| 概念 | 说明 |
|------|------|
| Tracer | 链路追踪器，用于创建 Span |
| Span | 跨度，表示一次操作的基本单元 |
| Meter | 指标创建器，用于创建指标 |
| Metric | 指标数据（Counter、Gauge、Histogram） |
| Exporter | 数据导出器，将数据发送到后端 |
| Collector | 收集器，接收并处理遥测数据 |

**OpenTelemetry SDK 配置：**

```java
import io.opentelemetry.api.OpenTelemetry;
import io.opentelemetry.api.metrics.MeterProvider;
import io.opentelemetry.api.trace.TracerProvider;
import io.opentelemetry.sdk.OpenTelemetrySdk;
import io.opentelemetry.sdk.metrics.SdkMeterProvider;
import io.opentelemetry.sdk.resources.Resource;
import io.opentelemetry.sdk.trace.SdkTracerProvider;
import io.opentelemetry.api.common.Attributes;
import io.opentelemetry.semconv.ResourceAttributes;

@Configuration
public class OpenTelemetryConfiguration {

    @Bean
    public OpenTelemetry openTelemetry() {
        // 构建资源信息
        Resource resource = Resource.getDefault()
            .merge(Resource.create(Attributes.of(
                ResourceAttributes.SERVICE_NAME, "shardingSphere-jdbc",
                ResourceAttributes.SERVICE_VERSION, "1.0.0",
                ResourceAttributes.DEPLOYMENT_ENVIRONMENT, "production"
            )));

        // 配置 TracerProvider
        SdkTracerProvider tracerProvider = SdkTracerProvider.builder()
            .setResource(resource)
            .addSpanProcessor(BatchSpanProcessor.builder(
                OtlpGrpcSpanExporter.builder()
                    .setEndpoint("http://otel-collector:4317")
                    .build())
                .build())
            .build();

        // 配置 MeterProvider
        SdkMeterProvider meterProvider = SdkMeterProvider.builder()
            .setResource(resource)
            .registerMetricReader(
                PeriodicMetricReader.builder(
                    OtlpGrpcMetricExporter.builder()
                        .setEndpoint("http://otel-collector:4317")
                        .build())
                    .setInterval(Duration.ofSeconds(30))
                    .build())
            .build();

        return OpenTelemetrySdk.builder()
            .setTracerProvider(tracerProvider)
            .setMeterProvider(meterProvider)
            .build();
    }
}
```

### 13.3.3 指标与链路追踪关联

OpenTelemetry 的一个重要特性是能够将指标和链路追踪关联起来，使得可以从 Span 上下文获取关联的指标数据。

```java
import io.opentelemetry.api.trace.Span;
import io.opentelemetry.api.metrics.LongCounter;

public class ShardingSphereMetricsInterceptor {

    private final MeterProvider meterProvider;
    private final Tracer tracer;

    public void recordSqlExecution(String sql, long durationMs) {
        // 创建 Span
        Span span = tracer.spanBuilder("sql.execute")
            .setAttribute("db.system", "mysql")
            .setAttribute("db.statement", sql)
            .startSpan();

        try {
            // 记录指标
            LongCounter counter = meterProvider.get("shardingsphere.sql")
                .counterBuilder("execute.total")
                .setDescription("SQL execution count")
                .build();

            counter.add(1, Attributes.of(
                AttributeKey.stringKey("sql.type"), extractSqlType(sql),
                AttributeKey.stringKey("schema"), currentSchema
            ));

            // 记录 Histogram
            meterProvider.get("shardingsphere.sql")
                .histogramBuilder("execute.duration")
                .ofLongs()
                .build()
                .record(durationMs, Attributes.of(
                    AttributeKey.stringKey("sql.type"), extractSqlType(sql)
                ));

        } finally {
            span.end();
        }
    }
}
```

## 13.4 链路追踪概念详解

### 13.4.1 Trace 与 Span 基础

**Trace（追踪）**：
- 代表一个完整的请求链路，从开始到结束
- 由多个 Span 组成，形成树状结构
- 具有全局唯一的 Trace ID

**Span（跨度）**：
- 代表一个独立的工作单元
- 拥有自己的 Span ID
- 记录开始时间、结束时间、属性和事件
- 通过 Parent Span ID 形成层级关系

**典型 Trace 结构：**

```
Trace: [TraceID: abc123]
│
├── Span: [SpanID: 1] "HTTP GET /api/orders"
│   │
│   ├── Span: [SpanID: 1.1] "Routing SQL to shards"
│   │   │
│   │   ├── Span: [SpanID: 1.1.1] "Execute on ds_0"
│   │   │
│   │   └── Span: [SpanID: 1.1.2] "Execute on ds_1"
│   │
│   └── Span: [SpanID: 1.2] "Result aggregation"
```

### 13.4.2 Span 生命周期

```
     startSpan
         │
         ▼
    ┌──────────┐
    │  Span    │
    │  Active  │
    └──────────┘
         │
    ┌────┴────┐
    │         │
 recordEvent │
 recordAttr  │  (多次)
    │         │
    └────┬────┘
         │
    endSpan
         │
         ▼
    ┌──────────┐
    │ Completed│
    │  Span    │
    └──────────┘
```

### 13.4.3 Span 上下文传播

在分布式系统中，Span 上下文需要跨进程传播：

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│  Service A   │         │  Service B   │         │  Service C   │
│              │         │              │         │              │
│  Span A      │───传播──▶│  Span B      │───传播──▶│  Span C      │
│  (本地创建)   │ W3C Trace│ (继续Span)   │ W3C Trace│ (继续Span)   │
└──────────────┘ Context  └──────────────┘ Context  └──────────────┘
```

**W3C Trace Context 传播格式：**

```
traceparent: 00-0af7651916cd43dd8448eb211c80319c-b7ad6b7169203331-01
tracestate: congo=t61rcWkgMzE
```

| 字段 | 说明 |
|------|------|
| version | Trace Context 版本（00） |
| trace-id | 128 位追踪 ID |
| parent-id | 64 位 Span ID |
| trace-flags | 采样标志（01 = 采样） |

**Jaeger 配置示例：**

```yaml
shardingsphere:
  tracing:
    enabled: true
    type: jaeger
    props:
      # Jaeger Agent 配置
      agent-host: localhost
      agent-port: 6831
      # 服务名称
      service-name: shardingSphere-jdbc

      sampler:
        type: const
        param: 1
      # Reporter 配置
```

**Java 代码配置：**

```java
import io.jaegertracing.internal.JaegerTracer;
import io.jaegertracing.internal.samplers.ConstSampler;
import io.jaegertracing.internal.reporters.RemoteReporter;
import io.jaegertracing.thrift.internal.senders.UdpSender;

@Configuration
public class JaegerTracingConfiguration {

    @Bean
    public JaegerTracer jaegerTracer() {
        // 配置采样器
        Sampler sampler = new ConstSampler(true);

        // 配置 Reporter（发送到 Agent）
        UdpSender sender = new UdpSender("localhost", 6831, 0);
        RemoteReporter reporter = RemoteReporter.builder()
            .setFlushInterval(1000)
            .setMaxQueueSize(100)
            .setSender(sender)
            .build();

        // 构建 Tracer
        return new JaegerTracer.Builder("shardingSphere-jdbc")
            .withSampler(sampler)
            .withReporter(reporter)
            .withSpanProcessor(new JaegerSpanProcessor())
            .build();
    }

    @Bean
    public TracingFeature tracingFeature(JaegerTracer tracer) {
        return new TracingFeature(tracer);
    }
}
```

```yaml
    type: zipkin
    props:
```

**Java 代码配置：**

```java
import io.opentelemetry.exporter.zipkin.ZipkinSpanExporter;
import io.opentelemetry.sdk.trace.SdkTracerProvider;
import io.opentelemetry.sdk.trace.export.BatchSpanProcessor;

@Configuration
public class ZipkinTracingConfiguration {

    @Bean
    public SdkTracerProvider tracerProvider() {
        // 创建 Zipkin 导出器
        ZipkinSpanExporter zipkinExporter = ZipkinSpanExporter.builder()
            .setEndpoint("http://localhost:9411/api/v2/spans")
            .build();

        // 配置批量处理器
        BatchSpanProcessor spanProcessor = BatchSpanProcessor.builder(zipkinExporter)
            .setMaxQueueSize(2048)
            .setMaxExportBatchSize(512)
            .setScheduleTimeout(java.time.Duration.ofSeconds(30))
            .build();

        return SdkTracerProvider.builder()
            .addSpanProcessor(spanProcessor)
            .build();
    }
}
```

## 13.7 SQL 监控详解

### 13.7.1 SQL 执行指标

ShardingSphere-JDBC 提供了丰富的 SQL 执行监控指标：

| 指标名称 | 类型 | 说明 |

### 13.8.2 连接池健康检查

**健康检查配置：**

```java
import com.zaxxer.hikari.HikariDataSource;
import com.zaxxer.hikari.HikariPoolMXBean;

@Configuration
public class ConnectionPoolHealthCheck {

    @Autowired
    private DataSource dataSource;

    @GetMapping("/health/pool")
    public Map<String, Object> poolHealth() {
        HikariDataSource hikariDataSource = (HikariDataSource) dataSource;
        HikariPoolMXBean poolMXBean = hikariDataSource.getHikariPoolMXBean();

        Map<String, Object> health = new HashMap<>();
        health.put("activeConnections", poolMXBean.getActiveConnections());
        health.put("idleConnections", poolMXBean.getIdleConnections());
        health.put("pendingRequests", poolMXBean.getPendingRequests());
        health.put("totalConnections", poolMXBean.getTotalConnections());
        health.put("threadsAwaitingConnection", poolMXBean.getThreadsAwaitingConnection());

        // 计算连接池健康度
        double healthScore = calculatePoolHealthScore(poolMXBean);
        health.put("healthScore", healthScore);
        health.put("status", healthScore > 0.7 ? "HEALTHY" : "DEGRADED");

        return health;
    }

    private double calculatePoolHealthScore(HikariPoolMXBean pool) {
        int total = pool.getTotalConnections();
        int active = pool.getActiveConnections();
        int pending = pool.getPendingRequests();

        if (total == 0) return 0.0;

        // 计算活跃率（越低越健康）
        double activeRate = (double) active / total;
        // 计算等待请求数（越多越不健康）
        double pendingPenalty = Math.min(pending / 10.0, 1.0) * 0.3;

        return Math.max(0, 1.0 - activeRate - pendingPenalty);
    }
}
```

|----------|------|------|

**数据分布监控实现：**

```java
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import org.apache.shardingsphere.infra.rule.ShardingRule;

@Configuration
public class ShardingDistributionMetrics {

    @Autowired
    private MeterRegistry meterRegistry;

    @Autowired
    private ShardingRule shardingRule;

    @PostConstruct
    public void registerMetrics() {
        // 注册数据分布 Gauge
        for (String datasource : shardingRule.getDataSourceNames()) {
            Gauge.builder("shardingsphere.sharding.data.count", 
                () -> getTableCountForDatasource(datasource))
                .tag("datasource", datasource)
                .description("Table count per datasource")
                .register(meterRegistry);
        }

        // 注册倾斜率 Gauge
        Gauge.builder("shardingsphere.sharding.skew.ratio",
            this::calculateSkewRatio)
            .description("Data distribution skew ratio")
            .register(meterRegistry);
    }

    private double calculateSkewRatio() {
        Map<String, Long> distribution = getDataDistribution();
        if (distribution.isEmpty()) return 0.0;

        double avg = distribution.values().stream()
            .mapToLong(Long::longValue)
            .average()
            .orElse(0);

        double maxDeviation = distribution.values().stream()
            .mapToDouble(count -> Math.abs(count - avg) / avg)
            .max()
            .orElse(0);

        return maxDeviation;
    }
}
```

### 13.10.2 自定义 Gauge 实现

```java
import io.micrometer.core.instrument.Gauge;
import io.micrometer.core.instrument.MeterRegistry;
import java.util.concurrent.atomic.AtomicLong;

public class CacheMetrics {

    private final AtomicLong cacheSize = new AtomicLong(0);
    private final AtomicLong cacheHits = new AtomicLong(0);
    private final AtomicLong cacheMisses = new AtomicLong(0);

    public CacheMetrics(MeterRegistry meterRegistry) {
        // 注册缓存大小 Gauge
        Gauge.builder("app.cache.size", cacheSize, AtomicLong::get)
            .description("Current cache size")
            .register(meterRegistry);

        // 注册缓存命中率 Gauge
        Gauge.builder("app.cache.hit.ratio", this, CacheMetrics::calculateHitRatio)
            .description("Cache hit ratio")
            .register(meterRegistry);
    }

    public void updateCacheSize(long size) {
        cacheSize.set(size);
    }

    public void recordCacheHit() {
        cacheHits.incrementAndGet();
    }

    public void recordCacheMiss() {
        cacheMisses.incrementAndGet();
    }

    private double calculateHitRatio() {
        long hits = cacheHits.get();
        long misses = cacheMisses.get();
        long total = hits + misses;
        return total == 0 ? 0.0 : (double) hits / total;
    }
}
```

### 13.10.3 标签设计最佳实践

```java
// 良好的标签设计
public class TagsDesign {

    // 推荐：为不同维度创建独立计数器
    public void recordRequestGood(String method, String path, int status) {
        meterRegistry.counter("http.requests",
            Tags.of(
                "method", method,      // 方法维度
                "path", normalizePath(path),  // 路径维度（需要归一化）
                "status", String.valueOf(status)  // 状态维度
            ))
            .increment();
    }

    // 不推荐：使用高基数标签
    public void recordRequestBad(String userId) {
        // 错误：userId 可能导致大量标签，导致指标爆炸
        meterRegistry.counter("http.requests", Tags.of("user_id", userId))
            .increment();
    }

    // 推荐：路径归一化
    private String normalizePath(String path) {
        // 将 /user/123/profile -> /user/{id}/profile
        return path.replaceAll("/\\d+/", "/{id}/");
    }
}
```

## 13.13 最佳实践总结

### 13.13.1 监控架构选型建议

| 场景 | 推荐方案 |
|------|----------|
| 小型项目（单实例） | Prometheus + Grafana + 内置指标 |
| 中型项目（多实例） | Prometheus + Grafana + Jaeger |
| 大型项目（微服务） | OpenTelemetry + Jaeger/Zipkin + 自建 Collector |
| 云原生项目 | OpenTelemetry + Datadog/New Relic |

### 13.13.2 监控配置检查清单

```
□ 确认指标导出端口（默认为 /actuator/prometheus）
□ 确认链路追踪 Agent 已正确部署
□ 确认告警规则已配置并测试
□ 确认 Grafana/Jaeger 数据源配置正确
□ 确认日志级别不会干扰监控数据
□ 确认采样率适合生产环境负载
□ 确认指标标签规范化（避免高基数）
□ 确认监控数据保留策略
```

### 13.13.3 常见问题排查

| 问题 | 可能原因 | 解决方案 |
|------|----------|----------|
| 指标数据缺失 | Prometheus 未正确抓取 | 检查 scrape 配置和网络连通性 |
| 链路追踪数据丢失 | Agent 与 Collector 连接问题 | 检查 Agent 配置和防火墙规则 |
| 告警重复触发 | 告警阈值设置过低 | 调整 for 参数和阈值 |
| 监控数据延迟 | Collector 处理能力不足 | 增加 Collector 实例或调整批量参数 |
| 高基数标签导致内存问题 | 标签设计不合理 | 使用归一化的标签值 |
