# 第5章 读写分离配置

## 5.1 读写分离概念与适用场景

### 5.1.1 什么是读写分离

读写分离是一种数据库架构模式，旨在将数据库的读操作和写操作分离到不同的数据库实例上。在传统的单体数据库架构中，所有读写请求都集中在同一个数据库服务器上，随着业务增长，读写压力会相互影响，导致性能瓶颈。

读写分离的核心思想是：
- **主库（Master）**：处理所有写操作（INSERT、UPDATE、DELETE），负责将数据变更记录到二进制日志（Binlog）
- **从库（Slave）**：处理读操作（SELECT），通过复制机制从主库同步数据

### 5.1.2 读写分离的优势

| 优势 | 说明 |
|------|------|
| **提升读取性能** | 将读请求分散到多个从库，大幅降低单库读取压力 |
| **提升写入性能** | 写操作集中在主库，避免读写竞争导致的锁等待 |
| **提高可用性** | 主从架构提供了数据冗余， 主库故障时可切换到从库 |
| **业务分离** | 可以针对不同业务场景选择不同的数据库实例 |
| **成本优化** | 可以使用较低配置的从库来承担大量读请求 |

### 5.1.3 适用场景

**适合使用读写分离的场景：**

1. **读多写少的业务**
   - 新闻资讯、博客系统
   - 电商商品的查看、搜索
   - 报表查询、数据分析

2. **需要水平扩展读能力的场景**
   - 单库无法承受大量并发读请求
   - 需要提供近乎无限的水平扩展能力

3. **对数据实时性要求不高的读操作**
   - 历史订单查询
   - 统计数据展示
   - 缓存预热

**不适合使用读写分离的场景：**

1. **写密集型业务**
   - 实时交易系统
   - 库存管理
   - 金融支付

2. **需要强一致性的场景**
   - 转账操作
   - 库存扣减
   - 分布式事务中的数据一致性要求高的操作

3. **包含写操作的短事务**
   - 写入后立即读取相同数据（可能读到未同步的旧数据）

### 5.1.4 读写分离的架构图

```
┌─────────────┐        ┌─────────────┐
│  客户端请求  │        │  客户端请求  │
│  (写操作)    │        │  (读操作)   │
└──────┬──────┘        └──────┬──────┘
       │                      │
       ▼                      ▼
┌─────────────┐        ┌─────────────┐
│   主库      │        │   从库1     │
│  (写操作)   │◄───────│  (读操作)   │
│             │ 复制   │             │
└─────────────┘        └─────────────┘
                              ▲
                              │
                        ┌─────────────┐
                        │   从库2     │
                        │  (读操作)   │
                        └─────────────┘
```

## 5.2 主从复制原理

### 5.2.1 Binlog 概述

Binlog（Binary Log）是 MySQL 数据库的核心组件，它记录了所有数据变更的操作。以事件形式存储，包括数据的修改、表的结构变更等。

**Binlog 的三大功能：**

1. **数据恢复**：利用 binlog 对数据库进行 point-in-time 恢复
2. **主从复制**：从库读取主库的 binlog 并执行，实现数据同步
3. **审计功能**：记录所有数据变更操作，用于审计分析

**Binlog 文件格式：**

- 文件名：`mysql-bin.000001`、`mysql-bin.000002` 等
- 索引文件：`mysql-bin.index`，记录所有 binlog 文件列表

### 5.2.2 Binlog 日志格式

MySQL 支持三种 Binlog 格式，各有优缺点。

#### 5.2.2.1 STATEMENT 格式

**原理**：记录执行的 SQL 语句，而不是每行的变化。

```sql
-- 主库执行
UPDATE orders SET amount = 100 WHERE id = 1;

-- Binlog 记录
UPDATE orders WHERE id = 1
```

**优点：**
- 日志量小，节省磁盘空间
- 记录了原始 SQL，方便审计和回放

**缺点：**
- 某些函数（如 NOW()、RAND()）在从库执行可能产生不同结果
- DELETE、UPDATE 语句需要再次执行才能确定影响的具体行
- 存在不确定性的 SQL 无法正确复制（如触发器、存储过程）

#### 5.2.2.2 ROW 格式

**原理**：记录每行数据的实际变更内容。

```sql
-- 主库执行
UPDATE orders SET amount = 100 WHERE id = 1;

-- Binlog 记录（伪SQL）
UPDATE orders SET amount=100 WHERE id=1 AND amount=50
```

**优点：**
- 准确记录每行数据变化
- 复制安全，不会出现主从不一致问题
- 支持更多 SQL 类型（如非确定性函数）

**缺点：**
- 日志量可能很大，特别是批量 UPDATE 时
- 可读性较差

#### 5.2.2.3 MIXED 格式

**原理**：结合 STATEMENT 和 ROW 格式，MySQL 自动选择最优方式。

- 一般使用 STATEMENT 格式
- 当 SQL 可能导致主从不一致时（如使用 RAND()、NOW()），自动切换为 ROW 格式

**配置方式：**

```ini
# my.cnf
binlog_format = MIXED
```

### 5.2.2.4 三种格式对比

| 特性 | STATEMENT | ROW | MIXED |
|------|-----------|-----|-------|
| 日志大小 | 小 | 大 | 中 |
| 复制准确性 | 可能不一致 | 精确 | 精确 |
| 可读性 | 高 | 低 | 中 |
| 性能 | 高 | 低 | 中 |
| 支持函数复制 | 部分 | 支持 | 支持 |

### 5.2.3 GTID 复制模式

#### 5.2.3.1 什么是 GTID

GTID（Global Transaction Identifier）是 MySQL 5.6 引入的特性，为每个已提交的事务分配一个全局唯一标识符。

**GTID 格式：**

```
source_id:transaction_id
```

示例：
```
3E11FA47-71CA-11E1-9E33-C80AA9429562:23
```

- `source_id`：MySQL 服务器的 UUID，在 `auto.cnf` 文件中定义
- `transaction_id`：事务序号，从 1 开始

#### 5.2.3.2 GTID 的优势

1. **简化主从切换**：不需要指定 binlog 文件名和位置
2. **更容易判断数据同步状态**：通过 GTID 判断从库已执行的事务
3. **自动定位**：从库自动找到需要执行的事务，无需手动指定
4. **支持多源复制**：可以同时从多个主库复制数据

#### 5.2.3.3 GTID 配置

```ini
# 主库配置
gtid_mode = ON
enforce_gtid_consistency = ON
binlog_gtid_simple_recovery = ON

# 从库配置
gtid_mode = ON
enforce_gtid_consistency = ON
relay_log_recovery = ON
```

### 5.2.4 主从复制原理详解

MySQL 主从复制采用 **半同步复制** 或 **异步复制** 机制，主要包含以下三个线程：

```
┌─────────────────────────────────────────────────────────────────┐
│                        主库 (Master)                            │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐      │
│  │   用户请求    │───►│   SQL线程    │───►│   Binlog     │      │
│  │  (写操作)     │    │              │    │   写入       │      │
│  └──────────────┘    └──────────────┘    └──────────────┘      │
│                                                  │              │
└──────────────────────────────────────────────────┼──────────────┘
                                                   │
                                            Binlog Dump 线程
                                                   │
                                                   ▼
┌──────────────────────────────────────────────────────────────────┐
│                        从库 (Slave)                              │
│  ┌──────────────┐    ┌──────────────┐    ┌──────────────┐       │
│  │  Relay Log   │◄───│  I/O 线程    │◄───│  Binlog 读取 │       │
│  │  (中转日志)  │    │              │    │              │       │
│  └──────┬───────┘    └──────────────┘    └──────────────┘       │
│         │                                                          │
│         ▼                                                          │
│  ┌──────────────┐                                                │
│  │   SQL线程    │                                                │
│  │   执行日志   │                                                │
│  └──────────────┘                                                │
└──────────────────────────────────────────────────────────────────┘
```

**复制流程：**

1. **主库 Binlog 写入**：主库执行事务时，先将操作写入 Binlog
2. **Binlog Dump 线程**：主库的 Binlog Dump 线程监听主库变化，发送 Binlog 数据给从库
3. **从库 I/O 线程**：从库的 I/O 线程接收 Binlog 数据，写入 Relay Log
4. **从库 SQL 线程**：从库的 SQL 线程读取 Relay Log，执行事务

### 5.2.5 复制延迟及其影响

复制延迟是从库应用事件的时间戳与主库事件执行时间戳的差值。

**导致延迟的因素：**

1. **网络延迟**：主从之间的网络传输时间
2. **从库执行速度**：从库 I/O 和 SQL 线程的性能
3. **大事务**：一个事务产生的 Binlog 越多，传输和应用时间越长
4. **并发复制能力**：从库 SQL 单线程执行，高并发时容易积压

**延迟对业务的影响：**

- 读写分离场景下，可能读到过期数据
- 数据同步的时间窗口内，无法保证强一致性

## 5.3 MySQL 主从复制配置

### 5.3.1 环境准备

假设环境：
- 主库：192.168.1.101:3306
- 从库：192.168.1.102:3306
- MySQL 版本：8.0

### 5.3.2 主库配置

**1. 修改 my.cnf 配置：**

```ini
[mysqld]
# 服务器唯一 ID
server-id = 1

# 开启 Binlog
log_bin = mysql-bin

# Binlog 格式
binlog_format = ROW

# 同步的数据库
binlog_do_db = sharding_db

# Binlog 缓存大小
binlog_cache_size = 4M

# 最大 Binlog 大小
max_binlog_size = 1G

# 保留时间（天）
expire_logs_days = 7

# GTID 模式
gtid_mode = ON
enforce_gtid_consistency = ON

# 步进值
auto_increment_increment = 1
auto_increment_offset = 1
```

**2. 创建复制账号：**

```sql
-- 创建专用复制用户
CREATE USER 'repl'@'192.168.1.%' IDENTIFIED BY 'repl_password';

-- 授予复制权限
GRANT REPLICATION SLAVE ON *.* TO 'repl'@'192.168.1.%';

-- 刷新权限
FLUSH PRIVILEGES;
```

**3. 查看主库状态：**

```sql
SHOW MASTER STATUS;

-- 输出示例：
-- +------------------+----------+--------------+------------------+
-- | File             | Position | Binlog_Do_DB | Binlog_Ignore_DB |
-- +------------------+----------+--------------+------------------+
-- | mysql-bin.000001 |     154  | sharding_db  |                  |
-- +------------------+----------+--------------+------------------+
```

### 5.3.3 从库配置

**1. 修改 my.cnf 配置：**

```ini
[mysqld]
# 服务器唯一 ID
server-id = 2

# 开启 Relay Log
relay_log = mysql-relay-bin

# 开启只读模式（生产环境建议开启）
read_only = ON

# 禁止 super_read_only（允许复制账号有特殊权限）
super_read_only = OFF

# Relay Log 清除策略
relay_log_purge = ON

# 从库是否支持 GTID
gtid_mode = ON
enforce_gtid_consistency = ON

# 并行复制数量（根据 CPU 核心数调整）
slave_parallel_workers = 4
slave_parallel_type = LOGICAL_CLOCK

# 复制延迟监控
slave_net_timeout = 60
```

**2. 配置主从连接：**

```sql
-- 停止复制线程
STOP SLAVE;

-- 设置主库连接信息
CHANGE MASTER TO
    MASTER_HOST = '192.168.1.101',
    MASTER_PORT = 3306,
    MASTER_USER = 'repl',
    MASTER_PASSWORD = 'repl_password',
    MASTER_AUTO_POSITION = 1;  -- 启用 GTID 模式

-- 启动复制线程
START SLAVE;

-- 查看复制状态
SHOW SLAVE STATUS\G
```

### 5.3.4 半同步复制配置

半同步复制（Semi-Synchronous Replication）确保从库至少有一个收到了 binlog 数据，才算事务提交成功。

**主库配置：**

```ini
[mysqld]
# 加载半同步插件
plugin_load = 'rpl_semi_sync_master=semisync_master.so'

# 开启半同步复制
rpl_semi_sync_master_enabled = ON

# 超时时间（毫秒）
rpl_semi_sync_master_timeout = 10000
```

**从库配置：**

```ini
[mysqld]
# 加载半同步插件
plugin_load = 'rpl_semi_sync_slave=semisync_slave.so'

# 开启半同步复制
rpl_semi_sync_slave_enabled = ON
```

**安装插件（动态加载）：**

```sql
-- 主库
INSTALL PLUGIN rpl_semi_sync_master SONAME 'semisync_master.so';

-- 从库
INSTALL PLUGIN rpl_semi_sync_slave SONAME 'semisync_slave.so';
```

### 5.3.5 并行复制配置

MySQL 5.7 引入了基于 Logical Clock 的并行复制，可以显著提升从库的复制速度。

**并行复制原理：**

```
主库                     从库
─────                    ─────
事务1 ─┐
事务2 ─┼─► binlog ─►     事务1 ─┐
事务3 ─┘                 事务2 ─┼─► 并行执行
                            事务3 ─┘
```

**配置参数：**

```ini
[mysqld]
# 并行复制类型
slave_parallel_type = LOGICAL_CLOCK

# 并行复制 worker 线程数
slave_parallel_workers = 8

# 开启基于组提交的并行复制
binlog_transaction_dependency_tracking = WRITESET
```

**WRITESET 模式说明：**

- `WRITESET`：基于行级别的冲突检测，更精确
- `WRITESET_SESSION`：同一个 session 内的事务按顺序执行

### 5.3.6 验证主从复制

**1. 在主库创建测试数据：**

```sql

-- 插入测试数据
```

## 5.4 ShardingSphere-JDBC 读写分离架构

### 5.4.1 整体架构

ShardingSphere-JDBC 的读写分离架构建立在连接池和 SQL 解析基础之上，通过透明的方式将读请求路由到从库，写请求路由到主库。

```
┌─────────────────────────────────────────────────────────────────┐
│                        应用层                                    │
│                      (Java Application)                         │
└────────────────────────────┬────────────────────────────────────┘
                             │
                             ▼
┌─────────────────────────────────────────────────────────────────┐
│                   ShardingSphere-JDBC                            │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │                    SQL 解析层                            │   │
│  │         SQL Parser → SQL Router → SQL Rewriter          │   │
│  └──────────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │                   读写分离核心                            │   │
│  │   ┌────────────┐    ┌────────────┐    ┌────────────┐    │   │
│  │   │  主库判断  │    │  Hint 管理 │    │ 负载均衡   │    │   │
│  │   │  逻辑表    │    │  强制路由  │    │  策略      │    │   │
│  │   └────────────┘    └────────────┘    └────────────┘    │   │
│  └──────────────────────────────────────────────────────────┘   │
│  ┌──────────────────────────────────────────────────────────┐   │
│  │                    连接管理层                            │   │
│  │         Connection Pool (HikariCP/Druid/etc)            │   │
│  └──────────────────────────────────────────────────────────┘   │
└────────────────────────────┬────────────────────────────────────┘
                             │
            ┌────────────────┼────────────────┐
            ▼                ▼                ▼
     ┌───────────┐    ┌───────────┐    ┌───────────┐
     │  主库     │    │  从库1    │    │  从库2    │
     │ (Write)   │    │ (Read)   │    │ (Read)   │
     └───────────┘    └───────────┘    └───────────┘
```

### 5.4.2 核心组件

**1. ReadWriteStrategy（读写分离策略）**

负责判断 SQL 类型（读/写），并决定路由目标。

```java
public interface ReadWriteStrategy {
    // 判断是否为写操作
    boolean isWriteOperation(String sql);

    // 获取读数据源
    String getReadDataSource();

    // 获取写数据源
    String getWriteDataSource();
}
```

**2. LoadBalanceStrategy（负载均衡策略）**

当存在多个从库时，决定具体使用哪个从库处理读请求。

```java
public interface LoadBalanceStrategy {
    // 选择一个从库
    String select(String readDataSourceName, String[] readWriteDataSourceNames);
}
```

**3. HintManager（Hint 强制路由）**

提供手动指定路由目标的能力，强制读请求走主库或指定从库。

### 5.4.3 路由决策流程

```
收到 SQL
    │
    ▼
┌─────────────────┐
│ SQL 类型判断     │
└────────┬────────┘
         │
    ┌────┴────┐
    │         │
  写操作    读操作
    │         │
    ▼         ▼
┌────────┐  ┌─────────────┐
│ 主库   │  │ 有 Hint？   │
└────────┘  └──────┬──────┘
                   │
              ┌────┴────┐
              │         │
            有         无
              │         │
              ▼         ▼
        ┌──────────┐  ┌──────────────┐
        │ Hint路由 │  │ 负载均衡策略 │
        └──────────┘  └──────┬───────┘
                             │
                      ┌─────┴─────┐
                      │           │
                   单从库      多从库
                      │           │
                      ▼           ▼
                  返回该从库   负载均衡选择
```

### 5.4.4 多副本支持

ShardingSphere 支持配置多个主库或多个从库，形成多主多从的复杂架构。


## 5.5 读写分离配置详解

### 5.5.1 数据源配置结构

```yaml
dataSources:
  # 主库
  ds_master:
    url: jdbc:mysql://192.168.1.101:3306/sharding_db?useSSL=false&serverTimezone=UTC
    username: root
    password: root123
    connectionPoolClassName: com.zaxxer.hikari.HikariDataSource
    props:
      maximumPoolSize: 50
```

## 5.6 负载均衡策略

### 5.6.1 内置负载均衡策略

ShardingSphere-JDBC 提供了四种内置负载均衡策略：

| 策略 | 说明 | 适用场景 |
|------|------|----------|
| ROUND_ROBIN | 轮询策略 | 负载均匀分配，各从库性能相近 |
| RANDOM | 随机策略 | 负载随机分配，简单场景 |
| WEIGHT | 权重策略 | 从库性能不均，需要按比例分配 |
| AUTO_COMPLEXITY | 自动复杂度策略 | 根据从库当前负载动态分配 |

### 5.6.2 轮询策略（ROUND_ROBIN）

**原理**：循环选择每个从库，保证每个从库被选择的次数尽量均匀。

**配置示例：**

```yaml
loadBalancers:
  round_robin:
    type: ROUND_ROBIN
    props:
      # 可选：权重配置（默认 1:1）
      weight.ds_slave_0: 1
      weight.ds_slave_1: 1
```

**Java 配置：**

```java
LoadBalanceStrategyConfiguration roundRobin =
    new LoadBalanceStrategyConfiguration("round_robin", "ROUND_ROBIN", Collections.emptyMap());
```

**轮询示意：**

```
请求1 → 从库0
请求2 → 从库1
请求3 → 从库0
请求4 → 从库1
...
```

### 5.6.3 随机策略（RANDOM）

**原理**：根据权重随机选择一个从库。

**配置示例：**

```yaml
loadBalancers:
  random:
    type: RANDOM
    props:
      # 权重配置
      weight.ds_slave_0: 1
      weight.ds_slave_1: 2
```

**Java 配置：**

```java
Map<String, Object> props = new HashMap<>();
props.put("weight.ds_slave_0", 1);
props.put("weight.ds_slave_1", 2);

LoadBalanceStrategyConfiguration random =
    new LoadBalanceStrategyConfiguration("random", "RANDOM", props);
```

**随机示意（1:2 比例）：**

```
从库0: ████ (25%)
从库1: ████████ (75%)

随机100次: 从库0约25次, 从库1约75次
```

### 5.6.4 权重策略（WEIGHT）

**原理**：按照配置的权重比例分配请求。

**配置示例：**

```yaml
loadBalancers:
  weight:
    type: WEIGHT
    props:
      ds_slave_0: 5
      ds_slave_1: 3
      ds_slave_2: 2
```

**权重分配示意：**

```
总权重 = 5 + 3 + 2 = 10

从库0: 5/10 = 50%
从库1: 3/10 = 30%
从库2: 2/10 = 20%

100请求分配: 从库0处理50个, 从库1处理30个, 从库2处理20个
```

### 5.6.5 自定义负载均衡策略

可以通过实现 `LoadBalanceStrategy` 接口来自定义负载均衡算法。

**1. 定义自定义策略类：**

```java
package com.example.sharding;

import org.apache.shardingsphere.readwritesplitting.spi.LoadBalanceAlgorithm;

import java.util.List;
import java.util.concurrent.ThreadLocalRandom;

public class CustomLoadBalanceStrategy implements LoadBalanceAlgorithm {

    private List<String> readDataSourceNames;

    @Override
    public void init(List<String> readDataSourceNames) {
        this.readDataSourceNames = readDataSourceNames;
    }

    @Override
    public String getDataSource(String name) {
        if (readDataSourceNames == null || readDataSourceNames.isEmpty()) {
            throw new IllegalStateException("No read data sources available");
        }

        // 自定义逻辑：最少连接数优先
        // 这里只是一个示例，实际需要结合监控数据
        return readDataSourceNames.get(
            ThreadLocalRandom.current().nextInt(readDataSourceNames.size())
        );
    }

    @Override
    public String getAlgorithmType() {
        return "CUSTOM_LOAD_BALANCE";
    }

    @Override
    public Properties getProperties() {
        return new Properties();
    }

    @Override
    public void setProperties(Properties properties) {
        // 设置属性
    }
}
```

**2. 注册为 SPI：**

在 `META-INF/services/org.apache.shardingsphere.readwritesplitting.spi.LoadBalanceAlgorithm` 文件中注册：

```
com.example.sharding.CustomLoadBalanceStrategy
```

**3. 配置使用：**

```yaml
loadBalancers:
  custom:
    type: CUSTOM_LOAD_BALANCE
    props:
      # 自定义属性
      some.property: value
```

## 5.7 事务中的读写分离处理

### 5.7.1 问题背景

在读写分离架构中，由于主从复制存在延迟，如果一个事务中先写入数据然后立即读取，可能会读到未同步到从库的旧数据。

```java
// 场景：先写后读
try (Connection conn = dataSource.getConnection()) {
    conn.setAutoCommit(false);

    // 步骤1：写入主库
    PreparedStatement ps = conn.prepareStatement(
        "INSERT INTO orders (order_no, amount) VALUES (?, ?)"
    );
    ps.setString(1, "ORDER001");
    ps.setDouble(2, 100.0);
    ps.executeUpdate();

    // 步骤2：立即读取（可能路由到从库，导致读不到刚插入的数据）
    ResultSet rs = conn.createStatement().executeQuery(
        "SELECT * FROM orders WHERE order_no = 'ORDER001'"
    );

    conn.commit();
}
```

### 5.7.2 Hint 强制路由

ShardingSphere-JDBC 提供了 `HintManager` 来强制指定路由目标，解决事务中的读写分离问题。

#### 5.7.2.1 基本用法

```java
import org.apache.shardingsphere.driver.api.yaml.YamlShardingSphereDataSourceFactory;
import org.apache.shardingsphere.infra.hint.HintManager;

// 获取 DataSource
DataSource dataSource = YamlShardingSphereDataSourceFactory.createDataSource(...);

try (Connection conn = dataSource.getConnection()) {
    // 创建 HintManager
    HintManager hintManager = HintManager.getInstance();

    // 强制路由到主库（写库）
    hintManager.setWriteRouteOnly();

    // 执行查询，会被路由到主库
    PreparedStatement ps = conn.prepareStatement(
        "SELECT * FROM orders WHERE order_no = ?"
    );
    ps.setString(1, "ORDER001");
    ResultSet rs = ps.executeQuery();

    // 使用完毕后关闭 HintManager
    hintManager.close();
}
```

#### 5.7.2.2 HintManager 核心 API

| API | 说明 |
|-----|------|
| `setWriteRouteOnly()` | 强制所有读操作路由到主库 |
| `setReadRouteOnly()` | 强制所有写操作路由到从库（通常不推荐） |
| `setPrimaryRouteOnly()` | 与 `setWriteRouteOnly()` 相同 |
| `clearPrimaryRoute()` | 清除强制路由设置，恢复自动判断 |
| `close()` | 关闭 HintManager，释放资源 |

#### 5.7.2.3 完整事务示例

```java
public class TransactionWithHintDemo {

    private DataSource dataSource;

    public void processOrder(String orderNo, BigDecimal amount) {
        // 方式1：try-with-resources 自动管理
        try (HintManager hintManager = HintManager.getInstance()) {
            // 强制写操作走主库
            hintManager.setWriteRouteOnly();

            try (Connection conn = dataSource.getConnection()) {
                conn.setAutoCommit(false);

                // 插入订单
                insertOrder(conn, orderNo, amount);

                // 立即查询刚插入的订单（确保能读到）
                Order order = selectOrder(conn, orderNo);

                // 更新订单状态
                updateOrderStatus(conn, order.getId(), "PAID");

                conn.commit();

                System.out.println("订单处理成功: " + order);
            }
        }
    }

    // 方式2：手动管理（适用于复杂场景）
    public void processOrderManual(String orderNo, BigDecimal amount) {
        HintManager hintManager = null;
        try {
            hintManager = HintManager.getInstance();
            hintManager.setWriteRouteOnly();

            Connection conn = dataSource.getConnection();
            conn.setAutoCommit(false);

            insertOrder(conn, orderNo, amount);
            Order order = selectOrder(conn, orderNo);

            conn.commit();

        } catch (SQLException e) {
            if (conn != null) {
                conn.rollback();
            }
            throw new RuntimeException("订单处理失败", e);
        } finally {
            if (hintManager != null) {
                hintManager.close();
            }
            if (conn != null) {
                conn.close();
            }
        }
    }
}
```

#### 5.7.3.1 下单后立即查询

```java

```

#### 5.7.3.2 分布式事务中的读写分离

```java
public void executeDistributedTransaction() {
    // 使用 Seata 或其他分布式事务框架
    TransactionTemplate transactionTemplate = new TransactionTemplate();

    transactionTemplate.execute(status -> {
        try (HintManager hintManager = HintManager.getInstance()) {
            hintManager.setWriteRouteOnly();

            // 在分布式事务中确保读写都走主库
            orderService.createOrder(...);
```

#### 5.7.3.3 强制读从库场景

某些场景可能需要强制所有操作（包括写）都走从库，例如：
- 数据只读场景
- 报表生成（不关心数据变更）

```java
public void generateReport() {
    try (HintManager hintManager = HintManager.getInstance()) {
        // 强制所有操作走从库（不推荐用于写操作）
        hintManager.setReadRouteOnly();

        try (Connection conn = dataSource.getConnection()) {
            Statement stmt = conn.createStatement();
            ResultSet rs = stmt.executeQuery("SELECT * FROM orders WHERE ...");

            // 处理结果集
            while (rs.next()) {
                // 生成报表
            }
        }
    }
}
```

### 5.7.4 注意事项

1. **HintManager 作用域**：每次 `getInstance()` 都会创建新的实例，需要在使用完毕后调用 `close()`

2. **性能影响**：强制主库路由会失去读写分离的优势，增加主库压力

3. **线程安全**：`HintManager` 不是线程安全的，多线程环境下需要分别创建

4. **作用域控制**：
   ```java
   // 正确示例：明确的作用域
   try (HintManager hm = HintManager.getInstance()) {
       hm.setWriteRouteOnly();
       // 业务代码
   } // 自动释放
   
   // 注意：不要在 try-with-resources 外长期持有 HintManager
   HintManager hm = HintManager.getInstance();
   hm.setWriteRouteOnly();
   // ... long operation ...
   hm.close(); // 手动关闭
   ```

## 5.8 读写分离延迟问题处理

### 5.8.1 延迟的原因

```
┌────────┐         ┌────────┐         ┌────────┐
│ 主库   │──Binlog──│ 从库   │         │ 从库   │
│ 写入   │   传输   │ I/O线程│   应用   │ SQL线程│
└────────┘         └────────┘         └────────┘
   │                              ▲
   │                              │
   │                          延迟
   │  <───── 复制延迟 ──────────>
```

**主要延迟来源：**

1. **Binlog 传输延迟**：网络带宽、延迟
2. **从库 I/O 线程处理**：从主库读取 Binlog 并写入 Relay Log
3. **从库 SQL 线程应用**：从 Relay Log 读取并执行事务
4. **大事务**：单个事务产生的 Binlog 内容越多，传输和应用时间越长
5. **从库负载**：从库正在执行其他查询，无法及时应用复制事件

### 5.8.2 解决方案

#### 5.8.2.1 架构层面的优化

**1. 半同步复制（Semi-sync）**

确保至少有一个从库收到 Binlog 后，主库才提交事务。

```ini
# 主库配置
rpl_semi_sync_master_enabled = ON
rpl_semi_sync_master_timeout = 10000
```

**2. 并行复制**

配置从库并行应用事务，显著降低延迟。

```ini
slave_parallel_type = LOGICAL_CLOCK
slave_parallel_workers = 8
binlog_transaction_dependency_tracking = WRITESET
```

**3. 级联复制**

```
主库 → 从库A(中转) → 从库B
           ↓
        降低主库负载
```

#### 5.8.2.2 应用层面的处理

**1. 强制主库读取（HintManager）**

对于必须读取最新数据的场景，强制路由到主库。

```java
try (HintManager hintManager = HintManager.getInstance()) {
    hintManager.setWriteRouteOnly();

    // 查询最新数据
    Order order = orderMapper.selectById(orderId);
}
```

**2. 读延迟敏感场景识别**

```java
public class ReadWriteService {

    private DataSource dataSource;

    /**
     * 读取订单（可接受延迟）
     */
    public List<Order> listOrders(Long userId) {
        // 普通的读请求，可以走从库
        return orderMapper.selectByUserId(userId);
    }

    /**
     * 读取订单详情（延迟敏感）
     */
    public Order getOrderDetail(Long orderId) {
        try (HintManager hintManager = HintManager.getInstance()) {
            hintManager.setWriteRouteOnly();

            // 强一致性读取，必须走主库
            return orderMapper.selectById(orderId);
        }
    }

    /**
     * 创建订单后立即查询
     */
    public Order createOrderAndGetDetail(Order order) {
        try (Connection conn = dataSource.getConnection()) {
            try (HintManager hintManager = HintManager.getInstance()) {
                hintManager.setWriteRouteOnly();

                conn.setAutoCommit(false);
                orderMapper.insert(order);

                // 立即查询，确保能读到
                Order result = orderMapper.selectById(order.getId());

                conn.commit();
                return result;
            }
        }
    }
}
```

#### 5.8.2.3 重试机制

```java
public <T> T executeWithRetry(Supplier<T> operation, int maxRetries) {
    int retryCount = 0;

    while (true) {
        try {
            return operation.get();
        } catch (DataReadNotFoundException e) {
            // 从库没有数据，可能是复制延迟
            retryCount++;

            if (retryCount >= maxRetries) {
                throw new RuntimeException("读取失败，已重试" + maxRetries + "次", e);
            }

            // 等待后重试
            try {
                Thread.sleep(100 * retryCount); // 递增等待时间
            } catch (InterruptedException ie) {
                Thread.currentThread().interrupt();
                throw new RuntimeException("重试被中断", ie);
            }
        }
    }
}

// 使用示例
public Order getOrderWithRetry(Long orderId) {
    return executeWithRetry(() -> {
        try (Connection conn = dataSource.getConnection()) {
            // 先尝试从从库读取
            return queryFromReplica(orderId);
        } catch (DataReadNotFoundException e) {
            // 从库没有，尝试从主库读取
            try (HintManager hintManager = HintManager.getInstance()) {
                hintManager.setWriteRouteOnly();
                return queryFromMaster(orderId);
            }
        }
    }, 3);
}
```

```java
import com.mysql.cj.jdbc.MysqlDataSource;

public class ReplicationMonitor {

    public void monitorDelay(DataSource dataSource) {
        try (Connection conn = dataSource.getConnection()) {
            ResultSet rs = conn.createStatement().executeQuery("SHOW SLAVE STATUS");

            if (rs.next()) {
                long secondsBehind = rs.getLong("Seconds_Behind_Master");
                String ioRunning = rs.getString("Slave_IO_Running");
                String sqlRunning = rs.getString("Slave_SQL_Running");

                // 延迟告警阈值（秒）
                long delayThreshold = 10;

                if (secondsBehind > delayThreshold) {
                    // 发送告警通知
                    sendAlert("从库延迟超过 " + secondsBehind + " 秒");
                }

                if (!"Yes".equals(ioRunning) || !"Yes".equals(sqlRunning)) {
                    // 复制线程异常
                    sendAlert("从库复制线程异常: IO=" + ioRunning + ", SQL=" + sqlRunning);
                }
            }
        } catch (SQLException e) {
            // 处理异常
            sendAlert("无法获取从库状态: " + e.getMessage());
        }
    }
}
```

```java
public DataSource createShardingAndReadWriteDataSource() throws SQLException {
    // 1. 配置所有数据源
    Map<String, DataSource> dataSourceMap = new HashMap<>();

    // 分片0：主库和从库
    dataSourceMap.put("ds_0_master", createDataSource("192.168.1.101:3306", "sharding_db_0"));
    dataSourceMap.put("ds_0_slave_0", createDataSource("192.168.1.102:3306", "sharding_db_0"));
    dataSourceMap.put("ds_0_slave_1", createDataSource("192.168.1.103:3306", "sharding_db_0"));

    // 分片1：主库和从库
    dataSourceMap.put("ds_1_master", createDataSource("192.168.1.104:3306", "sharding_db_1"));
    dataSourceMap.put("ds_1_slave_0", createDataSource("192.168.1.105:3306", "sharding_db_1"));
    dataSourceMap.put("ds_1_slave_1", createDataSource("192.168.1.106:3306", "sharding_db_1"));

    // 2. 配置数据分片规则
    TableRuleConfiguration orderTableRule = new TableRuleConfiguration("t_order", "ds_$->{0..1}.t_order_$->{0..15}");

    ShardingRuleConfiguration shardingRuleConfig = new ShardingRuleConfiguration();
    shardingRuleConfig.getTables().add(orderTableRule);

    // 3. 配置读写分离规则
    ReadWriteSplittingDataSourceRuleConfiguration readWriteConfig0 =
        new ReadWriteSplittingDataSourceRuleConfiguration(
            "ds_0", "ds_0_master",
            Arrays.asList("ds_0_slave_0", "ds_0_slave_1"),
            "round_robin"
        );

    ReadWriteSplittingDataSourceRuleConfiguration readWriteConfig1 =
        new ReadWriteSplittingDataSourceRuleConfiguration(
            "ds_1", "ds_1_master",
            Arrays.asList("ds_1_slave_0", "ds_1_slave_1"),
            "round_robin"
        );

    Map<String, LoadBalanceStrategyConfiguration> loadBalancers = new HashMap<>();
    loadBalancers.put("round_robin", new LoadBalanceStrategyConfiguration(
        "round_robin", "ROUND_ROBIN", Collections.emptyMap()));

    ReadWriteSplittingRuleConfiguration rwRuleConfig = new ReadWriteSplittingRuleConfiguration(
        Arrays.asList(readWriteConfig0, readWriteConfig1),
        loadBalancers
    );

    // 4. 创建数据源
    return ShardingSphereDataSourceFactory.createDataSource(
        dataSourceMap,
        Arrays.asList(shardingRuleConfig, rwRuleConfig),
        new HashMap<>()
    );
}
```

```java
    /**
     * 创建订单（写操作，路由到主库）
     */
    public Order createOrder(String orderNo, BigDecimal amount, Long userId) throws SQLException {
        String sql = "INSERT INTO orders (order_no, amount, user_id, status, created_at) VALUES (?, ?, ?, ?, NOW())";

        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {

            conn.setAutoCommit(false);

            ps.setString(1, orderNo);
            ps.setBigDecimal(2, amount);
            ps.setLong(3, userId);
            ps.setString(4, "PENDING");

            int affectedRows = ps.executeUpdate();

            if (affectedRows > 0) {
                try (ResultSet generatedKeys = ps.getGeneratedKeys()) {
                    if (generatedKeys.next()) {
                        Long orderId = generatedKeys.getLong(1);

                        // 提交事务
                        conn.commit();

                        log.info("订单创建成功: orderId={}, orderNo={}", orderId, orderNo);
                        return new Order(orderId, orderNo, amount, userId, "PENDING");
                    }
                }
            }

            conn.rollback();
            throw new SQLException("创建订单失败");
        }
    }

    /**
     * 查询订单列表（读操作，默认路由到从库）

            ps.setLong(1, userId);

                List<Order> orders = new ArrayList<>();

                while (rs.next()) {
                    orders.add(new Order(
                        rs.getLong("id"),

                        rs.getTimestamp("created_at")

                return orders;
            }
        }
    }

     * 创建订单后立即查询（演示事务中的读写分离处理）
     */
    public Order createOrderAndGetDetail(String orderNo, BigDecimal amount, Long userId) throws SQLException {
        // 使用 HintManager 确保读取操作路由到主库
        try (HintManager hintManager = HintManager.getInstance()) {
            hintManager.setWriteRouteOnly();

            try (Connection conn = dataSource.getConnection()) {
                conn.setAutoCommit(false);

                // 步骤1：创建订单
                String insertSql = "INSERT INTO orders (order_no, amount, user_id, status, created_at) VALUES (?, ?, ?, ?, NOW())";
                try (PreparedStatement ps = conn.prepareStatement(insertSql, Statement.RETURN_GENERATED_KEYS)) {
                    ps.setString(1, orderNo);
                    ps.setBigDecimal(2, amount);
                    ps.setLong(3, userId);
                    ps.setString(4, "PENDING");
                    ps.executeUpdate();

                    // 获取生成的订单 ID
                    try (ResultSet generatedKeys = ps.getGeneratedKeys()) {
                        if (generatedKeys.next()) {
                            Long orderId = generatedKeys.getLong(1);

                            // 步骤2：立即查询刚创建的订单（确保能读到）
                            String selectSql = "SELECT * FROM orders WHERE id = ?";
                            try (PreparedStatement selectPs = conn.prepareStatement(selectSql)) {
                                selectPs.setLong(1, orderId);

                                try (ResultSet rs = selectPs.executeQuery()) {
                                    if (rs.next()) {
                                        Order order = new Order(
                                            rs.getLong("id"),
                                            rs.getString("order_no"),
                                            rs.getBigDecimal("amount"),
                                            rs.getLong("user_id"),
                                            rs.getString("status"),
                                            rs.getTimestamp("created_at")
                                        );

                                        conn.commit();
                                        return order;
                                    }
                                }
                            }
                        }
                    }

                    conn.rollback();
                    throw new SQLException("创建订单失败");
                }
            }
        }
    }

    /**
     * 更新订单状态
     */
    public boolean updateOrderStatus(Long orderId, String newStatus) throws SQLException {
        String sql = "UPDATE orders SET status = ? WHERE id = ?";

        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql)) {

            ps.setString(1, newStatus);
            ps.setLong(2, orderId);

            int affectedRows = ps.executeUpdate();

            log.info("更新订单状态: orderId={}, newStatus={}, affected={}", orderId, newStatus, affectedRows);
            return affectedRows > 0;
        }

    /**
     * 批量查询订单（演示负载均衡）

    public List<Order> listOrdersByUserIds(List<Long> userIds) throws SQLException {
        if (userIds == null || userIds.isEmpty()) {
            return new ArrayList<>();
        }

        StringBuilder sql = new StringBuilder("SELECT * FROM orders WHERE user_id IN (");
        for (int i = 0; i < userIds.size(); i++) {
            sql.append(i > 0 ? "," : "").append("?");
        }
        sql.append(")");

        try (Connection conn = dataSource.getConnection();
             PreparedStatement ps = conn.prepareStatement(sql.toString())) {

            for (int i = 0; i < userIds.size(); i++) {
                ps.setLong(i + 1, userIds.get(i));
            }

            try (ResultSet rs = ps.executeQuery()) {
                List<Order> orders = new ArrayList<>();

                while (rs.next()) {
                    orders.add(new Order(
                        rs.getLong("id"),
                        rs.getString("order_no"),
                        rs.getBigDecimal("amount"),
                        rs.getLong("user_id"),
                        rs.getString("status"),
                        rs.getTimestamp("created_at")
                    ));
                }

                return orders;
            }
        }
    }
```
