# 第16章：常见问题与解决方案

## 16.1 概述

本章旨在汇总 ShardingSphere-JDBC 在实际生产环境中使用过程中可能遇到的各类问题，并提供系统性的排查思路和解决方案。通过阅读本章，开发者和运维人员可以快速定位问题根因，采取针对性措施，确保系统的稳定运行。

ShardingSphere-JDBC 作为一款强大的数据库中间件，其问题排查往往涉及多个层面：分片策略配置、事务一致性、连接池管理、网络通信、SQL 兼容性等。本章按照问题类型进行分类，每类问题都包含典型症状、问题原因分析、解决方案以及预防措施，帮助读者建立完整的问题解决知识体系。

## 16.2 分片相关问题

### 16.2.1 跨分片查询性能差

**典型症状**

跨分片查询响应时间明显慢于单分片查询，有时甚至出现超时错误。执行 `COUNT`、`SUM`、`AVG` 等聚合查询时，客户端只收到部分结果或结果明显不正确。带有分页的查询出现数据重复或遗漏，页面显示的数据条数与预期不符。

**问题原因分析**

跨分片查询是 ShardingSphere-JDBC 中最具挑战性的场景之一。当查询条件无法精确匹配分片键时，系统不得不将 SQL 广播到所有分片执行，然后对结果进行内存聚合。这种「scatter-gather」模式在高并发场景下会带来显著的性能开销。

具体原因包括：

- **分片键选择不当**：查询条件未包含分片键，导致全分片扫描
- **分片键条件不精确**：使用了 `LIKE` 模糊匹配或范围查询 `BETWEEN`，导致多个分片被命中
- **缺失必要的索引**：分片表上未建立合适的索引，查询只能走全表扫描
- **结果集合并策略不当**：未根据业务场景选择合适的结果合并器

**解决方案**

**方案一：优化分片键选择**

```yaml
# 配置示例：根据常见查询模式选择分片键
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..3}
      databaseStrategy:
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: mod
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: mod
```

**方案二：配置分片算法的范围复写**

```java
// 自定义复合分片算法，处理跨分片范围查询
public class OrderRangeShardingAlgorithm implements RangeShardingAlgorithm<Long> {
    
    @Override
    public Collection<String> doSharding(
            Collection<String> availableTargetNames,
            RangeShardingValue<Long> rangeShardingValue) {
        
        Long lowerEndpoint = rangeShardingValue.getValueRange().hasLowerBound() 
            ? rangeShardingValue.getValueRange().lowerEndpoint() : 0L;
        Long upperEndpoint = rangeShardingValue.getValueRange().hasUpperBound()
            ? rangeShardingValue.getValueRange().upperEndpoint() : Long.MAX_VALUE;
        
        Set<String> result = new LinkedHashSet<>();
        for (long i = lowerEndpoint; i <= upperEndpoint; i++) {
            long dbIndex = i % 4;
            long tbIndex = (i / 4) % 4;
            String targetName = String.format("ds_%d.t_order_%d", dbIndex, tbIndex);
            if (availableTargetNames.contains(targetName)) {
                result.add(targetName);
            }
        }
        return result;
    }
}
```

**方案四：前端限制跨分片查询**

- 在应用层对跨分片查询进行限制或提示
- 对于必须跨分片的报表查询，考虑使用异步处理或定时任务
- 使用 ES/Hive 等专门的分析引擎处理跨分片聚合

### 16.2.2 分片键选择不当导致数据倾斜

**典型症状**

某些分片节点的数据量远超其他分片，导致存储不均衡。查询时部分节点负载极高，而其他节点却处于空闲状态。在进行数据迁移或备份时，个别分片的耗时远超预期。数据库报警显示某些实例的磁盘空间增长过快。

**问题原因分析**

分片键选择是数据分片的核心决策，选择不当会导致严重的数据倾斜问题。

- **选择低基数列作为分片键**：如使用状态字段（status: 0/1）、性别字段（gender: M/F）等，导致数据无法有效分散
- **使用自增ID作为分片键**：新数据总是写入最后一个分片，造成写入热点
- **按时间分片但数据不均匀**：业务高峰集中在某段时间，导致该时间段的分片数据量远大于其他分片
- **未考虑业务增长趋势**：分片数量固定，但某些业务线数据增长远超预期

**解决方案**

**方案一：重新选择高基数分片键**

```yaml
# 错误的分片键配置 - 使用低基数的 status 字段
t_order:
  tableStrategy:
    standard:
      shardingColumn: status  # 仅0/1两个值，数据严重倾斜
      shardingAlgorithmName: mod

# 正确的分片键配置 - 使用高基数的 user_id
t_order:
  tableStrategy:
    standard:
      shardingColumn: user_id  # 用户ID基数大，数据分散均匀
      shardingAlgorithmName: mod
```

**方案二：使用复合分片键**

```yaml
# 复合分片键配置示例
t_order:
  actualDataNodes: ds_${0..3}.t_order_${0..3}
  tableStrategy:
    complex:
      shardingColumns: user_id, order_id
      shardingAlgorithmName: user_order_complex

shardingAlgorithms:
  user_order_complex:
    type: COMPLEX_MOD
    props:
      v1.shardingAlgorithm.type: MOD
      v1.shardingAlgorithm.props.opaque: 4
      v2.shardingAlgorithm.type: MOD
      v2.shardingAlgorithm.props.opposite: 4
```

**方案三：自定义取模算法避免热点**

```java
// 使用哈希取模替代简单取模，减少数据倾斜
public class HashModShardingAlgorithm implements StandardShardingAlgorithm<Long> {
    
    private int shardingCount;
    
    @Override
    public void init(Properties props) {
        this.shardingCount = Integer.parseInt(
            props.getProperty("sharding-count", "4"));
    }
    
    @Override
    public String doSharding(
            Collection<String> availableTargetNames,
            PreciseShardingValue<Long> shardingValue) {
        long hash = Math.abs((long) shardingValue.getValue().hashCode());
        long index = hash % shardingCount;
        String suffix = String.valueOf(index);
        for (String targetName : availableTargetNames) {
            if (targetName.endsWith(suffix)) {
                return targetName;
            }
        }
        throw new UnsupportedOperationException(
            "No target found for value: " + shardingValue.getValue());
    }
}
```

**方案四：数据重分布**

当已有数据出现严重倾斜时，需要进行数据重分布：

1. 评估倾斜程度：`SELECT user_id, COUNT(*) FROM t_order GROUP BY user_id ORDER BY COUNT(*) DESC`
2. 制定数据迁移计划
3. 使用 ShardingSphere 的数据迁移工具或编写自定义迁移脚本
4. 验证数据一致性后切换分片规则

### 16.2.3 分片不均匀导致存储和性能问题

**典型症状**

监控显示某些分片的数据量是其他分片的数倍甚至数十倍。查询响应时间在不同分片间差异巨大。数据库实例的磁盘使用率不均衡，部分实例已接近存储上限。在进行扩容时，新增分片无法分担老分片的负载。

**问题原因分析**

分片不均匀的根本原因在于分片算法与实际数据分布的不匹配。

- **取模算法遇上数据热点**：某些特定用户或实体的数据量远超平均值
- **按时间分片但业务不均匀**：促销活动期间的数据量是平时的数倍
- **分片数量与业务规模不匹配**：初始分片数设置过少，无法承载当前数据量
- **未考虑数据生命周期**：缺乏冷热数据分离策略，热数据持续累积

**解决方案**

**方案一：采用一致性哈希算法**

```java
// 一致性哈希分片算法配置
public class ConsistentHashModShardingAlgorithm implements StandardShardingAlgorithm<Long> {
    
    private final TreeMap<Long, String> hashNodes = new TreeMap<>();
    private int virtualNodeCount = 100;
    
    @Override
    public void init(Properties props) {
        // 初始化虚拟节点
    }
    
    @Override
    public String doSharding(
            Collection<String> availableTargetNames,
            PreciseShardingValue<Long> shardingValue) {
        long hash = hash(sortingKey(shardingValue));
        Map.Entry<Long, String> entry = hashNodes.ceilingEntry(hash);
        if (entry == null) {
            entry = hashNodes.firstEntry();
        }
        return actualDataNode(entry.getValue());
    }
}
```

**方案二：配置多种分片策略**

```yaml
rules:
- !SHARDING
  tables:
    t_order:
      actualDataNodes: ds_${0..3}.t_order_${0..15}
      # 为不同数据量级的表配置不同策略
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: order_id_mod
      
  shardingAlgorithms:
    order_id_mod:
      type: INLINE
      props:
        algorithm-expression: t_order_${order_id % 16}
```

**方案三：定期监控与预警**

```sql
-- 监控各分片数据量分布
SELECT 
    SUBSTRING_INDEX(SUBSTRING_INDEX(table_name, '_', -1), '.', 1) as tb_index,
    TABLE_ROWS 
FROM information_schema.tables 
WHERE table_schema LIKE 'ds_%' 
  AND table_name LIKE 't_order_%'
ORDER BY TABLE_ROWS DESC;
```

**方案四：扩容策略**

当分片不均匀问题严重时，需要扩容：

1. **增加分片数量**：修改分片算法，将原 `MOD 4` 改为 `MOD 8`
2. **数据迁移**：将热点分片的数据拆分到新分片
3. **双写策略**：在新旧分片同时写入，逐步切换读操作到新分片

```yaml
# 扩容配置示例：从4分片扩展到8分片
rules:
- !SHARDING
  tables:
    t_order:
      # 过渡期配置，同时支持新旧分片
      actualDataNodes: ds_${0..7}.t_order_${0..15}
      # 新分片算法
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: order_id_mod_new
      
  shardingAlgorithms:
    order_id_mod_new:
      type: INLINE
      props:
        algorithm-expression: t_order_${order_id % 16}
```

## 16.3 事务相关问题

### 16.3.1 分布式事务超时

**典型症状**

应用日志中出现大量 `Transaction timeout` 或 `Transaction rollback` 异常。某些长事务操作莫名其妙地被回滚，但找不到明确的错误原因。数据库端显示事务长时间处于 `ACTIVE` 状态，锁未释放。前端请求超时，但后端事务仍在执行。

**问题原因分析**

分布式事务超时是 ShardingSphere-JDBC 使用 XA 或柔性事务时最常见的问题之一。

- **事务范围过大**：将大量分片操作放在单个事务中，导致事务时间过长
- **网络延迟累积**：跨多个分片的事务需要协调者多次网络通信
- **锁竞争严重**：跨分片分布式锁获取等待时间过长
- **默认超时配置不合理**：不同业务场景需要不同的超时时间
- **数据库端超时配置**：数据库的 `wait_timeout` 小于应用端配置

**解决方案**

**方案一：优化事务范围**

```java
// 错误的做法 - 事务范围过大
@Transactional
public void processLargeBatch(List<Order> orders) {
    for (Order order : orders) {
        orderService.create(order);  // 1000次分片操作在一个事务中
    }
}

// 正确的做法 - 分批处理，每批独立事务
public void processLargeBatch(List<Order> orders) {
    List<List<Order>> batches = Lists.partition(orders, 50);
    for (List<Order> batch : batches) {
        transactionTemplate.execute(status -> {
            for (Order order : batch) {
                orderService.create(order);
            }
            return null;
        });
    }
}
```

**方案二：配置合理的超时时间**

```yaml
# application.yml
spring:
  transaction:
    default-timeout: 30  # 默认事务超时时间（秒）
    
# 或在代码中指定
@Transactional(timeout = 30)
public void updateOrder(Order order) {
    // 操作
}
```

**方案三：使用柔性事务替代 XA**

对于一致性要求不那么严格的场景，可以使用柔性事务（Saga 或 Seata AT）：

```yaml
# 启用 Saga 柔性事务
saga:
  # Saga 事务超时时间
  transaction.timeout: 300
  # 补偿操作重试次数
  retry.max: 3
  # 补偿操作重试间隔
  retry.interval: 1000
```

```java

    // 主业务操作
}

@Compensable(compensationMethod = "cancelOrder")

    // 确认订单
}

public void cancelOrder(Long orderId) {
    // 补偿操作：取消订单
}
```

**方案四：处理超时异常**

```java
try {
    // 执行分布式事务操作
    orderService.create(order);
} catch (TransactionTimeoutException e) {
    // 超时处理：查询订单状态，决定是否需要人工干预

        orderService.confirmOrRollback(order.getId());
    }
} catch (Exception e) {
    // 其他异常处理

}
```

### 16.3.2 分布式死锁

**典型症状**

多个事务相互等待对方持有的锁，形成循环依赖。应用日志显示 `Deadlock found when trying to get lock`。部分请求长时间阻塞，系统吞吐量骤降。数据库监控显示多个事务处于 `Waiting for lock` 状态。

**问题原因分析**

分布式死锁比单机数据库死锁更复杂，因为死锁可能发生在多个分片之间。

- **跨分片锁顺序不一致**：不同事务以不同顺序访问多个分片的相同行
- **缺乏全局锁顺序机制**：ShardingSphere-JDBC 默认不提供跨分片全局锁顺序保证
- **大事务持有锁时间过长**：修改行数过多，锁范围大
- **索引缺失导致锁升级**：全表扫描时锁住大量行

**解决方案**

**方案一：统一锁访问顺序**

```java
// 错误：不同事务以不同顺序访问数据
// 事务1: 先锁A分片订单，再锁B分片订单
// 事务2: 先锁B分片订单，再锁A分片订单

// 正确：所有事务按统一顺序访问
public void transfer(Long fromUserId, Long toUserId, BigDecimal amount) {
    // 始终先锁 ID 较小的用户，再锁 ID 较大的用户
    Long firstId = fromUserId.compareTo(toUserId) < 0 ? fromUserId : toUserId;
    Long secondId = fromUserId.compareTo(toUserId) < 0 ? toUserId : fromUserId;
    
    if (fromUserId.equals(firstId)) {
        debit(firstId, amount);   // 先扣款
        credit(secondId, amount); // 再存款
    } else {
        credit(firstId, amount);  // 先存款
        debit(secondId, amount);  // 再扣款
    }
}
```

**方案二：使用乐观锁减少锁冲突**

```yaml
# 配置乐观锁版本控制
rules:
- !SHARDING
  tables:
    t_account:
      actualDataNodes: ds_${0..3}.t_account_${0..3}
      tableStrategy:

```

```java
public class Account {
    @Id
    private Long userId;
    
    private BigDecimal balance;

}

        .orElseThrow(() -> new AccountNotFoundException(userId));
    
    account.setBalance(account.getBalance().add(amount));
    accountRepository.save(account);
    // 若 version 不匹配，抛出 OptimisticLockException
}
```

**方案四：死锁检测与处理**

```java
// 定期检测并处理可能的死锁
@Scheduled(fixedDelay = 10000)
public void detectAndResolveDeadlock() {
    try {
        List<Long> blockedTransactions = transactionManager
            .getBlockedTransactions();
        
        for (Long transactionId : blockedTransactions) {
            TransactionInfo info = transactionManager.getTransactionInfo(transactionId);
            if (info.getWaitTime() > DEADLOCK_THRESHOLD_MS) {
                // 超时阈值强制回滚
                transactionManager.forceRollback(transactionId);
                log.warn("Force rollback blocked transaction: {}", transactionId);
            }
        }
    } catch (Exception e) {
        log.error("Deadlock detection failed", e);
    }
}
```

### 16.3.3 数据不一致

**典型症状**

查询结果与预期不符，某些分片的数据与其他分片不一致。事务提交后部分分片成功、部分分片失败，但应用未正确处理回滚。读写分离场景下，从库数据落后主库太多。报表数据与业务数据对不上，差异无法解释。

**问题原因分析**

数据不一致是分布式系统中最严重的问题之一，可能导致业务层面的错误决策。

- **柔性事务补偿失败**：Saga 或 TCC 事务的补偿操作执行失败或未执行
- **异步复制延迟**：主从复制配置不当，导致读取旧数据
- **事务过程中异常未完全回滚**：部分分片提交成功，但异常处理逻辑有缺陷
- **分片键计算错误**：同一业务数据被路由到不同分片
- **并发更新导致更新丢失**：缺乏适当的隔离级别或锁机制

**解决方案**

**方案一：使用 XA 强一致性事务**

```yaml
# 启用 XA 事务模式
spring:
  shardingsphere:
    transaction:
      default-type: XA
      provider-type: Atomikos

# 自定义 XA 配置
shardingsphere:
  transaction:
    xa:
      # XA 事务超时时间
      timeout: 60
      # 属性配置
      properties:
        maxPoolSize: 100
        minPoolSize: 10
```

```java
// 使用 @Transactional 保证强一致性
@Transactional(rollbackFor = Exception.class)
public void createOrderWithItems(Order order, List<OrderItem> items) {
    // XA 事务确保所有分片要么全部成功，要么全部回滚
    orderRepository.save(order);
    for (OrderItem item : items) {
        itemRepository.save(item);
    }
}
```

**方案二：实现数据一致性校验**

```java
// 定期数据一致性校验
@Component
public class DataConsistencyChecker {
    
    @Autowired
    private DataSource dataSource;
    
    public ConsistencyReport checkOrderConsistency() {
        ConsistencyReport report = new ConsistencyReport();
        
        // 1. 检查订单主表与明细表的关联一致性

            SELECT o.order_id, COUNT(oi.item_id) as item_count, 
                   COALESCE(SUM(o.total_amount), 0) as total
            FROM t_order o
            LEFT JOIN t_order_item oi ON o.order_id = oi.order_id
            GROUP BY o.order_id
            HAVING COUNT(oi.item_id) = 0 OR ABS(MAX(o.total_amount) - SUM(oi.price * oi.quantity)) > 0.01
            """;
        
        // 2. 检查各分片间的数据一致性
        // 遍历所有分片，比对关键业务数据
```

## 16.4 性能相关问题

### 16.4.1 连接池耗尽

**典型症状**

应用响应缓慢，部分请求等待数据库连接超时。错误日志中出现 `Connection is not available` 或 `Pool exhausted` 异常。数据库服务器连接数正常，但应用端连接不够用。在峰值时段问题严重，低峰时段可能自动恢复。

**问题原因分析**

连接池耗尽是 ShardingSphere-JDBC 性能问题中最常见的一种。

- **分片过多导致连接数倍增**：每个分片都需要独立连接，连接总数 = 分片数 × 每分片连接数
- **慢查询占用连接**：复杂查询执行时间过长，导致连接被长时间占用
- **连接泄漏**：连接未正确关闭或归还
- **事务范围过大**：大事务持有连接时间过长
- **连接池配置过小**：最小连接数设置不足，最大连接数限制过低

**解决方案**

**方案一：优化连接池配置**

```yaml
# HikariCP 连接池配置
spring:
  datasource:
    hikari:
      # 最小空闲连接数

      # 最大连接数
      maximum-pool-size: 100
      # 连接超时时间
      connection-timeout: 30000
      # 空闲超时
      idle-timeout: 600000
      # 最大生命周期
      max-lifetime: 1800000
      # 连接测试查询
      connection-test-query: SELECT 1
```

**方案二：使用 ShardingSphere 统一连接池**

```yaml

      # ...类似配置
```

### 16.4.2 SQL 执行变慢

**典型症状**

某些之前正常的 SQL 现在执行时间明显变长。同样的数据量，跨分片查询比单分片慢很多。带有分页的查询随着页码增大越来越慢。带有 ORDER BY 的查询性能急剧下降。

**问题原因分析**

SQL 性能下降的原因多种多样，需要系统性排查。

- **缺少分片键条件**：全分片扫描导致性能下降
- **分片键条件不精确**：范围查询导致多分片扫描
- **索引失效**：分片表索引因路由计算错误而未使用
- **结果集过大**：未限制返回行数，导致跨分片结果合并耗时
- **统计信息陈旧**：数据库优化器选择了错误的执行计划

**解决方案**

**方案一：确保 SQL 使用分片键**

```sql
-- 高效查询：分片键精确条件
SELECT * FROM t_order WHERE order_id = 12345;

-- 低效查询：缺少分片键，全分片扫描
SELECT * FROM t_order WHERE user_id = 100;

-- 低效查询：分片键使用函数
SELECT * FROM t_order WHERE YEAR(create_time) = 2024;

-- 高效查询：分片键范围查询
SELECT * FROM t_order WHERE order_id BETWEEN 1000 AND 2000;
```

**方案二：添加必要索引**

```sql

CREATE INDEX idx_user_id ON t_order_${n} (user_id);
CREATE INDEX idx_create_time ON t_order_${n} (create_time);

-- 对于所有分片统一添加索引（使用 ShardingSphere 的自动索引功能）
-- 或使用脚本批量添加

    mysql -hlocalhost -uroot -e "CREATE INDEX idx_user_id ON ds_$((i/4)).t_order_$i (user_id)"
done
```

- **配置未完全替换**：使用 `-D` 参数覆盖了 YAML 配置，但覆盖不完整

### 16.5.2 配置冲突

**典型症状**

同时配置了分片策略和读写分离策略，行为不确定。多个规则同时作用于同一张表，结果不符合预期。配置报错 `Conflicting rules` 或 `Rule conflict detected`。某些配置似乎被忽略。

**问题原因分析**

配置冲突通常发生在多个规则作用于同一目标时。

- **分片规则与读写分离规则冲突**：同时配置导致路由行为不确定
- **多个数据源配置重复**：同一个数据源被定义多次
- **加密规则与分片规则冲突**：字段既被加密又被分片
- **绑定表配置不一致**：关联表未使用相同的分片算法
- **重写规则冲突**：同一 SQL 被多条重写规则处理

```yaml
  - !READWRITE_SPLITTING
    ds_ms:
      writeDataSourceName: ds_0
      readDataSources:
        - ds_1
        - ds_2
  
  # 3. 分片配置
  - !SHARDING
    tables:
      t_order:
        actualDataNodes: ds_ms.t_order_${0..3}
```

## 16.6 迁移相关问题

### 16.6.1 历史数据迁移

**典型症状**

迁移脚本执行时间过长，影响业务运行。迁移过程中出现数据丢失或重复。迁移后查询结果与原数据库不一致。部分特殊字符或编码在迁移后乱码。

**问题原因分析**

历史数据迁移是一个高风险操作，问题可能源于多个环节。

- **迁移方案不完善**：未制定详细的数据迁移计划和回滚方案
- **数据量估算不足**：低估了数据规模和迁移耗时
- **迁移窗口选择不当**：在业务高峰期进行迁移，导致性能问题
- **字符编码问题**：源数据库和目标数据库字符集不一致
- **分片键变更**：迁移过程中分片键生成规则发生变化

**解决方案**

**方案一：制定完整的迁移计划**

```
1. 迁移前准备
   - 评估数据量和复杂度

   - 准备回滚方案
   - 备份原数据

2. 迁移执行
   - 数据校验（checksum）
   - 分批迁移
   - 增量同步
   - 迁移验证

3. 迁移后验证
   - 数据一致性校验
   - 性能对比测试
   - 业务功能验证
```

```java
// 分批迁移订单数据
@Service
public class OrderMigrationService {
    
    @Autowired
    private JdbcTemplate sourceJdbcTemplate;
    
    @Autowired
    private ShardingSphereDataSource targetDataSource;
    
    // 迁移批次大小
    private static final int BATCH_SIZE = 5000;
    
    public MigrationResult migrateOrders(Long startId, Long endId) {
        long totalRows = 0;
        long successRows = 0;
        long failedRows = 0;
        
        Long currentStart = startId;
        JdbcTemplate targetJdbc = new JdbcTemplate(targetDataSource);
        
        while (currentStart <= endId) {
            Long currentEnd = Math.min(currentStart + BATCH_SIZE - 1, endId);
            
            // 从源库读取数据
            String selectSql = "SELECT * FROM t_order WHERE order_id BETWEEN ? AND ?";
            List<Order> orders = sourceJdbcTemplate.query(selectSql, 
                (rs, rowNum) -> mapOrder(rs), 
                currentStart, currentEnd);
            
            // 写入目标分片
            String insertSql = """
                INSERT INTO t_order (order_id, user_id, total_amount, status, create_time) 
                VALUES (?, ?, ?, ?, ?)
                ON DUPLICATE KEY UPDATE status = VALUES(status)
                """;
            
            for (Order order : orders) {
                try {
                    targetJdbc.update(insertSql, 
                        order.getOrderId(),
                        order.getUserId(),
                        order.getTotalAmount(),
                        order.getStatus(),
                        order.getCreateTime());
                    successRows++;
                } catch (Exception e) {
                    log.error("Failed to migrate order: {}", order.getOrderId(), e);
                    failedRows++;
                }
            }
            
            totalRows += orders.size();
            currentStart = currentEnd + 1;
            
            // 每批之间短暂休息，避免数据库压力
            if (currentStart <= endId) {
                try {
                    Thread.sleep(100);
                } catch (InterruptedException e) {
                    Thread.currentThread().interrupt();
                    break;
                }
            }
        }
        
        return new MigrationResult(totalRows, successRows, failedRows);
    }
}
```

**方案四：迁移后数据校验**

```java
// 数据一致性校验
@Service
public class MigrationValidator {
    
    public ValidationReport validateMigration(Long startId, Long endId) {
        ValidationReport report = new ValidationReport();
        
        // 1. 校验记录数
        long sourceCount = sourceJdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM t_order WHERE order_id BETWEEN ? AND ?", 
            Long.class, startId, endId);
        long targetCount = targetJdbcTemplate.queryForObject(
            "SELECT COUNT(*) FROM t_order WHERE order_id BETWEEN ? AND ?", 
            Long.class, startId, endId);
        
        if (sourceCount != targetCount) {
            report.addError("Row count mismatch: source={}, target={}", sourceCount, targetCount);
        }
        
        // 2. 校验关键字段 checksum
        String sourceChecksum = sourceJdbcTemplate.queryForObject(
            "SELECT MD5(GROUP_CONCAT(order_id, total_amount)) FROM t_order WHERE order_id BETWEEN ? AND ?",
            String.class, startId, endId);
        String targetChecksum = targetJdbcTemplate.queryForObject(
            "SELECT MD5(GROUP_CONCAT(order_id, total_amount)) FROM t_order WHERE order_id BETWEEN ? AND ?",
            String.class, startId, endId);
        
        if (!sourceChecksum.equals(targetChecksum)) {
            report.addError("Checksum mismatch");
        }
        
        // 3. 抽样比对
        sampleCompare(startId, endId, 100);
        
        return report;
    }
}
```

### 16.6.2 分片方案变更

**典型症状**

扩容或缩容后数据分布不均匀。部分数据无法被正确查询到。原有数据与新数据路由到不同分片。变更期间服务不可用时间过长。

**问题原因分析**

分片方案变更涉及数据重新分布，是最具挑战性的运维操作之一。

- **取模基数变化**：从 `MOD 4` 改为 `MOD 8` 导致所有数据需要迁移
- **分片键变更**：原有数据使用不同分片键，需要完全重新分布
- **迁移过程中双写**：新、旧分片同时写入，增加复杂度
- **灰度切换困难**：难以逐步将流量切换到新分片

**解决方案**

**方案一：平滑扩容策略**

```java
// 扩容三阶段
// 阶段1：双写期 - 同时写入新旧分片
@EnableSharding
public class DualWriteMigration {
    
    private volatile boolean dualWriteEnabled = true;
    
    @Transactional
    public void insertOrder(Order order) {
        // 写入新分片
        insertToNewSharding(order);
        
        if (dualWriteEnabled) {
            // 同时写入旧分片（兼容性处理）
            insertToOldSharding(order);
        }
    }
}

// 阶段2：切换期 - 逐步切换读操作到新分片
public void switchReadsToNewSharding(double percentage) {
    HintManager hintManager = HintManager.getInstance();
    if (Math.random() < percentage) {
        hintManager.setDatabaseShardingValue("new_sharding");
    }
}

// 阶段3：清理期 - 停止双写，清理旧数据
public void cleanupOldSharding() {
    // 停止写入旧分片
    dualWriteEnabled = false;
    
    // 异步清理旧数据
    asyncDeleteOldData();
}
```

**方案二：使用一致性哈希实现平滑扩容**

```java
// 一致性哈希配置
public class ConsistentHashMigrationStrategy {
    
    private final TreeMap<Long, String> ring = new TreeMap<>();
    private final int virtualNodes;
    
    public ConsistentHashMigrationStrategy(int virtualNodes) {
        this.virtualNodes = virtualNodes;
    }
    
    // 扩容时只迁移少部分数据
    public void addNode(String node) {
        // 添加新节点到哈希环
        for (int i = 0; i < virtualNodes; i++) {
            long hash = hash(node + "#VN" + i);
            ring.put(hash, node);
        }
    }
    
    // 数据迁移量 = 新节点数据量 - 重叠数据量
    public Set<String> getMigratingData(String newNode, String oldNode) {
        // 计算需要从 oldNode 迁移到 newNode 的数据
        // 由于一致性哈希特性，只有相邻节点间的数据需要迁移
        return calculateMigrationKeys(newNode, oldNode);
    }
}
```

## 16.8 异常处理相关问题

### 16.8.1 ShardingSphere 常见异常类型

ShardingSphere-JDBC 在执行过程中可能抛出多种异常，以下是常见异常类型及处理方法。

| 异常类型 | 触发场景 | 处理建议 |
|---------|---------|---------|
| `ShardingException` | 分片规则配置错误 | 检查 YAML 配置语法 |
| `SQLRewriteException` | SQL 改写失败 | 检查 SQL 语法是否支持 |
| `SQLRouteException` | 无法确定路由目标 | 检查分片键条件 |
| `ShardingTransactionException` | 分布式事务异常 | 检查事务配置和状态 |
| `DataNegateiveException` | 负数分片值 | 检查分片键值范围 |
| `DuplicateSignatureException` | 重复的算法签名 | 检查算法配置 |
| `UnsupportedOperationException` | 不支持的 SQL 操作 | 考虑使用其他实现 |

**全局异常处理示例**

```java
@RestControllerAdvice
public class ShardingSphereExceptionHandler {
    
    @ExceptionHandler(ShardingException.class)
    public ResponseEntity<ErrorResponse> handleShardingException(ShardingException e) {
        log.error("Sharding error", e);
        return ResponseEntity
            .status(HttpStatus.INTERNAL_SERVER_ERROR)
            .body(new ErrorResponse("SHARDING_ERROR", e.getMessage()));
    }
    
    @ExceptionHandler(SQLRouteException.class)
    public ResponseEntity<ErrorResponse> handleSQLRouteException(SQLRouteException e) {
        log.error("SQL route error", e);
        return ResponseEntity
            .status(HttpStatus.BAD_REQUEST)
            .body(new ErrorResponse("SQL_ROUTE_ERROR", e.getMessage()));
    }
    
    @ExceptionHandler(ShardingTransactionException.class)
    public ResponseEntity<ErrorResponse> handleTransactionException(
            ShardingTransactionException e) {
        log.error("Transaction error", e);
        // 事务异常通常需要回滚并重试
        return ResponseEntity
            .status(HttpStatus.CONFLICT)
            .body(new ErrorResponse("TRANSACTION_ERROR", e.getMessage()));
    }
}
```

### 16.8.2 SQL 兼容性异常

**典型症状**

某些 SQL 在 ShardingSphere 中执行报错，但直接连接数据库执行正常。聚合函数、分页、JOIN 等操作报错。存储过程或函数无法使用。

**问题原因分析**

ShardingSphere-JDBC 在 SQL 执行前会进行解析、改写，部分 SQL 语法可能不被支持。

- **不支持的 SQL 语法**：如某些数据库特有的函数或语法
- **分片键在函数中**：如 `WHERE YEAR(create_time) = 2024`
- **不跨分片的子查询**：如 `WHERE id IN (SELECT id FROM ...)`
- **跨分片 UNION**：需要结果合并的 UNION 操作

**解决方案**

**方案一：检查不支持的 SQL 模式**

```yaml
# 配置不支持的 SQL 治理策略
shardingsphere:
  sql:
    # 遇到不支持的 SQL 时的策略
    # WARN: 记录日志但继续执行
    # ERROR: 抛出异常
    parseRule:
      unsupportedStrategy: WARN
```

**方案二：重写不支持的 SQL**

```java
// 错误示例：分片键在函数中
SELECT * FROM t_order WHERE YEAR(create_time) = 2024;

// 正确示例：将函数应用于结果而非分片键
SELECT * FROM t_order WHERE create_time >= '2024-01-01' AND create_time < '2025-01-01';

// 错误示例：跨分片子查询
SELECT * FROM t_order WHERE user_id IN (SELECT user_id FROM t_user WHERE status = 1);

// 正确示例：分两次查询，在应用层合并
List<Long> userIds = userRepository.findActiveUserIds();
List<Order> orders = orderRepository.findByUserIds(userIds);
```

**方案三：使用 Hint 强制路由**

```java

    HintManager hintManager = HintManager.getInstance();
```

## 16.11 社区常见问题汇总

### 16.11.1 官方 FAQ 精选

**Q1: ShardingSphere-JDBC 与 ShardingSphere-Proxy 如何选择？**

A: 根据以下场景选择：

- **ShardingSphere-JDBC**：适合 Java 技术栈，性能要求高，微服务架构
- **ShardingSphere-Proxy**：适合多语言环境，需要数据库协议兼容，现有系统改造

**Q2: 分片后能否支持 JOIN 操作？**

A: 同分片的表可以直接 JOIN，跨分片 JOIN 需要通过 BindingTable 或应用层处理。建议将关联紧密的表配置为同一分片。

**Q3: 如何实现分片键变更？**

A: 需要数据迁移：
1. 配置双写，同时写入新旧分片
2. 使用迁移工具迁移历史数据
3. 逐步切换读流量
4. 停止双写，清理旧数据

**Q4: 分片表是否支持自增主键？**

A: 支持，但建议使用 Snowflake 等分布式 ID 生成器，避免自增ID成为热点。

**Q5: 如何选择分片数量？**

A: 考虑因素：
- 当前数据量及增长预期
- 单分片容量上限（建议不超过 5000 万）
- 数据库连接数限制
- 扩缩容复杂度

### 16.11.2 常见错误代码

| 错误代码 | 含义 | 解决方案 |
|---------|------|---------|
| `2000` | 分片配置不完整 | 检查 YAML 配置 |
| `2001` | 分片键未找到 | 添加分片键条件 |
| `2002` | 不支持 SQL 语法 | 改写 SQL |
| `2003` | 连接获取超时 | 增加连接池大小 |
| `2004` | 事务超时 | 拆分事务范围 |
| `3000` | 规则冲突 | 调整规则配置 |
| `3001` | 数据源不可用 | 检查网络和数据库 |

### 16.11.3 性能调优建议

1. **避免全分片扫描**：始终使用分片键条件
2. **合理设置分片数量**：分片过多增加连接开销
3. **使用 BindingTable**：优化 JOIN 性能
4. **配置合适的连接池**：根据分片数和并发量调整
5. **定期维护索引**：确保分片表索引有效
6. **监控关键指标**：QPS、响应时间、连接使用率

本章系统性地介绍了 ShardingSphere-JDBC 在实际生产环境中可能遇到的各类问题及其解决方案。

**分片相关问题**的核心在于分片键的选择和分片算法的设计。建议选择高基数、分布均匀的字段作为分片键，避免数据倾斜。对于跨分片查询，应尽量优化查询条件或通过应用层处理。

**事务相关问题**需要特别关注事务范围的控制和超时配置。分布式事务应遵循「小事务、快速执行」的原则，避免长事务占用资源。

**性能相关问题**的排查应从连接池配置、慢 SQL 分析、索引优化等角度入手。连接池耗尽是最常见的性能问题，应根据分片数量和并发量合理配置连接池参数。

**配置问题**往往源于配置语法错误或加载顺序不当。建议使用配置验证工具，在启动时打印完整配置进行确认。

**迁移问题**是高风险操作，必须制定完善的迁移计划和回滚方案。建议采用双写、灰度切换等策略实现平滑迁移。

**Debug 和日志分析**是问题定位的关键。启用 DEBUG 日志，追踪 SQL 路由和改写过程，可以快速定位问题根因。

通过本章的学习，读者应该能够建立系统性的问题解决能力，在遇到 ShardingSphere-JDBC 相关问题时快速定位并解决。
