# 第1章 ShardingSphere-JDBC概述与快速入门

## 1.1 ShardingSphere 项目简介

### 1.1.1 项目定位

Apache ShardingSphere 是一款**分布式数据库生态系统**，旨在**化异构数据库为统一的数据库中间件生态**。它将数据分片、读写分离、数据加密、分布式事务等能力以**中间件**的形式注入到应用层，让开发者像使用单一数据库一样使用分布式数据库。

ShardingSphere 的核心设计哲学：

- **面向未来的架构**：不绑定特定数据库品牌，支持 MySQL、PostgreSQL、SQL Server、Oracle 等多种数据库
- **混合引擎策略**：支持多种治理模式（Local、Standalone、Cluster），可灵活应对不同部署环境
- **插件化设计**：所有功能均为可插拔模块，用户可根据需求自由组合
- **高性能优先**：优先保证数据库性能，对代理模式带来的额外开销保持警惕

### 1.1.2 发展历史

| 时间 | 版本 | 重要里程碑 |
|------|------|-----------|
| 2016年 | -- | 当当网内部项目 `Sharding-JDBC` 诞生，用于解决数据库分库分表问题 |
| 2018年 | 1.x | 开源并更名为 `ShardingSphere`，增加了读写分离、分布式事务等能力 |
| 2019年 | 2.x | 完成 MySQL、PostgreSQL 等数据库的适配，架构向平台化演进 |
| 2020年 | 4.x | 进入 Apache 软件基金会孵化，4.x 版本成为主流 |
| 2021年 | 5.x | 从分片中间件向**分布式数据库生态**全面升级，引入了可插拔架构、增强的分布式治理能力 |
| 2022年至今 | 5.4+ | 持续迭代，新增数据加密、影子库、弹性伸缩等企业级特性 |

> **版本选择提示**：生产环境推荐使用 5.4.x 或 5.5.x 最新稳定版。5.x 系列已经非常成熟，4.x 已进入维护模式不再推荐用于新项目。

### 1.1.3 生态组成

ShardingSphere 生态由以下核心项目组成：

```
ShardingSphere 生态
├── ShardingSphere-JDBC       # Java JDBC 驱动程序，嵌入应用进程
├── ShardingSphere-Proxy       # 独立部署的数据库代理服务
├── ShardingSphere-Sidecar     # Kubernetes 环境的数据库代理边车（正在发展）
└── ShardingSphere-UI          # 图形化控制台（仅适用于 Proxy 模式）
```

| 组件 | 描述 | 典型应用场景 |
|------|------|-------------|
| **ShardingSphere-JDBC** | 纯 Java 实现，以 JDBC 驱动的形式集成到应用程序中，轻量级、无需额外部署 | Java 微服务、Spring Boot 应用 |
| **ShardingSphere-Proxy** | 独立部署的数据库代理，以 MySQL/PostgreSQL 协议对外提供服务 | 多语言异构环境、对数据库协议有特殊要求的场景 |
| **ShardingSphere-Sidecar** | 面向 Kubernetes 的下一代部署形态 | 云原生环境 |

## 1.2 ShardingSphere-JDBC 与 ShardingSphere-Proxy 的区别

理解两者的核心差异是做出正确架构选择的前提。

### 1.2.1 核心架构对比

| 对比维度 | ShardingSphere-JDBC | ShardingSphere-Proxy |
|----------|---------------------|---------------------|
| **架构形态** | Java 库，以 JDBC 驱动嵌入应用进程 | 独立服务进程，需要单独部署 |
| **运行位置** | 应用层（Java 进程内） | 数据库代理层（独立进程） |
| **数据库协议** | 直接操作 JDBC，完全兼容 MySQL/PostgreSQL 协议 | MySQL/PostgreSQL 协议网络代理 |
| **多语言支持** | 仅限 Java | 支持任意编程语言（通过数据库协议） |
| **性能损耗** | 几乎零网络开销，性能高 | 额外的网络跳点，有一定性能损耗 |
| **部署复杂度** | 通过 Maven 引入依赖即可 | 需要额外部署服务，运维成本高 |
| **资源占用** | 共享应用服务器资源 | 独立部署，需要额外服务器资源 |
| **配置方式** | 配置文件或代码 API | 配置文件 + Admin API |
| **适用规模** | 中小规模分片（百级数据节点内） | 大规模分片、跨语言异构环境 |

### 1.2.3 选型建议

- **选择 ShardingSphere-JDBC**：
  - Java / Kotlin 应用
  - 微服务架构中使用 Spring Boot / Spring Cloud
  - 分片数量不多（不超过 100 个数据节点）
  - 对性能要求苛刻，不希望引入额外的网络跳点
  - 希望最小化部署和运维复杂度

- **选择 ShardingSphere-Proxy**：
  - 非 Java 语言应用（Python、Node.js、Go 等）
  - 需要统一管理多个异构语言应用的数据库访问
  - 分片数量庞大，需要独立的对接层来管理连接池
  - 有专职 DBA 团队可以维护独立代理服务
  - 需要图形化管理界面来管理分片规则

## 1.3 ShardingSphere-JDBC 核心功能

### 1.3.1 数据分片（Data Sharding）

数据分片是 ShardingSphere 最核心的功能，用于解决单库数据量过大的问题。

**支持的分片策略**：

| 分片类型 | 说明 | 典型场景 |
|---------|------|---------|
| **哈希分片** | 根据分片键的哈希值路由到不同数据节点 | 用户ID、订单ID 等均匀分布字段 |
| **范围分片** | 根据分片键的范围区间路由 | 时间范围（按月、按天分表） |
| **取模分片** | 根据分片键对分片数取模路由 | 固定分片数的业务 |
| **自定义分片** | 用户通过算法接口实现自定义路由逻辑 | 复杂业务规则 |

**分片维度**：

- **库内分表**：单库内多张表水平切分
- **分库分表**：跨多个库的水平和垂直切分
- **分片键选择**：支持单分片键和多分片键（绑定表场景）

```yaml
# 分片配置示例
schema:
  tables:
    t_order:
      actualDataNodes: ds_${0..1}.t_order_${0..15}
      databaseStrategy:
        standard:
          shardingColumn: user_id
          shardingAlgorithmName: mod
      tableStrategy:
        standard:
          shardingColumn: order_id
          shardingAlgorithmName: mod
```

### 1.3.2 读写分离（Read/Write Splitting）

在不改变应用代码的情况下，将读请求路由到从库，写请求路由到主库。

**特性**：

- 支持一主多从、多主多从等架构
- 支持配置从库权重（负载均衡）
- 支持强制路由到主库（写后读一致性场景）
- 支持配置探活检测，剔除故障从库

```yaml
read-write-split:
  groups:
    ds_master_slave:
      writeDataSourceName: ds_0
      readDataSourceNames:
        - ds_1
        - ds_2
      loadBalancerName: round_robin
  loadBalancers:
    round_robin:
      type: ROUND_ROBIN
```

### 1.3.3 分布式事务（Distributed Transaction）

ShardingSphere 支持多种分布式事务模式，适用于不同的业务场景：

| 事务模式 | 实现原理 | 一致性 | 性能 | 适用场景 |
|---------|---------|--------|------|---------|
| **LOCAL** | 无分布式协调，仅保证本地事务 | 弱一致 | 最高 | 同一分片内跨表操作 |
| **XA** | 基于两阶段提交协议（Atomikos/Seata） | 强一致 | 中等 | 跨分片强一致场景 |
| **BASE** | 柔性事务，基于 Saga 模式 | 最终一致 | 较高 | 可接受最终一致的业务 |
| **Synchronous** | 同步模式（实验性） | 强一致 | 中等 | 跨库同步写入 |

> **实践建议**：跨分片的写入操作务必使用 XA 事务；同一分片内的操作可以使用 LOCAL 事务以获得最佳性能。

### 1.3.4 数据加密（Data Encryption）

在数据写入前和读取后，对敏感字段进行加密/解密处理，对应用完全透明。

**支持的加密算法**：

| 算法类型 | 示例 | 说明 |
|---------|------|------|
| 哈希加密 | MD5、SHA-256 | 单向，不可解密 |
| 对称加密 | AES、RC4 | 可解密，需配置密钥 |
| 非对称加密 | RSA | 高安全场景 |

```yaml
encrypt:
  tables:
    t_user:
      columns:
        password:
          cipher:
            algorithm: AES
            key: your_aes_key
          type: AES
```

### 1.3.5 分布式治理（Distributed Governance）

支持注册中心式的集群管理，主要功能：

- **配置中心**：集中管理分片规则、动态生效
- **注册中心**：服务发现、故障转移
- **元数据管理**：表结构缓存、分片元数据同步
- **可观测性**：性能指标、链路追踪（支持 Prometheus、OpenTelemetry）

支持的注册中心：ZooKeeper、etcd、Nacos、Apollo

### 1.3.6 影子库（Shadow Database）

用于在生产环境前对 SQL 进行压测和验证，通过影子表/影子库将压测流量与生产流量隔离。

```yaml
shadow:
  enable: true
  dataSourceNames:
    - ds_0
  shadowRuleNames:
    - shadow_rule
```

## 1.4 ShardingSphere-JDBC 架构特点

### 1.4.1 轻量级（Lightweight）

ShardingSphere-JDBC 以 JAR 包形式发布，通过 Maven 引入即可使用：

```xml
<dependency>
    <groupId>org.apache.shardingsphere</groupId>
    <artifactId>shardingsphere-jdbc-core</artifactId>
    <version>5.5.0</version>
</dependency>
```

整个 JAR 包仅约 10MB（包含所有模块），无需额外部署服务进程，运行时消耗的内存资源与业务应用共享。

### 1.4.2 无代理（Proxy-less）

与 Proxy 模式不同，JDBC 模式不需要独立的代理服务进程。ShardingSphere-JDBC 以 JDBC 驱动的形式拦截和改写 SQL，对应用来说完全是透明的——应用仍然使用标准的 JDBC API 进行数据库操作，无需修改任何业务代码。

### 1.4.3 嵌入应用（In-Process）

ShardingSphere-JDBC 运行在 Java 应用进程内部：

- **零网络开销**：SQL 改写和路由在进程内完成，不增加额外的网络跳点
- **共享资源**：使用应用服务器的 CPU 和内存资源，无需独立服务器
- **快速故障检测**：与数据库直连，数据库故障可在毫秒级感知

### 1.4.4 可插拔架构（Pluggable）

ShardingSphere 5.x 采用的可插拔架构是最大亮点之一：

```
┌─────────────────────────────────────────────────────────┐
│                     ShardingSphere                       │
│  ┌─────────────────────────────────────────────────────┐ │
│  │              Database Protocol Layer                │ │
│  │        (MySQL / PostgreSQL / openGauss ...)         │ │
│  └─────────────────────────────────────────────────────┘ │
│                           │                              │
│  ┌─────────────────────────────────────────────────────┐ │
│  │                    Core Layer                       │ │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐ ┌─────────┐    │ │
│  │  │  SQL    │ │  SQL    │ │ Dist.   │ │ Dist.   │    │ │
│  │  │ Parser  │ │Rewriter │ │Transaction│ Governance│    │ │
│  │  └─────────┘ └─────────┘ └─────────┘ └─────────┘    │ │
│  └─────────────────────────────────────────────────────┘ │
│                           │                              │
│  ┌─────────────────────────────────────────────────────┐ │
│  │                  Feature Layer                       │ │
│  │  ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐ ┌──────┐     │ │
│  │  │Sharding│ │ RW   │ │Encrypt│ │ XA   │ │Shadow│     │ │
│  │  │      │ │Split │ │      │ │Trans │ │      │     │ │
│  │  └──────┘ └──────┘ └──────┘ └──────┘ └──────┘     │ │
│  └─────────────────────────────────────────────────────┘ │
└─────────────────────────────────────────────────────────┘
```

每一层均为可插拔模块，用户可以根据需要引入特定模块（分片、读写分离、数据加密等），不会引入不必要的依赖。

package com.example.shardingsphere.entity;

    private String username;

        try {
            // 1. 初始化 ShardingSphere DataSource（通过 YAML 配置）

            // 2. 设置到 DriverManager（使 JDBC 驱动可被发现）

            System.out.println("\n=== 订单操作演示（分片场景） ===");

            Order order1 = new Order(1L, 1L, new BigDecimal("299.00"), "PAID");
            Order order2 = new Order(2L, 1L, new BigDecimal("599.00"), "PAID");

    private static DataSource createDataSource() throws SQLException {
        // 从 classpath 加载 YAML 配置文件
        File configFile = new File("src/main/resources/config/sharding-databases-tables.yaml");
        return YamlShardingSphereDataSourceFactory.createDataSource(configFile);

    private static void setDataSource(DataSource dataSource) {
        // 将 DataSource 注册到 DriverManager，供 Repository 获取连接
        // 在实际 Spring 环境中，DataSource 会被自动注入
        try {
            Connection connection = dataSource.getConnection();
            connection.close();
        } catch (SQLException e) {
            // 忽略初始化连接的错误
        }
        // 将 dataSource 放入静态引用，供 getConnection 使用
        DataSourceHolder.setDataSource(dataSource);
    }

## 1.8 版本选择建议

### 1.8.1 版本号说明

Apache ShardingSphere 的版本号遵循语义化版本规范：

- **5.5.0**：大版本号，通常表示架构和 API 有重大变化
- **5.4.2**（小版本号）：表示功能增强和 bug 修复
- **SNAPSHOT**：开发中版本，不建议在生产环境使用

### 1.8.2 版本选择对照表

| 场景 | 推荐版本 | 原因 |
|------|---------|------|
| 新项目（生产环境） | **5.5.0** 或 **5.4.x 最新版** | 功能完整，性能稳定，已通过大量生产验证 |
| 已有项目升级 | 5.4.x 系列 | 避免跨越大版本升级带来的兼容性风险 |
| 学习研究 | 5.5.0 | 包含最新功能和最佳文档 |
| 保守型项目 | 5.3.x（ LTS ） | 长期支持版本，稳定性优先 |
| 尝试新特性 | 5.5.x（最新预览版） | 包含实验性功能 |

### 1.8.3 版本升级注意事项

1. **5.3 → 5.4 升级**：配置格式可能有微小调整，建议查看官方升级指南
2. **5.4 → 5.5 升级**：分片算法命名空间有变化，旧的算法名需要更新
3. **配置文件格式**：YAML 配置的命名空间从 `sharding.jdbc.` 变更为 `spring.shardingsphere.`，Spring Boot Starter 模式下尤其明显

## 1.9 适用场景分析

### 1.9.1 何时应该使用 ShardingSphere-JDBC

**强烈推荐使用的场景**：

| 场景 | 说明 | 收益 |
|------|------|------|
| **单库数据量过亿** | MySQL 单表超过 5000 万行，查询性能明显下降 | 将数据分散到多表/多库，解决单表瓶颈 |
| **高并发写入** | 大促期间写入 TPS 超过 10 万 | 分库写入，突破单库写入上限 |
| **读写分离需求** | 读多写少，一主多从架构 | 将读请求分流到从库，减轻主库压力 |
| **敏感数据加密** | 需要对用户身份信息、银行卡号等加密存储 | 无需修改业务代码，透明加密 |
| **多租户隔离** | SaaS 平台需要逻辑隔离不同租户的数据 | 分租户分库，物理隔离 |

**需要谨慎评估的场景**：

| 场景 | 挑战 | 建议 |
|------|------|------|
| 超过 1000 个分片节点 | 配置管理复杂、连接池压力巨大 | 考虑使用 ShardingSphere-Proxy 统一管理 |
| 跨库关联查询（JOIN）频繁 | 跨库 JOIN 性能差，部分场景无法支持 | 考虑数据聚合层（如 Elasticsearch） |
| 强一致事务跨分片 | XA 事务有性能损耗 | 评估业务是否接受最终一致性 |
| 复杂动态报表 | 分片后的二级索引受限 | 考虑引入读写分离的只读副本 |

### 1.9.2 典型业务场景选型

**场景一：电商订单系统**

```
特征：数据量大、写入密集、查询维度多
推荐方案：分库分表（按 user_id 分库，按 order_id 分表）+ 读写分离
分片数：2-4 库 × 12-24 表（按月分表）
```

**场景二：用户中心（SSO）**

```
特征：读多写少、关联查询多、数据增长平稳
推荐方案：读写分离（一主多从）+ 数据加密
特点：重点保护用户隐私数据（身份证号、手机号加密）
```

**场景三：日志系统**

```
特征：写入量极大、数据价值低、查询简单
推荐方案：直接按时间分表（单库多表即可）
特点：不需要分布式事务，直接使用 LOCAL 模式
```

### 1.9.3 不适合使用 ShardingSphere 的场景

- **OLAP 实时分析**：复杂 JOIN 和聚合查询场景，ClickHouse、GreenPlum 等更合适
- **TB 级大字段存储**：图片、视频等非结构化数据，对象存储更合适
- **超简单业务**：单表数据量不超过千万行，业务逻辑简单，增加分片复杂度不划算
- **强依赖数据库特性**：大量使用存储过程、触发器、复杂函数，ShardingSphere 可能不兼容
