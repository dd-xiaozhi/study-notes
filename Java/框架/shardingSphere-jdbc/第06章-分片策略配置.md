# 第6章 分片策略配置

## 6.1 分片策略概述

在 ShardingSphere-JDBC 中，分片策略是实现数据分片的核心组件。它决定了数据应当路由到哪个数据节点，以及如何根据分片键的值进行数据拆分。分片策略由分片键（Sharding Column）和分片算法（Sharding Algorithm）共同组成，二者缺一不可。

### 6.1.1 分片策略的核心组成

分片策略包含两个核心要素：

**分片键（Sharding Column）**
- 又称为分片字段，是用于实现数据分片的数据库表字段
- 通常选择具有高度区分度的字段，如用户ID、订单ID等
- 一个分片策略可以包含一个或多个分片键

**分片算法（Sharding Algorithm）**
- 决定数据如何根据分片键的值进行路由和拆分
- ShardingSphere-JDBC 提供了多种内置分片算法，同时也支持自定义算法
- 分片算法与分片键配合工作，实现精确的数据路由

### 6.1.2 分片策略类型总览

ShardingSphere-JDBC 支持以下几种分片策略：

| 策略类型 | 说明 | 适用场景 |
|---------|------|---------|
| 标准分片策略 | 基于单分片键的策略 | 简单分片场景 |
| 复合分片策略 | 基于多分片键的策略 | 复杂业务场景 |
| 行表达式分片策略 | 使用表达式进行分片 | 快速配置场景 |
| Hint 分片策略 | 强制路由到特定数据节点 | 特殊路由需求 |

### 6.1.3 分片策略配置层级

ShardingSphere-JDBC 的分片策略配置分为两个层级：

**逻辑数据源级别**
- 配置在数据源层面，对所有表生效
- 通过 `default-database-strategy` 配置

**逻辑表级别**
- 配置在单个表层面，优先级高于数据源级别
- 通过 `tables.<logic-table>.table-strategy` 配置

配置优先级：逻辑表级别 > 逻辑数据源级别

### 6.1.4 分片策略配置流程

完整的分片策略配置流程如下：

```
1. 定义数据源配置
   └── 配置真实数据源列表（ds_0, ds_1, ds_2...）

2. 定义分片规则
   ├── 配置逻辑表与真实表的映射关系
   ├── 配置分片键
   └── 配置分片算法

3. 配置分片策略
   ├── 选择策略类型（standard/complex/inline/hint）
   ├── 配置分片键
   └── 配置分片算法参数

4. 使用逻辑表进行数据操作
   └── 系统自动根据分片策略路由到真实表
```

## 6.2 标准分片策略配置

标准分片策略（Standard Sharding Strategy）是最常用的分片策略类型，它基于单一分片键进行数据分片。该策略支持 `=`, `IN`, `BETWEEN`, `LIKE` 等多维度查询路由。

### 6.2.1 策略结构

标准分片策略的配置结构如下：

```yaml
tables:
  <logic_table_name>:
    database-strategy:
      standard:
        sharding-column: <column_name>      # 分片键
        precise-algorithm-class-name: <class_name>   # 精确分片算法（用于 =, IN）
        range-algorithm-class-name: <class_name>    # 范围分片算法（用于 BETWEEN）
```

**参数说明：**
- `sharding-column`: 分片键字段名
- `precise-algorithm-class-name`: 精确匹配算法类，用于处理 `=` 和 `IN` 操作
- `range-algorithm-class-name`: 范围匹配算法类，用于处理 `BETWEEN` 操作（可选）

### 6.2.2 精确分片算法接口

精确分片算法需要实现 `PreciseShardingAlgorithm` 接口：

```java
package org.apache.shardingsphere.api.config.sharding.strategy;

import org.apache.shardingsphere.sharding.api.sharding.PreciseShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.ShardingValue;

public interface PreciseShardingAlgorithm<T extends Comparable<T>> extends ShardingAlgorithm {
    
    /**
     * 根据分片值精确返回数据源或表名称
     * @param shardingValue 分片值
     * @return 目标数据源或表名称
     */
    String doSharding(PreciseShardingValue<T> shardingValue);
}
```

### 6.2.3 范围分片算法接口

范围分片算法需要实现 `RangeShardingAlgorithm` 接口：

```java
package org.apache.shardingsphere.api.config.sharding.strategy;

import org.apache.shardingsphere.sharding.api.sharding.RangeShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.ShardingValue;

public interface RangeShardingAlgorithm<T extends Comparable<T>> extends ShardingAlgorithm {
    
    /**
     * 根据分片值范围返回数据源或表名称集合
     * @param shardingValue 分片值范围
     * @return 目标数据源或表名称集合
     */
    Collection<String> doSharding(RangeShardingValue<T> shardingValue);
}
```

### 6.2.4 配置示例：按订单 ID 分库

假设我们有 4 个数据源 `ds_0`, `ds_1`, `ds_2`, `ds_3`，需要根据 `order_id` 进行分库。

**自定义精确分片算法：**

```java
package com.example.sharding.algorithm;

import org.apache.shardingsphere.sharding.api.sharding.PreciseShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.PreciseShardingAlgorithm;

import java.util.Collection;

public class OrderIdDatabaseShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        Long orderId = shardingValue.getValue();
        String dataSourceName = shardingValue.getDataSourceName();
        
        // 按 order_id 取模分片
        long dbIndex = orderId % 4;
        return dataSourceName + "_" + dbIndex;
    }
}
```

**YAML 配置：**

```yaml
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3

tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..15}
    databaseStrategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: com.example.sharding.algorithm.OrderIdDatabaseShardingAlgorithm
    tableStrategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: com.example.sharding.algorithm.OrderIdTableShardingAlgorithm
```

### 6.2.5 配置示例：带范围查询的场景

对于需要支持 `BETWEEN` 查询的场景，需要同时配置精确分片算法和范围分片算法。

**范围分片算法实现：**

```java
package com.example.sharding.algorithm;

import org.apache.shardingsphere.sharding.api.sharding.RangeShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.RangeShardingAlgorithm;

import java.util.Collection;
import java.util.HashSet;
import java.util.Set;

public class OrderIdRangeShardingAlgorithm implements RangeShardingAlgorithm<Long> {
    
    @Override
    public Collection<String> doSharding(RangeShardingValue<Long> shardingValue) {
        Long lowerEndpoint = shardingValue.getValueRange().lowerEndpoint();
        Long upperEndpoint = shardingValue.getValueRange().upperEndpoint();
        
        Set<String> result = new HashSet<>();
        
        // 遍历范围内所有可能的分片键值
        for (long i = lowerEndpoint; i <= upperEndpoint; i++) {
            long dbIndex = i % 4;
            result.add("ds_" + dbIndex);
        }
        
        return result;
    }
}
```

**配置更新：**

```yaml
tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..15}
    databaseStrategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: com.example.sharding.algorithm.OrderIdDatabaseShardingAlgorithm
        range-algorithm-class-name: com.example.sharding.algorithm.OrderIdRangeShardingAlgorithm
```

### 6.2.6 标准分片策略的工作流程

标准分片策略的执行流程如下：

```
SQL: SELECT * FROM t_order WHERE order_id = 12345

1. 解析 SQL，提取分片键值
   └── order_id = 12345

2. 调用精确分片算法
   └── doSharding(PreciseShardingValue<Long>(12345))
   └── 返回: ds_1

3. 路由到目标数据源
   └── ds_1.t_order_$->{0..15}

4. 执行查询
   └── 在 ds_1 的所有分片表中执行查询
```

### 6.2.7 注意事项

1. **分片键必须出现在 WHERE 条件中**：否则将进行全路由（所有数据源/表都执行）

2. **精确算法必须实现**：即使不配置范围算法，精确算法也必须配置

3. **范围算法可选**：如果业务不需要 BETWEEN 查询，可以不配置范围算法

4. **分片键类型**：分片键值必须是可比较的类型（如数字、字符串、日期等）

## 6.3 复合分片策略配置

复合分片策略（Complex Sharding Strategy）支持基于多个分片键进行数据分片。当业务场景需要同时根据多个字段进行分片时，应使用复合分片策略。

### 6.3.1 适用场景

复合分片策略适用于以下场景：

- 业务需要同时根据用户ID和时间进行分片
- 查询条件包含多个分片键的组合
- 单一分片键无法满足业务区分度要求

### 6.3.2 策略结构

```yaml
tables:
  <logic_table_name>:
    database-strategy:
      complex:
        sharding-columns: <column1>,<column2>  # 多个分片键，用逗号分隔
        algorithm-class-name: <class_name>    # 复合分片算法类
```

### 6.3.3 复合分片算法接口

复合分片算法需要实现 `ComplexKeysShardingAlgorithm` 接口：

```java
package org.apache.shardingsphere.api.config.sharding.strategy;

import org.apache.shardingsphere.sharding.api.sharding.ComplexShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.ShardingValue;

import java.util.Collection;

public interface ComplexKeysShardingAlgorithm<T extends Comparable<T>> extends ShardingAlgorithm {
    
    /**
     * 根据多个分片键的值返回数据源或表名称
     * @param shardingValue 包含多个分片键的值
     * @return 目标数据源或表名称集合
     */
    Collection<String> doSharding(ComplexShardingValue<T> shardingValue);
}
```

### 6.3.4 配置示例：用户ID + 时间分片

假设订单表需要根据 `user_id` 和 `create_time` 两个字段进行分片。

**复合分片算法实现：**

```java
package com.example.sharding.algorithm;

import org.apache.shardingsphere.sharding.api.sharding.ComplexShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.ComplexKeysShardingAlgorithm;

import java.util.Collection;
import java.util.HashSet;
import java.util.Map;
import java.util.Set;

public class OrderComplexShardingAlgorithm implements ComplexKeysShardingAlgorithm<Long> {
    
    @Override
    public Collection<String> doSharding(ComplexShardingValue<Long> shardingValue) {
        Map<String, Object> valueMap = shardingValue.getValueMap();
        Set<String> result = new HashSet<>();
        
        // 获取分片键的值
        Long userId = (Long) valueMap.get("user_id");
        Long createTime = (Long) valueMap.get("create_time");
        
        if (userId == null || createTime == null) {
            // 如果分片键值为空，返回所有数据源
            for (int i = 0; i < 4; i++) {
                result.add("ds_" + i);
            }
            return result;
        }
        
        // 复合分片算法：根据 user_id 取模确定库，根据月份确定表
        long dbIndex = userId % 4;
        int month = calculateMonth(createTime);
        
        // 生成目标数据源和表
        String dataSource = "ds_" + dbIndex;
        for (int i = 0; i <= month / 3; i++) {
            result.add(dataSource + ".t_order_" + i);
        }
        
        return result;
    }
    
    private int calculateMonth(long timestamp) {
        // 根据时间戳计算月份
        return (int) (timestamp / 2592000000L) % 12;
    }
}
```

**YAML 配置：**

```yaml
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3

tables:
  t_order:
    actualDataNodes: ds_$->{0..3}.t_order_$->{0..3}
    databaseStrategy:
      complex:
        sharding-columns: user_id,create_time
        algorithm-class-name: com.example.sharding.algorithm.OrderComplexShardingAlgorithm
    tableStrategy:
      complex:
        sharding-columns: user_id,create_time
        algorithm-class-name: com.example.sharding.algorithm.OrderTableComplexShardingAlgorithm
```

### 6.3.5 复合分片值对象

`ComplexShardingValue` 提供了获取分片值的方法：

```java
public class ComplexShardingValue<T extends Comparable<T>> implements ShardingValue {
    
    // 获取所有分片键的值映射
    Map<String, Object> getValueMap();
    
    // 获取指定分片键的值
    Comparable<?> getValue(String columnName);
    
    // 获取分片键列表
    List<String> getColumnNames();
    
    // 获取逻辑表名称
    String getLogicTableName();
}
```

### 6.3.6 复合分片策略的路由特点

复合分片策略的路由有以下特点：

1. **多键路由**：可以同时根据多个分片键的值进行路由
2. **灵活算法**：业务可以在算法中自定义路由规则
3. **可能返回多目标**：根据算法实现，可能返回多个数据源或表

### 6.3.7 性能优化建议

1. **避免笛卡尔积**：在算法中应精确控制返回的目标表/库，避免返回不必要的节点
2. **缓存热点数据**：对于高频查询的分片键组合，可以使用缓存减少计算
3. **索引优化**：确保复合分片键的各个字段都有合适的索引

## 6.4 行表达式分片策略（Inline 策略）

行表达式分片策略（Inline Sharding Strategy）是 ShardingSphere-JDBC 中最简洁的分片策略配置方式。它使用 Groovy 表达式定义分片规则，适合快速配置和简单分片场景。

### 6.4.1 表达式语法

Inline 策略使用 `${ expression }` 或 `$->{ expression }` 语法：

- `${ expression }`：表达式结果参与 SQL 路由
- `$->{ expression }`：表达式结果不参与 SQL 路由，仅用于生成配置

### 6.4.2 支持的表达式操作

**取模运算**
```
ds_${user_id % 4}          # user_id 对 4 取模，确定数据源
t_order_${order_id % 16}   # order_id 对 16 取模，确定表
```

**范围简化**
```
ds_${0..3}                 # 生成 ds_0, ds_1, ds_2, ds_3
t_order_${0..15}           # 生成 t_order_0 到 t_order_15
```

**枚举值**
```
ds_${['main', 'backup']}   # 生成 ds_main, ds_backup
```

### 6.4.3 配置示例：简单取模分片

**基础配置**

```yaml
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3

tables:
  t_order:
    actualDataNodes: ds_${0..3}.t_order_${0..15}
    database-strategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: org.apache.shardingsphere.sharding.strategy.algorithm.inline.InlineShardingAlgorithm
        props:
          algorithm.expression: ds_${order_id % 4}
    tableStrategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: org.apache.shardingsphere.sharding.strategy.algorithm.inline.InlineShardingAlgorithm
        props:
          algorithm.expression: t_order_${order_id % 16}
```

**简化配置（使用 inline 策略）**

```yaml

  - ds_0
  - ds_1
  - ds_2
  - ds_3

tables:
  t_order:
    actualDataNodes: ds_${0..3}.t_order_${0..15}
    database-strategy:
      inline:
        sharding-column: order_id
        algorithm-expression: ds_${order_id % 4}
    tableStrategy:
      inline:
        sharding-column: order_id
        algorithm-expression: t_order_${order_id % 16}
```

### 6.4.6 Inline 策略的工作原理

Inline 策略底层使用 `InlineShardingAlgorithm`，其工作原理如下：

```java
package org.apache.shardingsphere.sharding.strategy.algorithm.inline;

import org.apache.shardingsphere.sharding.api.sharding.PreciseShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.PreciseShardingAlgorithm;

import java.util.Properties;

public class InlineShardingAlgorithm implements PreciseShardingAlgorithm {
    
    private String expression;
    
    @Override
    public void init(Properties props) {
        this.expression = props.getProperty("expression");
    }
    
    @Override
    public String doSharding(PreciseShardingValue shardingValue) {
        // 解析表达式，将 ${column_name} 替换为实际值
        String result = expression;
        
        // 遍历表达式中的占位符
        for (String placeholder : extractPlaceholders(expression)) {
            // 获取分片键值并计算
            Object value = shardingValue.getValue(placeholder);
            Object resultValue = evaluate(expression, placeholder, value);
            result = result.replace("${" + placeholder + "}", resultValue.toString());
        }
        
        return result;
    }
    
    // 计算表达式中的数学运算
    private Object evaluate(String expr, String placeholder, Object value) {
        // 解析类似 ${user_id % 4} 的表达式
        // 并使用实际的分片键值进行计算
    }
}
```

### 6.4.7 Inline 策略的限制

1. **不支持范围查询优化**：Inline 策略主要用于精确分片，对于 BETWEEN 查询会全路由

2. **不支持多分片键**：Inline 策略只支持单一分片键

3. **表达式复杂度限制**：复杂业务逻辑不适合使用 Inline 表达式

4. **无法自定义路由**：路由逻辑受限于表达式语法

### 6.4.8 Inline vs 标准分片策略对比

| 特性 | Inline 策略 | 标准分片策略 |
|------|------------|-------------|
| 配置复杂度 | 低 | 中 |
| 灵活性 | 低 | 高 |
| 多分片键支持 | 不支持 | 支持（通过复合策略） |
| 范围查询优化 | 不支持 | 支持 |
| 自定义路由逻辑 | 有限 | 完全支持 |
| 适用场景 | 简单取模分片 | 复杂业务场景 |

### 6.4.9 最佳实践建议

**适合使用 Inline 的场景：**
- 简单的取模分片
- 开发测试环境快速搭建
- 分片键与分片数有明确数学关系

**建议使用标准分片策略的场景：**
- 需要自定义分片逻辑
- 分片算法复杂
- 需要优化范围查询
- 多分片键场景

## 6.5 Hint 分片策略（强制分片路由）

Hint 分片策略是一种强制路由机制，允许开发者在运行时通过编程方式指定分片路由目标，而不是依赖 SQL 解析和分片键匹配。适用于一些特殊业务场景，如分片键不在 SQL 条件中、需要在特定场景下强制路由到某个数据节点等。

### 6.5.1 核心概念

**HintManager**
- 是 Hint 分片策略的核心 API
- 提供了设置分片值、强制路由等功能
- 需要在操作完成后手动清理

### 6.5.2 主要 API

```java
package org.apache.shardingsphere.api;

public interface HintManager {
    
    // 设置分片值，强制路由到指定数据源/表
    void setShardingValue(ShardingValue shardingValue);
    
    // 强制路由到指定数据源
    void setDatabaseShardingValue(ShardingValue shardingValue);
    
    // 强制路由到指定表
    void setTableShardingValue(ShardingValue shardingValue);
    
    // 强制路由到所有数据源
    void setDatabaseShardingValueForAllNodes(ShardingValue shardingValue);
    
    // 强制路由到所有表
    void setTableShardingValueForAllNodes(ShardingValue shardingValue);
    
    // 获取当前 HintManager 实例
    static HintManager getInstance();
    
    // 清理资源
    void close();
}
```

### 6.5.3 配置方式

**YAML 配置**

```yaml
tables:
  t_order:
    actualDataNodes: ds_${0..3}.t_order_${0..15}
    database-strategy:
      hint:
        algorithm-class-name: com.example.sharding.algorithm.HintDatabaseShardingAlgorithm
    tableStrategy:
      hint:
        algorithm-class-name: com.example.sharding.algorithm.HintTableShardingAlgorithm
```

**Hint 分片算法接口**

```java
package org.apache.shardingsphere.api.config.sharding.strategy;

import org.apache.shardingsphere.sharding.api.sharding.HintShardingValue;
import org.apache.shardingsphere.sharding.api.sharding.ShardingValue;

import java.util.Collection;

public interface HintShardingAlgorithm<T extends Comparable<T>> extends ShardingAlgorithm {
    
    /**
     * 根据 Hint 设置的分片值进行路由
     * @param shardingValue Hint 分片值
     * @return 目标数据源或表名称集合
     */

}
```

### 6.5.4 使用示例：分片键不在SQL条件中

某些业务场景下，分片键可能不在 WHERE 条件中，但需要根据其他上下文信息进行分片。

**场景：订单表按 user_id 分片，但查询时只知道订单ID**

```java
@Test
public void testQueryWithHint() {
    // 1. 创建 HintManager
    HintManager hintManager = HintManager.getInstance();
    
    try {
        // 2. 设置强制分片值
        // 假设我们需要查询 order_id = 12345 的订单
        // 通过某种方式（如缓存、关联查询）获取到 user_id = 67890
        hintManager.setDatabaseShardingValue("user_id", 67890L);
        hintManager.setTableShardingValue("user_id", 67890L);
        
        // 3. 执行查询
        // 这条 SQL 没有分片键，但通过 Hint 强制指定路由
        String sql = "SELECT * FROM t_order WHERE order_id = 12345";
        List<Order> orders = jdbcTemplate.query(sql, orderRowMapper);
        
    } finally {
        // 4. 清理资源
        hintManager.close();
    }
}
```

**对应的分片算法：**

```java

public class UserIdHintShardingAlgorithm implements HintShardingAlgorithm<Long> {
    
    @Override
    public Collection<String> doSharding(HintShardingValue<Long> shardingValue) {
```

### 6.5.7 HintManager 常用方法详解

```java
// 获取 HintManager 实例
HintManager hintManager = HintManager.getInstance();

// 添加数据库级别分片值
hintManager.addDatabaseShardingValue("t_order", "user_id", 67890L);

// 添加表级别分片值
hintManager.addTableShardingValue("t_order", "order_id", 12345L);

// 强制路由到所有节点（用于统计等场景）
hintManager.setDatabaseShardingValueForAllNodes("order_id");
hintManager.setTableShardingValueForAllNodes("order_id");

// 设置分片值（等价于上面的方法）
hintManager.setShardingValue(new PreciseShardingValue<>("t_order", "user_id", 67890L));

// 关闭（非常重要，必须调用）
hintManager.close();

// 使用 try-with-resources 自动关闭
try (HintManager hintManager = HintManager.getInstance()) {
    hintManager.setDatabaseShardingValue("user_id", 67890L);
    // 执行操作
}
```

### 6.5.8 注意事项

1. **资源清理**：使用完 HintManager 后必须调用 `close()` 方法，建议使用 try-with-resources

2. **线程安全**：HintManager 不是线程安全的，不要在多线程环境中共享

3. **性能影响**：强制路由会绕过 SQL 解析优化，可能影响性能

4. **SQL 改写**：使用 Hint 后，系统不会进行 SQL 改写，需要手动确保 SQL 语法正确

5. **分布式环境**：在分布式环境中使用 Hint，确保所有节点配置一致

### 6.5.9 Hint 策略的应用场景总结

| 场景 | 说明 | 示例 |
|-----|------|-----|
| 分片键不在 SQL 中 | 分片键通过应用层计算，不在查询条件中 | 根据订单ID查询，user_id在缓存中 |
| DBA 维护操作 | 需要操作所有分片数据 | 全量数据统计、数据迁移 |
| 特殊路由需求 | 需要强制路由到特定节点 | 测试环境指定节点、读写分离 |
| 多表关联查询 | 多表分片键不同，需要 Hint 指定 | 跨分片的关联查询 |

## 6.6 分片策略选择建议

在实际项目中，选择合适的分片策略是成功实施分库分表的关键。以下是分片策略选择的详细建议。

### 6.6.1 策略选择决策树

```
选择分片策略
    │
    ├── 是否需要强制路由？
    │       ├── 是 → 使用 Hint 策略
    │       └── 否 → 继续判断
    │
    ├── 分片键数量？
    │       ├── 单一分片键 → 继续判断
    │       └── 多个分片键 → 使用复合策略
    │
    ├── 是否是简单取模？
    │       ├── 是 → Inline 策略（快速配置）
    │       └── 否 → 使用标准策略（自定义算法）
    │
    └── 是否需要优化范围查询？
            ├── 是 → 标准策略 + 范围算法
            └── 否 → 任意适用策略
```

### 6.6.2 各策略对比表

| 策略 | 配置复杂度 | 灵活性 | 性能 | 适用场景 |
|------|-----------|--------|------|---------|
| Inline | 低 | 低 | 高 | 简单取模、分片键固定 |
| 标准 | 中 | 高 | 高 | 精确路由、需要范围优化 |
| 复合 | 中 | 高 | 中 | 多分片键、复杂业务 |
| Hint | 低 | 极高 | 中 | 强制路由、特殊场景 |

### 6.6.3 场景化推荐

**场景一：用户中心（按用户ID分片）**

特点：
- 查询主要以用户ID为主
- 分片键明确为用户ID
- 业务逻辑简单

推荐策略：**Inline 策略**

```yaml
tables:
  t_user:
    actualDataNodes: ds_${0..3}.t_user_${0..15}
    database-strategy:
      inline:
        sharding-column: user_id
        algorithm-expression: ds_${user_id % 4}
    tableStrategy:
      inline:
        sharding-column: user_id
        algorithm-expression: t_user_${user_id % 16}
```

**场景二：订单系统（按订单ID分片，支持时间范围查询）**

特点：
- 主键查询为主
- 需要支持按时间范围查询订单
- 查询条件复杂

推荐策略：**标准分片策略 + 范围算法**

```java
// 自定义分片算法
public class OrderDatabaseShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        long orderId = shardingValue.getValue();
        return "ds_" + (orderId % 4);
    }
}

public class OrderRangeShardingAlgorithm implements RangeShardingAlgorithm<Long> {
    @Override
    public Collection<String> doSharding(RangeShardingValue<Long> shardingValue) {
        // 返回查询范围内所有可能的数据源
        Long lower = shardingValue.getValueRange().lowerEndpoint();
        Long upper = shardingValue.getValueRange().upperEndpoint();
        
        Set<String> result = new HashSet<>();
        for (long i = lower; i <= upper; i++) {
            result.add("ds_" + (i % 4));
        }
        return result;
    }
}
```

**场景三：多租户系统（按租户ID + 用户ID分片）**

特点：
- 需要同时按租户和用户进行分片
- 查询条件包含多个分片键
- 业务逻辑复杂

推荐策略：**复合分片策略**

```java
public class TenantUserComplexShardingAlgorithm implements ComplexKeysShardingAlgorithm<Long> {
    @Override
    public Collection<String> doSharding(ComplexShardingValue<Long> shardingValue) {
        Long tenantId = (Long) shardingValue.getValueMap().get("tenant_id");
        Long userId = (Long) shardingValue.getValueMap().get("user_id");
        
        // 根据租户确定库，根据用户确定表
        int dbIndex = tenantId % 4;
        int tableIndex = userId % 16;
        
        return Collections.singletonList("ds_" + dbIndex + ".t_user_" + tableIndex);
    }
}
```

**场景四：数据统计（跨分片聚合）**

特点：
- 需要汇总多个分片的数据
- 分片键不在查询条件中
- 要求全量数据

推荐策略：**Hint 策略**

```java
try (HintManager hintManager = HintManager.getInstance()) {
    // 强制路由到所有数据源
    hintManager.setDatabaseShardingValueForAllNodes("id");
    
    // 执行汇总查询
    String sql = "SELECT SUM(amount) FROM t_order WHERE create_time > ?";
    // 需要在应用层合并结果
}
```

### 6.6.4 策略迁移

如果在项目进行中需要更改分片策略，需要注意：

1. **数据迁移**：更改分片策略可能导致数据需要重新分布
2. **停机窗口**：可能需要停机进行数据迁移
3. **兼容性**：新旧策略需要一段时间并行运行
4. **回滚计划**：制定详细的回滚计划以应对迁移失败

## 6.7 分片键选取原则

分片键（Sharding Key）的选择是分库分表设计中最重要的决策之一。合理的分片键选择能够提高查询效率，避免跨库查询，提升系统整体性能。

### 6.7.1 分片键选取原则

**1. 高度离散原则**

选择具有高区分度的字段作为分片键，确保数据均匀分布。

```
✓ 好的选择：user_id, order_id, transaction_id（高基数、离散度高）
✗ 差的选择：status, type, gender（低基数、离散度低）
```

**2. 查询匹配原则**

分片键应该是高频查询条件中的字段，确保查询能够定位到单一分片。

```
✓ 好的选择：WHERE user_id = ?
✗ 差的选择：WHERE create_time LIKE '2023%'（无法定位分片）
```

**3. 业务相关原则**

选择与业务紧密相关的字段作为分片键，通常是核心实体的主键或外键。

```
✓ 好的选择：订单表用 order_id，用户表用 user_id
✗ 差的选择：随意选择非业务相关字段
```

**4. 避免跨库关联原则**

分片键应考虑是否会频繁进行跨分片关联操作。

### 6.7.2 常用分片键选择方案

**方案一：主键ID分片**

```yaml
tables:
  t_order:
    actualDataNodes: ds_${order_id % 4}.t_order_${order_id % 16}
    database-strategy:
      inline:
        sharding-column: order_id
        algorithm-expression: ds_${order_id % 4}
```

适用场景：
- 查询以主键为主
- 历史数据不再更新
- 单表数据量巨大

**方案二：业务ID分片**

```yaml
tables:
  t_order:
    actualDataNodes: ds_${user_id % 4}.t_order_${user_id % 16}
    database-strategy:
      inline:
        sharding-column: user_id
        algorithm-expression: ds_${user_id % 4}
```

适用场景：
- 查询以用户ID为主
- 需要按用户维度查询订单
- 用户间数据相对独立

**方案三：时间分片**

```yaml
tables:
  t_order:
    actualDataNodes: ds_${create_time?string('yyyy')}.t_order_${create_time?string('yyyyMM')}
    tableStrategy:
      inline:
        sharding-column: create_time
        algorithm-expression: t_order_${create_time?string('yyyyMM')}
```

适用场景：
- 时效性数据查询（如报表、日志）
- 数据有明显的生命周期
- 需要定期归档或清理

### 6.7.3 分片键选取失败案例分析

**失败案例一：按状态分片**

```yaml
# 错误示例
database-strategy:
  inline:
    sharding-column: status
    algorithm-expression: ds_${status.hashCode() % 4}
```

问题：
- status 字段值有限（通常只有几个值：待支付、已支付、已取消等）
- 数据无法均匀分布，某些分片数据量巨大
- 查询性能瓶颈

**失败案例二：按非查询字段分片**

```yaml
# 错误示例
database-strategy:
  inline:
    sharding-column: id
    algorithm-expression: ds_${id % 4}
```

问题：
- 业务查询主要以 username 查询
- 导致全路由查询，性能极差

### 6.7.4 分片键设计建议

**核心表分片键设计**

| 表类型 | 推荐分片键 | 理由 |
|--------|-----------|------|
| 用户表 | user_id | 查询以用户为中心 |
| 订单表 | user_id 或 order_id | 两种查询场景都需要考虑 |
| 商品表 | category_id 或 goods_id | 根据主查询场景选择 |
| 交易表 | transaction_id | 查询以交易为主 |

**复合分片键设计**

当单一分片键无法满足需求时，可以考虑复合分片键：

```yaml
database-strategy:
  complex:
    sharding-columns: tenant_id,user_id
    algorithm-class-name: com.example.TenantUserShardingAlgorithm
```

复合分片键使用原则：
- 复合分片键中的字段顺序很重要
- 查询条件中应包含复合分片键的前缀字段
- 避免使用过多的分片键，通常不超过3个

### 6.7.5 分片键与查询优化

**单表查询优化**

```
✓ 支持：SELECT * FROM t_order WHERE order_id = 12345
✓ 支持：SELECT * FROM t_order WHERE user_id = 100 AND order_id = 12345
✗ 不支持：SELECT * FROM t_order WHERE order_id IN (1,2,3,4)
```

**范围查询优化**

```
✓ 支持：SELECT * FROM t_order WHERE user_id = 100 AND create_time BETWEEN '2023-01-01' AND '2023-12-31'
✗ 不支持：SELECT * FROM t_order WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'（无 user_id 条件）
```

### 6.8.3 分片算法属性配置

自定义分片算法可以通过 Properties 传递参数：

```yaml

    database-strategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: com.example.OrderShardingAlgorithm

          shard.size: 4
          strategy.type: hash
```

**算法中接收属性：**

```java
public class OrderShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    
    private int shardSize;
    private String strategyType;
    
    @Override
    public void init(Properties props) {
        this.shardSize = Integer.parseInt(props.getProperty("shard.size", "4"));
        this.strategyType = props.getProperty("strategy.type", "mod");
    }
    
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        long orderId = shardingValue.getValue();
        
        if ("hash".equals(strategyType)) {
            return "ds_" + (Math.abs(orderId.hashCode()) % shardSize);
        } else {
            return "ds_" + (orderId % shardSize);
        }
    }
}
```

## 6.9 分片策略组合使用

在实际业务场景中，往往需要同时使用多种分片策略来满足不同的业务需求。ShardingSphere-JDBC 支持在数据库层面和表层面分别配置不同的分片策略。

### 6.9.1 数据库级别与表级别策略组合

**配置示例：不同表使用不同策略**

```yaml
dataSourceNames:
  - ds_0
  - ds_1
  - ds_2
  - ds_3

# 默认数据库策略
defaultDatabaseStrategy:
  standard:
    sharding-column: user_id
    precise-algorithm-class-name: com.example.UserDbShardingAlgorithm

tables:
  # 订单表：按 user_id 分库，按 order_id 分表
  t_order:
    actualDataNodes: ds_${0..3}.t_order_${0..15}
    database-strategy:
      standard:
        sharding-column: user_id
        precise-algorithm-class-name: com.example.UserDbShardingAlgorithm
    table-strategy:
      standard:
        sharding-column: order_id
        precise-algorithm-class-name: com.example.OrderTableShardingAlgorithm
  
  # 商品表：按 category_id 分库
  t_goods:
    actualDataNodes: ds_${0..3}.t_goods
    database-strategy:
      standard:
        sharding-column: category_id
        precise-algorithm-class-name: com.example.CategoryDbShardingAlgorithm
  
  # 统计表：使用默认策略
  t_stats:
    actualDataNodes: ds_${0..3}.t_stats
```

### 6.9.2 分库策略与分表策略组合

### 6.9.4 策略优先级

在分片策略执行过程中，按以下优先级进行路由：

```
1. Hint 强制路由（最高优先级）
   └── 通过 HintManager 设置的分片值直接路由

2. 表级别分片策略
   └── 查询的表有独立的分片策略

3. 数据库级别分片策略
   └── 没有表级别策略时，使用默认数据库策略

4. 全路由（最低优先级）
   └── 无法确定分片键时，广播到所有节点
```

## 6.10 最佳实践

### 6.10.1 分片策略设计最佳实践

**1. 分片键设计原则**

```
最佳实践 checklist:
□ 分片键具有高度离散性
□ 分片键是高频查询条件
□ 避免大范围查询
□ 考虑数据倾斜问题
□ 预留扩展空间
```

**2. 分片数量设计原则**

```
分片数量计算公式：

分片数 = 数据总量 / 单表可承载数据量

示例：
- 数据总量：1亿条
- 单表承载：100万条
- 分片数 = 100000000 / 1000000 = 100

建议：
- 每个分片数据量控制在 50-100 万
- 分片数取 2 的幂次方（如 64、128）
- 考虑未来 3 年的数据增长
```

**3. 分片算法设计原则**

```
推荐的分片算法实现模式：

public class OrderShardingAlgorithm implements PreciseShardingAlgorithm<Long> {
    
    private int dbCount;
    private int tableCount;
    
    @Override
    public void init(Properties props) {
        // 从配置中读取分片数
        this.dbCount = Integer.parseInt(props.getProperty("dbCount", "4"));
        this.tableCount = Integer.parseInt(props.getProperty("tableCount", "16"));
    }
    
    @Override
    public String doSharding(PreciseShardingValue<Long> shardingValue) {
        Long id = shardingValue.getValue();
        
        // 计算数据源
        long dbIndex = id % dbCount;
        
        // 计算表
        long tableIndex = (id / dbCount) % tableCount;
        
        return String.format("ds_%d.t_order_%d", dbIndex, tableIndex);
    }
}
```

### 6.10.3 性能优化最佳实践

**1. 避免全路由**

```
✗ 错误示例：分片键不在 WHERE 条件中
SELECT * FROM t_order WHERE create_time > '2023-01-01'
原因：无法确定分片键值，需要广播到所有分片

✓ 正确示例：分片键在 WHERE 条件中
SELECT * FROM t_order WHERE user_id = 123 AND create_time > '2023-01-01'
原因：可以定位到具体的分片
```

**2. 合理使用分片键**

```
✓ 支持精准路由的查询：
WHERE order_id = 12345                    # 精准到单表
WHERE user_id = 123                       # 精准到单库多表
WHERE user_id = 123 AND order_id = 456    # 精准到单表

✗ 不支持精准路由的查询：
WHERE create_time BETWEEN '2023-01-01' AND '2023-12-31'  # 跨分片
WHERE status = 'PAID'                    # 无分片键
```

**3. 使用 Hint 优化特定场景**

```java
// 批量查询优化：使用 Hint 减少路由计算
public List<Order> batchQueryOrders(List<Long> orderIds) {
    // 按分片键分组
    Map<Long, List<Long>> groupedIds = orderIds.stream()
        .collect(Collectors.groupingBy(id -> id % 4));
    
    List<Order> result = new ArrayList<>();
    
    for (Map.Entry<Long, List<Long>> entry : groupedIds.entrySet()) {
        try (HintManager hintManager = HintManager.getInstance()) {
            hintManager.setDatabaseShardingValue("user_id", entry.getKey());
            
            String sql = "SELECT * FROM t_order WHERE order_id IN " + entry.getValue();
            result.addAll(jdbcTemplate.query(sql, orderMapper));
        }
    }
    
    return result;
}
```

### 6.10.6 常见问题与解决方案

**问题一：数据倾斜**

```
症状：部分分片数据量远超其他分片
原因：分片键分布不均匀

解决方案：
1. 重新选择分片键
2. 使用哈希分片代替取模分片
3. 调整分片算法
```

**问题二：跨分片查询慢**

```
症状：跨分片查询响应时间长
原因：需要合并多个分片的结果

解决方案：
1. 使用 Hint 强制路由减少分片数
2. 优化合并算法
3. 考虑使用读写分离
4. 使用本地多表关联代替跨库关联
```

**问题三：分片策略变更困难**

```
症状：需要更改分片策略但数据迁移风险大
原因：历史数据与新策略不兼容

解决方案：
1. 采用双写双读策略
2. 使用数据同步工具
3. 制定详细的数据迁移计划
4. 保留回滚方案
```
