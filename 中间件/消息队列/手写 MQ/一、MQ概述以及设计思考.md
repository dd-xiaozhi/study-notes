# 概述

什么是 MQ（Message Quene），MQ 本质上就是一个队列，用于程序应用之间进行通信的中间件，它可以实现应用的的解耦、异步通信、流量削峰填谷、事务消息等功能。常见的 mq 有 RabbitMQ、RocketMQ、Kafka、ActiveMQ（社区活跃度不高）

**使用场景**：

- 应用解耦：比如用户下单之后系统需要发送通知给客户，此时如果我们使用硬编码的方式每增加一种通知方式就需要在代码中新增不同的通知逻辑，我们可以使用 MQ 来做中转站，系统下单之后将消息发送到 MQ，不同的方式可以交给不同的消费者来订阅处理，这样每增加一个我们只需要增加一个对应的消费者即可
- 异步处理：对于一些实时性要求不高的系统我们可以将消息放入到 MQ 中，根据消费端的处理能力来处理这些数据，这样可以保证系统接受更多的请求
- 流量削峰：在高并发场景下，会有大量的用户请求进来，服务器可能会被打垮，所以我们会采用服务降级或将请求放入队列中排队，应用服务根据自身的硬件能力来对请求做处理，如果我们发现请求量非常大我们的消费端处理不过来，我们还可以新增多个消费者来对请求做处理
- 解决分布式事务：在 seata 出来之前，解决分布式事务一般都是使用消息队列来处理，它利用半消息的特性来保障分布式事务。（这里我们先了解，后面会讲解具体的执行步骤）

**缺点**：

- 系统可用性降低：在加入 MQ 之前我们不需要考虑 MQ 消息丢失或者宕机，引入之后我们就需要考虑这些情况
- 系统的复杂性提高：加入 MQ 后需要考虑 MQ 的消息是否有被重复消费，消息是否按照设定好的顺序消费，消息是否有丢失等情况
- 数据一致性，使用 MQ 会导致传统的数据库事务无法保障数据一致性，比如 A 服务提交了事务，然后将消息发送到 MQ，B服务消费 MQ 的消息后处理失败了，此时只有 A 服务的事务已经提交了，无法感知下游的服务是否成功。虽然我们可以使用 MQ 的分布式事务消息来解决这个问题，但是也提高了系统的复杂性。
- 运维和资源管理负担：运维和监控成本高，需要专门的人员和工具来监控 MQ 的系统指标。

### 三款mq的差异以及使用场景

| 特性                     | RabbitMQ                                           | RocketMQ                                                     | Kafka                                                        |
| :----------------------- | :------------------------------------------------- | :----------------------------------------------------------- | :----------------------------------------------------------- |
| 单机吞吐量               | 万级，比 RocketMQ、Kafka 低一个数量级              | 10 万级，支撑高吞吐                                          | 10 万级，高吞吐，一般配合大数据类的系统来进行实时数据计算、日志采集等场景 |
| topic 数量对吞吐量的影响 |                                                    | topic 可以达到几百/几千的级别，吞吐量会有较小幅度的下降，这是 RocketMQ 的一大优势，在同等机器下，可以支撑大量的 topic | topic 从几十到几百个时候，吞吐量会大幅度下降，在同等机器下，Kafka 尽量保证 topic 数量不要过多，如果要支撑大规模的 topic，需要增加更多的机器资源 |
| 时效性                   | 微秒级，这是 RabbitMQ 的一大特点，延迟最低         | ms 级                                                        | 延迟在 ms 级以内                                             |
| 可用性                   | 高，基于主从架构实现高可用                         | 非常高，分布式架构                                           | 非常高，分布式，一个数据多个副本，少数机器宕机，不会丢失数据，不会导致不可用 |
| 消息可靠性               | 基本不丢                                           | 经过参数优化配置，可以做到 0 丢失                            | 同 RocketMQ                                                  |
| 功能支持                 | 基于 erlang 开发，并发能力很强，性能极好，延时很低 | MQ 功能较为完善，支持分布式部署，扩展性好                    | 功能较为简单，主要支持简单的 MQ 功能，在大数据领域的[实时计算](https://cloud.tencent.com/product/oceanus?from_column=20421&from=20421)以及日志采集被大规模使用 |
