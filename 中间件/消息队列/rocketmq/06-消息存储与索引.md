# 第6章-消息存储与索引

## 6.1 消息存储结构

RocketMQ 的消息存储采用混合型存储模式，所有消息都集中存储在 CommitLog 中，而消费队列 ConsumeQueue 作为消息的索引存在。这种设计实现了消息存储与消息消费的完全解耦。

### CommitLog

CommitLog 是 RocketMQ 消息存储的主体，所有消息内容都顺序写入该文件。

**源码位置**：`store/src/main/java/org/apache/rocketmq/store/CommitLog.java`

**关键特性**：
- 文件名格式：`00000000000000000000`、`00000000001073741824`（起始物理偏移量）
- 默认文件大小：1GB（`mappedFileSize` 配置）
- 消息存储顺序：按消息到达顺序追加到文件末尾
- 消息体结构：包含消息头、消息体、消息属性等完整信息

```java
// CommitLog 消息写入核心逻辑
public AppendMessageResult appendMessage(MessageExtBrokerInner msg, PutMessageContext context) {
    // 计算写入位置
    long wroteOffset = (long) queueOffsetNums;
    // 获取当前 MappedFile
    MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();
    // 追加写入
    return mappedFile.appendMessage(msg, this.appendMessageCallback);
}
```

### ConsumeQueue

ConsumeQueue 是消息消费的逻辑队列，每个 Topic 下的每个 MessageQueue 都有对应的 ConsumeQueue。

**源码位置**：`store/src/main/java/org/apache/rocketmq/store/ConsumeQueue.java`

**存储结构**：
- 目录路径：`$HOME/store/consumequeue/{topic}/{queueId}/`
- 文件名格式：与 CommitLog 类似，采用起始偏移量命名
- 记录格式：20 字节固定长度（commitLog 物理偏移量 8 字节 + 消息大小 4 字节 + 消息 tag hashcode 8 字节）

```java
// ConsumeQueue 单条记录结构
public class ConsumeQueue {
    // 8 字节：commitLog 物理偏移量
    // 4 字节：消息长度
    // 8 字节：消息 Tag HashCode
    // -------------------
    // 总计：20 字节/条
}
```


## 6.2 索引机制

RocketMQ 提供了基于时间戳和消息 Key 的消息索引功能，用于支持消息按条件查询。

### IndexFile 索引文件

**源码位置**：`store/src/main/java/org/apache/rocketmq/store/index/IndexFile.java`

**文件结构**：
| 区域 | 说明 | 大小 |
|------|------|------|
| 文件头 | 索引文件元数据 | 40 字节 |
| Hash 槽 | Hash 槽数组，每个槽 4 字节 | 500 万 × 4 字节 ≈ 20MB |
| 索引数据 | 索引记录数组，每条 20 字节 | 500 万 × 20 字节 ≈ 100MB |

**索引头结构**：
```java
class IndexHeader {
    long beginTimestamp;          // 首条消息时间戳
    long endTimestamp;            // 最后一条消息时间戳
    long beginPhyOffset;          // 首条消息物理偏移量
    long endPhyOffset;            // 最后一条消息物理偏移量
    int hashSlotCount;            // Hash 槽已使用数量
    int indexCount;               // 索引条目数量
}
```

**索引条目结构**（20 字节）：
```
+----------+----------+----------+----------+
| 4 字节   | 8 字节   | 4 字节   | 4 字节   |
| msgKey   | phyOffset| timeDiff | next    |
| hashcode | 物理偏移 | 时间差   | 下一条   |
+----------+----------+----------+----------+
```

### 消息查找流程

**按 MessageKey 查找**：

```
1. 计算 key 的 hashcode
2. 通过 hashcode % hashSlotCount 定位 Hash 槽
3. 读取 Hash 槽中的索引位置
4. 沿着索引链表遍历，逐一比较 key
5. 匹配成功则根据 phyOffset 读取 CommitLog 获取完整消息
6. 链表结束或匹配失败则返回不存在
```

**按时间戳查找**：
1. 在 IndexHeader 中找到目标时间戳所在的物理偏移量范围
2. 根据时间差定位可能的索引条目
3. 通过二分查找快速定位

### 索引结构图解

```
IndexFile 物理结构：

+----------------------------------+
|          IndexHeader (40B)       |
+----------------------------------+
|  HashSlot[0]  │ 4B │              |
|  HashSlot[1]  │ 4B │              |
|  HashSlot[2]  │ 4B │              |
|     ...      │....│              |
|  HashSlot[N]  │ 4B │              |
+----------------------------------+
|  IndexNode[0]│20B │              |
|  IndexNode[1]│20B │  索引数据区   |
|  IndexNode[2]│20B │              |
|     ...      │....│              |
|  IndexNode[N]│20B │              |
+----------------------------------+

Hash 槽与索引节点链表关系：

HashSlot[0] ──→ IndexNode[A] ──→ IndexNode[B] ──→ null
HashSlot[1] ──→ null
HashSlot[2] ──→ IndexNode[C] ──→ IndexNode[D] ──→ null
...
```

## 6.3 磁盘存储优化

RocketMQ 在消息存储性能优化方面做了大量工作，核心是通过内存映射和顺序写入最大化磁盘 IO 效率。

### 内存映射机制（MappedFile）

**源码位置**：`store/src/main/java/org/apache/rocketmq/store/MappedFile.java`

**核心原理**：利用 Java NIO 的 MappedByteBuffer，将文件直接映射到进程的虚拟内存地址空间，避免传统 read/write 的内核缓冲区拷贝。

```
传统 IO 流程：                          内存映射流程：
+-------------+                        +-------------+
|  User Space │                        |  User Space │
+-------------+                        +-------------+
      │                                     │
      ↓                                     ↓
+-------------+                        +-------------+
| Kernel Buf  │  ← COPY                |   Mapped    │
+-------------+                        |   Buffer    │
      │                                +-------------+
      ↓                                     ↑
+-------------+                        +-------------+
| Disk Driver │                        | Disk Driver │
+-------------+                        +-------------+
```

**关键实现**：
```java
// 文件映射创建
RandomAccessFile raf = new RandomAccessFile(file, "rw");
FileChannel channel = raf.getChannel();
MappedByteBuffer mappedByteBuffer = channel.map(
    MapMode.READ_WRITE,  // 读写模式
    0,                    // 起始位置
    fileSize              // 映射大小
);
```

**预热机制**：RocketMQ 在 Broker 启动时会进行 MappedFile 预热，将文件内容预先加载到物理内存，避免运行时缺页中断。

### 顺序写入原理

CommitLog 采用顺序追加写入模式，这种设计带来以下优势：

1. **顺序 IO 效率高**：磁盘磁头无需频繁寻道，顺序写入速度接近内存速度
2. **写入放大最小化**：操作系统 page cache 合并写请求，合并磁盘物理写入
3. **写入吞吐量大**：充分利用磁盘带宽

```
写入流程：

CommitLog 文件 1GB                    内存 (Page Cache)
[████████████████████] ←────────── [||||||||||||||||||]
 已写入部分    待写入位置              积累的消息

随着消息不断到达，Page Cache 积累到一定量后，一次性刷盘到磁盘。
```

### 刷盘策略

RocketMQ 支持两种刷盘策略，通过 `flushDiskType` 配置。

**同步刷盘（SYNC_FLUSH）**：

源码位置：`store/src/main/java/org/apache/rocketmq/store/CommitLog.java`

```java
// 同步刷盘等待
public void flush() {
    MappedFile mappedFile = this.mappedFileQueue.getLastMappedFile();
    mappedFile.hold();
    // 强制刷到磁盘
    mappedByteBuffer.force();
    // 等待刷盘完成通知
}
```

特点：
- 消息写入后立即刷盘，安全性高
- 吞吐量较低，适合对可靠性要求极高的场景
- 流程：`消息写入 MappedByteBuffer → force() → 等待返回 → 返回成功`

**异步刷盘（ASYNC_FLUSH）**：

```java
// 异步刷盘基于定时任务或阈值触发
public class CommitLog {
    // 刷盘服务
    private final FlushCommitLogService flushCommitLogService;

    // 定时刷盘：默认 500ms 检查一次
    // 阈值刷盘：达到指定条数或大小触发
}
```

特点：
- 吞吐量高，适合高并发场景
- 存在短暂数据丢失窗口（最多一个刷盘周期）
- Broker 默认配置

**刷盘策略对比**：

| 特性 | 同步刷盘 | 异步刷盘 |
|------|----------|----------|
| 可靠性 | 极高 | 高 |
| 吞吐量 | 低 | 高 |
| 延迟 | 高 | 低 |
| 适用场景 | 金融交易 | 普通消息 |

### 过期文件清理

**源码位置**：`store/src/main/java/org/apache/rocketmq/store/StoreStatsService.java`

RocketMQ 采用定期清理策略处理过期文件，避免磁盘空间耗尽。

**清理机制**：

```java
// 文件保留时间，默认 72 小时（3 天）
private int fileReservedTime = 72;

// 清理任务执行
public void cleanExpiredChannel() {
    // 遍历 commitlog 目录

    // 删除超过 fileReservedTime 的文件
}
```

**清理策略**：

1. **基于时间**：文件保留时长超过 `fileReservedTime`（默认 72 小时）则删除
2. **基于空间**：磁盘使用率超过 `diskMaxSpaceWarningGuardRatio` 时触发强制清理
3. **基于配置**：
   - `deleteWhen`：清理执行时间点，默认凌晨 4 点
   - `deleteFileInterval`：删除文件间隔，默认 100ms

**注意事项**：

- 异步刷盘场景下，未刷盘的消息可能随文件一起删除
- 清理前需确认消息已正常消费且无引用
- 建议生产环境配置监控告警，防止磁盘空间不足

## 本章小结

本章介绍了 RocketMQ 的消息存储与索引核心机制：

1. **存储结构**：CommitLog 作为消息主体，ConsumeQueue 作为消费索引，实现存储与消费解耦
2. **索引机制**：IndexFile 支持按 MessageKey 和时间戳查询，通过 Hash 槽和链表实现高效定位
3. **性能优化**：内存映射减少 IO 拷贝，顺序写入提升吞吐，同步/异步刷盘平衡可靠性与性能

理解这些核心机制对于性能调优、故障排查和深度应用至关重要。
