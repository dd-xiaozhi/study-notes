# 第8章-监控与性能调优

## 8.1 监控指标

### 8.1.1 监控维度：TPS、延迟、堆积

在生产环境中，监控是保障 RocketMQ 稳定运行的关键。以下三个维度是日常监控的核心：

**TPS（Transaction Per Second）**
- Producer TPS：每秒发送消息数量，反映消息生产速率
- Consumer TPS：每秒消费消息数量，反映消息消费速率
- 正常情况下 Producer TPS 应略高于 Consumer TPS（留有缓冲空间）
- 如果 Producer TPS 持续高于 Consumer TPS，说明消费能力不足，需要扩容或优化消费逻辑

**延迟（Latency）**
- 发送延迟：从消息发送到确认写入的时间
- 消费延迟：从消息投递给消费者到消费完成的时间
- 延迟突增通常是系统负载过高或出现阻塞的先兆
- 建议设置延迟阈值告警，例如：发送延迟 > 500ms 触发告警

**消息堆积（Message Backlog）**
- 指已发送但尚未被消费的消息总数
- 堆积过大会导致消息消费延迟增加，严重时可能影响业务
- 常见原因：消费者宕机、消费能力不足、消费者异常导致重试频繁
- 建议：堆积量超过 10 万条时触发告警

### 8.1.2 Prometheus + Grafana 集成

RocketMQ 提供了完善的 Prometheus 监控指标导出能力。

**启用监控指标**

在 broker.conf 中添加以下配置：

```properties
# 开启 metrics 指标暴露
enableMetricsRateLimiter=true
metricsProducerThreadPoolCapacity=10
```

**Prometheus 配置示例**

```yaml
# prometheus.yml
scrape_configs:
  - job_name: 'rocketmq'
    static_configs:
      - targets: ['localhost:9090']
    metrics_path: '/metrics'
    params:
      cluster: ['DefaultCluster']
```

**Grafana 仪表盘推荐面板**

| 面板名称 | 监控指标 | 说明 |
|---------|---------|------|
| Producer TPS | rocketmq_producer_tps | 各 Producer 发送速率 |
| Consumer TPS | rocketmq_consumer_tps | 各 Consumer 消费速率 |
| 发送延迟 P99 | rocketmq_send_latency_p99 | 99 分位发送延迟 |
| 消息堆积 | rocketmq_message_backlog | 各 Queue 堆积量 |
| 消费线程池活跃度 | rocketmq_consumer_thread_pool_active | 消费线程繁忙程度 |

### 8.1.3 核心监控指标说明

**Broker 级别指标**

| 指标名称 | 含义 | 正常范围 | 异常告警阈值 |
|---------|------|---------|-------------|
| rocketmq_broker_tps | Broker 总处理 TPS | 根据业务量浮动 | 持续 > 5 万需扩容 |
| rocketmq_send_success_rate | 发送成功率 | > 99.9% | < 99% 需排查 |
| rocketmq_get_latency_99th | 99 分位拉取延迟 | < 100ms | > 500ms 需优化 |
| rocketmq_pull_thread_pool_queue_size | 拉取线程池队列 | < 1000 | > 5000 需关注 |
| rocketmq_dispatch_behind_bytes | 转发落后字节数 | 接近 0 | 持续增长需处理 |

**Consumer 级别指标**

| 指标名称 | 含义 | 正常范围 | 异常告警阈值 |
|---------|------|---------|-------------|
| rocketmq_consumer_tps | 消费 TPS | 稳定 | 突降需排查 |
| rocketmq_consumer_failed_tps | 消费失败 TPS | 接近 0 | 持续 > 100 需处理 |
| rocketmq_consumer_thread_pool_active | 线程活跃数 | < 线程池容量 | 等于容量时可能瓶颈 |
| rocketmq_consumer_process_time | 消息处理耗时 | < 50ms | > 200ms 需优化 |

## 8.2 性能瓶颈分析

### 8.2.1 四大资源瓶颈排查

**CPU 瓶颈**

症状表现：
- CPU 使用率持续 > 80%
- 系统负载高，但 I/O 等待不高
- 消息发送/消费延迟增加

排查命令：
```bash
# 查看 CPU 使用情况
top -Hp <java_pid>

# 查看 RocketMQ 各线程 CPU 消耗
jstack <java_pid> | grep "tid" | head -50
```

常见原因：
- 消息序列化/反序列化开销大
- 正则表达式匹配消耗（如消息过滤）
- 大量字符串操作

**内存瓶颈**

症状表现：
- GC 频繁或 GC 时间过长
- 堆内存使用率持续 > 80%
- 出现 OOM 异常

排查命令：
```bash
# 查看 GC 情况
jstat -gc <java_pid> 1000

# 查看堆内存分布
jmap -heap <java_pid>
```

常见原因：
- 消息体过大（建议 < 64KB）
- 消费者处理速度慢导致消息积压在内存
- 堆内存设置不合理（建议 Broker 4G-8G）

**磁盘瓶颈**

症状表现：
- 磁盘 I/O 使用率 > 70%
- 写入延迟增加
- 消息发送变慢但 CPU 不高

排查命令：
```bash
# 查看磁盘 I/O
iostat -x 1

# 查看磁盘使用
df -h
```

常见原因：
- 同步刷盘导致 I/O 阻塞
- 磁盘 I/O 能力不足（建议 SSD）
- 存储文件过多未清理

**网络瓶颈**

症状表现：
- 网络流量接近带宽上限
- 消息发送超时
- 跨机房延迟高

排查命令：
```bash
# 查看网络流量
sar -n DEV 1

# 查看连接数
netstat -an | grep ESTABLISHED | wc -l
```

常见原因：
- 大消息发送（建议消息体 < 1MB）
- 连接数过多（注意连接池复用）
- 网络带宽不足

### 8.2.2 常见瓶颈场景

**场景一：消费者处理能力不足导致堆积**

```
问题：消息快速堆积，消费 TPS 提不上去
排查：消费线程池是否满载？业务处理是否有阻塞IO？
解决：
  1. 增加消费线程数（但别超过 CPU 核心数太多）
  2. 优化业务处理逻辑，减少同步阻塞
  3. 将耗时操作异步化
```

**场景二：发送延迟突增**

```
问题：原本正常的发送延迟突然增加到秒级
排查：Broker 是否在 Full GC？磁盘 I/O 是否飙高？
解决：
  1. 检查 GC 日志，优化堆内存配置
  2. 如果是同步刷盘，考虑改为异步刷盘
  3. 检查是否有大消息集中到达
```

**场景三：多消费者分组争抢**

```
问题：多个消费者分组竞争同一 Topic，导致部分分组饥饿
排查：各消费者分组的订阅关系是否正确？分配是否均衡？
解决：
  1. 确保订阅关系正确，避免不必要的竞争
  2. 调整消费者数量与分区数匹配
  3. 考虑拆分 Topic 实现负载分离
```

### 8.2.3 排查方法论

```
1. 确定现象：先明确是发送端问题还是消费端问题
2. 收集指标：查看 TPS、延迟、堆积三维度数据
3. 资源分析：逐个排查 CPU、内存、磁盘、网络
4. 缩小范围：通过日志和监控定位到具体组件
5. 验证假设：调整一个变量，观察是否改善
6. 根本解决：避免只处理表面症状
```

## 8.3 调优策略

### 8.3.1 Producer 调优：并发数、批量大小

**并发数调优**

```java
// DefaultMQProducer 配置
DefaultMQProducer producer = new DefaultMQProducer("my-producer-group");
producer.setProducerBeanClazz(ProducerImpl.class);

// 并发发送线程数（默认 5）
producer.setSendThreadCount(10);

// 消息队列数量（影响并发度）
producer.setDefaultTopicQueueNums(10);
```

调优建议：
- 低延迟场景：适当增加线程数（10-20），牺牲吞吐量换取低延迟
- 高吞吐场景：线程数 5-10，配合批量发送效果更佳
- 避免过度并发：线程数过多会导致上下文切换开销，反而降低性能

**批量大小调优**

```java
// 批量发送配置
producer.setBatchSize(1024);  // 批量大小
producer.setMaxMessageSize(1024 * 1024);  // 最大消息大小
```

关键参数：
- `batchSize`：批量内消息数量（默认 256），适合高吞吐场景
- `sendBatchTimeout`：批量发送超时（默认 10 秒）

实践经验：
- 批量发送可提升 3-5 倍吞吐，但会增加延迟
- 批量大小建议 100-1000 条，不宜过大
- 批量消息总大小建议 < 256KB

**其他 Producer 优化**

```java
// 异步发送回调（避免阻塞）
producer.send(message, new SendCallback() {
    @Override
    public void onSuccess(SendResult sendResult) {
        // 成功处理
    }

    @Override
    public void onException(Throwable e) {
        // 失败重试或记录
    }
});

// 消息压缩（减少网络传输）
producer.setCompressMsgBodyOverHowmuch(4096);  // > 4KB 启用压缩
```

### 8.3.2 Consumer 调优：消费线程数

**消费线程数配置**

```java
// DefaultMQPushConsumer 配置
DefaultMQPushConsumer consumer = new DefaultMQPushConsumer("my-consumer-group");

// 最小消费线程数（默认 20）
consumer.setConsumeThreadMin(20);

// 最大消费线程数（默认 64）
consumer.setConsumeThreadMax(64);

// 单线程处理消息数（默认 1）
consumer.setConsumeMessageBatchMaxSize(32);
```

调优原则：
```
CPU 密集型业务：线程数 ≈ CPU 核心数
IO 密集型业务：线程数可以 > CPU 核心数（通常 2-4 倍）
最佳实践：从小到大逐步调整，观察 CPU 和处理延迟
```

**推荐配置参考**

| 业务类型 | consumeThreadMin | consumeThreadMax | 备注 |
|---------|-----------------|-----------------|------|
| 轻量处理（日志记录） | 10 | 20 | 避免资源浪费 |
| 普通业务（库存、订单） | 20 | 32 | 平衡资源与吞吐 |
| 重量处理（AI 推理、大数据） | 32 | 64 | 注意内存和 CPU |
| IO 密集型（外部 API 调用） | 32 | 128 | 配合异步框架效果更佳 |

**消费模式影响**

```java
// 集群消费模式（默认，推荐）
consumer.setMessageModel(MessageModel.CLUSTERING);

// 广播消费模式（每个消费者都消费全量消息）
consumer.setMessageModel(MessageModel.BROADCASTING);
```

注意：广播消费模式下，消费能力取决于单个消费者，堆积会更快，需要更关注消费性能。

### 8.3.3 Broker 调优：刷盘策略、堆内存

**刷盘策略配置**

```properties
# broker.conf

# 异步刷盘（默认，推荐，吞吐量优先）
flushDiskType=ASYNC_FLUSH
# 同步刷盘（低延迟优先，但吞吐会下降）
# flushDiskType=SYNC_FLUSH

# 刷盘间隔（默认 500ms）
flushIntervalOfCommitLog=500

# 每次刷盘消息数（默认 1）
commitCommitLogLeastPages=4
```

**同步刷盘 vs 异步刷盘选择**

| 场景 | 刷盘模式 | 原因 |
|-----|---------|------|
| 普通业务场景 | 异步刷盘 | 吞吐量优先，允许少量消息丢失 |
| 金融支付场景 | 同步刷盘 | 数据一致性要求高，不允许丢失 |
| 日志收集场景 | 异步刷盘 | 允许少量丢失，追求高吞吐 |

**堆内存配置**

```properties
# bin/runbroker.sh

# 推荐堆内存配置（根据 Broker 角色调整）
# Master Broker: 8G-16G
JAVA_OPT="${JAVA_OPT} -Xms8g -Xmx8g -Xmn4g"

# Slave Broker: 4G-8G（承担读操作）
JAVA_OPT="${JAVA_OPT} -Xms4g -Xmx4g -Xmn2g"
```

**JVM 垃圾回收优化**

```properties
# 使用 G1 垃圾收集器（适合大内存）
JAVA_OPT="${JAVA_OPT} -XX:+UseG1GC"
JAVA_OPT="${JAVA_OPT} -XX:MaxGCPauseMillis=100"
JAVA_OPT="${JAVA_OPT} -XX:InitiatingHeapOccupancyPercent=70"

# 大内存分页优化
JAVA_OPT="${JAVA_OPT} -XX:+LargePageSizeInBytes=16m"

# GC 日志配置（生产环境必开）
JAVA_OPT="${JAVA_OPT} -Xlog:gc*:file=logs/gc.log:time,uptime:filecount=10,filesize=100m"
```

**Broker 其他关键参数**

```properties
# 存储路径配置（建议使用独立磁盘）
storePathRootDir=/data/rocketmq/store
storePathCommitLog=/data/rocketmq/store/commitlog

# 消息存储文件保留时间（默认 72 小时）
fileReservedTime=72

# 消息删除时间间隔（默认每 10 秒检查一次）
deleteWhen=04

# 堆外内存配置（用于零拷贝）
-XX:MaxDirectMemorySize=15g

# 网络线程数（默认 8）
sendServerThreadPoolNums=16
```

### 8.3.4 网络参数优化

**OS 内核参数优化**

```bash
# /etc/sysctl.conf

# 文件描述符限制（处理大量连接）
fs.file-max=655360
fs.nr_open=655360

# 网络缓冲区优化
net.core.rmem_max=16777216
net.core.wmem_max=16777216
net.ipv4.tcp_rmem=4096 87380 16777216
net.ipv4.tcp_wmem=4096 65536 16777216

# TCP 连接优化
net.tcp_max_syn_backlog=65536
net.core.netdev_max_backlog=65536

# TIME_WAIT 复用
net.ipv4.tcp_tw_reuse=1
net.ipv4.tcp_fin_timeout=30
```

**进程文件描述符限制**

```bash
# /etc/security/limits.conf

# 软限制
* soft nofile 655360

# 硬限制
* hard nofile 655360
```

**RocketMQ 网络相关配置**

```properties
# broker.conf

# Broker 对外服务端口
listenPort=10911

# HA 端口（主从同步）
haListenPort=10912
```

**客户端网络优化**


## 8.4 调优检查清单

### 上线前检查

```
[ ] Broker 堆内存是否根据角色合理配置（Master 8G+，Slave 4G+）
[ ] 刷盘策略是否匹配业务场景（异步/同步）
[ ] 消费线程数是否与业务处理能力匹配
[ ] 是否开启了 GC 日志和监控指标
[ ] OS 内核参数是否已优化（文件描述符、网络缓冲区）
```

### 日常巡检

```
[ ] TPS 和延迟是否在正常范围
[ ] 消息堆积是否在可控范围（< 10 万）
[ ] GC 频率和时间是否正常（Full GC < 1 次/小时）
[ ] 磁盘 I/O 使用率是否正常（< 70%）
[ ] 是否有异常告警未处理
```

### 性能问题处理流程

```
1. 查看监控：确认是发送端还是消费端问题
2. 查看日志：寻找错误和异常信息
3. 资源排查：CPU、内存、磁盘、网络逐一排查
4. 参数调优：根据瓶颈类型调整对应参数
5. 验证效果：观察指标是否改善
6. 记录归档：记录问题和解决方案，积累经验
```
