# Chapter 2: RocketMQ 核心概念与架构

## 2.1 核心概念

- **Topic**：消息主题，消息的一级分类，用于消息的逻辑管理。Producer 将消息发送到 Topic，Consumer 通过订阅 Topic 来消费消息。
- **Tag**：消息标签，消息的二级分类，用于在同一 Topic 下进行消息过滤。一个 Topic 可以包含多个 Tag，Tag 格式为 `TagA || TagB || TagC`。
- **Message**：消息主体，RocketMQ 的基本消息单元，包含以下关键属性：
  - `body`：消息体，存放实际业务数据
  - `keys`：消息索引键，用于消息检索和过滤
  - `flags`：业务标记
  - `tags`：消息标签
  - `waitStoreMsgOK`：是否等待消息存储完成
- **Queue**：队列，Topic 的物理分片。一个 Topic 可以配置多个 Queue，分布在不同的 Broker 上，实现消息的并行存储和处理。

## 2.2 架构组件

- **NameServer**：服务注册与发现中心，无状态节点，提供以下功能：
  - Broker 管理：接收 Broker 注册、心跳保活、路由信息管理
  - 客户端发现：Producer/Consumer 通过 NameServer 获取 Broker 路由信息
  - 集群管理：各 NameServer 之间无数据同步，通过部署多节点保证高可用

- **Broker**：消息存储和转发的核心组件，主要功能包括：
  - 消息存储：基于 CommitLog 文件顺序写入
  - 消息发送：高并发、低延迟的消息投递
  - 消息消费：支持推（Push）和拉（Pull）两种消费模式
  - 主从同步：支持主从架构，实现数据冗余
  - 负载均衡：多个 Consumer 之间的消息分发

- **Producer**：消息生产者，负责消息发送：
  - 普通生产者：同步发送消息
  - 顺序生产者：确保消息按发送顺序消费
  - 事务生产者：支持事务消息机制
  - 支持延迟消息、批量消息等高级特性

- **Consumer**：消息消费者，负责消息处理：
  - 推消费者（PushConsumer）：服务端推送消息，低延迟
  - 拉消费者（PullConsumer）：客户端主动拉取消息，更灵活
  - 集群消费：消息在 Consumer 集群中负载均衡
  - 广播消费：每条消息投递给所有 Consumer

## 2.3 消息存储机制

RocketMQ 的消息存储采用混合存储模式，核心结构如下：

- **CommitLog**：消息存储的核心文件
  - 所有消息顺序写入 CommitLog 文件
  - 文件默认大小为 1GB
  - 采用顺序写入，利用顺序 I/O 提升性能
  - 消息在 CommitLog 中的物理偏移量（physical offset）作为消息的唯一标识

- **ConsumeQueue**：消息消费队列（索引文件）
  - 逻辑队列，按 Topic 和 Queue 分组
  - 存储消息在 CommitLog 中的物理偏移量、消息大小、Tag Hash
  - 每个 ConsumeQueue 条目固定 20 字节
  - 设计目的是加速消息消费，避免读取 CommitLog

- **IndexFile**：消息索引文件（用于消息检索）
  - 基于时间戳建立的消息索引
  - 通过消息 Key 构建 Hash 索引
  - 支持根据 Key 或时间区间快速查找消息

- **内存映射机制（MappedByteBuffer）**：
  - 使用 NIO 的内存映射机制
  - 将磁盘文件映射到内存，减少数据复制
  - 提升大文件的读写性能
  - 结合 OS 的页缓存机制，优化 I/O 性能

- **消息过期与删除**：
  - 基于时间维度删除过期消息
  - 存储文件默认保留 3 天（可配置）
  - 定时清理过期文件

## 2.4 高可用架构设计

RocketMQ 通过以下机制保证系统的高可用性：

- **主从复制机制**：
  - Master Broker 支持配置多个 Slave Broker
  - 采用 `Dlegde` 模式实现异步复制或同步复制
  - 同步复制（SYNC_MASTER）：消息需要同步到 Slave 后才算发送成功，数据可靠性高
  - 异步复制（ASYNC_MASTER）：消息发送成功后异步复制到 Slave，延迟低
  - Slave 只读不写，负责提供消息消费能力

- **故障自动切换**：
  - NameServer 集群无状态部署，任一节点宕机不影响服务
  - Broker 通过 NameServer 心跳检测实现故障感知
  - 客户端自动切换：当 Master 不可用时，Producer 自动向 Slave 写入（配置 ASYNC_MASTER）
  - Consumer 自动切换到其他 Broker 的 Queue 进行消费
  - 消费进度（ConsumerOffset）持久化存储，避免消息丢失

- **负载均衡策略**：
  - Topic 的 Queue 均匀分布在多个 Broker 上
  - Producer 端负载均衡：基于 NameServer 路由信息轮询或随机选择 Broker
  - Consumer 端负载均衡：
    - 集群模式：Queue 数量平均分配给 Consumer 集群
    -Rebalance 机制：Consumer 数量变化时自动重新分配 Queue
  - 消息过滤：在 Broker 端基于 Tag 进行初步过滤，减少无效数据传输

- **跨机房部署支持**：
  - 支持多 NameServer 节点跨机房部署
  - Broker 主从可跨机房配置，保证机房级容灾
  - 消息延迟敏感业务可通过读写分离优化性能
