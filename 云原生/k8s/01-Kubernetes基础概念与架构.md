## 1. Kubernetes 的诞生背景

### 1.1 传统部署时代的挑战

在早期，企业应用主要部署在物理服务器上。那时候的应用部署方式面临诸多问题：

```
┌─────────────────────────────────────────────────────────────┐
│                    传统物理服务器部署                         │
├─────────────────────────────────────────────────────────────┤
│  服务器A: 应用1  │  服务器B: 应用2  │  服务器C: 应用3         │
│  CPU: 30%       │  CPU: 70%       │  CPU: 20%              │
│  内存: 40%      │  内存: 85%       │  内存: 30%             │
└─────────────────────────────────────────────────────────────┘

问题：
1. 资源分配不均 - 某些服务器资源紧张，另一些却闲置
2. 扩展困难 - 需要购买新硬件、配置环境、部署应用
3. 环境冲突 - 不同应用需要不同版本的依赖
4. 故障恢复慢 - 服务器宕机需要人工干预
```

### 1.2 虚拟化时代的到来

VMware、Hyper-V 等虚拟化技术带来了革命性的变化：

```
┌─────────────────────────────────────────────────────────────┐
│                    虚拟化部署                                 │
├─────────────────────────────────────────────────────────────┤
│  服务器（物理机）                                              │
│  ┌────────────┐ ┌────────────┐ ┌────────────┐              │
│  │   虚拟机1   │ │   虚拟机2   │ │   虚拟机3   │              │
│  │  应用1     │ │  应用2     │ │  应用3     │              │
│  │  独立系统   │ │  独立系统   │ │  独立系统   │              │
│  └────────────┘ └────────────┘ └────────────┘              │
│                                                              │
│  优势：资源隔离、独立扩展、环境独立                           │
│  问题：每个虚拟机都运行完整操作系统，资源开销大                │
└─────────────────────────────────────────────────────────────┘
```

### 1.3 容器技术的兴起

Docker 的出现让容器技术真正流行起来：

```bash
# Docker 的核心优势：轻量级虚拟化
# 容器 vs 虚拟机 的资源对比

容器特点：
- 共享宿主机操作系统内核
- 启动时间：秒级（虚拟机：分钟级）
- 资源开销：极小（虚拟机：GB级别）
- 镜像大小：MB级别（虚拟机：GB级别）
```

```
┌─────────────────────────────────────────────────────────────┐
│                    容器化部署                                │
├─────────────────────────────────────────────────────────────┤
│  服务器（物理机）                                              │
│  ┌─────────────────────────────────────────────────┐       │
│  │              容器运行时 (Container Runtime)       │       │
│  │  ┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐    │       │
│  │  │容器1   │ │容器2   │ │容器3   │ │容器4   │    │       │
│  │  │应用A   │ │应用B   │ │应用C   │ │应用D   │    │       │
│  │  └────────┘ └────────┘ └────────┘ └────────┘    │       │
│  └─────────────────────────────────────────────────┘       │
│                                                              │
│  优势：极致轻量、快速启动、跨环境一致                          │
└─────────────────────────────────────────────────────────────┘
```

### 1.4 Google 的内部经验：Borg 系统

Kubernetes 并非凭空诞生，它是 Google 15年+ 容器编排经验的结晶。

Google 内部使用 **Borg** 系统来管理数百万个容器，积累了丰富的实践经验。2014年，Google 将这些经验开源，诞生了 Kubernetes（简称 K8s，8代表 "ubernete" 中间的8个字母）。

```
Google 的容器管理演进历程：

2003-2004: Borg 系统诞生
     ↓
2013-2014: Omega 项目（borg的改进版）
     ↓
2014年: Kubernetes 开源发布
     ↓
2015年: Kubernetes 1.0 发布，捐赠给 CNCF
     ↓
至今: 成为容器编排领域的标准
```

## 2. 核心设计理念

### 2.1 Kubernetes 的目标

Kubernetes 的核心目标可以用一个公式概括：

```
Kubernetes = 声明式 API + 自动化 + 可扩展性
```

**声明式 API** 的含义：

```yaml
# 你只需要告诉 Kubernetes "你想要什么"
# 而不是告诉它 "如何去做"

apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
spec:
  replicas: 3                    # 我想要 3 个副本
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app-container
        image: my-app:1.0        # 使用这个镜像
        ports:
        - containerPort: 80
```

Kubernetes 会自动处理：
- 副本数量始终保持为 3
- 如果某个 Pod 宕机，自动创建新的
- 如果 Node 不可用，在其他 Node 上启动替代 Pod

### 2.2 核心设计原则

```
┌─────────────────────────────────────────────────────────────┐
│                   Kubernetes 核心设计原则                     │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 声明式配置 (Declarative Configuration)                   │
│     → 你描述期望状态，Kubernetes 负责达成                       │
│                                                              │
│  2. 自我修复 (Self-Healing)                                   │
│     → 自动替换、自动重启、自动恢复                             │
│                                                              │
│  3. 水平扩展 (Horizontal Scaling)                            │
│     → 根据负载自动增减 Pod 数量                               │
│                                                              │
│  4. 服务发现与负载均衡 (Service Discovery & LB)              │
│     → 内部 DNS，自动负载分发                                  │
│                                                              │
│  5. 存储编排 (Storage Orchestration)                         │
│     → 自动挂载存储系统                                        │
│                                                              │
│  6. 密钥与配置管理 (Secrets & ConfigMaps)                     │
│     → 敏感信息和配置分离，安全管理                             │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

### 2.3 为什么选择 Kubernetes？

```
对比手动管理 vs Kubernetes：

手动管理：
❌ 需要人工监控服务器状态
❌ 服务器故障需要人工干预
❌ 扩展应用需要手动部署
❌ 版本更新可能造成服务中断
❌ 资源利用率无法优化

Kubernetes：
✅ 自动监控、自动恢复
✅ 故障自动转移
✅ 一键扩展/收缩
✅ 滚动更新，零停机
✅ 智能资源调度
✅ 跨集群管理
```

## 4. 核心组件详解

### 4.1 kube-apiserver

**功能定位**：集群的网关，所有操作都通过 API Server 进行。

```bash
# API Server 的核心职责

1. 提供 RESTful API 接口
2. 处理所有 API 请求
3. 认证（Authentication）
4. 授权（Authorization）
5. 准入控制（Admission Control）
6. 数据校验
```

```
请求流程示例：

用户 kubectl → 认证 → 授权 → 准入控制 → 验证 → etcd

           ┌──────────────────────────────────────┐
           │           kube-apiserver              │
           │                                       │
           │  ┌─────────────────────────────────┐ │
           │  │  1. 认证 (Authentication)        │ │
           │  │    - 验证用户身份                 │ │
           │  │    - 支持证书、Token、OIDC等      │ │
           │  └─────────────────────────────────┘ │
           │                   ↓                    │
           │  ┌─────────────────────────────────┐ │
           │  │  2. 授权 (Authorization)         │ │
           │  │    - RBAC (基于角色的访问控制)    │ │
           │  │    - 判断用户权限                 │ │
           │  └─────────────────────────────────┘ │
           │                   ↓                    │
           │  ┌─────────────────────────────────┐ │
           │  │  3. 准入控制 (Admission)         │ │
           │  │    - Mutating: 修改请求         │ │
           │  │    - Validating: 验证请求        │ │
           │  └─────────────────────────────────┘ │
           │                   ↓                    │
           │  ┌─────────────────────────────────┐ │
           │  │  4. 数据验证与存储               │ │
           │  │    - 验证资源对象                │ │
           │  │    - 写入 etcd                   │ │
           │  └─────────────────────────────────┘ │
           └──────────────────────────────────────┘
```

**API Server 的特点**：
- 支持水平扩展，多实例并行工作
- 默认以 etcd 为后端存储
- 使用 HTTPS，提供 JSON API
- 是唯一与 etcd 通信的组件

### 4.2 etcd

**功能定位**：高可用、强一致性的键值存储，保存集群所有数据。

```bash
# etcd 的核心特性

1. 分布式键值存储
2. Raft 一致性算法保证强一致性
3. 高可用：通常部署 3 或 5 个节点
4. 监听机制：支持 watch 操作（用于通知变更）
5. 存储内容：
   - Pod、Service、Deployment 等资源定义
   - 集群状态信息
   - 业务配置
```

```
etcd 存储结构示例：

/registry/
├── pods/
│   └── default/
│       └── nginx-pod-xxx/
│           └── spec.json
├── services/
│   └── default/
│       └── my-service/
│           └── spec.json
├── deployments/
│   └── default/
│       └── my-app/
│           └── spec.json
└── nodes/
    └── node-1/
        └── spec.json
```

**etcd 的重要性**：

```
⚠️ 重要提示：etcd 是 Kubernetes 的 "大脑"

如果 etcd 损坏或丢失：
❌ 所有集群配置丢失
❌ 所有 Pod 定义丢失
❌ 集群无法恢复

最佳实践：
✅ 定期备份 etcd 数据
✅ 生产环境使用 3 或 5 节点 etcd 集群
✅ 配置合适的存储类型
✅ 监控 etcd 的健康状态
```

**功能定位**：运行各种控制器进程，负责集群的自动化控制。

**控制器的工作模式**：

```bash
# 控制器使用 "控制循环" 模式工作

控制循环的核心逻辑：

while (true) {
    1. 获取当前状态 (actualState)          # 从 API Server 查询实际状态
    2. 获取期望状态 (desiredState)          # 从 etcd 获取期望状态
    3. 比较两个状态                         # 是否存在差异？
    4. 如果有差异，采取行动                  # 执行修复操作
    5. 重复执行，直到状态一致                # 最终达到期望状态
}
```

**举个例子：ReplicationController**

```
场景：用户创建一个 Deployment，要求 3 个 Nginx Pod 副本

控制循环执行过程：

Step 1: 读取期望状态
   → "replicas: 3"

Step 2: 检查当前状态
   → 当前运行的 Pod 数量：0

Step 3: 发现差异
   → 差异 = 3 - 0 = 3，需要创建 3 个 Pod

Step 4: 创建 Pod
   → 调用 API Server 创建 3 个 Pod

Step 5: 再次检查
   → 当前运行：3，期望：3 ✓ 状态一致，停止调整
```

### 4.4 kube-scheduler

**功能定位**：为新创建的 Pod 选择最合适的工作节点。

```bash
# Scheduler 的核心职责

1. 监听新创建的、尚未分配节点的 Pod
2. 为每个 Pod 选择最合适的工作节点
3. 将决策结果写入 etcd
```

```
调度决策流程：

                    ┌─────────────────────────┐
                    │  新 Pod 被创建          │
                    │  (node: <none>)         │
                    └────────────┬────────────┘
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │  预选阶段 (Filtering)    │
                    │                         │
                    │  排除所有不适合的节点：   │
                    │  - 资源不足              │
                    │  - 条件不满足            │
                    │  - 有污点不匹配           │
                    └────────────┬────────────┘
                                 │
                    ┌────────────▼────────────┐
                    │  打分阶段 (Scoring)      │
                    │                         │
                    │  对剩余节点进行评分：     │
                    │  - 资源利用率            │
                    │  - 亲和性规则            │
                    │  - 拓扑位置              │
                    └────────────┬────────────┘
                                 │
                                 ▼
                    ┌─────────────────────────┐
                    │  选择最高分节点           │
                    │  绑定 Pod 到该节点       │
                    └─────────────────────────┘
```

**调度因素**：

```
┌────────────────────────────────────────────────────────────────────┐
│                       调度考虑因素                                   │
├────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  1. 资源需求                                                       │
│     - CPU 请求/限制                                                 │
│     - 内存请求/限制                                                 │
│     - 临时存储请求/限制                                             │
│                                                                      │
│  2. 亲和性与反亲和性                                                 │
│     - 节点亲和性：Pod 倾向于调度到特定节点                           │
│     - Pod 亲和性：Pod 倾向于与其他 Pod 在一起                       │
│     - Pod 反亲和性：Pod 倾向于与其他 Pod 分开                       │
│                                                                      │
│  3. 污点与容忍                                                     │
│     - 节点可以设置 "污点"，拒绝 Pod 调度                            │
│     - Pod 可以设置 "容忍"，忽略污点                                 │
│                                                                      │
│  4. 拓扑位置                                                       │
│     - 区域/可用区                                                   │
│     - 减少跨区域网络延迟                                            │
│                                                                      │
│  5. 优先级                                                         │
│     - PriorityClass                        │
│     - 高优先级 Pod 优先调度                                         │
│                                                                      │
└────────────────────────────────────────────────────────────────────┘
```

### 4.5 kubelet

**功能定位**：运行在每个工作节点上的主要代理，负责管理 Pod 的生命周期。

```bash
# kubelet 的核心职责

1. 向 API Server 注册节点
2. 监听 Pod 分配到本节点的指令
3. 创建/启动/停止 Pod 容器
4. 监控容器健康状态
5. 汇报节点和 Pod 状态给 API Server
6. 执行容器存活探测 (liveness probe)
```

```
kubelet 工作流程：

         API Server                    kubelet                    Container Runtime
              │                           │                              │
              │  "请在这个节点运行 Pod X"  │                              │
              │ ─────────────────────────>│                              │
              │                           │                              │
              │                           │   拉取镜像                    │
              │                           │ ────────────────────────────>│
              │                           │                              │
              │                           │   创建容器                    │
              │                           │ ────────────────────────────>│
              │                           │                              │
              │                           │   启动容器                    │
              │                           │ ────────────────────────────>│
              │                           │                              │
              │  "Pod X 运行正常"         │                              │
              │ <─────────────────────────│                              │
              │                           │                              │
              │                           │   监控容器状态                 │
              │                           │ <───────────────────────────│
              │                           │                              │
              │  定期汇报节点状态           │                              │
              │ <─────────────────────────│                              │
```

**kubelet 的特点**：
- 不管理非 Kubernetes 创建的容器
- 只听命于 API Server，不会主动执行任务
- 每个节点上必须运行的组件

### 4.6 kube-proxy

**功能定位**：运行在每个节点上的网络代理，维护网络规则，实现 Service 的负载均衡。

```bash
# kube-proxy 的核心职责

1. 维护节点上的网络规则
2. 实现 Service 的服务发现
3. 实现 Service 的负载均衡
4. 支持 iptables 或 IPVS 模式
```

## 5. 核心概念与关系

### 5.1 Pod

**Pod 是 Kubernetes 中的最小调度单位**。一个 Pod 可以包含一个或多个容器。

```
┌────────────────────────────────────────────────────────────────────┐
│                              Pod                                   │
├────────────────────────────────────────────────────────────────────┤
│                                                                      │
│  ┌────────────────────────────────────────────────────────────┐    │
│  │                         Pod                                 │    │
│  │                                                             │    │
│  │   ┌─────────────────┐   ┌─────────────────┐                │    │
│  │   │    Container    │   │    Container    │                │    │
│  │   │    主容器        │   │    边车容器      │                │    │
│  │   │   (Main App)    │   │   (Sidecar)     │                │    │
│  │   │                 │   │  - 日志收集     │                │    │
│  │   │   nginx:1.21   │   │  - 监控代理     │                │    │
│  │   └─────────────────┘   └─────────────────┘                │    │
│  │                                                             │    │
│  │   ┌─────────────────────────────────────────────────┐      │    │
│  │   │              共享存储 (Volume)                   │      │    │
│  │   │         /shared-data                             │      │    │
│  │   └─────────────────────────────────────────────────┘      │    │
│  │                                                             │    │
│  │   ┌─────────────────────────────────────────────────┐      │    │
│  │   │              共享网络 (Network)                  │      │    │
│  │   │         localhost:8080                          │      │    │
│  │   └─────────────────────────────────────────────────┘      │    │
│  │                                                             │    │
│  └─────────────────────────────────────────────────────────────┘    │
│                                                                      │
└────────────────────────────────────────────────────────────────────┘
```

**Pod 的特点**：

```bash
# 1. 共享网络命名空间
#    - 同一 Pod 内的容器可以通过 localhost 互相访问
#    - 共享相同的 IP 地址和端口空间

# 2. 共享存储卷
#    - 同一 Pod 内的容器可以共享访问同一个存储卷
#    - 用于数据共享或持久化

# 3. 原子性调度
#    - Pod 内的容器总是被调度到同一个节点
#    - 不可拆分

# 4. 短暂的生命周期
#    - Pod 本身是临时存在的
#    - 通常通过更高层的控制器（Deployment）来管理
```

**Pod 示例**：

```yaml
# 一个简单的 Nginx Pod
apiVersion: v1
kind: Pod
metadata:
  name: nginx-pod
  labels:
    app: nginx
    version: v1
spec:
  containers:
  - name: nginx
    image: nginx:1.21
    ports:
    - containerPort: 80

    # 资源限制
    resources:
      requests:
        memory: "64Mi"
        cpu: "250m"
      limits:
        memory: "128Mi"
        cpu: "500m"

    # 存活探针
    livenessProbe:
      httpGet:
        path: /
        port: 80
      initialDelaySeconds: 3
      periodSeconds: 10
```

**Node 的元数据**：

```bash
#    - 内存大小
```

**Cluster 的特点**：

```bash

#    - kubectl 将请求发送到 apiserver

# 2. 高可用
```

### 5.4 Namespace

**Namespace 是 Kubernetes 用于隔离资源的逻辑分组**。

```
┌────────────────────────────────────────────────────────────────────┐
│                    多个 Namespace 的集群                            │
├────────────────────────────────────────────────────────────────────┤
│                                                                      │
│   ┌───────────────┐ ┌───────────────┐ ┌───────────────┐          │
│   │   namespace   │ │   namespace   │ │   namespace   │          │
│   │    default    │ │     kube-     │ │    my-app     │          │
│   │               │ │    system     │ │               │          │
│   │  ┌─────────┐  │ │  ┌─────────┐  │ │  ┌─────────┐  │          │
│   │  │ Pod A   │  │ │  │  DNS    │  │ │  │ Pod X   │  │          │
│   │  │ Service │  │ │  │  Pod    │  │ │  │ Service │  │          │
│   │  │ Config  │  │ │  │ Metrics│  │ │  │ Config  │  │          │
│   │  └─────────┘  │ │  └─────────┘  │ │  └─────────┘  │          │
│   │               │ │              │ │               │          │
│   └───────────────┘ └───────────────┘ └───────────────┘          │
│                                                                      │
│   ┌───────────────────────────────────────────────────────────┐   │
│   │                     Node (共享资源)                         │   │
│   │   所有 Namespace 的 Pod 最终都调度到这些物理节点上运行         │   │
│   └───────────────────────────────────────────────────────────┘   │
│                                                                      │
└────────────────────────────────────────────────────────────────────┘
```

**常见的内置 Namespace**：

```bash
# default - 默认的命名空间，如果没有指定就使用这个
# kube-system - Kubernetes 系统组件（DNS、Metrics、Proxy等）
# kube-public - 公开可访问的资源（通常很少用）
# kube-node-lease - 节点心跳检测（Kubernetes 1.14+）
```

**Namespace 的作用**：

```bash
# 1. 资源隔离
#    - 不同团队的资源的隔离
#    - 不同环境的隔离（dev、test、prod）

# 2. 资源配额
#    - 可以给每个 Namespace 设置资源限制
#    - 防止某个 Namespace 耗尽集群资源

# 3. 权限控制
#    - 可以基于 Namespace 做 RBAC
#    - 控制谁可以访问哪个 Namespace

# 4. 命名空间级别资源
#    - Pod、Service、Deployment、ConfigMap 等
#    - 都是 Namespace 级别的资源

# 5. 集群级别资源
#    - Node、PersistentVolume、ClusterRole 等
#    - 不属于任何 Namespace
```

**Namespace 示例**：

```yaml
# 创建命名空间
apiVersion: v1
kind: Namespace
metadata:
  name: production
---
# 在 production 命名空间中创建 Deployment
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app
  namespace: production    # 指定命名空间
spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app
  template:
    metadata:
      labels:
        app: my-app
    spec:
      containers:
      - name: my-app
        image: my-app:1.0
```

## 8. 总结

### 8.1 核心要点回顾

```
┌────────────────────────────────────────────────────────────────────┐
│                      Kubernetes 核心要点                            │
├────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  1. Kubernetes 是什么？                                             │
│     - 容器编排平台                                                  │
│     - 源自 Google 的 Borg 系统                                       │
│     - CNCF 主导的开源项目                                           │
│                                                                     │
│  2. 核心组件                                                        │
│     - 控制平面: apiserver, etcd, scheduler, controller-manager      │
│     - 工作节点: kubelet, kube-proxy, container runtime              │
│                                                                     │
│  3. 核心概念                                                        │
│     - Pod: 最小调度单位，可以包含多个容器                            │
│     - Node: 工作机器，提供计算资源                                   │
│     - Cluster: 整个 Kubernetes 系统                                 │
│     - Namespace: 资源隔离的逻辑分组                                  │
│                                                                     │
│  4. 核心设计理念                                                    │
│     - 声明式 API: 你描述期望状态，K8s 负责达成                       │
│     - 自我修复: 故障自动恢复                                         │
│     - 水平扩展: 按需扩展/收缩                                        │
│                                                                     │
│  5. 工作流程                                                        │
│     - 用户提交资源 → API Server 认证/授权 → 控制器创建 Pod           │
│     → Scheduler 调度 → kubelet 创建容器 → kube-proxy 网络通信        │
│                                                                     │
└────────────────────────────────────────────────────────────────────┘
```
