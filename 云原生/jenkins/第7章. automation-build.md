# 第7章：自动化构建实践

## 7.1 自动化构建的概念与价值

### 什么是自动化构建

自动化构建是指通过工具和配置，使代码从提交到产物的全过程无需人工干预即可自动完成的技术实践。它涵盖了代码检出、依赖安装、编译、测试、打包等环节。

### 自动化构建的核心价值

**1. 效率提升**
- 消除人工构建的等待时间，提交代码后立即触发构建流程
- 夜间或节假日无人值守时，仍能保证持续集成
- 并行构建多个平台版本，最大化资源利用率

**2. 质量保障**
- 每次提交都触发构建，尽早发现问题（Shift Left）
- 自动化测试随构建一同执行，防止缺陷扩散
- 构建结果一致性，消除"在我机器上能跑"的问题

**3. 快速反馈**
- 开发者在几分钟内即可获知代码是否有问题
- 缩短问题发现到修复的周期（S书 P')
- 减少集成阶段的风险和成本

**4. 可追溯性**
- 每次构建都有完整的记录，包括源码版本、环境参数、构建日志
- 便于回溯问题根因，定位哪个版本引入了缺陷
- 构建产物与源码版本一一对应，支持精准回滚

### Jenkins 在自动化构建中的角色

Jenkins 作为流行的开源持续集成/持续部署平台，提供了：
- 灵活的流水线定义（Pipeline as Code）
- 丰富的插件生态（覆盖几乎所有构建工具链）
- 分布式构建支持（Master-Slave架构）
- 完善的构建记录和产物管理
- 多种触发机制和参数化构建能力

## 7.2 构建触发方式详解

### 7.2.1 代码提交触发（Git Hooks）

Git Hooks 是 Git 提供的钩子机制，允许在特定 Git 操作前后自动执行自定义脚本。Jenkins 支持通过 Git Hooks 实现代码提交时自动触发构建。

#### 常用 Git Hooks 类型

| Hook 名称 | 触发时机 | 适用场景 |
|-----------|----------|----------|
| pre-commit | `git commit` 执行前 | 代码格式检查、 lint |
| post-receive | 仓库接收到 push 后 | 触发 CI 构建 |
| pre-rebase | 变基操作前 | 保护分支规范 |
| commit-msg | 提交信息填写后 | 提交信息格式校验 |

#### post-receive Hook 配置步骤

**第一步：在 Git 服务器上创建 Hook 脚本**

```bash
# 在 Git 服务器的仓库目录下创建 post-receive 文件
vim /path/to/repo.git/hooks/post-receive

# 添加以下内容
#!/bin/bash
while read oldrev newrev refname; do
    branch=$(echo $refname | sed 's/refs\/heads\///')
    # 只在推送到 master 或 develop 分支时触发
    if [[ "$branch" == "master" ]] || [[ "$branch" == "develop" ]]; then
        curl -s http://JENKINS_URL/generic-webhook-trigger/invoke \
             --request POST \
             --header "Content-Type: application/json" \
             --data "{\"token\": \"your-secret-token\", \"branch\": \"$branch\"}"
    fi
done
```

**第二步：设置执行权限**

```bash
chmod +x /path/to/repo.git/hooks/post-receive
```

**第三步：Jenkins 端配置 Generic Webhook Trigger 插件**

在 Jenkins 中安装 `Generic Webhook Trigger` 插件后，Job 配置：

1. 在 Job 配置页勾选 **"Generic webhook trigger"**
2. 设置 Token（与 Hook 脚本中的 token 对应）
3. 在流水线中使用以下语法接收参数：

```groovy
pipeline {
    agent any
    triggers {
        GenericTrigger(
            genericVariables: [
                [key: 'branch', value: '$.branch', expressionType: 'JSONPath']
            ],
            token: 'your-secret-token',
            causeString: 'Triggered by Git push',
            printContributedVariables: true,
            printPostContent: true
        )
    }
    stages {
        stage('Checkout') {
            steps {
                echo "Branch: ${branch}"
                git branch: '${branch}',
                    url: 'https://github.com/your-org/your-repo.git'
            }
        }
        stage('Build') {
            steps {
                // 构建步骤
            }
        }
    }
}
```

### 7.2.2 定时构建

定时构建适用于需要定期执行的构建任务，如每日构建、定时回归测试等。

#### 配置方法

在 Jenkins Job 配置中找到 **"Build Triggers"** -> **"Build periodically"**，使用 CRON 语法：

```
# 格式：MINUTE HOUR DOM MON DOW
# MINUTE: 0-59
# HOUR: 0-23
# DOM: Day of Month, 1-31
# MON: Month, 1-12
# DOW: Day of Week, 0-7 (0和7都是周日)
```

#### 常用定时构建配置示例

```groovy
# 每周一到周五凌晨2点执行
H 2 * * 1-5

# 每天上午9点和下午6点各执行一次
H 9,18 * * *

# 每4小时执行一次
H H/4 * * *

# 每周日凌晨3点执行
H 3 * * 0

# 每月1号和15号中午12点执行
H 12 1,15 * *

# 工作日每半小时执行一次（持续集成监控）
H/30 * * * 1-5
```

#### 在 Jenkins Web 界面配置

1. 登录 Jenkins -> 进入 Job -> 点击 **"Configure"**
2. 找到 **"Build Triggers"** 部分
3. 勾选 **"Build periodically"**
4. 在 Schedule 输入框中填写 CRON 表达式
5. 可选：勾选 **"Poll SCM"** 并设置相同的 CRON 表达式，实现定时检查代码变更并构建

**注意**：`Poll SCM` 会检查代码是否有变更，有变更才构建；`Build periodically` 则无论是否有代码变更都会执行。

### 7.2.3 远程触发（curl / JENKINS_URL/job/name/build）

Jenkins 提供远程触发构建的 API，适用于从外部系统（如监控报警、部署平台）触发的场景。

#### 无认证触发

```bash
# 基本格式
curl http://JENKINS_URL/job/JOB_NAME/build

# 带 Token 的触发方式（需要在 Job 中配置 Build Token Root）
curl http://JENKINS_URL/job/JOB_NAME/build?token=YOUR_TOKEN
```

#### 带认证的触发方式

```bash
# 使用 API Token（用户 -> Configure -> API Token）
curl -u USER_ID:API_TOKEN http://JENKINS_URL/job/JOB_NAME/build

# 或使用用户名和密码
curl -u username:password http://JENKINS_URL/job/JOB_NAME/build
```

#### 带参数的构建触发

```bash
curl -u USER_ID:API_TOKEN \
     -X POST \
     http://JENKINS_URL/job/JOB_NAME/buildWithParameters \
     --data "PARAM1=value1&PARAM2=value2"
```

#### Jenkins Job 配置远程触发

1. 安装 `Build Token Root` 插件
2. 在 Job 配置中勾选 **"Enable built-in token"** 或自行设置 Token
3. 配置 **"Security Realm"** 允许远程触发（通常需配合 Matrix Authorization Strategy）
4. 外部系统通过 HTTP 请求即可触发

### 7.2.4 其他 Job 触发（Build after other projects are built）

Jenkins 允许配置 Job 之间的依赖关系，在一个或多个 Job 构建完成后自动触发当前 Job。

#### 配置步骤

1. 进入 Job -> **Configure** -> **Build Triggers**
2. 勾选 **"Build after other projects are built"**
3. 填写要监听的项目名称（多个用逗号分隔）
4. 选择触发条件：
   - **Trigger only if build is stable**：仅在依赖项目构建成功时触发
   - **Trigger even if build fails**：依赖项目构建失败也触发
   - **Trigger even if build is unstable**：依赖项目构建不稳定（测试失败）也触发

#### Pipeline 中的 Job 触发

```groovy
pipeline {
    agent any
    triggers {
        // 监听上游 Job
        upstream(
            upstreamProjects: '上游Job1, 上游Job2',
            threshold: hudson.model.Result.SUCCESS
        )
    }
    stages {
        stage('Downstream Job') {
            steps {
                echo "上游 Job 构建成功，开始执行当前 Job"
            }
        }
    }
}
```

#### 通过 `step` 触发其他 Job

```groovy
pipeline {
    agent any
    stages {
        stage('Trigger Other Jobs') {
            steps {
                // 同步等待其他 Job 完成
                build job: '其他Job名称', parameters: [
                    string(name: 'BRANCH', value: 'main'),
                    booleanParam(name: 'IS_PRODUCTION', value: false)
                ]

                // 异步触发，不等待完成
                build job: '并行Job1', wait: false
                build job: '并行Job2', wait: false
            }
        }
    }
}
```

## 7.3 Webhook 配置

Webhook 是一种高效的触发机制，当源码仓库发生特定事件（如代码 push、MR/PR）时，仓库主动向 Jenkins 发送 HTTP 请求，触发构建。

### 7.3.1 GitHub Webhook 配置

#### GitHub 端配置

**第一步：获取 Jenkins 可访问的 URL**

确保 Jenkins 已在公网可访问，或使用 ngrok 等内网穿透工具：

```bash
# 方式1：使用 Jenkins 内置的 ngrok 集成插件
# 方式2：手动启动 ngrok
ngrok http 8080
```

**第二步：在 GitHub 仓库设置 Webhook**

1. 进入 GitHub 仓库 -> **Settings** -> **Webhooks**
2. 点击 **"Add webhook"**
3. 填写配置：
   - **Payload URL**：`https://YOUR_JENKINS_URL/github-webhook/`（注意 trailing slash）
   - **Content type**：选择 `application/json`
   - **Secret**：设置 Secret Token（与 Jenkins 配置对应）
   - **Which events would you trigger this webhook?**：
     - 选择 **"Just the push event"**（仅 push 事件）
     - 或选择 **"Let me select individual events"** -> 勾选 **Push**, **Pull requests**
4. 点击 **"Add webhook"**

**第三步：可选的 GitHub APP 认证方式**

1. 在 GitHub 设置 Developer settings -> **GitHub Apps**
2. 创建新的 GitHub App：
   - **Homepage URL**：Jenkins URL
   - **Webhook URL**：Jenkins URL
   - 勾选必要的权限（Repository permissions）
3. 安装 App 到你的仓库
4. 在 Jenkins 安装 `GitHub Branch Source` 插件

#### Jenkins 端配置

**方式1：使用 Generic Webhook Trigger 插件**

```groovy
pipeline {
    agent any
    triggers {
        GenericTrigger(
            genericVariables: [
                [key: 'ref', value: '$.ref', expressionType: 'JSONPath'],
                [key: 'repository', value: '$.repository.full_name', expressionType: 'JSONPath']
            ],
            token: 'github-webhook-token',
            causeString: 'GitHub Webhook Trigger',
            printContributedVariables: true
        )
    }
    stages {
        stage('Checkout') {
            steps {
                echo "Received ref: ${ref}"
                git credentialsId: 'github-credentials',
                    url: 'https://github.com/your-org/your-repo.git',
                    branch: '*${ref.replace("refs/heads/", "")}*'
            }
        }
    }
}
```

**方式2：使用 Pipeline 语法自动生成**

在 Job 配置页面 -> **Pipeline** -> **Definition** -> 选择 **"Pipeline script from SCM"** -> **Settings** -> 勾选 **"GitHub hook trigger for GITScm polling"**

### 7.3.2 GitLab Webhook 配置

#### GitLab 端配置

1. 进入 GitLab 仓库 -> **Settings** -> **Webhooks**
2. 点击 **"Add webhook"**
3. 填写配置：
   - **URL**：`http://JENKINS_URL/generic-webhook-trigger/invoke`
   - **Secret token**：设置 Secret
   - **Trigger**：选择 **Push events**, **Merge request events**
4. 点击 **"Add webhook"**

#### Jenkins 端配置

```groovy
pipeline {
    agent any
    triggers {
        GenericTrigger(
            genericVariables: [
                [key: 'object_kind', value: '$.object_kind', expressionType: 'JSONPath'],
                [key: 'ref', value: '$.ref', expressionType: 'JSONPath'],
                [key: 'project', value: '$.project.path_with_namespace', expressionType: 'JSONPath']
            ],
            token: 'gitlab-webhook-token'
        )
    }
    stages {
        stage('Build') {
            steps {
                echo "GitLab event: ${object_kind}, ref: ${ref}"
                // 构建逻辑
            }
        }
    }
}
```

**GitLab Push Hook 完整 Payload 示例**：

```json
{
  "object_kind": "push",
  "ref": "refs/heads/main",
  "project": {
    "path_with_namespace": "group/project"
  },
  "commits": [...]
}
```

## 7.4 Git Hooks 配置详解

### 7.4.1 pre-commit Hook

`pre-commit` 钩子在 `git commit` 执行前触发，适合放置代码质量检查工具（如 ESLint、Prettier、lint-staged）。

#### 本地 pre-commit Hook 配置

**第一步：在项目根目录创建 `.git/hooks/pre-commit` 文件**

```bash
#!/bin/bash

# 禁止直接 commit 到 main 或 master 分支
BRANCH=$(git symbolic-ref --short HEAD)
if [[ "$BRANCH" == "main" ]] || [[ "$BRANCH" == "master" ]]; then
    echo "Error: Direct commit to $BRANCH is not allowed. Please use pull request."
    exit 1
fi

# 运行 ESLint
echo "Running ESLint..."
npx eslint .

# 运行单元测试
echo "Running unit tests..."
npm test

if [ $? -ne 0 ]; then
    echo "Pre-commit checks failed. Please fix the issues above."
    exit 1
fi

echo "All pre-commit checks passed."
exit 0
```

**第二步：设置执行权限**

```bash
chmod +x .git/hooks/pre-commit
```

**第三步：推荐使用 Husky 管理 Git Hooks**

```bash
# 安装 husky
npm install husky --save-dev

# 初始化 husky
npx husky install

# 添加 pre-commit hook
npx husky add .husky/pre-commit "npx lint-staged"

# 现在 .husky/pre-commit 文件内容类似：
# #!/bin/sh
# . "$(dirname "$0")/_/husky.sh"
# npx lint-staged
```

**package.json 配置 lint-staged**：

```json
{
  "lint-staged": {
    "*.{js,jsx,ts,tsx}": ["eslint --fix", "prettier --write"],
    "*.{css,scss}": ["stylelint --fix"],
    "*.{java}": ["google-java-format"]
  }
}
```

### 7.4.2 post-receive Hook

`post-receive` 钩子在 Git 服务器接收到 push 并完成更新后调用，适合触发 CI 构建、发送通知等。

#### 服务器端 post-receive Hook 完整示例

```bash
#!/bin/bash
# 文件路径: /path/to/repo.git/hooks/post-receive

# Jenkins 服务器信息
JENKINS_URL="http://jenkins.example.com"
JOB_NAME="my-project"
TOKEN="your-webhook-token"

# 日志函数
log() {
    echo "[$(date '+%Y-%m-%d %H:%M:%S')] $*" >> /var/log/githook.log
}

while read oldrev newrev refname; do
    # 提取分支名（去掉 refs/heads/ 前缀）
    branch=$(echo "$refname" | sed 's|refs/heads/||')

    # 只处理特定分支
    case "$branch" in
        main|develop|feature/*|release/*)
            log "Push detected: branch=$branch oldrev=$oldrev newrev=$newrev"
            ;;
        *)
            log "Ignoring push to branch: $branch"
            continue
            ;;
    esac

    # 构建触发负载
    PAYLOAD=$(cat <<EOF
{
    "token": "$TOKEN",
    "branch": "$branch",
    "oldrev": "$oldrev",
    "newrev": "$newrev",
    "repository": "$(basename $(dirname $(git rev-parse --git-dir)))"
}
EOF
    )

    # 触发 Jenkins 构建
    response=$(curl -s -w "%{http_code}" -X POST \
        -H "Content-Type: application/json" \
        -d "$PAYLOAD" \
        "$JENKINS_URL/generic-webhook-trigger/invoke")

    http_code="${response: -3}"
    body="${response:0:${#response}-3}"

    if [[ "$http_code" == "200" ]] || [[ "$http_code" == "201" ]]; then
        log "Jenkins build triggered successfully (HTTP $http_code)"
    else
        log "Failed to trigger Jenkins build (HTTP $http_code): $body"
    fi

done
```

## 7.5 多分支流水线自动构建（Multibranch Pipeline）

多分支流水线是 Jenkins 中实现 GitFlow/CD 工作流的核心功能。它能自动发现仓库中的分支，为每个分支创建对应的 Job，并自动触发构建。

### 7.5.1 创建 Multibranch Pipeline Job

#### 基础配置步骤

1. Jenkins 首页 -> **"New Item"**（新建任务）
2. 输入任务名称，选择 **"Multibranch Pipeline"**（多分支流水线）
3. 点击 **"OK"** 进入配置页面

#### General 配置

- **Display Name**：任务显示名称
- **Description**：任务描述
- **在 "Branch Sources" 部分配置源码仓库**：
  - 点击 **"Add source"** -> 选择 **Git**
  - **Project Repository**：仓库地址
  - **Credentials**：添加认证凭据（用户名/密码或 SSH Key）
  - **Behaviors**：
    - **Discover branches**：配置分支发现策略
      - All branches：发现所有分支
      - Only branches with PR：仅发现 PR 中的分支
    - **Filter by name (with regular expression)**：使用正则过滤分支名
    - **Include branches**：包含规则，如 `main|develop|feature/.*`
    - **Exclude branches**：排除规则，如 `bugfix/.*|hotfix/.*`

### 7.5.2 全面的 Multibranch Pipeline 配置示例

```groovy
// Jenkinsfile 放在仓库根目录
pipeline {
    agent {
        // 动态代理标签选择
        label 'docker && linux'
    }

    options {
        // 构建超时设置
        timeout(time: 30, unit: 'MINUTES')

        // 构建丢弃策略
        buildDiscarder(
            LogRotator(
                artifactDaysToKeepStr: '7',
                artifactNumToKeepStr: '10',
                daysToKeepStr: '30',
                numToKeepStr: '50'
            )
        )

        // 禁用并发构建同一分支
        disableConcurrentBuilds()

        // 保持构建过程输出
        preserveStashes()
    }

    parameters {
        choice(
            name: 'ENVIRONMENT',
            choices: ['dev', 'staging', 'production'],
            description: '选择部署环境'
        )
        booleanParam(
            name: 'RUN_INTEGRATION_TESTS',
            defaultValue: true,
            description: '是否运行集成测试'
        )
    }

    triggers {
        // GitHub 仓库有 push 或 PR 时触发
        push.trigger {
            branches toList: ['main', 'develop']
        }
        pullRequest.trigger {
            plugins: [
                [type: 'github']
            ]
        }
        // 定时扫描分支（兜底策略）
        cron {
            // 没15分钟检查一次分支变化
            triggers { 'H/15 * * * *' }
        }
    }

    environment {
        APP_NAME = 'my-app'
        REGISTRY = 'registry.example.com'
    }

    stages {
        stage('Initialize') {
            steps {
                script {
                    env.BRANCH_NAME = env.BRANCH_NAME ?: 'main'
                    env.BUILD_NUMBER = env.BUILD_NUMBER ?: '0'
                }
                echo "Building branch: ${BRANCH_NAME} #${BUILD_NUMBER}"
            }
        }

        stage('Checkout') {
            steps {
                script {
                    // 根据分支名决定是否跳过某些阶段
                    env.SKIP_DEPLOY = (env.BRANCH_NAME.startsWith('feature/')) ? 'true' : 'false'
                }
                checkout scm
            }
        }

        stage('Build') {
            steps {
                sh '''
                    echo "Building ${APP_NAME}..."
                    # 检测构建工具
                    if [ -f "pom.xml" ]; then
                        echo "Detected Maven project"
                        mvn clean package -DskipTests
                    elif [ -f "build.gradle" ] || [ -f "build.gradle.kts" ]; then
                        echo "Detected Gradle project"
                        ./gradlew assemble
                    elif [ -f "package.json" ]; then
                        echo "Detected Node.js project"
                        npm ci
                    fi
                '''
            }
        }

        stage('Test') {
            steps {
                sh '''
                    if [ -f "pom.xml" ]; then
                        mvn test
                    elif [ -f "package.json" ]; then
                        npm test
                    fi
                '''
            }
            post {
                always {
                    // 收集测试报告
                    junit '**/target/surefire-reports/*.xml'
                    jacoco execReport: '**/target/jacoco.exec'
                }
            }
        }

        stage('Security Scan') {
            steps {
                sh '''
                    #OWASP 依赖检查
                    if [ -f "pom.xml" ]; then
                        mvn org.owasp:dependency-check-maven:check
                    fi
                '''
            }
        }

        stage('Docker Build') {
            when {
                anyOf {
                    branch 'main'
                    branch 'develop'
                    tag "*"
                }
            }
            steps {
                script {
                    def imageTag = "${env.REGISTRY}/${env.APP_NAME}:${env.BRANCH_NAME}-${env.BUILD_NUMBER}"
                    def image = docker.build(imageTag, "-f Dockerfile .")
                    docker.withRegistry('https://registry.example.com', 'docker-registry-credentials') {
                        image.push()
                    }
                }
            }
        }

        stage('Deploy') {
            when {
                allOf {
                    branch 'main'
                    expression { env.SKIP_DEPLOY != 'true' }
                    expression { params.ENVIRONMENT == 'production' }
                }
            }
            steps {
                echo "Deploying to production..."
                // 实际部署逻辑
            }
        }
    }

    post {
        always {
            // 始终清理工作空间
            cleanWs()
        }
        success {
            echo "Build completed successfully!"
            // 发送成功通知
        }
        failure {
            echo "Build failed!"
            // 发送失败通知
        }
        unstable {
            echo "Build is unstable..."
        }
    }
}
```

### 7.5.3 组织扫描（Organization Scan）

组织扫描是 Jenkins 用于自动发现并管理 GitHub/GitLab 组织（或 Bitbucket 团队）下所有仓库的多分支流水线功能。它大大简化了为每个仓库单独创建多分支流水线的管理工作。

#### 前提条件

安装以下插件：
- `GitHub Branch Source Plugin`（GitHub 组织）
- `GitLab Branch Source Plugin`（GitLab 组织）
- `Bitbucket Branch Source Plugin`（Bitbucket 团队）

#### GitHub Organization 配置

1. Jenkins -> **"New Item"** -> 选择 **"GitHub Organization"**
2. 输入名称，点击 **"OK"**

3. 在 **"GitHub Organizations"** 部分：
   - **Owner**：GitHub 用户名或组织名
   - **Credentials**：添加 GitHub API Token（Personal Access Token）
     - 需要 Token：在 GitHub -> Settings -> Developer settings -> Personal access tokens
     - 权限：需要 `repo`, `read:org`, `admin:repo_hook`

4. **Behaviors** 配置：
   - **Include repositories**：使用正则包含特定仓库，如 `my-app-.*`
   - **Exclude repositories**：排除特定仓库，如 `.*-deprecated`
   - **API mode**：选择 GitHub API 模式
   - **Discover tags**：是否发现 Tags
   - **Build strategies**：选择构建策略：
     - Default：所有分支都构建
     - Tags only：仅 Tags
     - All branches with PR：所有 PR 分支
     - 选择性策略：只构建特定分支模式

5. **Project Recognizers**：
   - 配置 Jenkins 如何识别仓库使用什么构建系统
   - 默认会自动检测 Jenkinsfile 或 Workflow

#### GitLab Group 配置

类似 GitHub Organization：
1. 新建 **"GitLab Group"**
2. 配置 GitLab Group 路径和 Credentials
3. 设置分组可见性（公开/私有）

### 7.6.1 参数化构建（Parameterized Build）

### 7.6.2 矩阵化构建（Matrix Project）

矩阵化构建（也称多配置流水线）允许为参数的每个组合创建一个构建配置，实现"一次定义，多种配置并行构建"的效果。常用于：
- 多平台编译（Windows/Linux/macOS）
- 多语言版本构建
- 多浏览器测试
- 多数据库兼容性测试

#### 在 Jenkins Web 界面配置

1. 新建任务 -> 选择 **"Matrix"**
2. 在 **"Configuration Matrix"** 部分定义轴（Axes）：

```
Label Expression 轴:
    NODE_LABEL = linux, windows, macos

User-defined 轴:
    JDK = jdk8, jdk11, jdk17
    BROWSER = chrome, firefox, safari
```

3. 配置 **"Combination Filter"** 过滤不需要的组合：

```
// 排除 macOS + JDK8 组合
!(NODE_LABEL=="macos" && JDK=="jdk8")
```

4. 在 **"Slaves"** 或 **"Touchstone builds"** 配置哪些组合先执行

#### Matrix Pipeline 配置示例

```groovy
pipeline {
    agent none  // 不使用固定 agent，由矩阵决定

    parameters {
        choice(
            name: 'BUILD_TYPE',
            choices: ['debug', 'release'],
            description: '构建类型'
        )
    }

    matrix {
        // 定义轴
        axes {
            axis {
                name 'PLATFORM'
                values 'linux', 'windows', 'darwin'
            }
            axis {
                name 'JDK_VERSION'
                values '11', '17', '21'
            }
        }

        // 组合过滤器，排除不兼容的组合
        exclude {
            axis {
                name 'PLATFORM'
                values 'windows'
            }
            axis {
                name 'JDK_VERSION'
                values '21'
            }
        }

        // 设置每个组合的代理标签
        agent {
            label "${PLATFORM}-agent"
        }

        // 组合过滤器（Groovy 表达式语法）
        when {
            expression {
                !(PLATFORM == 'windows' && JDK_VERSION == '21')
            }
        }

        environment {
            PLATFORM_DIR = "${PLATFORM}"
        }

        stages {
            stage('Configure') {
                steps {
                    echo "Building ${PLATFORM} with JDK ${JDK_VERSION}"
                    sh '''
                        echo "Platform: $PLATFORM"
                        echo "Java: $JDK_VERSION"
                    '''
                }
            }

            stage('Build') {
                steps {
                    sh '''
                        case "$PLATFORM" in
                            linux)
                                ./gradlew build
                                ;;
                            windows)
                                gradlew.bat build
                                ;;
                            darwin)
                                ./gradlew build
                                ;;
                        esac
                    '''
                }
            }

            stage('Test') {
                steps {
                    sh './gradlew test --info'
                }
                post {
                    always {
                        junit '**/build/test-results/**/*.xml'
                    }
                }
            }
        }

        // 矩阵级别的 post
        post {
            always {
                echo "Completed ${PLATFORM} + JDK ${JDK_VERSION} build"
            }
        }
    }
}
```

```groovy
    }
```


#### 带有条件判断的重试

```groovy
stage('Network Operation') {
    steps {
        script {
            def retries = 3
            def waitTime = 10
            def attempt = 0
            def success = false

            while (attempt < retries && !success) {
                attempt++
                echo "Attempt $attempt of $retries"

                try {
                    sh 'curl -s http://service.example.com/api/health'
                    success = true
                } catch (Exception e) {
                    if (attempt < retries) {
                        echo "Attempt failed, waiting ${waitTime}s before retry..."
                        sleep(waitTime)
                        waitTime *= 2  // 指数退避
                    } else {
                        echo "All retry attempts failed"
                        throw e
                    }
                }
            }
        }
    }
}
```

#### 超时 + 重试组合

```groovy
stage('Flaky Test') {

                sh './run-flaky-test.sh'
            }
        }
    }
    post {
        failure {
            echo "Test failed after retries"
        }
    }
}
```

## 7.8 构建废弃策略（丢弃旧的构建）

合理的构建废弃策略可以控制 Jenkins 磁盘空间，防止旧的构建记录无限堆积。

### 7.8.1 Web 界面配置

在 Job -> Configure -> **General** -> 勾选 **"Discard old builds"**：

- **Days to keep builds**：保留多少天的构建记录（0 表示不限制）
- **Max number of builds to keep**：最多保留多少个构建（0 表示不限制）

### 7.8.2 Pipeline 中的配置

```groovy
pipeline {
    agent any
    options {
        buildDiscarder(
            LogRotator(
                // 产物丢弃策略
                artifactDaysToKeepStr: '7',      // 产物保留7天
                artifactNumToKeepStr: '10',      // 最多保留10个产物的构建
                // 构建记录丢弃策略
                daysToKeepStr: '30',             // 构建记录保留30天
                numToKeepStr: '100'              // 最多保留100条构建记录
            )
        )
    }
    stages {
        stage('Build') {
            steps {
                sh 'make build'
            }
        }
    }
}
```

### 7.8.3 丢弃策略详解

| 参数 | 含义 | 建议值 |
|------|------|--------|
| `daysToKeepStr` | 构建记录保留天数 | 7-30 |
| `numToKeepStr` | 构建记录保留条数 | 50-100 |
| `artifactDaysToKeepStr` | 产物保留天数 | 7 |
| `artifactNumToKeepStr` | 产物保留条数 | 5-10 |

### 7.8.4 不同 Job 类型的高级丢弃策略

```groovy
// 生产环境保留更多历史
properties([
    [$class: 'BuildDiscarderProperty', strategy: [$class: 'LogRotator',
        artifactDaysToKeepStr: '30',
        artifactNumToKeepStr: '50',
        daysToKeepStr: '90',
        numToKeepStr: '200'
    ]]
])

// 开发环境快速丢弃
properties([
    [$class: 'BuildDiscarderProperty', strategy: [$class: 'LogRotator',
        daysToKeepStr: '7',
        numToKeepStr: '20'
    ]]
])
```

## 7.11 Docker 镜像构建集成

### 7.11.1 Docker Pipeline 插件配置

#### 安装必要插件

- `Docker Pipeline` 插件
- `docker-build-step` 插件

#### 基础 Docker 构建 Pipeline

```groovy
pipeline {
    agent {
        label 'docker-agent'
    }

    environment {
        REGISTRY = 'registry.example.com'
        IMAGE_NAME = 'my-app'
        REGISTRY_CREDENTIALS = 'docker-registry-credentials'
    }

    stages {
        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build') {
            steps {
                script {
                    // 构建 Docker 镜像
                    def imageTag = "${env.REGISTRY}/${env.IMAGE_NAME}:${env.BUILD_NUMBER}"
                    def image = docker.build(imageTag, """
                        --build-arg VERSION=${env.BUILD_NUMBER}
                        --build-arg BUILD_DATE=$(date -u +'%Y-%m-%dT%H:%M:%SZ')
                        -f Dockerfile .
                    """)

                    // 推送到镜像仓库
                    docker.withRegistry("https://${env.REGISTRY}", env.REGISTRY_CREDENTIALS) {
                        image.push('latest')
                        image.push("${env.BUILD_NUMBER}")
                    }
                }
            }
        }

        stage('Security Scan') {
            steps {
                script {
                    def scanner = docker.image('aquasec/trivy:latest')
                    scanner.pull()

                    scanner.run(
                        '--format json -o /tmp/trivy-result.json --scanners vuln ${env.REGISTRY}/${env.IMAGE_NAME}:${env.BUILD_NUMBER}'
                    )
                }
            }
        }
    }
}
```

### 7.12.2 产物的指纹追踪

指纹功能可以追踪某个产物来自哪次构建，当产物被复制或引用时能追溯到原始构建。

```groovy
post {
    always {
        archiveArtifacts artifacts: 'target/*.jar', fingerprint: true
```

## 7.13 完整实战案例

### 案例：Spring Boot 项目的全自动化构建与发布

```groovy
@Library('shared-pipeline-library') _

pipeline {
    agent {
        kubernetes {
            label 'maven-pod'
            defaultContainer 'maven'
            yaml '''
                apiVersion: v1
                kind: Pod
                spec:
                    containers:
                    - name: maven
                      image: maven:3.9-eclipse-temurin-17
                      command:
                      - cat
                      tty: true
                    - name: docker
                      image: docker:24-dind
                      securityContext:
                          privileged: true
                      command:
                      - cat
                      tty: true
            '''
        }
    }

    parameters {
        choice(
            name: 'BRANCH',
            choices: ['main', 'develop', 'release/*'],
            description: '选择构建分支'
        )
        choice(
            name: 'ENVIRONMENT',
            choices: ['dev', 'staging', 'production'],
            description: '部署环境'
        )
        booleanParam(
            name: 'SKIP_TESTS',
            defaultValue: false,
            description: '跳过测试'
        )
    }

    options {
        timeout(time: 60, unit: 'MINUTES')
        disableConcurrentBuilds()
        buildDiscarder(
            LogRotator(
                daysToKeepStr: '30',
                numToKeepStr: '50',
                artifactDaysToKeepStr: '14',
                artifactNumToKeepStr: '20'
            )
        )
    }

    triggers {
        // GitHub Push 触发
        push.trigger {
            branches: ['main', 'develop']
        }
        // PR 触发
        pullRequest.trigger {
            plugins: [[type: 'github']]
        }
    }

    environment {
        APP_NAME = 'spring-boot-app'
        REGISTRY = 'registry.example.com'
        DOCKER_CREDS = credentials('docker-registry-credentials')
    }

    stages {
        stage('Initialize') {
            steps {
                script {
                    env.PACKAGE_VERSION = sh(
                        script: "grep -P '<version>[^<]+</version>' pom.xml | head -1 | sed 's/.*<version>\\([^<]+\\)<\\/version>/\\1/'",
                        returnStdout: true
                    ).trim()
                }
                echo "Building ${env.APP_NAME} v${env.PACKAGE_VERSION}"
            }
        }

        stage('Checkout') {
            steps {
                checkout scm
            }
        }

        stage('Build') {
            steps {
                container('maven') {
                    sh '''
                        mvn clean package -DskipTests=false \
                            -Dmaven.test.failure.ignore=false \
                            -Dmaven.javadoc.skip=true
                    '''
                }
            }
        }

        stage('Test Reports') {
            steps {
                container('maven') {
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }

        stage('Static Code Analysis') {
            steps {
                container('maven') {
                    sh '''
                        mvn spotbugs:check
                        mvn pmd:pmd
                        mvn checkstyle:checkstyle
                    '''
                }
            }
        }

        stage('Security Scan') {
            steps {
                container('maven') {
                    sh 'mvn org.owasp:dependency-check-maven:check'
                }
            }
        }

        stage('Docker Build') {
            steps {
                script {
                    def imageTag = "${env.REGISTRY}/${env.APP_NAME}:${env.BUILD_NUMBER}"
                    def imageName = "${env.REGISTRY}/${env.APP_NAME}"

                    container('docker') {
                        sh """
                            docker build \
                                --build-arg VERSION=${env.BUILD_NUMBER} \
                                --build-arg BUILD_DATE=$(date -u +'%Y-%m-%dT%H:%M:%SZ') \
                                -t ${imageName}:${env.BUILD_NUMBER} \
                                -t ${imageName}:latest \
                                -f Dockerfile .
                        """
                        sh """
                            echo ${DOCKER_CREDS_PSW} | docker login ${env.REGISTRY} -u ${DOCKER_CREDS_USR} --password-stdin
                            docker push ${imageName}:${env.BUILD_NUMBER}
                            docker push ${imageName}:latest
                        """
                    }
                }
            }
        }

        stage('Deploy to Dev') {
            when {
                expression { params.ENVIRONMENT == 'dev' }
            }
            steps {
                sh '''
                    kubectl config use-context dev-cluster
                    kubectl set image deployment/${APP_NAME} \
                        app=${REGISTRY}/${APP_NAME}:${BUILD_NUMBER}
                '''
            }
        }

        stage('Deploy to Staging') {
            when {
                expression { params.ENVIRONMENT == 'staging' }
            }
            steps {
                input message: '确认部署到 Staging 环境？', ok: '确认部署'
                sh '''
                    kubectl config use-context staging-cluster
                    kubectl set image deployment/${APP_NAME} \
                        app=${REGISTRY}/${APP_NAME}:${BUILD_NUMBER}
                '''
            }
        }

        stage('Deploy to Production') {
            when {
                allOf {
                    branch 'main'
                    expression { params.ENVIRONMENT == 'production' }
                }
            }
            steps {
                input message: '即将部署到生产环境！确认继续？', ok: '确认部署'
                script {
                    timeout(time: 10, unit: 'MINUTES') {
                        sh '''
                            kubectl config use-context prod-cluster
                            kubectl set image deployment/${APP_NAME} \
                                app=${REGISTRY}/${APP_NAME}:${BUILD_NUMBER}
                            kubectl rollout status deployment/${APP_NAME}
                        '''
                    }
                }
            }
        }
    }

    post {
        always {
            script {
                // 收集测试覆盖率报告
                publishHTML(
                    target: [
                        allowMissing: true,
                        alwaysLinkToLastBuild: true,
                        reportDir: 'target/site/jacoco',
                        reportFiles: 'index.html',
                        reportName: 'JaCoCo Report'
                    ]
                )
                // 清理工作空间
                cleanWs()
            }
        }
        success {
            echo "构建成功！产物版本: ${env.BUILD_NUMBER}"
            // 发送成功通知（Slack/Email/飞书）
        }
        failure {
            echo "构建失败！请查看日志: ${env.BUILD_URL}"
            // 发送失败通知
        }
    }
}
```

## 7.14 最佳实践

### 触发机制选择指南

| 场景 | 推荐触发方式 |
|------|--------------|
| 实时 CI/CD | Webhook（GitHub/GitLab） |
| 定时回归测试 | Cron Build |
| 跨项目依赖 | Upstream Trigger |
| 外部系统触发 | Remote API（curl） |
| 多分支自动发现 | Multibranch Pipeline |

### 构建性能优化

1. **使用增量构建**：尽可能使用增量编译而非全量
2. **并行阶段**：将独立的阶段并行执行
3. **分布式构建**：配置多个 Slave 分担构建负载
4. **构建缓存**：利用 Maven/Gradle/npm 的缓存机制
5. **Docker 层缓存**：合理拆分 Dockerfile 利用层缓存

### 安全性建议

1. **凭据管理**：使用 Jenkins Credentials 存储所有密钥
2. **矩阵权限**：配置基于 Job 的细粒度权限
3. **安全审计**：定期检查构建日志和安全扫描报告
4. **隔离构建**：使用 Kubernetes Pod 或 Docker 容器隔离构建环境
5. **Secret 保护**：不在日志中打印敏感参数
