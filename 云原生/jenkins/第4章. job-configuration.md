# 第4章：Job 配置与管理

## 概述

Jenkins Job 是 CI/CD 流程的核心单元，每一个 Job 代表一个完整的构建/测试/部署流程。本章将详细介绍 Jenkins 中各种 Job 类型的特点与适用场景、源码管理的配置方法、构建触发器的机制、构建步骤的定义方式，以及后构建操作的配置。通过本章的学习，你将掌握 Jenkins Job 配置的完整知识体系，能够根据实际需求创建和管理各种类型的构建任务。

---

## 4.1 Job 类型详解

Jenkins 提供了四种主要的 Job 类型，每种类型都有其特定的使用场景和配置方式。理解这些类型的区别对于设计良好的 CI/CD 流程至关重要。

### 4.1.1 Freestyle Project（自由风格项目）

Freestyle Project 是 Jenkins 最基本、最灵活的 Job 类型。它允许你自由组合各种构建步骤、源码管理选项和触发器，适用于各种简单的构建需求。

**特点：**
- 配置灵活，可自由组合各种配置选项
- 支持多种源码管理工具（Git、SVN、CVS等）
- 支持多种构建触发器
- 可配置多个构建步骤（Shell 脚本、Windows 批处理等）
- 支持后构建操作（归档构建产物、发送通知等）

**适用场景：**
- 简单的构建任务（如编译一个项目）
- 需要执行自定义构建脚本的任务
- 不适合 Maven 项目结构但需要完整配置的任务

**创建 Freestyle Project 的基本步骤：**

1. 点击 Jenkins 首页左侧的"新建任务"（New Item）
2. 输入任务名称，选择"构建一个自由风格的软件项目"
3. 点击"确定"进入配置页面
4. 根据需要配置源码管理、构建触发器、构建步骤和后构建操作

### 4.1.2 Maven Project（Maven 项目）

Maven Project 是专门为 Maven 项目设计的 Job 类型，它预配置了 Maven 的构建和测试功能，简化了 Maven 项目的配置过程。

**特点：**
- 自动识别项目的 pom.xml 文件
- 内置 Maven 构建步骤（ Goals 和 Maven 选项）
- 自动处理测试报告和构建产物
- 简化了 SNAPSHOT 版本的检测和处理

**适用场景：**
- Java Maven 项目
- 需要利用 Maven 依赖管理的大型项目
- 标准 Maven 生命周期的构建（compile、test、package、install、deploy）

**配置示例：**

在 Maven Project 的配置页面中，你需要设置：
- Maven 版本（需要提前在系统配置中配置）
- Root POM 路径（默认 pom.xml）
- Goals and options（例如：`clean package -DskipTests=false`）

### 4.1.3 Multi-configuration Project（多配置项目）

Multi-configuration Project（也称为 Matrix Project）允许你基于不同的配置组合来运行相同的构建任务。这对于需要在多种环境下测试或构建的项目特别有用。

**特点：**
- 支持配置多个维度（axes），每个维度可以包含多个值
- 自动组合所有维度的配置生成构建矩阵
- 可以针对特定配置进行筛选和排除
- 支持分布式构建，每个配置可以在不同标签的节点上执行

**适用场景：**
- 需要在多个 JDK 版本上测试的项目
- 需要在多个操作系统上构建的项目
- 需要在多个浏览器上进行测试的前端项目
- 数据库兼容性测试

**配置示例：**

假设你需要在一个 Java 项目在 JDK 8、JDK 11、JDK 17 三个版本上测试，可以配置：

1. 在"配置轴"（Axis）中添加"JDK Axis"
2. 添加值：`JDK8`、`JDK11`、`JDK17`
3. 构建将自动生成三个配置组合并执行

### 4.1.4 Pipeline（流水线）

Pipeline 是 Jenkins 2.x 引入的核心功能，它允许你将整个 CI/CD 流程定义为代码，存储在 Jenkinsfile 中，实现Pipeline即代码（Pipeline as Code）的理念。

**特点：**
- 使用 Groovy DSL 定义 Pipeline
- 支持版本控制（Pipeline 代码可以存储在 Git 仓库中）
- 支持复杂的构建流程（条件分支、循环、并行执行等）
- 支持可视化编辑（Pipeline Syntax）和蓝绿部署
- 内置强大的日志和可视化功能

**适用场景：**
- 复杂的 CI/CD 流程
- 需要版本控制和代码审查的构建流程
- 微服务架构中的多阶段部署
- 需要并行执行的任务

**Declarative Pipeline 示例：**

```groovy
pipeline {
    agent any
    
    environment {
        APP_NAME = 'my-application'
        DEPLOY_ENV = 'staging'
    }
    
    options {
        timestamps()
        timeout(time: 1, unit: 'HOURS')
    }
    
    stages {
        stage('Checkout') {
            steps {
                echo '正在拉取代码...'
                git branch: 'main', 
                    credentialsId: 'git-credentials',
                    url: 'https://github.com/example/my-app.git'
            }
        }
        
        stage('Build') {
            steps {
                echo '正在构建项目...'
                sh 'mvn clean package -DskipTests=false'
            }
        }
        
        stage('Test') {
            steps {
                echo '正在执行测试...'
                sh 'mvn test'
            }
            post {
                always {
                    junit 'target/surefire-reports/*.xml'
                }
            }
        }
        
        stage('Deploy') {
            when {
                branch 'main'
            }
            steps {
                echo '正在部署到测试环境...'
                sh './deploy.sh staging'
            }
        }
    }
    
    post {
        success {
            echo '构建成功！'
            emailext(
                subject: "构建成功: ${APP_NAME}",
                body: "构建 ${env.BUILD_NUMBER} 成功完成",
                to: 'team@example.com'
            )
        }
        failure {
            echo '构建失败！'
            emailext(
                subject: "构建失败: ${APP_NAME}",
                body: "构建 ${env.BUILD_NUMBER} 失败，请检查日志",
                to: 'team@example.com'
            )
        }
        always {
            cleanWs()
        }
    }
}
```

**Scripted Pipeline 示例：**

```groovy
node('docker') {
    stage('Checkout') {
        checkout scm
    }
    
    stage('Build') {
        def image = docker.build("myapp:${env.BUILD_NUMBER}")
    }
    
    stage('Test') {
        image.withRun('-p 8080:8080') { container ->
            sh 'curl -s http://localhost:8080/health'
        }
    }
    
    stage('Push') {
        docker.withRegistry('https://registry.example.com', 'docker-registry-cred') {
            image.push('latest')
            image.push(env.BUILD_NUMBER)
        }
    }
}
```

## 4.2 源码管理（Source Code Management）

源码管理是 Jenkins Job 配置的重要组成部分，它定义了 Jenkins 如何从版本控制系统获取源代码。本节将详细介绍 Git 和 SVN 的配置方法。

### 4.2.1 Git 配置

#### 基本配置

在 Job 配置页面的"源码管理"部分，选择"Git"，然后配置以下参数：

**仓库地址（Repository URL）：**
- 支持多种协议：HTTPS、SSH、Git协议等
- 格式示例：
  - HTTPS: `https://github.com/username/repository.git`
  - SSH: `git@github.com:username/repository.git`

**凭据（Credentials）：**
- 如果仓库需要认证，需要添加并选择对应的凭据
- 支持以下类型的凭据：
  - 用户名/密码
  - SSH 用户名/私钥
  - Secret 文本

**分支配置：**
- Specified branches：指定特定分支
- 默认为 `*/main` 或 `*/master`
- 支持多分支配置：使用通配符如 `*/feature/*`
- 支持多仓库配置：添加多个仓库源

**高级配置选项：**

| 选项 | 说明 |
|------|------|
| Name of remotes | 远程仓库名称，默认为 origin |
| Refspec | 自定义 Git refspec |
| Included Regions | 只构建匹配正则表达式的分支 |
| Excluded Regions | 排除匹配正则表达式的分支 |
| Included Tags | 只构建匹配正则表达式的标签 |
| Excluded Tags | 排除匹配正则表达式的标签 |
| Build Wrappers | 构建包装器配置 |

#### Git 高级功能配置

**使用 SSH 密钥进行认证：**

1. 首先在 Jenkins 中添加 SSH 凭据
   - 进入"系统管理" -> "凭据" -> "添加凭据"
   - 选择"SSH Username with private key"
   - 输入用户名（如 git）
   - 选择"Enter directly"或"From a file on Jenkins master"
   - 粘贴私钥内容

2. 在 Job 配置中选择对应的凭据

**配置多个仓库源：**

```groovy
pipeline {
    agent any
    stages {
        stage('Checkout') {
            steps {
                checkout([
                    $class: 'GitSCM',
                    branches: [[name: '*/main']],
                    doGenerateSubmoduleConfigurations: false,
                    extensions: [
                        [$class: 'RelativeTargetDirectory', 
                         relativeTargetDir: 'main-repo'],
                        [$class: 'CloneOption', 
                         depth: 1, 
                         noTags: true, 
                         shallow: true]
                    ],
                    submoduleCfg: [],
                    userRemoteConfigs: [[
                        credentialsId: 'git-credentials',
                        url: 'https://github.com/example/main-repo.git'
                    ]]
                ])
                
                checkout([
                    $class: 'GitSCM',
                    branches: [[name: '*/develop']],
                    doGenerateSubmoduleConfigurations: false,
                    extensions: [
                        [$class: 'RelativeTargetDirectory', 
                         relativeTargetDir: 'shared-lib']
                    ],
                    submoduleCfg: [],
                    userRemoteConfigs: [[
                        credentialsId: 'git-credentials',
                        url: 'https://github.com/example/shared-lib.git'
                    ]]
                ])
            }
        }
    }
}
```

**Git 子模块配置：**

```groovy
checkout scm: [$class: 'GitSCM',
    branches: [[name: '*/main']],
    userRemoteConfigs: [[
        url: 'https://github.com/example/repo.git',
        credentialsId: 'git-credentials'
    ]],
    submoduleCfg: [
        [
            $class: 'SubmoduleOption',
            disableSubmodules: false,
            parentCredentials: true,
            recursiveSubmodules: true,
            reference: '',
            trackingSubmodules: false
        ]
    ]
]
```

### 4.2.2 SVN 配置

#### 基本配置

在 Job 配置页面的"源码管理"部分，选择"Subversion"，然后配置以下参数：

**仓库地址（Repository URL）：**
- 格式：`svn://server/path/to/repo` 或 `https://svn.example.com/repo`
- 支持认证后的访问

**凭据配置：**
- 如果仓库需要认证，点击"凭据"旁边的"添加"链接
- 输入用户名和密码

**检出选项：**

| 选项 | 说明 |
|------|------|
| 检出深度 | Full（完全递归）、Immediate（仅直接子项）、File（仅文件）、Infinity（无限递归） |
| 忽略外链 | 是否忽略外部链接 |
| 检出策略 | 使用 `-update` 还是 `-checkout` |

**高级配置：**

- Externals（外部依赖）：配置 SVN 外部依赖处理方式
- Workspace verison（工作区版本）：指定工作区格式版本

#### SVN 配置示例（Pipeline）

```groovy
pipeline {
    agent any
    stages {
        stage('Checkout SVN') {
            steps {
                checkout([
                    $class: 'SubversionSCM',
                    additionalCredentials: [],
                    excludedCommitMessages: '',
                    filterChangelog: false,
                    ignoreDirChanges: false,
                    includedRegions: '',
                    excludedRegions: '',
                    excludedUsers: '',
                    excludedRevprop: '',
                    excludedCommitMessages: '',
                    extClasspath: '',
                    locations: [[
                        credentialsId: 'svn-credentials',
                        depthOption: 'infinity',
                        locale: 'en_US',
                        module: 'https://svn.example.com/repo/trunk',
                        timeout: '30'
                    ]],
                    workspaceUpdater: [
                        $class: 'UpdateUpdater'
                    ]
                ])
            }
        }
    }
}
```

## 4.3 构建触发器（Build Triggers）

构建触发器定义了何时以及如何触发 Jenkins Job 的构建。Jenkins 提供了多种触发器类型，本节将详细介绍每种类型的配置方法。

### 4.3.1 定时构建（Build after other projects are built）

这是最简单的一种触发方式，在其他指定的 Job 构建完成后自动触发。

**配置方式：**
1. 在 Job 配置页面勾选"构建后触发其他项目"
2. 输入要监听的项目名称（支持多个项目，用逗号分隔）
3. 选择触发条件：
   - 总是触发（Always）
   - 仅在构建成功时触发（Only if build succeeds）
   - 仅在构建失败时触发（Only if build fails）
   - 仅在构建不稳定时触发（Only if build is unstable）

**应用场景：**
- 依赖链：比如 Job B 需要在 Job A 成功后才开始
- 多阶段构建：编译 Job 完成后自动触发测试 Job

### 4.3.2 轮询源码（Poll SCM）

轮询源码是一种定期检查源码仓库变化的触发方式。当检测到代码变化时，Jenkins 会自动触发构建。

**配置方式：**
1. 在 Job 配置页面勾选"轮询源码"
2. 在"日程表"文本框中按 cron 格式配置轮询频率

**cron 格式说明：**

| 字段 | 允许值 | 特殊字符 |
|------|--------|----------|
| 分钟 | 0-59 | , - * / |
| 小时 | 0-23 | , - * / |
| 日期 | 1-31 | , - * / |
| 月份 | 1-12 或 JAN-DEC | , - * / |
| 星期 | 0-7 或 SUN-SAT（0和7都是周日） | , - * / |

**常用 cron 表达式示例：**

| 表达式 | 说明 |
|--------|------|
| `H H * * *` | 每天任意时间执行（推荐，自动选择稳定时间） |
| `H/15 * * * *` | 每15分钟轮询一次 |
| `H H(9-16) * * 1-5` | 工作日每小时执行一次（上午9点到下午5点） |
| `0 0 * * *` | 每天午夜执行 |
| `0 H * * *` | 每天任意时间执行一次 |
| `0 2 * * *` | 每天凌晨2点执行 |
| `H H(9-17) * * 1-5` | 工作日（周一到周五）上午9点到下午5点之间每小时执行 |

**注意事项：**
- 轮询会消耗 Jenkins 的资源，建议合理设置轮询间隔
- 对于大型项目，建议使用 Webhook 代替轮询
- 可以使用 `H` 符号实现负载均衡（Hash，会在时间窗口内自动选择时间）

**配置示例：**

```groovy
// Pipeline 中配置轮询
pipeline {
    agent any
    triggers {
        pollSCM('H/15 * * * *')
    }
    stages {
        stage('Build') {
            steps {
                echo 'Building...'
            }
        }
    }
}
```

### 4.3.3 定时构建（Build periodically）

定时构建按照预设的时间表自动触发构建，无论代码是否有变化。

**配置方式：**
1. 在 Job 配置页面勾选"定期构建"
2. 在"日程表"文本框中按 cron 格式配置构建频率

**使用场景：**
- 定期巡检：比如每天凌晨检查依赖是否有安全漏洞
- 定时打包：比如每天凌晨生成版本
- 保持节点活跃：使用轻量级构建任务保持节点活跃

**定时构建与轮询的区别：**

| 特性 | 定期构建 | 轮询源码 |
|------|----------|----------|
| 触发条件 | 时间到了就触发 | 检测到代码变化才触发 |
| 资源消耗 | 稳定消耗 | 取决于代码变化频率 |
| 使用场景 | 定时任务、巡检 | 代码变化触发构建 |

### 4.3.4 Webhook 触发

Webhook 是最高效的触发方式，当代码仓库有变化时，通过 HTTP 请求立即触发 Jenkins 构建。

#### GitHub Webhook 配置

1. **在 GitHub 仓库设置 Webhook：**
   - 进入 GitHub 仓库 -> Settings -> Webhooks
   - 点击"Add webhook"
   - Payload URL：`https://your-jenkins-url/github-webhook/`
   - Content type：选择 `application/json`
   - Secret：设置与 Jenkins 匹配的 secret
   - 选择触发事件：Push（推送代码）、Pull request（拉取请求）

2. **在 Jenkins 中配置 GitHub 插件：**
   - 安装 "GitHub Integration" 插件
   - 在 Job 配置页面勾选"GitHub hook trigger for GITScm polling"

3. **Pipeline 中配置 Webhook：**

```groovy
pipeline {
    agent any
    triggers {
        githubPush()
    }
    stages {
        stage('Build') {
            steps {
                echo 'Building from GitHub webhook...'
            }
        }
    }
}
```

#### GitLab Webhook 配置

1. **在 GitLab 仓库设置 Webhook：**
   - 进入 GitLab 仓库 -> Settings -> Webhooks
   - URL：`https://your-jenkins-url/project/your-job-name`
   - Trigger：选择 Push events、Merge request events 等
   - 如果需要认证，添加 Secret token

2. **在 Jenkins 中配置 GitLab 插件：**
   - 安装 "GitLab Plugin" 插件
   - 在 Job 配置页面勾选"Build when a change is pushed to GitLab"

#### SVN/WebDAV 触发配置

对于 SVN 仓库，可以通过 post-commit hook 触发 Jenkins：

```bash
#!/bin/bash
# 在 SVN 仓库的 hooks 目录下创建 post-commit 文件

JENKINS_URL="https://your-jenkins-url"
JOB_NAME="your-job-name"
REPOS="$1"
REV="$2"

curl -s -X POST \
    "${JENKINS_URL}/job/${JOB_NAME}/build?token=YOUR_TOKEN"
```

### 4.3.5 远程触发构建

通过 URL 远程触发 Jenkins 构建，适合与其他系统集成。

**配置方式：**
1. 在 Job 配置页面勾选"允许远程触发"
2. 设置认证令牌（Authentication Token）

**触发 URL 格式：**
```
https://username:password@jenkins-url/job/job-name/build?token=TOKEN
```
或
```
https://jenkins-url/job/job-name/build?token=TOKEN&cause=原因
```

**Pipeline 中配置远程触发：**

```groovy
pipeline {
    agent any
    triggers {
        genericTrigger(
            genericVariables: [
                [variable: 'BRANCH', type: 'STRING']
            ],
            genericHeaderVariables: [
                [variable: 'x-token', header: 'X-Token']
            ],
            causeString: 'Remote trigger',
            token: 'my-secret-token',
            version: '1'
        )
    }
    stages {
        stage('Build') {
            steps {
                echo "Building branch: ${BRANCH}"
            }
        }
    }
}
```

### 4.3.6 触发器组合使用

在 Pipeline 中可以组合使用多个触发器：

```groovy
pipeline {
    agent any
    triggers {
        // 组合多个触发器
        parameterizedCron([
            // 每周一凌晨3点执行
            '0 0 3 * * 1': 'BRANCH=main',
            // 工作日每小时执行（排除午休时间）
            'H 9-16 * * 1-5': 'BRANCH=develop'
        ])
        githubPush()
        pollSCM('H/30 * * * *')
    }
    stages {
        stage('Build') {
            steps {
                echo 'Building...'
            }
        }
    }
}
```

## 4.4 构建步骤（Build Steps）

构建步骤是 Jenkins Job 的核心部分，定义了实际的构建操作。不同类型的 Job 支持不同类型的构建步骤。

### 4.4.1 Windows 相关构建步骤

#### 执行 Windows 批处理命令（Execute Windows batch command）

**使用场景：**
- Windows 环境下的构建
- 调用 Windows 原生命令
- 执行 .bat 或 .cmd 脚本

**配置方法：**
1. 在 Job 配置页面的"构建"部分
2. 点击"增加构建步骤" -> "执行 Windows 批处理命令"
3. 在文本框中输入要执行的命令

**示例 - 编译 C# 项目：**
```batch
@echo off
echo ============================================
echo 开始编译项目...
echo ============================================

:: 还原 NuGet 包
nuget restore MyProject.sln

:: 编译项目
msbuild MyProject.sln /p:Configuration=Release /p:Platform=x64

if %ERRORLEVEL% NEQ 0 (
    echo 编译失败！
    exit /b 1
)

echo ============================================
echo 编译成功！
echo ============================================
```

**示例 - PowerShell 脚本：**
```batch
powershell -ExecutionPolicy Bypass -Command "& { .\build.ps1 -Configuration Release }"
```

#### 执行 PowerShell 脚本（Execute Windows PowerShell command）

**配置方法：**
1. 点击"增加构建步骤" -> "执行 Windows PowerShell 命令"

**示例：**
```powershell
Write-Host "开始构建..."

# 清理之前的构建产物
if (Test-Path "./dist") {
    Remove-Item "./dist" -Recurse -Force
}

# 执行构建
npm run build

if ($LASTEXITCODE -ne 0) {
    Write-Host "构建失败！"
    exit 1
}

Write-Host "构建完成！"
```

## 4.6 后构建操作（Post-build Actions）

后构建操作用于在构建完成后执行额外任务，如归档构建产物、发送通知、触发其他 Job 等。

### 4.6.1 归档构建产物（Archive the artifacts）

**配置方法：**
1. 在 Job 配置页面点击"增加构建后步骤" -> "归档成品"
2. 在"归档路径"中输入要归档的文件路径（支持通配符）
3. 配置归档选项：
   - 仅在构建成功时归档
   - 归档所有构建产物
   - 允许缺少归档文件

**常用归档配置：**

| 通配符 | 说明 |
|--------|------|
| `dist/**/*.zip` | 归档 dist 目录下所有 zip 文件 |
| `target/*.jar` | 归档 target 目录下所有 jar 文件 |
| `build/artifacts/**/*` | 归档所有构建产物 |
| `**/*.war` | 归档所有 war 文件 |

```groovy
pipeline {
    agent any
    stages {
        stage('Build') {
            steps {
                sh 'mvn package -DskipTests'

    post {
        success {
            archiveArtifacts artifacts: 'target/*.jar',
                fingerprint: true,
                onlyIfSuccessful: true
        }
    }
}
```

**高级归档选项：**

```groovy
archiveArtifacts [
    artifacts: 'target/**/*.jar, target/**/*.war',
    defaultExcludes: true,
    fingerprint: true,
    onlyIfSuccessful: false,
    allowMissing: false
]
```

参数化构建允许在触发构建时动态传入参数，使 Job 更加灵活和可复用。

### 4.7.1 常用参数类型

#### 字符串参数（String Parameter）

**配置：**
1. 勾选"参数化构建过程"
2. 添加"字符串参数"
3. 设置名称和默认值

```groovy

        )

])

pipeline {
    agent any

            }
        }
    }
}
```

#### 布尔参数（Boolean Parameter）

```groovy
parameters([

        defaultValue: false,
        description: '是否跳过测试',

```

#### 选择参数（Choice Parameter）

```groovy
parameters([
```

```groovy
parameters([
```

```groovy
parameters([
```

#### 级联参数（Cascading Parameters）

```groovy
def environments = ['dev', 'staging', 'production']
def services = [
    'dev': ['user-api', 'order-api', 'product-api'],
    'staging': ['user-api', 'order-api', 'product-api'],
    'production': ['user-api', 'order-api', 'payment-api', 'product-api']
]

properties([
    parameters([
        [
            $class: 'ChoiceParameterDefinition',
            name: 'ENVIRONMENT',
            choices: environments.join('\n'),
            description: '选择环境'
        ],
        [
            $class: 'ChoiceParameterDefinition',
            name: 'SERVICE',
            choices: services['dev'].join('\n'),
            description: '选择服务'
        ]
    ])
])

script {
    // 根据环境更新服务选项
    def newChoices = services[params.ENVIRONMENT].join('\n')
    def serviceParam = parameters.find { it.name == 'SERVICE' }
    if (serviceParam) {
        serviceParam.choices = newChoices
    }
}
```

## 4.8 Job 配置最佳实践

### 4.8.1 Job 命名规范

- 使用有意义的名称，如 `frontend-app`、`backend-api`

### 4.8.2 常用 Job 模板

```groovy
// templates/build.groovy
def call(Map config) {

            stage('Checkout') {
                steps {
                    checkout scm
                }
            }
            
            stage('Build') {
                steps {
                    sh config.buildCommand
                }
            }
            
            stage('Test') {
                steps {
                    sh config.testCommand
                }
            }
        }
        
        post {
            always {
                junit config.testReportPattern
                cleanWs()
            }
        }
    }

// 使用模板
call(buildCommand: 'mvn package', testCommand: 'mvn test', testReportPattern: 'target/surefire-reports/*.xml')
```

### 4.8.3 配置版本控制

将 Job 配置存储在 Git 仓库中：

```groovy
// Jenkinsfile
@Library('jenkins-shared-library') _

        }
    }
}
```

### 4.8.4 安全配置

- 启用"不允许并发构建"防止资源竞争
- 使用凭据管理敏感信息
- 限制可以触发 Job 的用户
- 定期轮换 API Token

## 4.9 小结

本章详细介绍了 Jenkins Job 配置与管理的各个方面：

1. **Job 类型**：Freestyle 灵活通用、Maven 简化 Java 项目配置、Multi-configuration 支持多环境构建、Pipeline 实现 CI/CD 即代码

2. **源码管理**：Git 支持分支、标签、子模块等高级功能；SVN 支持外部依赖和工作区管理

3. **构建触发器**：定时触发适合周期性任务、轮询适合低频率变更检测、Webhook 实现实时触发

4. **构建步骤**：Windows 批处理/PowerShell、Shell 脚本、Maven Goals、条件执行、并行执行

5. **后构建操作**：归档产物、邮件通知、触发下游 Job、清理工作空间

6. **参数化构建**：支持字符串、选择、布尔、密码等多种参数类型，实现灵活的动态构建

通过本章的学习，你已经掌握了 Jenkins Job 配置的核心技能。在实际工作中，建议根据项目需求选择合适的 Job 类型和配置组合，逐步建立起完善 CI/CD 流程。
